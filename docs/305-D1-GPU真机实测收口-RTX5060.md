# 305 · D1 GPU 真机实测收口（RTX 5060 / cu128）——「沙箱为 CPU torch」是伪前提

> 日期：2026-10-19 · 结论：**D1 不被阻塞**，detect 阶段 P95 **0.743s** < 1.5s 目标，退出码 0。
> 本阶段的核心价值不是新数字，而是**推翻一条被长期当作事实的错误前提**，并给出 GPU↔CPU 严格 A/B。

## 一、起因：一条自相矛盾的开放项

上一轮收口真值基线时，我在「剩余开放项」里写下：

> ③ D1 GPU/API 实测（需 RTX 5060 真机 + 运行 API，**沙箱为 CPU torch**）

但同一次运行的日志头部白纸黑字写着：

```
[core.device_manager:273] 自动选择设备：NVIDIA GeForce RTX 5060 Laptop GPU
[core.detector:164] EasyOCR 阅读器初始化完成（GPU 模式）。
```

两者直接冲突。按项目铁律「工具矛盾视为 bug / 标定前必须提供隔离证明」，
**不能凭印象选一个信**，必须用探针实证裁决。

## 二、探针一：GPU 真可用性（scripts/_gpu_probe_1219.py）

| 判据 | 实测 | 结论 |
|---|---|---|
| T1 torch | 2.9.1+cu128（built for CUDA 12.8 / cuDNN 91002） | GPU 轮子，非 CPU 轮 |
| T2 `cuda.is_available()` | True | — |
| T3 设备 | RTX 5060 Laptop / **sm_120** / 7.93 GiB | Blackwell 已被 cu128 正确识别 |
| T4 **真实 CUDA 运算** | `matmul` on `cuda:0`，max\|Δ\| vs CPU ref = **7.248e-05** | 非布尔声明，数值级证实 |

**T4 是关键**：只信 `is_available()` 是自证式断言；真跑一次 GPU 张量运算并与 CPU
参考比对，才能排除「torch 装了但算子落到 CPU」这类静默降级。

T5/T6 报 FAIL 是**探针自身缺陷**（非产品缺陷）：easyocr reader 与 LaMa device 都是
懒加载/挂在对象上，探针用 `getattr(模块, ...)` 猜名字自然取不到。

## 三、探针二：端到端 GPU 通道（scripts/gpu_perf_probe.py）

真实调用产品公开 API（`detect_watermark_mask` / `inpainter.inpaint`），读回真实 device：

| 判据 | 实测 |
|---|---|
| E1 device_info | `NVIDIA GeForce RTX 5060 Laptop GPU \| kind=cuda \| vram=8123MB` |
| E1 torch_device | `cuda:0` |
| EasyOCR | **GPU 模式**初始化完成 |
| LaMa | `big-lama.pt` **映射至 cuda:0** 加载完成 |
| 裁剪修复 | `INFER_CROP_TO_MASK=True`，实测裁到 5.9%–100% 包围盒 |

**⇒ 「沙箱为 CPU torch」判定为伪前提，D1 解封。**

## 四、GPU ↔ CPU 严格 A/B（同 12 张 ≥2048px 真实图，仅设备不同）

严格控制变量：同一脚本、同一图集、同一 warmup=2、同一 `--min-side 2048`；
仅以 `WME_DEVICE_MODE=cpu` 切换设备。

| 指标 | GPU（RTX 5060） | CPU（同机对照） | **GPU 加速比** |
|---|---|---|---|
| detect P50 | 1.199s | 6.292s | **5.25×** |
| **detect P95** | **1.282s** | 6.823s | **5.32×** |
| full P50 | 4.316s | 17.198s | **3.98×** |
| full P95 | 10.454s | 22.677s | **2.17×** |

CPU 模式 detect P95 6.823s **远超** 1.5s 目标（`detect_target_met: false`）；
GPU 模式 1.282s 达标。**这从因果上解释了为什么 D1 必须是 GPU 口径**：
1.5s 目标在 CPU 上结构性不可达，与代码优化无关。

## 五、权威口径复核：项目自有 perf_probe

上面是本阶段探针的自定义口径。为避免「用自己的尺子量自己」，再用**项目既有门禁**
`scripts/perf_probe.py` 复核（该脚本本就为 GPU/CI 场景设计了
`--stage full --enforce-target`）：

### detect 阶段（GPU）→ ✅ 退出码 0
```
统计：min=0.371s  P50=0.633s  P95=0.743s  max=0.743s  均值=0.624s
相对噪声 = 0.041（阈值 0.20）→ ✅ 可信
锚点图 轮首 0.748s → 轮尾 0.698s（0.933）→ ✅ 无渐变
回归护栏：P95 0.743s vs 基线 0.679s ×(1+30%) = 0.882s → ✅ 在护栏内
绝对目标（--enforce-target）：P95 0.743s vs 1.50s → ✅ 达目标
✅ 性能门禁通过（退出码 0）
```

### full 阶段（GPU）→ 退出码 2，但**不是失败，是两道正当护栏各司其职**
```
统计：min=4.362s  P50=5.885s  P95=8.891s  max=8.891s  均值=6.297s
相对噪声 = 0.377（阈值 0.20）→ ❌ 超过（本次测量受污染，探针如实拒绝下结论）
stage 不一致（基线 detect vs 本次 full）→ 跳过判定
```
两道 guard 都在**正确工作**：
1. 噪声护栏抓到 `ai_logo_04` 首轮 36.1s 的异常（另一轮仅 8.891s），
   极差/P95=0.377 超阈 ⇒ 探针**拒绝**用一个自己都认为不可信的测量下结论。
2. stage 护栏抓到「拿 full 去比 detect 基线」的口径错误 ⇒ 拒绝跨 stage 比较。

**这正是门禁体系应有的行为**：宁可跳过，也不产出不可信结论。full 阶段要成为
一等公民需单独标定一份 full 基线（`--update`），属独立工作项。

## 六、诚实披露：三处口径差异（避免误读）

1. **1.282s vs 0.743s 不是矛盾，是图集与口径不同**：
   `gpu_perf_probe` 取「短边 ≥2048px」的最重子集且含首轮冷启动；`perf_probe` 取固定
   10 张基准图、`repeat=3 取 min`（能力度量而非冷启动度量）。**权威口径取 0.743s**。
2. **full P95 三值并存**（10.45s / 8.891s / 22.68s）分别来自不同 warmup 与图集，
   跨口径不可比；且 full 阶段本次测量被噪声护栏判为不可信，**不作为结论**。
3. **历史基线的真值**：`benchmark_real/perf_baseline.json` 实为
   `device: cuda` / `gpu_name: RTX 5060` / P95 0.679s / measured_at **2026-10-06**
   ⇒ **D1 的 detect 侧早在 10-06 就已在本机 GPU 上标定过**。
   「D1 因缺 GPU 而阻塞」这一记忆条目本身是错的，本阶段予以更正。

## 七、一个附带发现：fp16 开关与实际行为

`use_fp16()` 返回 True，但日志显示 LaMa 实际保持 float32：

```
[core.model_manager:566] 模型 lama 已知 fp16 不安全，保持 float32（见 _FP16_UNSAFE_MODELS 的实测依据）
```

这**不是缺陷**，而是阶段 207 的既定设计（fp16 实测毁图，故 LaMa 列白名单），
且 `_run_lama_tile` 以**模型 dtype 为唯一真值来源**。但它暴露出一个表述风险：
`use_fp16()` 的返回值仅代表「设备允许 fp16」，不代表「本次推理用了 fp16」。
后续引用该函数时必须同时说明模型侧是否在 `_FP16_UNSAFE_MODELS` 内，避免误读为性能杠杆。

## 八、结论与后续

- **D1（GPU 侧）收口**：GPU 通道打通且经数值级证实；detect P95 0.743s 达标（退出码 0）；
  GPU 相对 CPU 加速 5.3×；「沙箱为 CPU torch」为伪前提，已更正。
- **full 阶段 1.5s 目标结构性不可达**：CPU 对照 6.823s 已证伪，GPU 下 P95 8.891s
  （本次测量被判噪声污染）。瓶颈仍是 LaMa 在大包围盒上的推理。
- **剩余待办**：① full 阶段单独标定基线（需 `--update` 授权，与真值基线同纪律）；
  ② API 侧并发默认值实测（需运行 API 服务）；③ `requirements-gpu.txt` / `Dockerfile.gpu`
  的 cu121→cu128 版本对齐仍待处理（当前本机 venv 已是 cu128，声明文件滞后）。
