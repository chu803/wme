## 2. 决定性证据（traceback 摘录）

`.scratch/stage252_traceback_batch08.txt`：

```
[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":426,"threshold":50,
                                                   "scope":"turn", ...}
E  AssertionError: api.py 自检失败（退出码 1）
```

其余批次（02/07/09/10/16）的 traceback **全部**是同一形态：

```
E  SystemExit: 1
```

即：测试内部的 `os.remove` / `shutil.rmtree` 被护栏拒绝 → `SystemExit(1)` → 用例失败。
**没有任何一条**是断言不成立或代码异常。

## 3. 结构性冲突（本阶段真正的发现）

| 量 | 值 |
|---|---|
| 护栏阈值 | **50 次删除 / turn** |
| 单批（12 文件）的临时文件删除量 | 数百次（各用例自己的 tmp_path/产物） |
| 一轮全量（17 批）的删除量 | **数千次**（实测累计计数 `count:426` 时已被拒） |

⇒ **一轮跑完全量必然触发护栏**，且触发后**剩余所有批次**里凡是碰删除的用例都会失败。
这解释了此前多轮全量里那些「五花八门、与代码无关」的失败集合（cache/orphan/history/
model_manager/rotation/legacy_selfcheck）。

**可行的规避（未验证，需下轮实测）**：
1. **分多轮跑**：每轮只跑 4 批左右，让单轮删除数 < 50，然后**结束该轮**（配额重置）；
2. 或**归档替代删除**（项目惯例：rename 优于删除），但 pytest 内部用 `rmtree`，改不动。

> 注：我这一轮**已经**把配额用尽（`count:426`），故无法在本轮内验证规避方案 1——
> 这是**已知的验证缺口**，如实登记。

## 4. 脚本的三处基建缺陷（244 脚本，本阶段修复）

### 缺陷 1 · 复用固定名 basetemp ⇒ **整批秒退、用例根本没跑**（249 同坑第二次）

`run_batch` 用固定名 `.pytest_bNN`。**第二次**全量跑时这些目录已存在且文件众多，
pytest 启动清空它们 ⇒ 撞护栏 ⇒ 每批 3~9 秒「**RC=1 但无 FAILED 行**」，17 批皆然。

> 这是我在 **249 已踩过一次**的坑（当时是自建检测器），**244 脚本一直带着同一缺陷**，
> 首次运行因目录不存在才没暴露。
> **若只看「失败总数 = 0」会误判为全绿**——「快得反常」第三次当了报警器。
> **修法**：`_RUN_TAG = str(int(time.time()))` ⇒ `.pytest_run{tag}_bNN`。
> **修后健康检查**：批 01 用时 **89–103s**（此前 6s）。

### 缺陷 2 · `--tb=no` ⇒ flaky **无法定性**（本阶段最关键的改进）

脚本只收 FAILED 行、不留 traceback。252 之前的 2 条 rotation 失败「隔离绿/单批绿/
3 批连跑绿」却**拿不到任何断言信息**，只能挂着「未定性的 flaky」。

**修法**：某批一旦有失败，自动用 `--tb=long` **重跑该批**并把完整输出落盘到
`.scratch/stage252_traceback_batchNN.txt`，文件头记录「首次失败清单 / 重跑是否仍失败」。

> **立刻兑现**：正是这份 traceback 让我们在 10 秒内定位到 `SystemExit: 1` +
> `count:426` ⇒ 从「14 条不明失败」变成「14 条同根因、且根因是环境护栏」。
> 这是本项目迄今**投入产出比最高的一次基建改进**。

### 缺陷 3 · 输出文件覆盖历史 ⇒ 权威输出被静默污染

脚本固定写 `.scratch/stage244_fullsuite.txt`。缺陷 1 那次坏跑把**13m32s 那次健康结果**
整个抹掉，只剩「17 批全 RC=1」——**读者不会察觉**。
与 249「数据可信先于结论正确」同源。
**修法**：输出文件名带 run tag（`stage244_fullsuite_{tag}.txt`），历史保留可对照。
