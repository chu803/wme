# 阶段 351 · CI 红 8 天的**第二个**原因：系统依赖写死了镜像代际的包名

> 日期 2026-10-27 · 性质：**CI 阻断级修复**（与阶段 347 的依赖 pin 是两个独立原因）

## 一、症状

修完依赖区间（347）后 CI 仍然红（#27/#28/#29，均 1m14s～1m32s）⇒ 说明**还有别的原因**。
「红得飞快」这个特征一直在提示：**失败在 setup 段，不在测试段**。

## 二、根因：Ubuntu 24.04（noble）把 glib 的运行时包改名了

* Ubuntu 24.04 起，64 位 time_t 过渡让一批运行时包带 **t64** 后缀：
  `libglib2.0-0` → **`libglib2.0-0t64`**（同批还有 `libatspi2.0-0t64` 等）。
* 而且 **过渡包 `libglib2.0-0` 在 Noble 里被删了**
  （launchpad bug #2063221「Drop libglib2.0-0 transitional package」）。
* 我们的 `ci.yml` / `publish.yml` 里写死了 `apt-get install … libglib2.0-0 …`
  ⇒ 镜像一滚到 noble，`apt` 直接 `Unable to locate package` ⇒ **整 job 一分钟红**，门禁都跑不到。

**为什么它是"镜像侧"变化**：不需要任何仓库改动就会发生 ⇒ 这正好解释了
「#14（10-18）绿、#15 起全红」这条时间线（#15 那天恰好 runner 镜像也换了）。

## 三、为什么是两个独立的原因（别以为修一个就够）

| 原因 | 阶段 | 症状 | 修法 |
|---|---|---|---|
| 依赖 pin 钉了**没有 cp311 轮子**的版本（numpy 2.5.1 / scipy 1.18.1） | 347 | runner 装不上依赖 | 改成区间（下界 = 上一版 CI 装成功过的版本） |
| 系统依赖写死了**镜像代际**的包名 | **351** | `apt` 找不到包 | 按镜像实际有什么来挑 |

两个都在"装依赖"这 10~20 秒里 ⇒ **症状一样（都是 fast red）**，
⇒ 只看时长无法区分 ⇒ 必须分别验证。

## 四、修法：系统依赖不许写死包名

```yaml
GLIB=$(apt-cache show libglib2.0-0t64 >/dev/null 2>&1 && echo libglib2.0-0t64 || echo libglib2.0-0)
sudo apt-get install -y --no-install-recommends libgl1 libsm6 libxext6 libxrender1 "$GLIB"
```

判据：**「runner 镜像自己会变」的系统依赖，必须按镜像实际有什么来挑，不能写死**。
守卫 `tests/test_workflow_system_deps351.py`（2×2 例）：
① 必须探测 `apt-cache show libglib2.0-0t64`；② 安装命令必须用 `"$GLIB"` 变量；
③ 安装参数里不许再出现写死的旧包名；④ 顺带断言两个 workflow 的 YAML 仍可解析、
**每个步骤都有 `id`**（阶段 332 的诊断靠 `toJSON(steps)` 拿「哪一步红了」）。

## 五、诚实边界
