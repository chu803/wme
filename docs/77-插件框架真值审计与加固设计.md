# 阶段 77 · 插件框架真值审计与加固设计

> 审计对象：`core/plugins.py`（引擎/插件注册与发现框架，阶段 11 建立，此后 66 个阶段未再审计）。
> 审计范式：**探针量化 → 定位根因 → 修复 → 回归测试 → 门禁化**（沿用阶段 49 起的核心链路真值审计期范式）。

---

## 1. 为什么审计插件框架

插件系统是本工作台唯一的**扩展点**，它决定「用户能否接入自己的 inpaint 模型」。
但它自阶段 11 建立后，在后续 66 个阶段的全部审计（检测器、修复器、掩码、导出、输入形态、
API 层……）中从未被触碰——是**覆盖面最大的一处审计空白**。

同时它天然具备阶段 70 归纳的风险特征：

> **声明的能力 ≠ 实现的能力**（阶段 70 教训）。
> 插件框架的文档（模块 docstring、`plugins/README.md`）对「命名、加载、失败隔离」
> 有明确承诺，而承诺是否被代码兑现，从未被验证。

因此本阶段用一次性探针脚本对六项承诺逐一取证。

## 2. 探针量化（修复前）

探针脚本在真实进程内构造极端插件（覆盖内建、非法命名、崩溃、同名、延迟目录），
逐项取证。结论如下：

| 编号 | 承诺（文档） | 实际行为（探针实测） | 判定 |
|---|---|---|---|
| **P1** | 引擎清单如实反映可用引擎 | 插件 `name="lama"` → `get_engine("lama")` **返回插件**，但 `list_engines()` 仍显示「LaMa 深度学习 / builtin=True」（内建描述被硬编码，且以内建键名 `continue` 跳过注册表实例） | **显示与执行脱节** |
| **P2** | 插件名为「唯一键（小写）」 | 只校验「非空」。`'bad name!'`、`'  '`（纯空格）、`'中文引擎'`、`'with.dot'`、`'9leading'` **全部注册成功** | 校验形同虚设 |
| **P3** | `load_plugins()` 返回「成功加载的插件文件数」 | 首次返回 1（文件数），二次返回 3（注册表规模）——**同一函数两种语义** | 语义不一致 |
| **P4** | 加载失败「只告警、不崩溃」 | 崩溃插件的模块对象**残留在 `sys.modules`**（`wme_plugins.boom_plugin`），成为半初始化模块 | 状态污染 |
| **P5** | 插件发现是「惰性」的 | 首次扫描时目录不存在 → `_LOADED = True` 被**无条件置位**，之后创建目录+插件**永远不再被发现** | 永久放弃 |
| **P6** | 放进目录即可，同名行为未定义 | 两个文件都注册 `dup_engine` → 按文件名字母序**后者静默覆盖前者**，全程无告警 | 静默裁决 |

探针原始输出（节选）：

```
覆盖后 get_engine('lama') -> _FakeLama 伪装引擎
清单里 lama 显示为         -> LaMa 深度学习 | builtin = True
>> 显示与实际是否一致：     False

name='  '             -> 已注册  (key='  ')
name='Bad Name!'      -> 已注册  (key='bad name!')

首次调用 -> 1
二次调用 -> 3 (注册表规模 = 3 )

加载失败文件数 -> 0 | 残留 sys.modules -> ['wme_plugins.boom_plugin']

后建目录的插件能否被查到 -> False

同名两插件最终生效 -> 第二个 （无任何告警）
```

## 3. 根因分析

六项缺陷分两类：

### 3.1 一类：**双真值来源**（P1）

```python
# 修复前 list_engines()
infos = [
    EngineInfo("auto", "自动选择", "有模型用 LaMa，否则降级 OpenCV", builtin=True),
    EngineInfo("lama", "LaMa 深度学习", "...", builtin=True, requires_model=True),   # ← 硬编码
    EngineInfo("opencv", "OpenCV 传统算法", "...", builtin=True),                    # ← 硬编码
]
for key, inst in _REGISTRY.items():
    if key in ("lama", "opencv", "auto"):
        continue                                                                     # ← 跳过真值
```

**同一份事实（lama 是谁）被写了两遍**：一份是硬编码的字面量，一份是注册表里的实例。
两者在无覆盖时恰好一致，一旦覆盖就分叉——而分叉方向恰好是「界面骗人、代码跑别的」。
这与阶段 70「声明的能力 ≠ 实现的能力」、阶段 61「死代码伪装成已验证功能」同族：
**冗余的第二真值来源不会主动报错，只会在边界条件下给出错误答案。**

### 3.2 二类：**缺省即放行**（P2/P3/P4/P6）

- 名称校验缺省放行（只查非空）；
- 重复注册缺省放行（直接 `_REGISTRY[key] = inst`）；
- 失败清理缺省不做；
- 返回值语义缺省按「缓存快路径」写（`return len(_REGISTRY)`）。

在正常情况下这些缺省都无害，但在**插件目录是用户可写、内容不可信**的场景里，
「缺省放行」等于把破坏面交给最不可控的输入。安全工程的一般原则是
**缺省拒绝（default-deny）**：只有当调用方显式要求时才允许危险操作。

P5 则属于**状态机过早收敛**：把「扫描动作已执行」误当成「扫描目标已穷尽」。

## 4. 修复设计

### 4.1 注册表成为唯一真值来源（P1）

`list_engines()` 重写：内建键位仍固定前置（保持历史顺序），但**元信息一律取自注册表实例**，
「是否内建」由实例属性 `is_builtin` 判定，不再由键名判定：

```python
for key in ("lama", "opencv"):
    inst = _REGISTRY.get(key)
    if inst is None:
        continue
    infos.append(EngineInfo(
        key,
        inst.display_name or key,          # ← 取实例，不取字面量
        inst.description or "",
        builtin=bool(getattr(inst, "is_builtin", False)),   # ← 取实例，不取键名
        requires_model=bool(inst.requires_model),
        source=getattr(inst, "source", "") or "",
    ))
```

由此得到一个可测试的**不变量**（已写入回归测试）：

> 对任意引擎名，`list_engines()` 中的 `display_name` / `description` / `builtin`
> 必须恒等于 `get_engine(name)` 返回实例的对应字段。

即使未来有人开启覆盖，清单也会如实显示覆盖者——**「显示 = 执行」由构造保证，而非靠纪律**。

### 4.2 缺省拒绝：覆盖保护 + 命名校验（P1/P2/P6）

`register_engine()` 重写为「校验 → 归一化 → 冲突裁决 → 落库」四步：

```
① 归一化：name.strip().lower()      （大写自动纠正并告警，兼容历史写法）
② 校验  ：^[a-z][a-z0-9_]{0,31}$    （不合法 → 拒绝 + 说明原因）
③ 冲突  ：已存在同键 → 默认拒绝 + 告警；allow_override（配置或参数）为真时放行但逐条 WARNING
④ 落库  ：_REGISTRY[name] = inst；回填 source
```

新增配置 **`PLUGIN_ALLOW_OVERRIDE`（默认 `False`）** 作为逃生舱：

- 默认情况下，内建引擎**不可能**被插件顶替；
- 确需顶替（自研 LaMa 加速版）时显式开启，且开启后**每一次覆盖都留痕**——
  「允许」不等于「静默」。

同时新增 `source` 追溯字段：注册时由加载上下文 `_CURRENT_PLUGIN_FILE` 回填，
使 `EngineInfo.source` 能回答「这个引擎来自哪个文件」。这既是同名排查的必要信息，
也是 P6「谁覆盖了谁」告警文案的数据来源。

### 4.3 返回值语义统一（P3）

```python
# 修复前
if _LOADED:
    return len(_REGISTRY)   # ← 两种语义混用

# 修复后
if force:
    _SCANNED_DIRS.clear(); _LOADED = False
elif _LOADED:
    return 0                # ← 「本次没有加载任何文件」
```

`main.py` 用它打印「已加载 N 个插件」，修好后语义与这句话严格一致。
**同一函数不得同时承载「本次动作的结果」与「全局状态的大小」**，
否则调用方对返回值的解释必然出错（此处错在「已加载 N 个」会随进程状态漂移）。

### 4.4 失败即清理（P4）

```python
_sys.modules[spec_name] = module
try:
    ...
except Exception:
    _sys.modules.pop(spec_name, None)   # 半初始化模块不得留驻
    raise
```

失败还要**可观测**：新增 `_LAST_REPORT["failed"] = [{"file", "error"}]`，
经 `get_plugin_report()` / `--list-engines` / `GET /health`（`plugins.failed`）三处暴露。
**兜底 except 必须留可观测痕迹**（阶段 73 教训）。

### 4.5 扫描状态机修正（P5）

`_LOADED` 语义从「扫描动作已执行」改为「**至少扫描到一个存在的目录**」：

```python
scanned_any_dir = False
for pdir in _resolve_plugin_dirs():
    if not pdir.exists() or not pdir.is_dir():
        continue
    scanned_any_dir = True
    ...
if scanned_any_dir:
    _LOADED = True
```

目录缺失时保持未完成，下次查询自动重试。**正常路径（`plugins/` 存在）零额外开销**——
仍是一次扫描后即置位，不会给热路径增加 `stat`。另引入 `_SCANNED_DIRS` 按目录去重，
使多目录配置下的增量扫描成为可能。

### 4.6 顺带修复：字节码缓存导致的「热加载不生效」

回归测试构造「同一路径、同长度、同秒内改写插件」时暴露了一个**真实语义缺陷**：

`spec.loader.exec_module()` 会读写 `__pycache__`，而其缓存命中判据是
**源文件 mtime（秒级）+ 字节大小**。同一秒内把 `"热加载 v1"` 改成 `"热加载 v2"`
（长度不变）→ 判定为「缓存新鲜」→ **执行的是陈旧字节码**。

插件目录恰恰是用户频繁手改的位置，语义上必须始终执行最新源码。故改为
`get_source + compile + exec`，**显式绕开 pyc 缓存**：

```python
source = spec.loader.get_source(spec_name)
code = compile(source, str(mod_path), "exec")
exec(code, module.__dict__)
```

代价是每次启动多花一次源码编译（毫秒级、仅启动时），换来「改了立刻生效」的确定性。
配套新增 `reload_plugins()`：注销全部非内建引擎后强制重扫，
使开发期「改插件 → 热加载 → 复测」形成闭环，无需重启进程。

### 4.7 实现中的一处隐蔽陷阱

`load_plugins()` 需要把「当前正在加载的文件」写入模块级变量 `_CURRENT_PLUGIN_FILE`，
供 `register_engine` 回填。首版漏写 `global`：

```python
_CURRENT_PLUGIN_FILE = str(mod_path)   # ← 无 global：创建的是局部变量
```

结果 `source` 恒为空串，而**所有正向断言仍全绿**（因为测试只查「source 以文件名结尾」
在插件存在时不会失败……实际会失败，但若测试只查「字段存在」则全绿）。
本阶段测试直接断言 `source.endswith(...)` 才当场抓住。
**教训：模块级可变状态在函数内赋值必须显式 `global`；「字段存在」类断言抓不住「值为空」。**

## 7. 已知边界（诚实记录）

- **覆盖保护不阻止「插件在自身 `inpaint()` 内做任意事」**——插件是本地可信代码，
  本框架只治理**注册与命名**层面的冲突，不做沙箱隔离。这与项目定位（本地离线、
  单人自用）一致；若未来要跑第三方插件，需另立沙箱议题。
- **`reload_plugins()` 为进程级操作**，不做并发保护。批量处理进行中调用热加载
  可能让正在执行的引擎实例被替换。定位为开发期工具，未接入任何界面按钮。
- **`source` 只记录文件路径**，未记录文件哈希/版本。如需校验「加载的确实是我改的那份」，
  应另加内容指纹（本轮不做，避免过度设计）。
- **`PLUGIN_ALLOW_OVERRIDE` 未纳入 `config.user_overrides.json` 白名单**——
  与同族的 `PLUGIN_DIRS` / `PLUGIN_ENABLED` 保持一致（这三者都是运维/开发者开关，
  走环境变量，不进终端用户的处理偏好面板）。

## 8. 结论

插件框架的六项缺陷有共同的结构特征：

> **文档承诺了「安全性」，实现却依赖「缺省放行」且没有第二道校验。**

修复贯彻三条原则：

1. **单真值来源**——「显示 = 执行」由构造保证（P1）；
2. **缺省拒绝**——覆盖、命名、重复注册一律先拒，需显式开启才放行且留痕（P2/P6）；
3. **状态与观测对齐**——返回值、模块缓存、扫描完成位都不得「撒谎」（P3/P4/P5）。

顺带修复的 pyc 缓存问题（§4.6）说明：**审计的价值常在于发现「没打算找的东西」**——
热加载缺陷并非本次审计目标，而是「同秒同长度改写」这一极端测试构造逼出来的。
这与阶段 66「同族参数主动列一遍」同源：**把同族场景系统性地走一遍，边界问题会自己浮出来。**
