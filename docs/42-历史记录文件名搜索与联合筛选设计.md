# 阶段 42：历史记录文件名搜索与「类型 + 关键词」联合筛选

> 上一阶段（41）补齐了历史记录的「类型筛选 + 按类型批量导出」，让 image / video / pdf 三类记录可被分类查看与打包。
> 本阶段在类型筛选之上，补齐**文件名模糊搜索**，并与类型筛选**叠加生效（AND）**，完成「历史记录可发现性」闭环：
> 视图（类型筛选）→ 搜索（文件名）→ 导出（按筛选+搜索）→ 下一步可对筛选结果做批量管理。

---

## 1. 目标与边界

- **目标**：历史页支持按文件名关键词（不区分大小写子串）过滤画廊；搜索与类型筛选叠加；
  筛选激活时在统计文案给出明确提示；「导出筛选结果（ZIP）」一并尊重搜索关键词。
- **非目标（本阶段不做）**：基于搜索结果的批量删除（破坏性操作，Gradio 6.22 无 `ConfirmDialog`，
  留待后续阶段配独立确认 UI）。本阶段坚持**非破坏性**增强。
- **合规**：仅影响历史页本地的展示/导出范围，不涉及任何文件删除或对外上传。

## 2. 改动清单（分层 ui → services → core/utils → config）

### 2.1 `services/cache_service.py`
- `HistoryRecord`（沿用）：无新增字段；`list_records` 增加 `query` 参数。
- `list_records(self, kind=None, query=None)`：
  - `kind`：沿用阶段 41 类型过滤。
  - `query`：非空（strip 后）时对 `original_name` 做 `q in name.lower()` 子串匹配；空/`None` 忽略。
  - 二者 **AND 叠加**。返回仍按 `ts` 倒序。

### 2.2 `services/export_service.py`
- `export_history_as_zip(..., kind=None, query=None)`：构造 `records` 时透传
  `cache.list_records(kind=kind, query=query)`，其余逻辑（成功结果、存在性校验、包内命名）不变。

### 2.3 `ui/tab_history.py`
- `load_gallery(compare, kind_filter="all", query=None)`：
  - **兼容优先**：仅当「有类型筛选」**或**「有关键词」时才透传 `kind=/query=`，
    否则走无参 `list_records()`，避免破坏既有无参桩（如 `lambda:[rec]`）——沿用阶段 41 的回归教训。
  - 命中筛选时，统计文案追加 `history.filter_active`（类型 + 关键词 + 命中数）。
- `export_history_filtered_zip(kind_filter="all", query=None)`：透传 `query` 给 `export_history_as_zip`。
- `build_history_tab`：
  - 新增 `search_box = gr.Textbox`（label/placeholder/info 用 i18n）。
  - 接线：`search_box.submit`（回车）、`search_box.change`（输入即筛）、`refresh_btn.click`、
    `kind_filter.change`、`export_filtered_btn.click` 全部带上 `query`。

### 2.4 `utils/i18n.py`（中英双语）
新增键（位于 `history` 块）：
- `search_label` / `search_placeholder` / `search_info`
- `filter_active`：`"\n\n🔎 当前筛选：类型 {kind} · 关键词 {q} · 命中 {n} 条"`

## 3. 关键设计决策

1. **搜索仅匹配 `original_name`**：历史记录的核心可检索字段即原文件名；不索引参数/时间，避免噪声。
2. **AND 叠加而非 OR**：「类型=图片 且 关键词=cat」语义最直观，符合用户心智。
3. **无参兼容**（重要）：阶段 40 的桩 `list_records = lambda:[rec]` 无参，若无条件透传 `kind=/query=` 会
   `TypeError`。本阶段与阶段 41 一致采用「未筛选走无参」策略，保证既有测试不破。
4. **非破坏性优先**：搜索/筛选只改变视图与导出范围，不触碰任何文件；批量删除留待配确认 UI 的后续阶段。
