## 2. 实验：护栏是否只管项目内？

**假设**：若护栏只统计项目目录内的删除，把 `--basetemp` 指向系统 Temp 即可单轮跑完全量。

| 组 | basetemp | 批 1 | 批 2 |
|---|---|---|---|
| A | 项目内 `.pytest_expA_*` | rc=0 / 54.8s / 0 失败 | rc=0 / 53.8s / 0 失败 |
| B | 系统 Temp `%TEMP%/wme_expB_*` | rc=0 / 47.5s / 0 失败 | rc=0 / 48.4s / 0 失败 |

⇒ **两组均未触发护栏、无差异** ⇒ 该假设**不成立**（护栏非路径相关）。
但实验顺带揭示了真正的关键：**4 批 × 12 个轻量文件完全没触发** ⇒
**删除量高度不均**，决定配额消耗的不是「批数」而是「**批里有没有删除密集型测试**」。

## 3. 方案：按删除密集度编排 + 跨轮续跑

`.scratch/stage253_runner.py`：

1. **按密集度编排**（而非等分批次）：
   - 轻测试：12 文件/批；
   - **删除密集**（`cache|orphan|purge|delete|history|model_manager|download|…`）
     与**写入密集**（`utils_audit|rotation|logging|logger|perf`）：**1 文件/批**；
   - 依据：252 的失败批（02/07/09/10）几乎全在删除密集类，而批 01 从不失败。
2. **护栏主动检测 + 停止**：某批出现 `SystemExit` / `SAFE_DELETE` 即**停下并保存进度**，
   而非硬跑完让后面几十批集体假红。**这是本方案的核心价值**。
3. **进度落盘** `stage253_progress.json`（已完成批号、累计失败、traceback 清单）。
4. **traceback 自动重跑落盘**（沿用 252 能力；失败批用 `--tb=long` 重跑并记录
   「是否仍失败/ 是否命中护栏」）。

## 4. 编排改进：把「写入密集」也隔离

253 第一轮里，那 2 条 rotation 失败出现在**批 015**（一个混合批）⇒ 说明
**写入密集型测试同样受配额牵连**：配额被同批其他测试耗尽后，pytest 清理
`tmp_path` 被拒 ⇒ 该用例受牵连失败。

> **这解释了 234/244/248 三轮的误判链**：rotation 用例被反复判为
> 「环境负载型 flaky / 批次争用」，实际是**配额耗尽时它恰好在同一批**。
> 它既不是代码缺陷，也不是 flaky，而是**编排问题**。

⇒ 新增 `_WRITE_HEAVY_PAT`，`test_utils_audit90.py` 现单独成批（批 032）。
**待下轮验证**：批 032 单独跑时那 2 条是否消失。
