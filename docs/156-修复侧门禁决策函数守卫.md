# 阶段 156 · 修复侧门禁决策函数守卫（e2e_real_probe.evaluate_gate）

> 审计对象：`scripts/e2e_real_probe.py` 的 `evaluate_gate`（修复侧第三道门禁的决策函数，驱动 `--gate` 退出码）。
> 触发：未审榜空（44 模块已登记 audited，截至 145）→ 刻意选点；检测侧门禁簇已审（152-155），本轮审修复侧。

## 结论

`evaluate_gate` 的红线方向契约**正确（by design）**，但既有测试（`test_e2e_real_probe.py` J1-J6）只覆盖**量测**
（removal/collateral/spill 是否响应），**未守卫决策函数本身**——量测被测 ≠ 决策被测。本阶段补 10 例守卫钉住
红线方向契约，并证明守卫有牙（翻转红线方向 → in-spec 输入被误判失败 → 还原字节级一致 → 绿）。

## 归因

1. **量测覆盖与决策覆盖是两件事**：J1-J6 把 `removal/collateral/spill` 的量测响应测得很全，但 `evaluate_gate`
   这个**把聚合值比对红线**、决定门禁红/绿的函数，没有任何断言钉住它。
2. **红线方向是契约**：`removal` 守**下界**（≥，低了变坏）、`collateral/overdraw/spill` 守**上界**（≤，高了变坏）。
   一旦方向写反（如 removal 错守上界），「去痕率跌成负值」会被静默放过——典型的「假绿」。
3. **`evaluate_gate` 确被 `main()` 接线**：`main()` 以 `fails` 驱动 `return 1`（`e2e_real_probe.py:588-603`），
   非死函数、无两套实现（排除阶段 153 那类「两套实现」缺陷）。

## 验证（探针 9 场景）

用托管 Python 直调真实 `evaluate_gate`（合成聚合），确认红线方向契约：

```
T1 in-spec corner_logo (baseline=None)        -> fails: []            (通过)
T2 removal 0.20 < 0.25 红线                    -> fails: [红线 corner_logo.removal = 0.2 < 0.25]
T3 collateral 1.50 > 1.40 红线                 -> fails: [红线 corner_logo.collateral = 1.5 > 1.4]
T4 overdraw 1.30 > 1.16 红线                  -> fails: [红线 corner_logo.overdraw = 1.3 > 1.16]
T5 spill 0.06 > 0.05 红线                     -> fails: [红线 corner_logo.spill = 0.06 > 0.05]
T6 n=0                                        -> fails: [corner_logo: 0/3 用例可评]
T7 缺类型                                     -> fails: [nonexistent_case: 未登记红线]
T8 基线引擎不符                               -> fails: [基线引擎为 opencv，当前 lama]
T9 漂移：removal 0.10 相对基线 0.30 跌 -66.7% -> fails: [[红线]...removal=0.1<0.25, [漂移]...-66.7%]
```

9 场景全部符合契约 ⇒ **by design 无误**；缺陷类是「缺守卫」而非「逻辑错」。

## 修复

`scripts/e2e_real_probe.py`：**无代码改动**（决策逻辑正确）。

新增 `tests/test_e2e_real_probe_gate.py`（10 例），钉住：

- `test_gate_in_spec_passes`：in-spec corner_logo → `fails == []`。
- `test_gate_redline_removal_below_fails`：`removal=0.20<0.25` → 含 removal 红线失败。
- `test_gate_redline_collateral_above_fails` / `..._overdraw_above_fails` / `..._spill_above_fails`：三类上界越界必失败。
- `test_gate_removal_high_is_not_failure`：`removal=0.90`（更好）绝不判失败（下界只守下限）。
- `test_gate_zero_cases_fails` / `test_gate_missing_case_fails` / `test_gate_baseline_engine_mismatch_fails`：三类边界必判失败。
- `test_gate_drift_removal_drop_fails`：removal 相对基线下跌超容忍 ⇒ `[漂移]` 失败。

## 注入式反例（守卫有牙）

沙箱拦截 `%TEMP%` 批量删除（pytest 临时目录清理），故改用**纯 Python 直调**验证，不再触发删除提示：

```

BROKEN evaluate_gate fails: ['[红线] corner_logo.removal = 0.3 > 0.25']   # 翻转 removal 方向后 in-spec 被误判
  -> guard catches breakage (broken -> red): OK
restored sha256 : 6524abf010c0a353a2cecd68fc19492bc64e4048e214a9f68723bd38cbc523b1 (byte-identical: OK)
RESTORED evaluate_gate fails: []                                          # 还原后正确（绿）
  -> restored behaves correctly (green): OK
COUNTER-EXAMPLE OK: broken->red, restored->sha identical->green
```

翻转 `evaluate_gate` 内 `("removal", "down")` → `("removal", "up")`：原本应通过 in-spec 输入（removal 0.30 ≥ 0.25）
被误判 `removal = 0.3 > 0.25` 失败 ⇒ `test_gate_in_spec_passes` 必红；还原后字节级一致、`evaluate_gate` 复原 `[]`。
