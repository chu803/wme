# 阶段 344 · 就绪探针要走真实 HTTP 往返——但探针**自己有副作用**

> 日期 2026-10-26 · 性质：**测试夹具竞态修复**（产品代码未动）

## 一、现象

`tests/test_api_security299.py::test_post_without_token_401` 今天**两次**在完整入口里变红
（331 之后各一次），而**隔离跑两次全绿**。这正是记录在案的那类「全量偶发红」：
不是产品回归，是夹具竞态。修法按纪律只能是「等它真的能用」，**不能放宽断言**。

## 二、为什么旧的等待不够

`_wait_ready()` 以前只做一次 TCP 连接成功就返回。问题是：
**`listen` backlog 会替应用接受连接** ⇒ 端口连上 ≠ `serve_forever()` 已经开始 accept。
3400 条用例并跑、机器被压满时，探针刚过，随后那个真 POST 就撞上 `ConnectionError`。
⇒ 就绪判据要走到**一次真实 HTTP 往返**（LESSONS #316 的同一条：探针要走用户实际通道）。

## 三、第一版修错了——探针吃掉了限流配额

把 `_wait_ready` 一律改成真实 `GET /api/capabilities` 之后，**隔离跑反而更红**：

```
E  AssertionError: 服务响应异常：实际 429
```

`rl_server` 这个夹具把限流设成 **1/min、burst 1**（它就是用来测 429 的），
而它自己也是每个 fixture 建立时调 `_wait_ready` ⇒ 我的探针**替测试把唯一那个令牌用掉了**，
随后的真请求自然 429。⇒ 探针不是只读的，**它有副作用**（消耗限流令牌、计入统计、写日志）。

修法：探针开关化，只有**限流宽松**的夹具（`secure_server` 100000/min、`open_server` 默认配置）
才付这次往返；`rl_server` 保持 TCP-only（它的语义就依赖每一个请求的计数）。
隔离跑 + 6 个 CPU 竞争者下跑 `test_api_security299 + test_api` 都 **rc=0**。

## 四、判据

1. **等待类辅助函数要问「等到什么程度才算 ready」**：连上 ≠ 可用；能拿到一次真实响应才算。
2. **加探针/预热请求时，先数它会碰到什么状态**：限流、计数、配额、缓存、日志、幂等键。
   这次是限流令牌——如果我没被测试打回，就会把一个偶发红换成一个必现红。
3. 改动的正当性来源仍是**测试自己变红**（429 那条），不是我意识到「也许有副作用」。
   所以：这类"看起来更严谨"的改动，必须**立刻在真实约束下跑一遍**再提交。
