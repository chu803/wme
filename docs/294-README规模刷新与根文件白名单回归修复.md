## 三、抓到自己引入的回归（跨阶段一致性）

- **现象**：跑更广测试集时 `test_repo_hygiene` 报 **2 例红**——`CONTRIBUTING.md`/`SECURITY.md`（291 加）、`docker-compose.yml`（C5 加）在白名单外且被 git 跟踪。
- **根因**：本会话 291/C5 新增根级文件时**未同步登记 `test_repo_hygiene._ALLOWED_ROOT_FILES`**；此前只跑靶向测试（docker/packaging），没跑更广集合，故漏到本轮。
- **修复**：按守卫提示将三个合法文件登记进白名单并注明理由（阶段 291 / 210·C5）。
- **教训（入记忆）**：**新增根级文件必须同步更新 `_ALLOWED_ROOT_FILES`**；且阶段收尾应跑一次更广回归（而非仅靶向文件），否则跨阶段一致性缺口会潜伏。这也再次证明守卫有效——它抓到了我自己前两阶段的遗漏。

## 四、规模下限守卫（`tests/test_readme_scale.py`）

- docs/测试文件数是**随阶段增长**的量 ⇒ 用 **≥ 下限**（非精确相等）：抗回归删除、对增长免疫；README 侧改「N+ 篇 / 219 文件 / 2500+ 用例」的「+」框架。
- **精确用例数（2500+）刻意不做廉价自动守卫**：需全量 `--collect-only`（秒级~数十秒），对卫生守卫过重；作为周期快照维护（同记分卡），README 引导「以 python -m pytest --co -q 为准」。

## 五、验证

- `pytest test_readme_scale.py test_repo_hygiene.py test_packaging_meta.py` → **RC=0**（13 例：修回归前 2 红，白名单补登后全绿）。
- README §4 数字与实测一致（docs 249 / tests 219 / 源码 ~36.7k）。

## 六、自反证伪

- 「README 曾 stale」以旧文本行号 + 实测数对照为证，非感觉。
- 规模守卫是**下限**非相等：若未来大规模删测试/文档会跌破下限变红（抗回归），新增不假红（抗脆弱）——两者皆为本设计意图，非缺陷。
- 未验证：精确用例数（需全量收集，留作周期快照）；全量回归本轮仍未跑（沙箱限制，见 290-b 经验 254 分批）。
