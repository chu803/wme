# 阶段 329 · 「不过门禁不发布」从未成立过：`| tee` 把退出码吞成 0

> 日期 2026-10-25 · 产物 `.github/workflows/ci.yml`、`.github/workflows/publish.yml`、
> `tests/test_run_all_checks.py`（+2 例，共 41 例）

## 一、怎么撞上的

328 刚把 `aggregate()` 的「环境错误(3) 被算成通过」修掉，我就顺着问了一句：
**CI 真的读得到这个退出码吗？** 两个 workflow 里那一步都写成：

```yaml
run: python scripts/run_all_checks.py 2>&1 | tee gate_output.txt
```

而两个文件**都没有声明 `shell:`**。GitHub Actions 在未指定 shell 时用 `sh -e`，
**不加 pipefail** ⇒ 管道的退出码取最后一个命令（`tee`）= **0**。

## 二、本机复现（用真实命令，不是比喻）

```
$ sh -e -c 'python scripts/run_all_checks.py --list 2>&1 | tee /dev/null; echo "旧写法读到=$?"'
旧写法读到=0            # 该命令本应返回 2

$ bash -eo pipefail -c 'python scripts/run_all_checks.py --list 2>&1 | tee /dev/null'
（整步以退出码 2 失败）   # 连 echo 都没执行到
```

上游佐证（结论一致：默认 shell 不带 pipefail，须显式指定 bash）：
[actions/runner#1212 "pipefail not set by default"](https://github.com/actions/runner/issues/1212)、
[github/docs#18933](https://github.com/github/docs/issues/18933)（文档曾错写「默认就带 -eo pipefail」）、
[codeinthehole TIL](https://til.codeinthehole.com/posts/github-actions-need-a-shell-specified-to-avoid-silent-pipeline-failures/)。

## 三、影响面（比 328 那一条更大）

1. `publish.yml` 第 9 行的注释写着「**不过门禁不发布**」——在这个配置下**它不成立**：
   门禁判 1（质量不合格）也会被吞成 0，构建与上传照常进行。
2. `ci.yml` 同理：步骤永远绿。
3. 连带一个静默后果：两步的失败诊断（`if: failure()` 写 Summary + 建 issue）**永远不会触发**，
   所以也没人从那儿发现异常。
4. **诚实边界**：我**没有** GH runner 可回溯验证历史（本机无 `act`）。能说的是——
   从这段配置写下起，「任何失败都不会被这个步骤读到」；至于历史上是否真有一次红被吞掉，
   要 push 之后看 Actions 记录才知道（本项目 CI 早在阶段 116 就写好，但按 `docs/184` 记录，
   仓库当时**还没有纳入 git**，CI 从未真正运行过 ⇒ 这次是它第一次要被真正激活）。

## 四、修法与守卫

两个文件同一形态（双保险：既给 shell，又在脚本体里显式开 pipefail，不依赖 runner 怎么拼 shell）：

```yaml
        shell: bash
        run: |
          set -eo pipefail
          python scripts/run_all_checks.py 2>&1 | tee gate_output.txt
```

守卫 `tests/test_run_all_checks.py::test_piped_gate_step_cannot_swallow_the_exit_code`
（参数化两个工作流文件）：扫描每个 `run:` 且含 `| tee` 的行，要求**就近 ±6 行内同时出现
`shell: bash` 与 `pipefail`**，否则报出行号。

**TDD 过程**：先写守卫 ⇒ 两条红，分别精确指到 `ci.yml:65` 与 `publish.yml:60`；
改 YAML ⇒ 41 例全绿；`yaml.safe_load` 两个文件都解析通过（步骤数 6 / 10）；再用第二节的
真实命令复现证明「旧写法读到 0 / 新写法整步失败」。

## 五、顺带记录的通用判据

**任何「把门禁输出用 `tee` 留档」的写法，都必须显式处理管道退出码。**
需要留档的现场（要日志给人看）恰恰是最不该吞码的地方——吞掉之后，日志里那一行 ❌ 和
CI 的绿勾会同时存在，而这正是人最容易相信绿勾的场合。
