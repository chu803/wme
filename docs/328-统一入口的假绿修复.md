# 阶段 328 · 统一入口的假绿：环境错误被聚合成「✅ 全部通过」

> 日期 2026-10-25 · 产物 `scripts/run_all_checks.py`（`aggregate` 四档 + `VERDICTS`/`STEP_MARKS`）、
> `tests/test_run_all_checks.py`（+8 例，共 39 例）

## 一、缺陷与它的形状

`real_gate` 约定用**退出码 3** 表示「环境错误（缺关键依赖）」，与「质量不合格(1)」「跳过(2)」区分
（见 `scripts/real_gate.py:1129/1181`）。而统一入口的聚合层只认 1：

```python
if any(rc == 1 for rc in rcs): return 1
if all(rc == 2 for rc in rcs): return 2
return 0                       # ← rc=3 落到这里：判成「通过」
```

于是真实后果不是「红一次」，而是**同一份输出自相矛盾**：

```
🚧 real_gate  rc=3   6.1s   真实图红线 + 漂移（严格范围）
✅ 全部通过（退出码 0）
```

而 `publish.yml` 的门禁步骤跑的正是 `python scripts/run_all_checks.py`
（`ci.yml` 同）⇒ **CI 环境缺依赖时，发布链会被判绿并继续 build → 上传 PyPI**。
顺带还有一处更早的坑：总结句用 `{0:...,1:...,2:...}[total]` 取值，
将来任何一步返回 3 都会让入口 **KeyError 崩溃**（我在改的时候撞到了这条）。

## 二、修法：四档语义 + 默认拒绝

```
1 = 有步骤判「质量未通过」；或出现约定集合外的码（127 / 崩溃 / 被信号杀）
3 = 有步骤判「环境错误」        ← 绝不再算通过，也不是质量失败
2 = 全部步骤都「跳过」
0 = 至少一步真通过，且无上述情形
```

优先级：`1 > 3 > 未知码(算 1) > 2 > 0`。措辞抽成模块级 `VERDICTS` / `STEP_MARKS`
两份**唯一真值来源**（含 3 的措辞明确写着「不是通过」），`main()` 与测试都读它们。

「未知码默认失败」是刻意的**默认拒绝**：说不清的结果不是通过——
旧行为等于「只要没明说失败就算过」，那正是这一类假绿的通用形态。

## 三、消费者都核过（没人依赖旧语义）

| 消费者 | 用法 | 结论 |
|---|---|---|
| `ci.yml` / `publish.yml` | `run: ... \| tee gate_output.txt`，靠退出码判定 | 3 非零 ⇒ 会失败（本就是要的效果） |
| 失败诊断步骤 | `if: failure()` + grep `FAILED` 文本 | 不受影响 |
| `test.sh` | `if "$PY" scripts/run_all_checks.py; then` | 非零即失败 ⇒ 语义变正确 |
| `test.bat` | 直接调用，透传退出码 | 同上 |
| 脚本内部 | 无人解析「全部通过」这句文本（只有 `ci_env_probe` / `docker_consistency_check` **自己**打印同款词，与入口无关） | 无耦合 |

## 四、TDD 过程（先红后绿）

1. 先加断言：`([0,3],3)`、`([3,0],3)`、`([2,3],3)`、`([0,127],1)`、`([0,4],1)`、`([1,3],1)` ⇒
   跑测试 **5 条红**（旧实现分别给 0/0/0/0/0），这就是缺陷的活证据；
2. 改 `aggregate` + 抽 `VERDICTS`/`STEP_MARKS` + 补头部退出码文档 ⇒ **39 例全绿**；
3. 端到端反例（不靠单元层自证）：`run_steps(build_steps(gates=True), runner=real_gate→3)`
   ⇒ 总码必须是 3，且**输出行里不得出现「全部通过」**；再造 `undef_scan→127` ⇒ 总码 1；
4. 结构守卫：`set(VERDICTS) == {0,1,2,3}`、`set(STEP_MARKS) == {0,1,2,3}`
   ——将来加一档忘了写措辞，就不会再是 KeyError 或「✅ 全部通过」。

## 五、诚实边界

- 我没有让 CI **真的**缺一次依赖来跑端到端（那需要改 runner 环境）；端到端证据是
  用假 runner 驱动**真实的 `run_steps`/聚合/打印**代码路径，只有子进程是假的。
- 本次不改 `real_gate` 自身的 3 语义（它的三档划分是对的），改的是**聚合层对它的处理**。
- 一个当时**没敢下结论**的疑点：`python ... | tee gate_output.txt` 里，门禁退出码会不会被管道吞掉？
  ⇒ 下一阶段查实：确实会被吞（workflow 未声明 `shell:` ⇒ GH 用 `sh -e`，无 pipefail），
  而且那才是更大的一条 —— 见 `docs/329-门禁退出码被tee吞掉.md`。
  **教训**：把疑点写下来是对的，但别停在疑点上——顺着它再挖一层就挖到了真问题。
