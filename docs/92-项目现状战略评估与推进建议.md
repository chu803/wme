# 阶段 92 · 项目现状战略评估与推进建议

> 本文不是功能开发记录，而是一次**面向决策的盘点**：91 个阶段之后，产品到底做完了没有、
> 哪些结论是可被证据支撑的、哪些是「绿灯但其实没验过」、以及接下来该往哪儿投时间。
> 所有数字均可在仓库内复现（脚本与文件路径逐条给出）。

---

## 0. 一句话结论

**功能面已经基本完整（能跑、能交付、有守卫）；但「验证面」与「功能面」严重不匹配**——
1199 个用例、94 份文档、两条门禁全绿，撑起的是一个**合成数据上很扎实、真实数据上只验了一个角**的系统。

具体说：
- 真实图门禁的 `recall = 1.0000` 是在 **30 张图 / 60 个标注点，且 60 个点全是 `corner_logo`** 上得到的；
- 同一个 `general` 预设在这 30 张真实图上，**平均把 16.15% 的画面判成水印区**，而预测掩码与真值水印的
  IoU 只有 **0.0617**——即「擦掉的面积里约 94% 不是水印」；
- 而这两个指标**都没有红线**（`mask_iou` 明文「仅监控」，`mask_coverage` 连监控都没登记）。

所以推荐的动作**不是**继续按现在的节奏一个模块一个模块地审下去，而是**先把验证面补齐**，
否则后续所有「门禁通过」的置信度都建立在同一个薄地基上。

## 2. 关键裂缝：验证面的三个缺口

### 2.1 缺口一：真实基准只覆盖 5 类水印中的 1 类

```
benchmark_real/ground_truth.json
  entries = 30          （每张图 2 个水印，共 60）
  style 分布 = {'corner_logo': 60}      ← 100% 是角标 LOGO
  labeled_by = 'manual:measured'        ← 确实是人标的，不是检测器自填（这点没问题）
```

而同一批图的清单里写的是：

```
benchmark_real/manifest.json
  watermark_style_hint 分布 = {'mixed': 30}   ← 30 张全标为「多种风格并存」
```

**清单说「mixed」，真值里只有 `corner_logo`。** 两者不可能同时为真，只能有一个解释：
标注时只标了看得清、认得准的角标 LOGO，其余（平铺 / 边缘小字 / 网格 / 渐变）没标进去。
后果很直接——**没被标注的水印不会被算成漏检**，于是：

> `real_gate` 的 `recall ≥ 0.98` 这条红线，实际上**只在守 corner_logo 的召回**。
> 其余 4 类在真实图上的召回是「未知」，不是「100%」。

README 对外承诺的 5 类（`ai_faint_tiled` / `ai_logo` / `ai_text_heavy` / `ai_grid` / `ai_gradient`），
在真实数据上只有第 2 类有真值支撑。

### 2.2 缺口二：预测掩码的「面积」没有任何红线

同样是 30 张真实图、同一个 `general` 预设（`benchmark_real/results/bench_20260914_155520.json`）：

| 指标 | 均值 | 中位数 | 最差 | 最好 |
|---|---|---|---|---|
| precision | 0.0388 | 0.0199 | 0.0082 | 0.1818 |
| recall | **0.9500** | 1.0000 | 0.5000 | 1.0000 |
| mean_iou（区域级最佳匹配） | 0.6571 | 0.6816 | 0.4814 | 0.8062 |
| **mask_iou（整幅掩码级）** | **0.0617** | 0.0429 | 0.0153 | 0.3638 |
| **mask_coverage（画面被判为水印的面积占比）** | **0.1615** | 0.1540 | 0.0226 | **0.2889** |
| pred_count（预测区域数 / 图） | **86.97** | 88.5 | 11 | **207** |

- 微平均：`tp=57 · fp=2552 · fn=3` → **P = 0.0218**。2609 个预测框里 2552 个是误报。
- 30 张图里 **27 张的掩码覆盖率 > 5%**，**8 张 > 20%**，最多一张覆盖 **28.89%**。
- 区域级 IoU 0.657（单框对得还行）× 掩码级 IoU 0.062（整体只有 6% 是对的）——
  这个**背离本身就是诊断**：不是「框偏了」，是「**框太多了**」。

要擦掉一个角标 LOGO，系统默认在全图找出 ~87 个区域、覆盖 ~16% 的画面。
`real_gate` 的红线是 `recall / precision / iou` 三条，**`mask_coverage` 与 `mask_iou` 都不在其中**。

**为什么这条最要紧**：对用户来说，「擦掉 16% 的画面去修一个角标」是产品级事故，
而它现在是**绿灯**。这也说明门禁设计有一个系统性偏向——**只惩罚「漏」（recall），
不惩罚「多」（coverage）**，因为 recall 容易构造红线，coverage 需要先约定「多少算多」。

### 2.3 缺口三：修复质量是用「真值掩码」验的，不是用实际掩码

`benchmark_real/results/decision_A_fixed.json` 自己标明了：

```
"mask_source": "truth"    ← 掩码来自真值
```

也就是「基线 27.67 → OpenCV 13.88」这个结论回答的是
「**给定正确的掩码**，引擎修得好不好」，而不是「**给实际管线产出的掩码**，最终结果好不好」。
而实际管线产出的掩码覆盖率是 16%（§2.2）——**端到端（真实图 → 预测掩码 → 修复）的质量，
至今没有被量化过。** 无真值的那次对决（`decision_20260913_144817.json`）只记录了
`masked_psnr`（改写量）与 `NIQE`，而 `NIQE` 在 30 张图里**全部为 null**（依赖不可用），
`masked_psnr` 已在文档里被明确标注为「高 ≠ 好」。

## 3. 不足清单（按严重度排序）

### S1 · 真实验证面窄（P0）
见 §2.1。`mixed` 清单 + 纯 `corner_logo` 真值。**后果**：4/5 类型在真实数据上的召回未知；
已知的信息论极限（`faint_tiled` 极淡平铺，合成图上任何参数召回 ≤ 7.4%）在真实图上**从未被确认过**，
对外却仍列为「支持的类型」。**这是当前最大的「结论超出证据」的地方。**

### S2 · 掩码面积无红线（P0）
见 §2.2。覆盖率 16.15% / mask_iou 0.0617 / 87 区域每图，三条都没进红线。
**后果**：任何让掩码进一步膨胀的改动都不会被门禁拦下。

### S3 · 端到端真实链路未验证（P0）
见 §2.3。detect → repair 的**合体**效果只在合成数据上量化过。
**后果**：真实图上「检测对但修得难看」「检测多导致大块重绘」这两类问题不可见。

### S4 · `ai_gradient` 没有任何正向验证，但对外是「支持类型」
`scripts/real_gate.py` 自己写着：

> 未登记预设（**如 ai_gradient 设计上恒为零输出**）只做监控与漂移，不设绝对红线。

而 `scripts/quality_gate.py` 的水印用例是 `CASES = (faint_tiled, corner_logo, edge_text, grid)`——
**没有渐变水印用例**（`("gradient", ...)` 出现在 `BASE_KINDS` 里，那是**底图**种类，不是水印种类）。
所以 `ai_gradient` 在合成门禁和真实门禁里**都没有正向样本**，同时 README §1 把它列为 5 大支持类型之一。
**二者必有一处需要修正**：要么承认它只是「用户主动确认后用」的兜底模式（那就把 README 措辞改准），
要么它是坏的功能（那就修或下线）。现状是文档承诺与门禁自述互相矛盾。

### S5 · 无参考质量分没有辨析力（P1）
阶段 85 已诚实记录：`quality_score` 辨析力 ≈ 随机，只进诊断工具、不入红线。
**后果**：批量场景下用户拿不到「这张修得好不好」的可信信号（`tab_batch.py` 里那套
`good / warn / review` 分级，其判据来源需要重新确认是否只依赖这个弱指标）。

### S6 · 引擎对决的样本量与数据面都偏小（P1）
真实图上 OpenCV : LaMa = 23 : 7（30 张、且全是 `corner_logo`，且用真值掩码）。
合成图上是 8 : 8 全胜。**7/30 的落败份额不算小**，且完全可能集中在某类底图上——
现在无法回答「LaMa 在哪些情况下更值得开」。**后果**：`INPAINT_DUAL_RUN` 维持 opt-in 是
对的保守选择，但「什么时候该开」这个真问题仍未回答。

### S7 · 审计覆盖严重不均（P1）
| 区域 | 覆盖 |
|---|---|
| `ui/` | 7 个文件审 **2** 个（`theme.py` / `app.py`）；`tab_models` 356/4、`tab_auto` 928/32、`tab_settings` 674/… |
| `services/` | 13 个审 **4** 个 |
| `core/` | `image_utils` / `detector` **从未独立审计** |
| `utils/` | `logger.py` 已覆盖（90） |

已审部分确实高产（11 模块 → 3 个 P0），说明**没审的地方大概率还有东西**。

### S8 · 工程侧遗留（P2）
- LaMa 纯 CPU 推理 ~3–4 s/图，未接 GPU；
- 真实超分权重缺失（需下载，网络受限）；
- `NIQE` 依赖不可用（30/30 null）；
- `__pycache__` 清理待授权（此前已拒绝过一次，保持不动）。

## 4. 还要不要一直往后推？

要区分三种目标，答案不同：

| 你的目标是 | 建议 | 理由 |
|---|---|---|
| **「能用」**（我自己修自己的图） | **已经够了，现在就能用** | 合成门禁扎实，真实图角标场景 recall 1.0，修复在真值掩码下 23/30 胜基线 |
| **「敢用」**（拿给别人用 / 上线） | **必须先补 S1–S3** | 现在对外承诺 5 类、真实数据只验 1 类；且默认会擦掉 16% 画面。这是「证据 > 承诺」的反面 |
| **「继续打磨质量」** | **建议改方向**：从「审计找 bug」转向「补验证面」 | 91 阶段的边际收益已经下降；继续按模块审下去，抓到的多是局部缺陷，而 S1–S3 是**系统性**缺口，不补则所有门禁绿灯的含金量都受限 |

一句话：**项目不缺「做」，缺「验」。** 继续推进是值得的，但推进的**对象**应该换。

## 5. 建议的下一步（按性价比排序）

### 第 1 步（最高性价比）：给真实基准补 4 类样式
不需要重做数据集，只需在现有 30 张里挑能体现其他风格的图、或新增少量图，**把真值标全**：
- 每类至少 **3–5 张**：`edge_text` / `faint_tiled` / `grid` / `gradient`（无真值则标 0，也要登记「此图无水印」）；
- 把 `manifest.watermark_style_hint` 从一律 `mixed` 改成**逐图精确**，并在真值校验里加一条
  「hint 与 truth 的 style 集合必须相容」的一致性检查——**这次的不一致正是靠肉眼发现的，应该由脚本发现**。
- 顺带给 `real_gate` 增加**分样式红线**（现在只有一条全局 P/R/IoU，混合了所有样式）。

### 第 2 步：给「面积」上红线
在 `real_gate.py` 里新增两条（先只监控、后收紧）：
- `mask_coverage ≤ 0.05`（现在是 0.1615，先定为「不得超过 2 倍当前值」作为第一步）；
- `mask_iou ≥ 0.15`（现在是 0.0617）。
**这是本次评估里最该做的一件事**：它把「擦掉 16% 画面」从一个看不见的事故变成一条会亮红的线。

### 第 3 步：用**实际掩码**重跑修复质量
把 `decision_A_fixed.json` 那套（seam_delta / white_frac）从 `mask_source=truth` 改成
**同时跑 truth 与 predicted 两列**，差值即「检测误差对修复质量的传导」。
这一步做完成立，S3 就闭环了。

### 第 4 步：裁决 `ai_gradient`
二选一，别让它继续悬着：改 README 措辞（降级为「需用户确认的兜底模式」），
或者给它补一个合成用例 + 一条红线。

### 第 5 步：审计继续，但排在验证面之后
候选顺序（沿用覆盖度荒漠选点法）：`ui/tab_auto`（928/32）→ `services/postprocess_service`（655/34）
→ `auto_pipeline`（575/10）→ `core/detector`（永未独审）。

### 明确不建议现在做的
- ❌ 继续给 `faint_tiled` 调参——已知是信息论极限（α≈0.09），调参收益是噪声；
- ❌ 上 GPU / 换更大的修复模型——在掩码覆盖率 16% 的前提下，修得再漂亮也没意义；
- ❌ 继续扩功能面（新格式、新预设）——验证面不补，功能越多、承诺越虚。

## 6. 什么情况算「完备」

给一个可判定（而不是感觉）的验收线：

1. `benchmark_real` 真值覆盖 **5 类样式**，每类 ≥ 3 张，`hint` 与 `truth` 一致性由脚本校验；
2. `real_gate` 对 **coverage / mask_iou 有红线**，且**分样式**报 P/R/IoU；
3. 修复质量报告同时给出 **truth 掩码**与**预测掩码**两列；
4. `ai_gradient` 的对外表述与门禁自述**一致**；
5. 1199 用例继续零失败（这条已经满足）。

这 5 条满足后，才能说「功能完善」这句话**有证据**。现在只能说「功能齐全，验证有偏」。
