# 阶段 330 · 「2 = 跳过」是各步骤自己的约定，不是全局的（pytest 收集期报错会被洗成绿）

> 日期 2026-10-26 · 性质：**329 的余波 → 已实施**（改 `run_all_checks.py` 的判定层，CI/发布文件一行没动）

## 一、为什么还会有一道

329 让 CI **真的开始读**统一入口的退出码了。读通之后紧接着的问题是：**读到的数对不对**。

入口原先只有一张全局表：`0 通过 / 1 失败 / 2 跳过 / 3 环境错误`，每个步骤的原始码直接进 `aggregate()`。
这张表对门禁家族（`real_gate`、`quality_gate`、`clean_bench_probe`、`perf_probe`、`media_gate`、
`removal_truth_probe`、`corner_signal_gate`）是对的——**它们是我们自己写的**，契约里就是这么定的。
但第 1 步是 pytest，而 pytest 的码表**跟我们的约定撞车**：

| pytest 码 | 官方含义 | 旧口径下入口怎么判 |
|---|---|---|
| 2 | Interrupted（**收集期报错**、用户中断） | ⏭ 跳过 |
| 3 | Internal Error（`.coveragerc` 那个坑就是它） | 🚧 环境错误 |
| 4 | Usage error（参数写错、路径不存在） | 约定外 ⇒ 1（碰巧对） |
| 5 | No tests collected（一条都没收集到） | 约定外 ⇒ 1（碰巧对） |

⇒ **最该报警的那一格是错的**。CI 用 `requirements-min.txt` 装最小依赖，缺包时的典型形态就是
「导入期炸」⇒ 收集错误 ⇒ pytest 报 2 ⇒ 入口判「⏭ 跳过」。
再看聚合：`[2, 0, 0, 0]` 里既没有 1 也没有 3，也不是「全部 2」 ⇒ **返回 0，总结句印「✅ 全部通过」**。
也就是说：**一条用例都没跑，CI 可以是绿的。** 329 修的是「码传不出去」，这一条修的是「码本身读错了」。

## 二、实测（不猜码表）

本机 venv 里直接量（注意别用 `| tail` 取退出码——那是 329 同一个坑，我第一次就踩了，
`$?` 拿到的是 tail 的 0）：

| 场景 | 命令要点 | 实测 rc |
|---|---|---|
| 收集期 ImportError（文件里 `import definitely_not_a_module_xyz`） | 单目录跑 | **2** |
| `-k zzz_nothing` 选到 0 条 | 同目录 | **2** |
| 路径不存在 `/tmp/no_such_dir_xyz` | | **4** |
| 未知参数 `--badopt-zz` | | **4** |

⇒ 「2 = 跳过」这条假设**被证伪**：2 恰恰是「编译期就没过」。（3/5 本次没能自然造出来，
按 pytest 官方 `ExitCode` 枚举处理，不编造实测值。）

## 三、修法：约定挂在步骤上，聚合前归一

不去改全局表（门禁家族那套是对的，动它就是把 328 的成果倒回去）。改成**每个步骤声明自己认哪些码**：

- `Step` 新增 `skip_codes=(2,)` / `env_codes=(3,)`，默认值就是门禁家族的约定 ⇒ **七道门禁一行没改**；
- `pytest` 步骤显式 `skip_codes=(), env_codes=()` —— 它没有「跳过/环境」这两档，2/3/4/5 全是事故；
- 新增纯函数 `normalize_rc(step, rc) -> 0/1/2/3`，`run_steps()` 逐步归一后才喂给 `aggregate()`；
  原始码继续印在日志里（不一致时那行显示 `rc=2→判1`），报告里同时留 `rc` 与 `verdict` 两个字段
  ——**判定改了口径要让读日志的人看得出是谁改的**，否则又是一种「说不清的绿」。

## 四、守卫（TDD：先红后绿）

`tests/test_run_all_checks.py` 里三条，先确认红：`pytest 返回 2 时入口应判失败，实得 2`。

1. `test_pytest_nonzero_codes_are_failures_not_skips` — 2/3/4/5 逐个 ⇒ 总码 1，
   且那行必须是 ❌ 并**带原始码**、报告里 `verdict==1`；
2. `test_gate_step_skip_and_env_codes_are_preserved` — 反向钉：`corner_signal_gate` 的 2 仍是「⏭ 跳过」、
   3 仍是「🚧 环境错误」，**别把环境缺资产误判成产品退化**（这条防止修复过头）；
3. `test_run_steps_all_skipped_returns_two` 改口径：原先「所有默认步骤一律回 2 ⇒ 总码 2」现在把
   pytest 排除在外。这不是为了让测试变绿而放宽断言——那条用例想测的是「**全跳过**」，
   而 pytest 回 2 根本不构成「跳过」，留着它只会测到一件正确失败的事。理由写在了测试注释里。

## 五、还没解开的：CI #17 为什么红

这道修复**不是**针对 #17 的诊断结论，因为诊断还没拿到证据。已排除与已知：

- ✅ 两个 workflow YAML 能被 `yaml.safe_load` 解析；门禁步骤确有 `shell: bash` + `set -eo pipefail`；
- ✅ `corner_signal_gate` 在把 `torch/torchvision/easyocr/pymupdf/fitz/requests/gradio/PIL/skimage/scipy`
  全部打桩屏蔽后仍 **rc=0**（325 实测），不会是无 torch 导致的红；
- ❌ 本机无法复刻 CI 环境：pip 连不上 PyPI（`from versions: none`），拿不到「min 依赖」的那套包；
- ⇒ **缺的是 CI 日志里「哪一步带 ❌」**。这一步只有用户点得开（Actions → CI #17 → test → 步骤列表）。
  在没有那一条证据前，我不给 #17 编原因。

值得注意：**如果 #17 恰好是「pytest 收集期炸」**，那这道修复就是它的解药——因为 329 之后
这类错误第一次有机会真的把 CI 弄红，而不是被洗成绿。换句话说，**#17 变红有可能正是我们
刚修好的那条链路在正常工作**。但这仍是假设，要靠日志证实或否证。

## 六、顺带发现的第二处「码不同源」——方向相反，本次**没改**

装完 per-step 约定后按同一把尺子扫其余步骤，撞到 `docker_consistency_check.py`：

```python
if warns:
    print("结论：无 ERROR，N 个 WARN（不阻断构建，但需知悉/决策）")
    return 2          # ← 它的 2 是「有 WARN」，不是「跳过」
```

⇒ 入口把它读成 ⏭ 跳过，聚合 `[0,0,2,0]` ⇒ **总码 0**：一句「需知悉/决策」被静默吞进绿里。
和 pytest 那条是**同一个病（共用一张表）、相反的方向**（pytest 那条是把事故洗成绿，这条是把提醒洗成绿）。

为什么这次不动它：两种改法都不是纯技术决定。

| 改法 | 代价 |
|---|---|
| A：`docker_static` 也声明 `skip_codes=()` ⇒ WARN 变 **CI 红** | 与脚本自己写的「不阻断构建」矛盾；未来任何 WARN 都会挡发布（325 刚说过「CI 常红」会把人逼去放宽断言） |
| B：加第五档「⚠ 警告」（判定 0、但印独立标记） | 要同时改四档契约、`STEP_MARKS`/`VERDICTS` 键集守卫与 header 文档——不是顺手能改完的量 |

现状至少**不是完全看不见**：`run_steps()` 对任何非零码都会附打末尾 12 行输出，那句「结论：无 ERROR，N 个 WARN」
会出现在日志里；**缺的是行首那个 ⏭ 的诚实度**。已登记为开放项，等用户拍 A/B 再动
（按项目纪律：改判定口径属于「对外可见」，先出判决再改）。
