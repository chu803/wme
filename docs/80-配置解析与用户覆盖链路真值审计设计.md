# 阶段 80 · 配置解析与用户覆盖链路真值审计设计

> 审计对象：`config.py` 的**配置读取链路**——
> 环境变量解析器（`_env_int/_env_float/_env_bool/_env_str/_env_list/_env_json`）
> 与用户覆盖链路（`_USER_OVERRIDABLE_KEYS` / `_USER_OVERRIDE_VALIDATORS` /
> `load_user_overrides` / `save_user_overrides`）。
> 审计范式：**探针量化 → 定位根因 → 修复 → 回归 + 跨入口守卫 → 门禁化**。

---

## 1. 为什么审计配置链路

`config.py` 是全项目**唯一的配置真值来源**：115 个数值配置、数十个布尔与列表配置，
被 core / services / ui / api / server / cli 全部模块读取。
它有两个特点使它值得一次专项审计：

1. **同一语义有多条入口**——环境变量（`WME_*`）、用户覆盖文件
   （`config.user_overrides.json`）、代码默认值，三条路径最终汇成一个运行期值；
2. **配置错了不会报错**——解析器被刻意设计成"永不抛异常、回退默认"，
   因此**错误只会表现为行为异常**，用户极难自查。

这与阶段 79 的 i18n 结构相同：**优雅的容错会成为错误的藏身处**。
而阶段 75/76 已围绕 `user_overrides` 做了两轮工作（白名单 6→11 键、设置页接线），
却始终没有验证「同一份配置在两条入口上是否得到同一个结果」。

---

## 2. 探针量化

探针覆盖六个维度：清单一致性、布尔解析、类型健壮性、端到端链路、
数值配置自洽性、格式白名单一致性。

| 编号 | 检测项 | 结果 |
|---|---|---|
| **C1** | 白名单 vs 验证器清单一致性 | ✅ 11 ↔ 11，无差集 |
| **C2** | **布尔解析：两条入口是否一致** | ❌ **完全相反**（见下） |
| C3 | 验证器对异常类型的健壮性 | ✅ 均抛异常并被上层捕获后回退 |
| **C4** | **超分后端名归一化** | ❌ 大小写敏感，`"ESRGAN"` 被丢弃 |
| C5 | 数值配置 min/default/max 自洽（115 个） | ✅ 不自洽 = 0 |
| C6 | 格式白名单一致性（alpha ⊆ 输出） | ✅ 通过 |

### C2 · 核心缺陷：同一语义、两条入口、两种结果

```
P8 环境变量路径（_env_bool）           P4 覆盖文件路径（bool(v)）
WME_...='false' -> False  ✅           {"INPAINT_DUAL_RUN": "false"} -> True  ❌
WME_...='0'     -> False  ✅           {"REAL_SUPERRES_ENABLED": "0"} -> True ❌
WME_...='no'    -> False  ✅           {"PNG_KEEP_ALPHA": "no"}       -> True ❌
WME_...='off'   -> False  ✅
WME_...='关'     -> False  ✅
WME_...='FALSE' -> False  ✅
WME_...='  false  ' -> False ✅
```

根因一行字：**`bool("false") is True`**。

覆盖文件链路用的是 `lambda v: bool(v)`，而 Python 中**任何非空字符串都是真值**——
所以用户想「关掉」的开关，只要值写成字符串，就会被**解释为开启**。

**真实后果**（按危险程度排序）：

| 配置 | 用户写入 | 实际效果 |
|---|---|---|
| `INPAINT_DUAL_RUN: "false"` | 以为关掉双跑 | **意外开启**，修复耗时翻倍（LaMa CPU 3~4s/张） |
| `REAL_SUPERRES_ENABLED: "0"` | 以为关掉超分 | **意外开启**真实超分（CPU 上极慢） |
| `PNG_KEEP_ALPHA: "no"` | 以为不保留透明 | 反而保留 alpha |
| `IMAGE_APPLY_EXIF_ORIENTATION: "off"` | 以为不做方向校正 | 反而启用 |

**触发路径**（两条，均已验证）：
1. 用户手工编辑 `config.user_overrides.json`，把布尔写成字符串（JSON 语法允许）；
2. 任何脚本/集成方调用 `config.save_user_overrides({"INPAINT_DUAL_RUN": "false"})`——
   验证器会把 `"false"` 变成 `True` 并**固化写入文件**，错误被持久化。

**为什么没被发现**：设置页写入的是原生 JSON 布尔（`true`/`false`），
`bool(True)` 恰好正确——**主路径正确掩盖了另一条路径的错误**。
本机现有的 `config.user_overrides.json` 正是设置页写的（值为原生布尔），
所以这个缺陷在常规使用中完全隐形。

### C4 · 同类不一致：同一张表里两种风格

```python
# 同一字典内：
"INPAINT_DUAL_SECONDARY": lambda v: str(v).lower() if str(v).lower() in (...) else "lama",  # ✅ 归一化
"REAL_SUPERRES_BACKEND":  lambda v: str(v) if str(v) in (...) else "auto",                  # ❌ 大小写敏感
```

用户写 `"ESRGAN"` 或 `" esrgan "` 会被**静默丢弃**、退回 `"auto"`，
而同表的副引擎键却正确做了 `.lower()`。
这是「同族参数只处理了一半」的典型（经验 12）：**改一处时要把同族的都列一遍**。

## 3. 根因分析

### 3.1 语义相同、实现分裂

「字符串 → 布尔」在全项目出现两次，而只有一处是认真写的：

```
_env_bool()                          ← 完整实现：7 个真值字面量 + 7 个假值字面量 + 回退默认
lambda v: bool(v)                    ← 随手实现：Python 真值语义
```

`bool(v)` 的问题不是"少写了几行"，而是**它借用了一个语义相近但不等价的规则**：
Python 的"真值性"（空字符串为假、非空为真）**不等于**配置语义的"布尔字面量"
（`false` 为假）。两者在 `""` 上恰好一致（都为假），在 `"false"` 上分道扬镳。

这与阶段 77 的「双真值来源」同构：**同一份事实写了两次，无冲突时一致、有冲突时给出错误答案。**

### 3.2 容错设计掩盖了数据错误

解析器被设计成"永不抛异常"，这是正确的工程选择（一个坏环境变量不该拖垮启动）。
但当**回退是静默的**，两类问题就会被吞掉：

- 值本身非法（本次的 C2/C4）；
- 值合法但被误解释（本次同样是 C2）。

`load_user_overrides` 此前对「校验失败」`except: continue`，**不留任何痕迹**——
用户遇到"配置写了却不生效"时，只能靠猜。
这与阶段 73 的教训一致：**兜底 except 必须留可观测痕迹**。

### 3.3 主路径正确造成的盲区

设置页写原生布尔 → `bool(True)` 正确 → 所有界面测试通过。
**只有"换个入口"才会暴露缺陷**——这与阶段 79 发现的「全量跑绿 ≠ 测试彼此独立」同源：

> **换一条入口/一种口径，缺陷才会现形。**

## 4. 修复设计

### 4.1 提取唯一真值来源：`parse_bool(value, default)`

新增模块级纯函数，作为**全项目布尔解析的唯一实现**：

```python
_BOOL_TRUE_LITERALS  = frozenset({"1", "true", "yes", "y", "on", "是", "开"})
_BOOL_FALSE_LITERALS = frozenset({"0", "false", "no", "n", "off", "否", "关"})

def parse_bool(value, default: bool) -> bool:
    if isinstance(value, bool):          # ← 必须最先判：isinstance(True, int) 为真
        return value
    if isinstance(value, (int, float)):
        if value == 1: return True       # 只接受明确的 0/1
        if value == 0: return False
        return default                   # 2/3/NaN 不猜
    if isinstance(value, str):
        text = value.strip().lower()
        if text in _BOOL_TRUE_LITERALS:  return True
        if text in _BOOL_FALSE_LITERALS: return False
    return default
```

要点：
- **支持原生布尔**（设置页写入形态）——行为不变，零回归；
- **支持字符串字面量**（手工编辑形态）——修复 C2；
- **不支持"非零即真"**——数字只认 0/1，`2` 退回默认，杜绝另一类隐式转换；
- **判断顺序**：`bool` 必须在 `int` 之前（否则 `True` 会被当数字处理）。

然后两条入口共用它：

```python
def _env_bool(key, default):
    ...
    return parse_bool(raw, default)                      # ← 环境变量路径

"INPAINT_DUAL_RUN": lambda v: parse_bool(v, False),      # ← 覆盖文件路径
```

### 4.2 同类不一致一并统一：`_normalize_superres_backend`

```python
def _normalize_superres_backend(v) -> str:
    text = str(v).strip().lower()
    return text if text in ("auto", "esrgan", "realesrgan") else "auto"
```

同时给 `INPAINT_DUAL_SECONDARY` 补上 `.strip()`（此前只 `.lower()`，
`" lama "` 会被丢弃）。**同族参数一次改齐**。

### 4.3 兜底留痕

```python
_validator = _USER_OVERRIDE_VALIDATORS.get(_key)
if _validator is None:
    print(f"[config] 用户覆盖项 {_key} 缺少校验器，已跳过…", file=sys.stderr)
    continue
try:
    _out[_key] = _validator(_raw[_key])
except Exception as _exc:
    print(f"[config] 用户覆盖项 {_key} 的值 {_raw[_key]!r} 校验失败…", file=sys.stderr)
    continue
```

用 `stderr` 而非 logger：`config.py` 是基础层，**不能依赖 `utils.logger`**
（后者本身读 config，会形成循环导入）——这个约束在改之前先确认过。

「文件不存在 / JSON 损坏」属正常缺省场景，**保持静默**（不制造噪声），
只对「有值但不可用」这类异常情形留痕。

## 5. 回归护栏与跨入口守卫

新增 `tests/test_config_parse.py`（**76 例**），核心是**跨入口一致性守卫**：

```python
@pytest.mark.parametrize("raw", _TRUE_LITERALS + _FALSE_LITERALS)
def test_bool_entries_agree_on_strings(raw):
    """环境变量路径与覆盖文件路径对同一输入必须给出相同结果。"""
    for key, default in BOOL_KEYS.items():
        assert config.parse_bool(raw, default) == config._USER_OVERRIDE_VALIDATORS[key](raw)
```

这条断言把「同一语义只有一套实现」变成可执行的不变量：
只要有人在任一条路径上重新引入分叉实现，它立刻失败。

配套守卫：

| 用例 | 断言 |
|---|---|
| `test_bool_validator_defaults_match_env_defaults` | 验证器回退默认与**源码里 `_env_bool("X", D)` 的 D** 一致（正则解析源码交叉验证） |
| `test_override_lists_are_consistent` | 白名单与验证器两份清单一一对应 |
| `test_parse_bool_passes_through_real_bools` | 原生布尔零回归 |
| `test_parse_bool_rejects_ambiguous_numbers` | `2/3/0.5/NaN/Inf` 一律回退默认（杜绝"非零即真"） |
| `test_false_literals_really_mean_false` | 直接锁定本次缺陷的 6 个假值字面量 |
| `test_load_user_overrides_parses_string_bools_as_written` | 端到端：临时文件注入字符串布尔 |
| `test_load_user_overrides_reports_invalid_value` | 非法值被忽略**且 stderr 有痕迹**（capsys 捕获） |
| `test_save_user_overrides_writes_validated_values` | 保存链路不得把 `"false"` 固化成 `True` |
| `test_superres_backend_normalized` / `test_dual_secondary_normalized` | 同族两键都大小写无关、去空白 |
| `test_superres_scale_range` / `test_invalid_values_fall_back_to_defaults` | 数值验证器边界 |

### 守卫的反例验证

一次性修复不能证明守卫有效，故做**注入式反例验证**：

```
1. 把 INPAINT_DUAL_RUN 的验证器改回 lambda v: bool(v)
2. 运行守卫 → 失败 10 例，覆盖 FALSE/False/0/no/n/off/否/关/"  false  " 及默认值用例
3. 还原 config.py（校验 bool(v) 残留为 0）→ 全部通过
```

## 7. 已知边界（诚实记录）

- **环境变量与覆盖文件的优先级不变**：显式参数 > 环境变量 > 覆盖文件 > 代码默认。
  本次只统一**解析语义**，未改动优先级（那属于产品决策，不是缺陷）。
- **`REAL_SUPERRES_SCALE` 校验范围是 1~8，而界面文案提示「2/4」**。
  校验器**宽于**界面建议：设 3 会被接受。未收窄——
  收窄会让现有配置（如 `SCALE=3`）突然失效，属行为破坏性变更；
  且下游对非 2/4 值的处理尚未审计。**记为待确认项，非遗漏**。
- **`load_user_overrides` 仍不抛异常、仍静默处理"文件不存在/损坏"**：
  这是刻意的容错设计（坏配置不该拖垮启动），本次只补齐了
  「有值但不可用」这一类的可观测性。
- **未审计 `_env_str` / `_env_json` 的业务语义**：探针显示二者的回退行为一致且安全
  （JSON 解析失败回退默认），但未穷举所有调用点的默认值合理性。

## 8. 结论

两条可以复用的规律：

**规律一：同一语义的多条入口，必须共用同一实现——并且用断言锁死。**

「字符串 → 布尔」在本项目有两条入口，一条认真、一条随手。
随手那条借用了**语义相近但不等价**的规则（Python 真值性 vs 配置字面量），
于是在 `"false"` 上给出相反答案。修复不只是把 `bool(v)` 换掉，
而是**抽出 `parse_bool` 让两条入口物理上无法分叉**，
再用 `test_bool_entries_agree_on_strings` 把一致性变成断言。

> 与阶段 77「单真值来源」、阶段 79「守卫」一脉相承：
> **先消除分叉的可能，再断言分叉没有发生。**

**规律二：主路径正确，是其他路径缺陷的最好掩护。**

设置页写原生布尔 → `bool(True)` 恰好正确 → 界面测试全绿 →
C2 缺陷从未被任何测试触碰。只有**换一条入口**（手工编辑 / 脚本调用）
才能让它现形。

这与阶段 79 的「全量跑绿 ≠ 测试彼此独立」是同一件事的不同侧面：

> **测试覆盖的是"我走过的那条路"，而不是"所有能走的路"。**
> 跨入口一致性断言，本质上是强制测试去走第二条路。
