# 阶段 205 · 追踪文件体积审计（205 MB 权重阻断 push）

> 起点：阶段 204 清理工作区残留时，顺手核对了「仓库追踪的内容到底是什么」——
> 结果发现**一个 205 MB 的模型权重被 git 追踪**。这与我一直建议的「推远端」直接冲突。

## 一、发现：205 MB 权重被追踪，而文档说它不会被追踪

阶段 204 取消追踪 `.pytest_*` 后，追踪文件从 5172 降到 743。这个降幅太大，
必须核实**没有误删真实源码**——核实中发现两个意外：

| 文件 | 体积 | 问题 |
|---|---|---|
| `models/big-lama.pt` | **205,669,692 B ≈ 196 MB** | 模型权重被追踪 |
| `models/.active_model.json` | 24 B | 运行时状态被追踪 |
| `.coverage` | 81,920 B | 覆盖率产物被追踪 |
| `covdata_parallel_quarantine.bin` | 77,824 B | 覆盖率产物被追踪 |

而 `models/.gitkeep` **白纸黑字**写着：

```
# 目录用途：存放 LaMa 模型权重文件（big-lama.pt，约 200MB）。
# 获取方式：在项目根目录执行 python download_model.py 自动下载。
# 注意：权重文件体积大，已被 .gitignore 忽略，不会上传到代码仓库。
```

**但 `.gitignore` 里根本没有 `models/` 或 `*.pt` 规则。**

⇒ 这是典型的**文档与实现矛盾**（同 LESSONS 218「承诺面必须实测」）：
承诺写了，规则没写，于是 **196 MB 被真实追踪**。

## 二、为什么这不止是「洁癖」

**GitHub 对单文件 > 100 MB 硬性拒收**（> 50 MB 仅警告）。196 MB 远超硬限
⇒ **`git push` 会被直接拒绝**。

也就是说：我在 199~204 反复建议的「推远端让 CI 跑起来」，
**会被这个缺陷当场阻断**，而当时**没有任何守卫能提前发现它**。
这是一条**卡住既定下一步的真实阻塞**，不是整洁度问题。

## 三、修复

### `.gitignore`

```
# 模型权重（阶段 205 修：`models/.gitkeep` 早就承诺「已被 .gitignore 忽略」，
# 但规则一直缺失 ⇒ 205MB 的 big-lama.pt 被真实追踪，会让 `git push` 被
# GitHub 的 100MB 单文件硬上限拒绝）。权重由 `python download_model.py` 获取。
# 保留 `models/.gitkeep`（空目录占位）与 README，故不忽略整个 models/。
models/*.pt
models/*.pth
models/*.onnx
models/*.safetensors
# 运行时状态（记录当前激活模型，随本机而变，非源码）
models/.active_model.json
```

### 停止追踪（保留磁盘文件）

`git rm --cached` 这 4 项：`models/big-lama.pt`、`models/.active_model.json`、
`.coverage`、`covdata_parallel_quarantine.bin`。
**磁盘文件全部保留**（权重仍可用于本机运行；`models/.gitkeep` 仍在追踪以占住目录）。

> 技术注：本项目 `git rm -r --cached <路径>` 会**清空整个索引**（实测两次，LESSONS 212⑥），
> 故一律改用 `git rm --cached --pathspec-from-file=- --pathspec-file-nul` 喂 NUL 分隔清单。

### 刻意**不动**的东西

`.workbuddy/scratch/` 下有阶段 158–167 的 `probe_*.py` / `inject_*.py`
——按 E1 约定「每阶段保留 1 份脚本与结果」，它们是**有意的阶段证据**，
**不纳入清理**（我一度加过 `.workbuddy/scratch/` 与 `*.bak` 两条规则，随即撤销
——过宽的规则会把阶段证据一并退管，属"清理过头"）。

## 四、新增守卫：`tests/test_repo_hygiene.py`

| 用例 | 锁定的不变式 |
|---|---|
| `test_no_tracked_file_exceeds_size_limit` | 任何**被追踪**文件 ≤ **50 MB**（取 GitHub 警告线，比 100 MB 硬限更早报警） |
| `test_documented_ignore_patterns_are_effective` | 文档承诺「已被忽略」的路径，必须**真的**匹配 `.gitignore` |

设计要点：
- 用 `git ls-files` 判定「追踪」——**唯一真值来源**；
  自己实现「哪些文件会被 git 追踪」等于重写一份 `.gitignore` 语义（必错）；
- git 不可用 / 非工作树 ⇒ **skip**（而非 fail），同 170「空真值是合法状态」；
- `_DOCUMENTED_IGNORES` 把「文档承诺 → 出处」显式登记，供人核对（不是装饰）。

## 六、诚实边界

- **未真跑 `git push`**（无远端可用），故"push 会失败"是**基于 GitHub 官方限制的推断**，
  非实测。但 196 MB > 100 MB 硬限是确定事实。
- 修复后**历史提交里仍含那个 196 MB blob**（`git rm --cached` 只影响此后）。
  若仓库尚未推送过，最干净的做法是**重建首个提交**或使用 `git filter-repo` 清历史；
  若已推送过则须 `filter-repo` + 强推。
  ⇒ **本阶段未动历史**（破坏性操作，需你决策）。

## 七、教训 → LESSONS 219

**① "清完还要看剩下的是什么"**——阶段 204 的退管让追踪数从 5172 掉到 743，
这个**降幅本身是信号**：幅度太大就必须**核实没有误伤**，而核实过程正好暴露了
196 MB 权重（本来不在清理目标里）。**磁盘清理由「该删什么」和「剩下的是什么」
两问组成**，只做前者会漏掉后者。

**② 体积是仓库的隐藏维度**——`.gitignore` 审查通常只看"哪些路径被忽略"，
不看"留下的有多大"。而 196 MB 单文件会让 `git push` **直接失败**
⇒ **仓库卫生审计必须包含体积维度**（本阶段补的守卫就是这个维度的机器判据）。

**③ 文档承诺必须与实现对账，尤其是"我不会做 X"型承诺**——
`models/.gitkeep` 说「不会被上传到代码仓库」，这是**否定式承诺**，
比"我会做 X"更容易悄悄失效（没人会去验证"没发生的事"）。
⇒ 否定式承诺要配**主动式的机器判据**（`git check-ignore` 实测），不能靠"看着像对的"。
