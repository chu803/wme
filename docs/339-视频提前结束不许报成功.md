# 阶段 339 · 视频解码提前停止不许被报成「✅ 处理完成」

> 日期 2026-10-26 · 性质：**产品诚实性修复**（第二轮审计 F3，已核实并修）

## 一、缺陷

`services/video_service.py` 的逐帧循环：

```python
ok, frame = cap.read()
if not ok:
    break          # 读完了（或读到坏帧），正常收尾   ← 两种情况被当成一种
```

`truncated` 只在「达到帧数上限」那一支被置位。于是**解码中途停止**时
（VBR 的 mp4/mkv 很常见，`CAP_PROP_FRAME_COUNT` 经常虚高）：

| 字段 | 实际值 | 界面表现 |
|---|---|---|
| `written_frames` | 210（源声称 900） | 只在 summary 里出现一次 |
| `status` | `"success"` | 「✅ 处理完成」 |
| `truncated` | `False` | 截断提醒不亮 |
| `warnings` | 空 | 一个字都不提 |
| `on_progress` | `1.0` | 进度条 100% |

⇒ 用户以为整段视频都修好了，实际后 3/4 画面**根本没进结果视频**。
这是 330–338 一直在追的同一族：**输出与做了多少事不一致**，只是这次少的是内容而不是状态码。

## 二、修法：不改判失败，而是把少掉的部分说出来

产出那 210 帧是**有效**的，判 `failed` 反而会误导（用户会以为整个视频废了）。所以：

```python
_total = int(result.total_frames or 0)
if not result.truncated and _total > 0 and result.written_frames < _total:
    result.truncated = True
    result.warnings.append(f"只写出 {written}/{_total} 帧：解码在中途停止（…）。未写出的部分不会出现在结果视频里。")
```

`ui/tab_media.py:522` 会把 `warnings` 逐条显示在结果文本里 ⇒ 这条提醒真的能被看见，
不是写进日志就算了。**前置条件写全**：`_total > 0`（有些容器读不到帧数，不能拿 0 去比）、
`not result.truncated`（上限截断已经报过一次，不重复追加）。

## 三、守卫与反例分布

`tests/test_video_truncated339.py`（3 例，用 `_FakeCap` 伪造「元数据 5 帧、实际只交付 2 帧」）：

| 用例 | 修复前 | 修复后 |
|---|---|---|
| 提前停止必须置 `truncated` 并说出 `2/5` | **红** | 绿 |
| 帧数齐平时不许凭空冒出截断告警 | 绿 | 绿 |
| 上限截断仍然只报一次（不与新告警重复） | 绿 | 绿 |

**1 红 / 2 绿**是这里最想要的分布：红的那条正是要修的，绿的两条证明
既没把正向路径改成新噪声、也没让原有语义退化（承 #305/#307/#338 的判据设计）。

写测试时踩的坑（也是产品代码的入口检查，值得记）：`process_video` 第一步就
`_os.path.isfile(src)`，光伪造 `VideoCapture` 不够 ⇒ 必须真的写出一个 src 文件，
之后帧内容/帧数才由替身接管。替身要**按被测函数的真实前置条件**造，否则会拿到
「找不到文件」这种与主题无关的失败。
