# 阶段 81 · 异常体系「定义 ↔ 使用」契约真值审计设计

> 审计对象：`utils/exceptions.py`（约 30 个异常类、8 大族）及其在
> core / services / ui / api / server / cli / main 中的**抛出与捕获使用面**。
> 审计范式：**探针量化 → 定位根因 → 修复 → 回归 + 契约守卫**。

---

## 1. 为什么审计异常体系

`utils/exceptions.py` 是本项目**设计密度最高**的模块之一。它明确承诺了三件事：

> ① 每个异常携带三段信息：`title`（标题）/ `reason`（带实际数值的原因）/ `suggestions`（可操作建议）；
> ② 「界面层拿到异常后，可以直接把这三段渲染成**结构化的提示框**」；
> ③ `to_markdown()`「用于 **Gradio 界面上的错误提示框**」。

一套承诺得如此具体的契约，却**从未被验证过是否真的被使用**。
而它此前**零测试覆盖**——`tests/` 下没有任何 exceptions 相关测试文件。

这正是阶段 78（命名链路零覆盖）、阶段 79（i18n 只有机制测试）的同一形态：
**设计越精致、文档越明确的模块，越容易掩盖「能力没有被接上」的事实。**

---

## 2. 探针量化

探针做**静态取证**：扫描全部生产代码，统计每个异常类的 `raise` 次数与 `except` 次数，
并检查呈现能力的调用点。

### 2.1 抛出 / 捕获矩阵（节选）

```

ImageError                          0       0   从未抛出

ModelError / NetworkError /         0       0   从未抛出
ResourceError / ServerError /

OutOfVRAMError                      0       0   从未抛出   ← 叶子类

```

```

```

## 3. 缺陷清单

| 编号 | 缺陷 | 证据 |
|---|---|---|
| **E1** | `to_markdown()` 是**死代码** | 文档写明「用于 Gradio 界面上的错误提示框」，生产代码**零调用**（唯一调用在测试里） |
| **E2** | `wrap_unknown_error()` 是**死代码** | 文档称「把原生 RuntimeError 智能转为显存不足异常」，生产代码**零调用** |
| **E3** | 业务代码从未按基类捕获 | `except WatermarkEraserError` 全项目 **0 处**；`except Exception` **200+ 处** |
| **E4** | 9 个叶子异常类从未被抛出 | `OutOfVRAMError` / `OutOfMemoryError` / `DiskFullError` / `DownloadTimeoutError` / `ModelDownloadError` / `PortInUseError` / `TaskCancelledError` / `TaskTimeoutError` / `InvalidConfigValueError` |
| **E5** | `InvalidConfigValueError` 是未使用导入 | `utils/path_helper.py:40` 导入后从未引用 |
| **E6** | 取消信号双实现 | `queue_worker._CancelSignal`（在用）vs `TaskCancelledError`（从未使用） |

**用户可见后果（E1+E3）**：界面上的错误提示是**未格式化的纯文本**，形如

```
【图片尺寸超出处理上限】
原因：图片体积 12.3 MB 超过上限 10 MB。
诊断：上限MB=10
建议：
  1. 先用图片压缩工具…
```

而基类为 Markdown 组件准备的 `### ❌ 标题` + `**原因**` + 编号列表结构**从未被渲染**。
更关键的是：`suggestions`（"用户照着做就能解决"的清单）只作为文本片段存在，
没有以任何交互形式呈现。

## 4. 根因分析

### 4.1 能力只建到了「定义层」，没有接上「使用层」

`exceptions.py` 的三层能力：

```
定义层：30 个异常类 + 三要素字段        ← 完成度 100%
渲染层：to_text() / to_markdown()      ← 完成度 100%（但 to_markdown 无人调用）
使用层：界面把异常渲染出来              ← 完成度 ~0%（只做了 str(exc) 拼接）
```

这与阶段 78 的 `normalize_unicode`、阶段 61 的「纹理细节重建」、阶段 77 的两处
「配置注释声称的行为从未实现」**完全同族**：
**一个能力只要完成了定义层，就有了"看起来已经做完"的外观**——
文档、自测、类型标注一应俱全，唯独没有在最外侧接上一根线。

### 4.2 为什么自测没能发现

`exceptions.py` 的模块自测（`if __name__ == "__main__"`）验证了：

```
【测试 1】显存不足异常的文本渲染      ← 打印 to_text()，肉眼确认"渲染正常"
【测试 2】智能识别 —— 把原生 RuntimeError 转为显存不足异常   ← 调用 wrap_unknown_error
【测试 4】异常转字典（用于 JSON 日志）
```

自测结论是「**全部渲染正常**」——它验证的每一件事都确实正常。
问题在于：**它验证的是「函数能工作」，而不是「函数有人调用」**。

这是阶段 79 结论的直接复现：

> **被测试的容错/能力，会成为错误的藏身处。**
> 自测通过 ≠ 能力生效；**必须有一条断言指向「它在生产路径上被使用」**。

### 4.3 「宽泛捕获」掩盖了分类体系的失效

`except Exception` 出现 200+ 次，而 `except WatermarkEraserError` 是 **0 次**。
这本身不算错（宽泛捕获在 UI 边界是合理的），但它带来一个后果：

**精心划分的 8 大异常族（Image / Media / Model / Network / Resource / Server / Task / Config），
在捕获侧完全没有被利用。** 于是在界面层无法区分：

- 「用户图片太大」（该给友好提示 + 建议）
- 「模型文件损坏」（该提示重新下载）
- 「程序内部 bug」（该记日志 + 报错）

三者走的是同一条 `except Exception as exc: return t("xxx.fail", exc=exc)`。

## 5. 修复设计

### 5.1 建立统一渲染入口 `format_exception_for_ui(exc)`

新增模块级函数（`utils/exceptions.py` 第 9 节）：

```python
def format_exception_for_ui(exc: BaseException) -> str:
    try:
        if isinstance(exc, WatermarkEraserError):
            return exc.to_markdown()      # ← 让 to_markdown 真正接上生产路径
    except Exception:
        pass
    try:
        return str(exc)                   # ← 内置异常保持原措辞
    except Exception:
        return exc.__class__.__name__     # ← 连 __str__ 都炸的极端对象
```

三个设计要点：

1. **自定义异常 → 结构化 Markdown**：把 E1 的死代码接上生产路径，
   界面从纯文本升级为 `### ❌ 标题` + `**原因**` + 诊断 + 编号建议列表；
2. **内置异常 → 原样 `str(exc)`**：**零回归**——现有 40 处提示的措辞逐字不变；
3. **自身绝不抛**：它处在错误处理路径上，再抛就会**掩盖原始错误**（双重失败）。

### 5.2 接入 40 处 UI 提示

把 `t("...", exc=exc)` 统一改为 `t("...", exc=format_exception_for_ui(exc))`，
涉及 7 个 tab 文件（auto 9 / settings 8 / single 6 / media 6 / history 6 / models 3 / batch 2 = 40 处），
并补齐各文件的 import。

因为内置异常分支与原行为**逐字一致**，这是一次**零回归**的升级：
界面上唯一的变化是——自定义异常终于显示了它本该显示的结构。

### 5.3 清理未使用导入

移除 `utils/path_helper.py` 中从未使用的 `from utils.exceptions import InvalidConfigValueError`。

### 5.4 把「定义了却没人用」变成必须显式决策

这是本阶段最重要的机制设计。9 个从未抛出的叶子异常类**不一定都是缺陷**——
`OutOfVRAMError` 在本机（CPU 后端）确实无触发路径，`PortInUseError` 属启动期预留。
但「合理预留」与「忘记接入」在代码上长得一模一样。

于是引入**预留登记清单**（写在测试里）：

```python
_RESERVED_EXCEPTIONS = {
    "OutOfVRAMError": "GPU 显存不足——本机为 CPU 后端，暂无触发路径",
    "DiskFullError":  "磁盘写满——导出/缓存落盘时可能触发，尚未接入",
    ...
}
```

并配守卫：

```python
def test_every_leaf_exception_is_raised_or_reserved():
    unaccounted = set(leaves) - raised - set(_RESERVED_EXCEPTIONS)
    assert not unaccounted, "请决定「接入」或「登记」"
```

**效果**：新增一个"定义了但不使用"的异常类，测试立刻失败，强制作者做出决策。
**并且反向检查**——已登记的项若后来被真的抛出了，也必须从清单移除（防止清单腐化）。

### 守卫的反例验证

两个核心守卫都做了**注入式反例验证**：

```
1. 注入 class ProbeUnusedError(ImageError)（定义了但从不抛出）
   → 守卫失败："以下叶子异常类既未被抛出、也未登记为预留"
2. 把 tab_batch.py 中一处改回裸 exc=exc
   → 守卫失败："以下文件仍在直接插值异常对象：['ui\\tab_batch.py']"

```

## 8. 已知边界（诚实记录）

- **`wrap_unknown_error()` 仍未接入生产**（E2 只做了一半）：它能把未知的
  `RuntimeError("CUDA out of memory")` 智能识别为 `OutOfVRAMError` 并附上建议，
  但接入点是「宽泛 except 的兜底分支」，一旦接入就会**改变现有非自定义异常的措辞**，
  存在提示质量退化的风险。故本轮**只修复死代码链路中的 `to_markdown`**，
  把 `wrap_unknown_error` 登记为预留能力，并用测试保证其不腐化。
  **这是"改动收益 vs 回归风险"的显式权衡，不是遗漏。**
- **`TaskCancelledError` 与 `_CancelSignal` 的双实现未合并**（E6）：
  二者语义并不完全等价——`_CancelSignal` 是**生成器内部的流程控制信号**
  （用于跳出迭代并返回已完成的成果），而 `TaskCancelledError` 表达的是
  **"任务被取消"这一业务状态**。合并需要重新设计批量队列的状态机，
  属独立议题；本轮将其**登记为预留**并记录语义差异。
- **未强制要求 `except WatermarkEraserError`**（E3）：宽泛捕获在 UI 边界是
  合理的工程实践。本轮修复的是"结构化信息在展示层丢失"，
  **没有**、也不应该强制全项目改用基类捕获（那会带来大量无收益的改动）。
- **9 个预留异常类保持存在**：删除它们会让未来接入时无类可用，
  而登记清单的维护成本极低。**留着的代价（几行代码）远低于删掉的代价（重新设计层级）。**

## 9. 结论

本阶段的缺陷全是"**能力建好了，但没有接线**"这一类。它带来两条可复用的规律：

**规律一：自测验证"能不能用"，必须另有一条断言验证"有没有用"。**

`exceptions.py` 的自测打印出漂亮的渲染结果并宣布"全部渲染正常"——
它说的每一个字都是真的，而 `to_markdown()` 依然是一次都没被调用过。
**"函数能工作"与"函数被调用"是两个必须分开验证的命题**，
后者只能靠「扫描生产代码的调用点」这类**结构性断言**来保证。

**规律二：把「合理预留」与「忘记接入」用显式清单区分开。**

"这个异常类为什么没被抛出？"——答案可能是"本机是 CPU 后端，用不到"，
也可能是"我写完就忘了接"。二者在代码里**完全无法区分**，
所以必须要求作者**显式写下理由**（`_RESERVED_EXCEPTIONS`），
并用双向守卫保证：新增未使用必须登记，登记项被使用后必须移出。

这与阶段 79 的「引用键必须存在」、阶段 80 的「跨入口必须一致」一脉相承：

> **把"沉默的默认"改成"必须发声的决策"**——
> 许可证式的白名单，比沉默的宽容更能保住系统的健康。
