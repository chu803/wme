# 阶段 340 · 画廊点「第 240 帧」，对比面板渲染的是第 4 帧

> 日期 2026-10-26 · 性质：**产品缺陷修复**（第二轮审计 F2，读码 + HEAD 行为取证确认）

## 一、两个「index」不是同一个东西

| 来源 | 含义 | 取值 |
|---|---|---|
| `_build_video_browse_gallery`（`ui/tab_media.py:363`） | 抽样的**真实帧号** `f["idx"]`，写进标题「第 240 帧」 | 0 … 视频总帧数 |
| `gr.Gallery` 的 `evt.index`（`on_frame_gallery_select:642`） | 被点格子在画廊里的**位置** | 0 … `VIDEO_COMPARE_FRAMES-1`（默认 6） |

处理器直接把位置写进滑块并交给 `run_video_compare(src, out, idx, mode)`，
而后者的 docstring 明写「**抽帧序号**（0 = 首帧）」（`:604`）。滑块范围是
`maximum=config.VIDEO_MAX_FRAMES`（几百），所以差异完全落在可见区间里。

`media.video.browse_info` 对用户承诺的是「点击任一帧即可加载到下方对比面板」⇒
**它看起来是成功的，只是给了另一帧**。这比崩掉糟：崩掉会被追，给错帧会被当成正确结果用。

## 二、HEAD 行为取证（不是推理）

在修复前的 worktree 里直接调用旧处理器（`run_video_compare` 用桩捕获入参）：

```
HEAD 行为取证：点第 5 格（标题写的真实帧号是 240）实际渲染 frame_idx = 4
```

新用例在 HEAD 上 **5 条全红**；但「全红」有一部分是因为新函数还不存在（API 缺失不等于行为错），
所以上面这条**行为取证**才是本阶段的反例主体。

## 三、修法：位置→帧号的映射与画廊**同源**

新增 `_VIDEO_BROWSE_INDICES`（按结果视频路径缓存「位置→帧号」表）：

* `_build_video_browse_gallery` 组装画廊时顺手记下 `[int(f["idx"]) for f in frames]`；
* `_browse_frame_indices(out)`：命中缓存直接用，未命中就按**同一个** `extract_sampled_frames`
  抽一次（不另写一份抽样公式——那会变成第二套真值来源，见 LESSONS #110/#114/#338）；
* 纯函数 `gallery_position_to_frame(indices, position)`：越界 / 无表 / 非整数 ⇒ `None`；
* `on_frame_gallery_select` 用映射后的帧号写滑块并渲染；**拿不到映射时明说「没选中」**，
  不许随便渲染另一帧冒充用户点的那一帧（这条由 `test_select_handler_refuses_to_show_a_wrong_frame` 钉住）。

为什么用缓存而不是每次点击重抽：抽 6 帧要解码 6 张图，点选是即时交互，每次重抽会把一次点击变成
几百毫秒；而缓存与画廊同源，不会出现「画廊显示 A、映射算出 B」。

## 四、写测试时又被「替身的真实契约」绊了一次

第一版把 `_normalize_file_value` 打桩成返回**列表**（`tab_batch` 的形状），
结果 `TypeError: _path_isfile: path should be ... not list`——
`tab_media` 的同名函数返回的是**字符串**（`:105`，两页各有自己的形状约定）。
这是 339 那条教训的第 N 次应验：**替身必须按被测函数的真实契约造**，
否则拿到的是与主题无关的失败。已在测试注释里写明这一点。

## 五、守卫

`tests/test_video_browse_frame340.py`（5 例）：位置→帧号的纯映射（含越界/`None`/非整数/空表）、
处理器必须用映射后的帧号（滑块也停在真实帧号）、拿不到映射不许渲染、越界位置安全。
