## 0. 本阶段定位：补全与强化，而非从零搭建

调研结论：**分块推理 / 设备缓存 / 模型单例 / 空显存释放，在阶段 14 之前已部分存在**，但分散且作用面有限：

| 能力 | 阶段 14 之前的状态 | 阶段 14 之后的状态 |
| --- | --- | --- |
| 分块推理 | 仅存在于 `core.inpainter` 的 LaMa 内部（`_inpaint_lama_tiled`） | 提升到 **框架层** `inpaint()` 的 `_tile_if_needed`，LaMa / OpenCV / 任意插件引擎大图统一分块 |
| 设备探测 | `device_manager.select_device()` 已带全局缓存 | 新增「入口级预选一次并复用句柄」，减少批量/视频逐次探测开销 |
| 进度回调 | 各层直接 `progress(p, msg)` | 新增 `ThrottledProgress` 节流包装器，避免高频重绘卡顿 |
| 空显存释放 | `empty_cache()` 每次推理结束调用一次 | 新增**时间间隔节流**，避免批量/视频逐帧同步 `empty_cache` 掉帧 |

因此阶段 14 的核心目标是 **「补全 + 强化 + 收口」**：把分散的能力统一到框架层、补齐缺失的节流控制、同时保持**修复核心算法（detector / image_utils / inpainter 内部修复数学）零改动**。

> 铁律约束：`ui → services → core → utils → config` 分层方向不变，core / services / utils 零 `gradio` 依赖。本阶段所有新增代码均遵守该约束。

## 1. 优化点一：框架级分块推理（覆盖所有引擎）

### 1.1 问题

阶段 14 之前，分块逻辑写在 LaMa 专用路径里。这意味着：

- 使用 **OpenCV 引擎**处理超大图时，没有分块，一次性把整张图塞进内存/显存，容易 OOM；
- 自定义插件引擎同理，需要自己重新实现分块，极易出错且拼接不一致。

### 1.2 方案

把分块决策从「LaMa 内部」上移到 `core.inpainter.inpaint()` 的 `_tile_if_needed(eng, image, mask, device, progress)`：

```
inpaint() 入口
   │
   ├─ 参数回填 / 掩码预处理
   ├─ 选择引擎 eng（来自插件注册表，LaMa/OpenCV/自定义统一）
   │
   └─ _tile_if_needed(eng, image, bin_mask, device, progress)
         │
         ├─ 长边 <= INFER_MAX_SIDE 或 ENABLE_TILING=False
         │      → 直接 eng.inpaint(image, mask)        # 单块直出
         │
         └─ 长边 > INFER_MAX_SIDE 且 ENABLE_TILING=True
                → split_into_tiles(image, mask, TILE_SIZE, TILE_OVERLAP)
                → 逐块：
                     · 若 t["skip"]（该块掩码为空）→ 原样保留，省一次推理
                     · 否则 → eng.inpaint(tile)        # 子块进度映射到 [0.2,0.8]
                → merge_tiles(...) 余弦权重窗无缝拼接回原尺寸
```

关键代码（`core/inpainter.py`）：

```python
def _tile_if_needed(eng, image, mask, device, progress):
    h, w = image.shape[:2]
    max_side = max(h, w)
    # 小图：直接整图送入引擎，不做分块。
    if not (config.ENABLE_TILING and max_side > config.INFER_MAX_SIDE):
        return eng.inpaint(image, mask, device=device, progress=progress)

    log.info("图像长边 %d 超过 %d，启用分块处理。", max_side, config.INFER_MAX_SIDE)
    tiles = split_into_tiles(image, mask, tile_size=config.TILE_SIZE,
                             overlap=config.TILE_OVERLAP)
    if len(tiles) <= 1:
        return eng.inpaint(image, mask, device=device, progress=progress)

    throttled = ThrottledProgress(progress, min_interval=config.PROGRESS_THROTTLE_SEC)
    for i, t in enumerate(tiles):
        if t["skip"]:
            t["result"] = t["img"]          # 无掩码区域直接保留，省推理
        else:
            sub = make_scoped(throttled, 0.2, 0.8)   # 子块进度映射进 [0.2,0.8]
            t["result"] = eng.inpaint(t["img"], t["mask"], device=device, progress=sub)
        throttled(0.2 + 0.6 * (i + 1) / len(tiles), "修复分块")
    return merge_tiles(tiles, h, w, overlap=config.TILE_OVERLAP)
```

### 1.3 不变性保证

- 拼接复用 `core.image_utils.merge_tiles` 的**余弦权重窗**，接缝无痕，与历史 LaMa 分块视觉结果一致；
- `_inpaint_lama_full` 简化为「只跑单块 `_run_lama_tile`」，不再内嵌分块循环；
- `inpaint()` 末尾 `empty_cache()` **统一释放一次**（见优化点三），无论分块还是单块都只释放一次。

## 2. 优化点二：进度回调节流（ThrottledProgress）

### 2.1 问题

批量 / 视频 / 分块场景会高频调用 `progress(p, msg)`：

- 分块推理：每块上报一次，几百块就几百次；
- 视频：每帧一次，1 分钟视频上千次；
- Gradio 每次回调都会触发一次前端重绘，过密会卡住交互。

### 2.2 方案

新增 `utils/progress.py`（零依赖、零 `gradio`），提供：

- `ThrottledProgress(progress, min_interval, min_step)`：包装任意进度回调，节流策略——**满足其一才真正上报**：
  1. `force=True`（终帧 / 显式 flush）；
  2. 距上次上报超过 `min_interval` 秒；
  3. 进度相对上次跃变 ≥ `min_step`。
- `make_scoped(progress, a, b)`：把子任务 0~1 进度线性映射到全局 `[a, b]`，用于把「分块修复」塞进 `[0.2, 0.8]` 区间。

节流判定核心逻辑（已修复两次边界 bug）：

```python
time_ok = self._min_interval <= 0 or (now - self._last_time) >= self._min_interval
step_ok = abs(p - self._last_p) >= self._min_step
# 开启时间节流：时间到了「或」步进达标即上报；
# 关闭时间节流(min_interval<=0)：仅看步进，避免每帧都上报。
emit = step_ok if self._min_interval <= 0 else (time_ok or step_ok)
```

> 关键设计：**首帧（p=0.0）、末帧（p>=1.0）、force 永远放行**，确保「完成」信号 100% 送达，不会因节流丢失终态。

### 2.3 用法落地

- 分块路径中对每块用 `ThrottledProgress` + `make_scoped(..., 0.2, 0.8)` 包装，避免几百块刷屏；
- `auto_pipeline.process_image` 内部把检测 / 修复进度分别映射到 `[0.10,0.40]`、`[0.45,0.90]`，本身已是子区间映射，节流包装器再叠加在 `inpaint()` 入口。

## 3. 优化点三：空显存释放节流（empty_cache）

### 3.1 问题

`torch.cuda.empty_cache()` 是**同步操作**，会打断 GPU 流水线。在批量 / 视频逐帧场景下，如果每帧修复结束都调用一次，会显著掉帧、拖慢连续推理。

### 3.2 方案

改造 `core/device_manager.empty_cache()`，引入时间间隔节流，记录上次真实释放的时间戳（`time.monotonic()`）：

```python
_last_empty_ts: float = 0.0

def empty_cache(*, force: bool = False) -> None:
    global _last_empty_ts
    if not config.DEVICE_EMPTY_CACHE_AFTER_RUN:
        return
    if not force:
        now = time.monotonic()
        if (now - _last_empty_ts) < config.EMPTY_CACHE_MIN_INTERVAL_SEC:
            return            # 间隔未到，跳过同步释放，交给 PyTorch 缓存池兜底
    try:
        import torch
        if torch.cuda.is_available():
            torch.cuda.empty_cache()
            _last_empty_ts = time.monotonic()
    except Exception:
        pass
```

- `force=True` 绕过节流（如显式卸载模型时）；
- 节流间隔内未真正释放的显存，由 **PyTorch 自身缓存池**管理，不会泄露；
- `inpaint()` 仅在整次修复结束时调用一次 `empty_cache()`，分块内部不再各自释放。

### 3.3 无 torch 环境

环境无 torch 时，`empty_cache()` 退化为 no-op，连续调用不抛异常（测试已覆盖）。

## 4. 优化点四：设备句柄预选复用（PERF_REUSE_DEVICE）

### 4.1 问题

批量 / 视频 / PDF 场景中，每张图（每帧 / 每页）都各自 `select_device()`。虽然 `device_manager` 内部已有全局缓存能命中，但「入口处提前选好一次、复用同一句柄」更符合批量场景语义，也避免任何逐次探测的边际开销。

### 4.2 方案

在三个批量型入口的参数回填之后，提前 `select_device()` 一次，把句柄透传给 `process_image(..., device=device)`：

- `services/video_service.process_video`：`device = select_device() if config.PERF_REUSE_DEVICE else None`
- `services/pdf_service.process_pdf`：同上
- `services/auto_pipeline.process_image / process_file`：签名新增 `device: Optional[object] = None`，透传给 `inpaint(..., device=device)`
- `inpaint()` 中：`device = select_device() if device is None else device`，保持单图入口「不传则自动选」的旧行为不变

### 4.3 关闭复用

`PERF_REUSE_DEVICE=False` 时三处均传 `None`，退回「每次修复各自 `select_device()`」的旧行为，保证可一键回退调试。

## 5. 配置项一览（第 8.x 节，均支持 .env 覆盖）

| 配置名 | 类型 | 默认值 | 取值范围 | 说明 |
| --- | --- | --- | --- | --- |
| `PROGRESS_THROTTLE_SEC` | float | `0.08` | 0.0 ~ 2.0 | 进度回调两次真实上报最小时间间隔（秒）。`0` 表示关闭时间节流，仅按步进节流 |
| `EMPTY_CACHE_MIN_INTERVAL_SEC` | float | `1.0` | 0.0 ~ 30.0 | 空显存释放最小间隔（秒）。`0` 表示每帧都释放（退回旧行为） |
| `PERF_REUSE_DEVICE` | bool | `True` | — | 批量/视频/PDF 是否预先选定设备并复用句柄 |
| `INFER_MAX_SIDE` | int | `2048` | 256 ~ 8192 | 触发分块的图片长边阈值 |
| `ENABLE_TILING` | bool | `True` | — | 是否启用大图分块（关闭则大图整体缩放修复） |
| `TILE_SIZE` | int | `512` | 128 ~ 2048 | 分块尺寸（512≈4GB 显存，1024≈8GB+） |
| `TILE_OVERLAP` | int | `64` | 0 ~ 512 | 分块重叠像素（取 TILE_SIZE 的 ~1/8 做无缝融合） |
| `TILE_SKIP_EMPTY` | bool | `True` | — | 掩码为空的块是否跳过推理（配套 `split_into_tiles`） |

以上字段均进入 `config.get_config_snapshot()`（新增「进度节流间隔(秒)」「空缓存节流间隔(秒)」「设备复用」「启用大图分块」「分块尺寸」「推理最大边长」等键），可在设置页与日志中查看。

## 8. 边界与注意事项

1. **分块边界**：`TILE_OVERLAP >= TILE_SIZE // 2` 会被 `validate_config()` 拦截（防止切图无限循环），阶段 14 沿用既有校验；
2. **进度节流边界**：`min_interval=0` 时退化为「仅看步进 `min_step`」，避免无时间维度时每帧都上报；`force`/首帧/末帧恒放行，终态不丢；
3. **空缓存节流边界**：间隔内未释放的显存由 PyTorch 缓存池兜底，不会泄露；`force=True` 用于显式卸载；
4. **设备复用边界**：`PERF_REUSE_DEVICE=False` 可一键回退为「每次 select_device()」，便于调试；
5. **无 torch 环境**：`empty_cache`、`select_device(GPU 分支)` 均安全降级，不抛异常；
6. **行为一致性**：分块与不分块修复结果在自检中验证一致，不影响最终画质。

## 10. 小结

阶段 14 在不触碰任何修复核心算法的前提下，完成了四项性能与内存优化：

1. **框架级分块推理** —— 让 OpenCV / 插件引擎也能安全处理超大图，避免 OOM；
2. **进度回调节流** —— `ThrottledProgress` + 子区间映射，杜绝高频 UI 重绘卡顿；
3. **空显存释放节流** —— `empty_cache` 按间隔合并，批量/视频不掉帧；
4. **设备句柄预选复用** —— 批量入口一次选定、全程复用，边际开销归零。

所有新增能力均通过统一配置暴露（`.env` + 配置快照），且默认行为与历史版本兼容、可一键回退。
