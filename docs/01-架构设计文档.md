## 二、分层架构设计

### 2.1 四层架构总览

本项目采用严格的四层分层架构。分层的核心价值在于：**每一层只关心自己那一件事，改动一层不会牵连其他层**。

```
┌──────────────────────────────────────────────────────────────┐
│  第四层  ui/          用户界面层（Gradio 网页）                 │
│  职责：收集用户操作 → 调用服务层 → 把结果画到网页上              │
│  禁止：编写任何图像算法、直接读写模型文件                        │
└───────────────────────────┬──────────────────────────────────┘
                            │ 只能向下调用
                            ▼
┌──────────────────────────────────────────────────────────────┐
│  第三层  services/    业务服务层（任务编排）                    │
│  职责：任务队列、进度上报、批量调度、缓存管理、文件导出           │
│  禁止：直接写 Gradio 组件代码、直接调用 PyTorch API             │
└───────────────────────────┬──────────────────────────────────┘
                            │ 只能向下调用
                            ▼
┌──────────────────────────────────────────────────────────────┐
│  第二层  core/        算法核心层（纯计算）                      │
│  职责：模型加载、掩码生成、水印检测、图像修复、分块拼接           │
│  禁止：打印界面提示、依赖 Gradio、直接决定文件存到哪              │
└───────────────────────────┬──────────────────────────────────┘
                            │ 只能向下调用
                            ▼
┌──────────────────────────────────────────────────────────────┐
│  第一层  utils/ + config.py   基础设施层                       │
│  职责：日志、异常定义、路径处理、输入校验、系统信息、全局配置      │
│  禁止：反向 import 上面任何一层（否则会循环导入崩溃）             │
└──────────────────────────────────────────────────────────────┘
```

### 2.2 依赖方向铁律

```
ui  ──▶  services  ──▶  core  ──▶  utils  ──▶  config
```

箭头**只能从左指向右**。任何反向依赖都会在项目后期造成循环导入，这是大型 Python 项目最常见的架构塌方原因。

**为什么必须这样约束？**举一个具体例子：如果 `core/inpainter.py` 直接调用了 Gradio 的进度条组件来汇报进度，那么这个修复算法就永远无法脱离网页界面单独使用 —— 你既不能给它写单元测试，也不能把它改造成命令行工具或 API 服务。正确做法是 `core` 层通过**回调函数**把进度数字抛出来，由上层决定这个数字是画成进度条、打印到控制台，还是干脆忽略。

## 四、核心数据流转

### 4.1 单张图片手动修复流程

```
用户拖入图片
    │
    ▼
[ui/tab_single] 收到 PIL.Image 对象
    │
    ▼
[utils/validators] 校验：格式在白名单？像素数未超限？文件未损坏？
    │  ├─ 校验失败 → 抛出 InvalidImageError → 界面红色提示，流程终止
    │  ▼ 校验通过
[ui/tab_single] 用户在画布上涂抹 / 拉矩形框
    │
    ▼
[core/mask_generator] 把涂抹图层转成标准二值掩码（白=修复区，黑=保留区）
    │      ├─ 按 MASK_THRESHOLD 二值化
    │      ├─ 按 MASK_DILATE 膨胀扩张
    │      └─ 按 MASK_FEATHER 高斯羽化边缘
    ▼
[services/task_service] 组装任务参数对象（图片 + 掩码 + 全部调节参数）
    │
    ▼
[core/inpainter] 修复引擎总调度
    │   ├─ 判断图片尺寸 > INFER_MAX_SIDE ？
    │   │     ├─ 是 且 ENABLE_TILING → [core/image_utils] 切块 → 逐块推理 → 融合拼接
    │   │     └─ 否 → 整图一次性推理
    │   ├─ 引擎选择：INPAINT_ENGINE
    │   │     ├─ lama   → [core/model_loader] 取模型单例 → TorchScript 推理
    │   │     ├─ opencv → cv2.inpaint(TELEA / NS)
    │   │     └─ auto   → 模型可用走 lama，缺失自动降级 opencv
    │   ├─ 按 INPAINT_STRENGTH 与原图做加权融合
    │   └─ 按 DENOISE_STRENGTH 做局部降噪
    ▼
[services/export_service] 按用户选择的格式与画质编码落盘
    │      └─ PNG 且 PNG_KEEP_ALPHA → 保留 Alpha 通道
    ▼
[services/cache_service] 写入历史记录索引 + 生成缩略图
    │
    ▼
[ui/tab_single] 左右对比预览 + 提供下载按钮
```

### 4.2 智能自动模式的差异

自动模式只是把「用户手动涂抹」这一步，替换为 `core/watermark_detect` 自动生成掩码，后续流程完全一致：

```
[core/watermark_detect] 三路并行检测
    ├─ 半透明水印检测：局部方差 + 饱和度异常 + 频域分析
    ├─ 角落 LOGO 检测：四角 ROI 区域内做边缘密度 + 连通域分析
    └─ 边缘小字检测：上下左右条带内做 MSER 文字区域检测（有 EasyOCR 则优先用）
    │
    ▼
候选区域合并 → 按 DETECT_MIN/MAX_AREA_RATIO 过滤 → 生成掩码
    │
    ▼
【关键设计】掩码必须回显给用户预览并允许手动增删，
            因为自动检测不可能 100% 准确，直接修复风险过高。
```

### 4.3 批量处理流程

```
用户选择文件夹
    ▼
[services/file_service] 递归扫描 → 按格式白名单过滤 → 逐个探测是否损坏
    ▼
[services/task_queue] 逐个封装为 Task 对象入队（超过 QUEUE_MAX_SIZE 则拒绝）
    ▼
工作线程循环取任务
    ├─ 每张图执行 4.1 的完整流程
    ├─ 成功 → 计数 +1，进度回调上报百分比
    ├─ 失败 → 按 QUEUE_TASK_RETRY 重试；仍失败则记入失败日志，继续下一张
    └─ 【铁律】单张失败绝不能中断整个批次
    ▼
[ui/tab_batch] 实时刷新进度条 + 成功/失败明细表
```

## 五、关键技术决策与权衡

### 决策 1：为什么选 LaMa 而不是 Stable Diffusion Inpainting？

| 对比维度 | LaMa | SD Inpainting |
| --- | --- | --- |
| 模型体积 | 约 200MB | 约 4~7GB |
| 显存需求 | 2GB 起 | 6GB 起 |
| CPU 可行性 | 可行，单图数秒至数十秒 | 基本不可行，单图数分钟 |
| 水印擦除效果 | 优秀（专为大面积遮挡修复设计） | 优秀但不稳定，可能生成无关内容 |
| 是否需要提示词 | 不需要 | 需要，对零基础用户不友好 |
| 结果可复现性 | 确定性输出 | 随机性输出，同参数结果不同 |

**结论**：面向个人本地使用、需兼容无显卡设备、要求零基础可用，LaMa 是明确更优解。

### 决策 2：为什么保留 OpenCV 备选方案？

三个不可替代的价值：

1. **兜底可用性**：模型未下载完成、显存不足、TorchScript 加载失败时，程序仍能工作而非直接罢工。
2. **速度优势**：擦除细小的日期水印、几个像素宽的线条时，OpenCV 耗时在毫秒级，而 LaMa 需要秒级。
3. **零依赖验证**：新用户可在不下载 200MB 模型的前提下，先跑通全流程确认环境无误。

### 决策 3：为什么用 Gradio 而不是 Flask + 前端框架？

Gradio 的取舍非常明确：**牺牲界面自由度，换取开发速度与零前端依赖**。对于个人工具，`gr.ImageEditor` 组件开箱即用地提供了画笔涂抹与图层导出能力，若自行实现需要写数百行 Canvas 交互代码。局限在于深度定制布局较受限，这一点将在阶段 6 通过注入自定义 CSS 来缓解。

### 决策 4：大图为什么必须分块？

LaMa 显存占用与图片面积近似成正比。实测参考值：

| 图片尺寸 | 峰值显存 | 4GB 显卡 | 8GB 显卡 |
| --- | --- | --- | --- |
| 512×512 | 约 0.9GB | 可行 | 可行 |
| 1024×1024 | 约 2.1GB | 可行 | 可行 |
| 2048×2048 | 约 7.5GB | 溢出 | 勉强 |
| 4096×4096 | 约 28GB | 溢出 | 溢出 |

因此长边超过 `INFER_MAX_SIDE`（默认 2048）时必须分块。分块引入的接缝问题，通过 `TILE_OVERLAP`（默认 64px）重叠区做余弦权重渐变融合来消除。

## 六、异常处理体系

| 异常场景 | 自定义异常类 | 处理策略 |
| --- | --- | --- |
| 模型文件不存在 | `ModelNotFoundError` | 提示并触发自动下载；下载失败则降级 OpenCV |
| 模型文件损坏 | `ModelCorruptedError` | 校验失败自动删除重下 |
| 图片格式不支持 | `UnsupportedFormatError` | 界面提示支持的格式清单 |
| 图片文件损坏 | `CorruptedImageError` | 批量场景跳过并记入失败日志 |
| 图片尺寸超限 | `ImageTooLargeError` | 提示上限值，建议先压缩 |
| 显存不足 | `OutOfVRAMError` | 清空缓存 → 自动降为 CPU → 仍失败则减小分块 |
| 系统内存不足 | `OutOfMemoryError` | 触发 GC，暂停队列，提示关闭其他程序 |
| 端口被占用 | `PortInUseError` | 自动尝试后续端口（最多 20 次） |
| 网络异常 | `NetworkError` | 多源切换 + 指数退避重试 |
| 磁盘空间不足 | `DiskFullError` | 落盘前预检可用空间 |

**总原则**：所有异常必须携带**中文可读描述**与**具体解决建议**，而非把 Python 原生堆栈直接甩给用户。
