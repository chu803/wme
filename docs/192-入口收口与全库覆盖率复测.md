## 3. 全库跑抓到的两处真实缺陷（均已修复）

### 3.1 `perf_probe` 缺「基线刷新护栏」（186 我引入的连带）
把 `perf_probe` 登记进 146 的门禁登记表后，守卫**一次暴露 5 条不符**：

```
刷新分支内有 return 0（静默通道）· 无法拒绝刷新 · 未 import baseline_guard
· 缺 --force-update 逃生门 · force_update 未参与判定
```

**为什么这是真缺陷**：其它门禁在 146 就被要求「刷新基线是受护栏约束的动作」——
否则**性能变慢也能被一次 `--update` 静默写进基线**。

**修复**（按家族规范）：
- ⓪ **可比性护栏**（本脚本特有）：旧基线存在时，若 `source / stage / repeat / 结构版本` 与本次不同
  ⇒ **拒绝覆盖**（否则 `--update --source synthetic` 就能冲掉真实图基线）；逃生门 `--force-update`；
- ① **向下刷新护栏**：`baseline_guard.check_downward_refresh`，规则 `{p95: ("max", 30%, 0)}`
  —— 本次 P95 比旧基线差出 30% 以上则拒绝写入并返回 1；
- ② **刷新后继续判定**：写完基线继续走护栏与绝对目标，**刷新不再是绕过判定的通道**。

**真实冒烟**：`perf_probe.py --update` → 写入基线 → 继续判定 → `✅ 性能门禁通过（退出码 0）`。

### 3.2 `normalize_file_paths` 顶层兜底**破坏了既有契约**（191 我自己引入的回归）
- 既有契约（`tests/test_tab_batch_helpers.py`）：
  **列表内**未知元素 → `str(item)`（`[123] → ["123"]`）；**顶层**未知标量 → **丢弃**（`3.14 → []`）。
- 我 191 的首版把顶层也写成 `str(value)` ⇒ `3.14 → ["3.14"]`，**直接把后一条打红**。
- 修复：末位兜底改回 `return []`，列表分支单独保留 `str(item)`；并把这段**不对称约定的由来**
  写进函数文档（避免下一个人「按直觉统一」）。我的 191 文档里「保留旧的兜底行为」的说法**是错的**，已改正。

## 4. 教训（LESSONS 205）

**改既有函数前，必须先找出该函数的全部既有测试并跑它们**——我 191 只跑了自己新写的测试，
于是打破了一条**早已被测试守着**的契约，直到 12 分钟的全库跑才发现。
与之对照的正面经验：**把新组件登记进家族守卫 = 免费获得该家族的全部不变式检查**
（`perf_probe` 一登记就暴露 5 条缺口，比我自己 review 有效得多）。
