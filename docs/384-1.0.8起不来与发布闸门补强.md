# 384 · 1.0.8 起不来：发布闸门只查"装不装得上"，没查"起不起来"（2026-11-05）

## 事故

1.0.8 发布后，用 PyPI 上的 wheel 做安装态复验，发现**界面根本起不来**：

```
[ERROR] [ui.app:545] 启动 Gradio 服务时发生未预期异常
TypeError: Blocks.launch() got an unexpected keyword argument 'analytics_enabled'
>>> 启动界面失败：Blocks.launch() got an unexpected keyword argument 'analytics_enabled'
```

原因：阶段 383 为关掉 Gradio 匿名统计，把 `analytics_enabled=` 加到了 **`app.launch(...)`**，
但该参数只存在于 **`gr.Blocks(...)` 构造器**（实测 `gradio.blocks`：`Blocks.launch` 的签名里没有它，
`Blocks.__init__` 里才有）。

## 为什么本地与 CI 都没拦住

1. **单测用的是鸭子替身**：`_FakeApp.launch(**kwargs)` 接受任意关键字，
   所以"断言 launch 收到了 analytics_enabled"这种测试**必然通过**——它验证的是替身，不是真实签名。
2. **发布闸门只做了"装得上 + 布局对"**：`scripts/verify_installed_layout.py` 建 venv、装 wheel、
   导入 config、检查目录，**从不启动程序** ⇒ 「能装不能起」的包一路放行。
3. CI 也不启动界面（入口只跑测试与静态检查）。

## 修法

1. `analytics_enabled` 改到 `gr.Blocks(...)` 构造器（`ui/app.py`）。
2. 新守卫 `tests/test_gradio_call_contract384.py`：**拿真实签名对账**——
   用 AST 取出 `app.launch(...)` / `gr.Blocks(...)` 的关键字，逐个核对
   `inspect.signature(gradio.Blocks.launch / __init__)` 里是否存在。
   替身再宽松也拦不住这条（它直接读真实签名）。
3. `scripts/verify_installed_layout.py` 增加**启动冒烟**：用宿主解释器（CI/本地都已有最小依赖）
   + `PYTHONPATH` 指向 venv 的 site-packages，跑的是 **wheel 里的代码**，等它真的响应 HTTP 200
   才算通过；失败时把启动日志尾部一并打出来。

## 验证（反例有效）

- 修好的 1.0.9 wheel：`[OK] 启动冒烟通过：界面已启动并响应 HTTP 200（端口 …）` ⇒ rc=0。
- **已发布的 1.0.8 wheel**（同一条命令）：`[FAIL] 安装后界面起不来`，并原样打出
  `TypeError: Blocks.launch() got an unexpected keyword argument 'analytics_enabled'` ⇒ rc=1。
  ⇒ 这道闸确实能拦住"装得上、起不来"的包。

## 影响与处置

- 1.0.8 在 PyPI 上**无法启动**（装得上、跑不起来）。官方源 `pip install wme-watermark-eraser`
  会拿到最新版本，1.0.8 只影响"在该时间窗内安装且不指定版本"的用户。
- 国内镜像仍停在 1.0.3（阶段 381 实测），**不受本次事故影响**。
- 下一版（1.0.9）修复并加闸；PyPI 的 yank 需要账号侧凭据（本机只有 GitHub 凭据），
  故本次**不 yank 1.0.8**，改为在 README 与 CHANGELOG 明确"1.0.8 有启动缺陷，请用 ≥1.0.9"。

## 边界

- 启动冒烟只证明"能起来并响应首页"，不覆盖完整功能链路（功能链路由真机黄金路径覆盖）。
- 冒烟用宿主解释器的依赖，可能与"纯净环境"略有差异；纯净环境的验收仍由阶段 381 的
  「全新 venv + 最小依赖」流程负责。
