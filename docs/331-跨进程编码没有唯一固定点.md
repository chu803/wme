# 阶段 331 · 跨进程编码没有唯一固定点：中文 Windows 上「一条用例没跑」与「19 条假红」同时存在

> 日期 2026-10-26 · 性质：**实测复现 → 已实施**（改的是边界与守卫，产品算法一行没动）

## 一、起点是 330 的那次真跑

330 改完，按纪律跑**真实统一入口**验证（不设任何环境变量，就是用户双击 `test.bat` 的那个环境）。
结果整条入口红：

```
❌ pytest               rc=1   699.2s   CI 等价子集（跳过 torch/network）
   …19 failed, 3339 passed, 7 skipped…
✅ undef_scan           rc=0     0.3s
❌ docker_static        rc=1     0.1s   ← 0.1 秒就红，根本没来得及检查任何东西
✅ corner_signal_gate   rc=0     7.9s
❌ 有步骤未通过（退出码 1）
```

`docker_static` 0.1 秒失败、`pytest` 里 19 条红的分布很散（selfcheck / 端到端 / i18n 泄漏守卫都有），
但每条都带同一种怪签名：

```
E  TypeError: unsupported operand type(s) for +: 'NoneType' and 'NoneType'
```

⇒ **不是产品回归，是测试自己拿到了 `stdout is None`**。

## 二、根因：编码约定靠「每个人记得」，于是两侧各自为政

跨进程打印有两个方向会错，本机**两种都真的在发生**：

| 方向 | 机制 | 现场 |
|---|---|---|
| 子进程**写** | 中文 Windows 的 stdout 默认 GBK，而 GBK 编不出 `⇒ ✅ ❌ ² −` | `docker_consistency_check.py` 打印 `audit()` 造的 `⇒` ⇒ `UnicodeEncodeError` ⇒ **rc=1** |
| 父进程**读** | `subprocess.run(text=True)` 按 **locale** 解码；子进程若已加固发 UTF-8，父进程按 GBK 读 | 读线程抛 `UnicodeDecodeError` ⇒ `CompletedProcess.stdout=None` ⇒ 断言炸在 `NoneType + str` |

机制本身一行的实验就够（不必读源码猜）：

```
$ PYTHONIOENCODING=gbk python -c "print('✅ x')"   →  rc=1  UnicodeEncodeError: 'gbk' codec can't encode '\u2705'
```

为什么阶段 170 的守卫没拦住：它的判据是**「`print(...)` 字面量里的非 GBK 字符」**，
而 `docker_consistency_check` 的 `⇒` 是 `audit()` **构造出来的字符串**——正是那条守卫文档里
自陈的盲区（「若某脚本把非 GBK 字符放在被 return 出去的字符串里再由调用方打印，本静态扫描看不到」）。
**盲区当天就咬到了我们**，而且咬在统一入口的默认第 3 步上。

静态枚举了一下欠了多少：

* `scripts/*.py` 里「有 `__main__` + 源码含非 ASCII + 没加固」——**13 个**；
* `tests/` 与 `scripts/` 里「文本模式子进程调用但没声明 `encoding=`」——**14 处**（15 个候选里
  `test_entry_encoding_and_path_guard.py:93` 是 bytes 模式，本来就不会解码，不算）；
  ⚠ **这份枚举自己也是分布式的**：第一版没扫仓库根的 `conftest.py`，于是漏掉 `cli_run` fixture
  ——它是 7 条 `test_cli.py` 用例的公共出口（后来守卫改成全仓枚举，实测全仓 23 处）；
* 更扎心的是 `download_model.py`：README 第 2170 行**让用户直接运行**它，它打印
  「✅ 模型已就绪」却没加固 ⇒ 中文 Windows 上**下载成功也会 rc=1**。

## 三、修法：在边界钉死一次，而不是祈祷每个文件都记得

| 层 | 改动 | 覆盖什么 |
|---|---|---|
| 写侧（唯一固定点） | `conftest.py`：`os.environ.setdefault("PYTHONIOENCODING","utf-8")` | 测试 spawn 的**所有**子进程（含 50 多个未逐个加固的库模块自检） |
| 写侧 + 读侧 | `run_all_checks.run_steps()` 给每步传 `env={**os.environ, PYTHONIOENCODING:"utf-8"}` + `encoding="utf-8", errors="replace"` | **产品路径**：`test.bat` / CI / publish 跑的就是这条入口 |
| 读侧 | 15 处调用点显式 `encoding="utf-8", errors="replace"`（14 处 + `conftest.py` 的 `cli_run`） | 不经入口的测试自spawn |
| 就地加固 | 13 个脚本 + `services/pdf_service.py` + `download_model.py`（共 15 个文件补 `force_utf8_stdio()`） | **人直接 `python scripts/x.py` / `python download_model.py`** 的路径 |

`errors="replace"` 是刻意的：第三方库（torch/EasyOCR 进度文案）里冒出什么字节都**不该把绿变红**，
宁可那一行花屏。**判定层不该被显示层绑架**——这正是阶段 146 当初写下那句话的地方：
「输出内容决定门禁退出码」是缺陷，不是特性。

`setdefault` 不会削弱对抗性守卫：`test_cli_survives_gbk_redirect` 用的是
`env["PYTHONIOENCODING"] = "gbk"`（**显式赋值**）⇒ hostile 环境照旧真测，加固失效它照样红。

## 四、守卫：把「盲区」本身机械化掉

`tests/test_scripts_console_encoding.py` 新增两条（同族、方向互补）：

1. `test_every_script_entrypoint_with_non_ascii_is_hardened`
   —— 判据**不看字符出现在哪里**（字面量/返回值/f-string 变量一律同等），
   代价是「非 ASCII 只在注释里」的脚本也会被要求加固。**误报方向是安全的**：加固调用无害，漏掉才是今天的红。
   带 `checked >= 20` 的反空转断言（枚举失效比断言失效更可怕）。
2. `test_text_mode_subprocess_calls_declare_encoding`
   —— 读侧同族判据：`tests/` 与 `scripts/` 里所有 `text=True` / `capture_output=True` 的
   `run/check_output/Popen/call` 都必须声明 `encoding=`；bytes 模式（只有 `capture_output` 没有 `text`）正确排除。
3. `tests/test_run_all_checks.py::test_run_steps_pins_the_cross_process_encoding`
   —— 行为级：用 spy runner 断言入口**对每一步**都传了 `encoding/errors/env.PYTHONIOENCODING`。
   这两个参数在代码里看着像噪音，最容易被人「顺手清理」掉，所以要有一条用例专门记住它们为什么在。

## 五、实测收口（同一入口跑了 5 次，逐次数清）

| # | 环境 | pytest | 其余三步 | 结论 |
|---|---|---|---|---|
| A | 修复前（330 那次真跑） | **19 failed** / 3339 passed，rc=1 | `undef_scan ✅`、**`docker_static ❌ rc=1`**、`corner ✅` | 缺陷现场 |
| B | 边界修完，**但 `conftest.py` 的 `cli_run` 还没修** | **8 failed** / 3353 passed | 三步全 ✅ | 19→8，docker 那一步从 0.1 秒红变成 ✅ |
| C | 与 B 同一份代码，但入口整体在 `PYTHONIOENCODING=gbk` 下启动（hostile） | **7 failed** / 3354 passed | 三步全 ✅ | hostile 环境不再改变判定（边界钉住的直接证据） |
| D | 补上 `cli_run` 后单跑 `test_cli + 三条新守卫 + test_run_all_checks + test_api_security299` | **rc=0 全绿** | — | 7 条 test_cli 红的根因确认 |
| E | 最终再跑一遍完整入口（默认环境） | **4/4 步 ✅，总退出码 0**（pytest 步 661.8s） | 三步全 ✅ | **收口：本地双击 `test.bat` 的环境不再假红** |

- B 与 A 差的 11 条、C 与 B 差的 1 条，**都是同一族**：`stdout=None` / `UnicodeEncodeError`。
- B 里多出的那 1 条 `test_api_security299::test_post_without_token_401`（`ConnectionError`）**与编码无关**：
  C 里没复现、D 单跑全绿 ⇒ 判为**并发抢占抖动**（跑 B 时我在同一台机器上并发了 13 个脚本的 `--help` 实跑）。
  该用例的 fixture 已经有 `_wait_ready(port)`（不是「未就绪就发请求」那种缺陷），所以**不动它**，只登记。
- 7 条 `test_cli.py` 的根因很具体：公共 fixture `cli_run`（`conftest.py:139`）用 `text=True` 却没写 `encoding`
  ⇒ 子进程 `cli.py` 早已自带加固、发的是 UTF-8 ⇒ 父进程按 GBK 读 ⇒ 读线程崩 ⇒ 7 条一起红。
  **教训**：我第一版静态枚举只扫了 `tests/` 与 `scripts/`，**没扫仓库根的 `conftest.py`**——
  漏的正好是「七个用例的公共出口」。守卫现在改成**全仓枚举**（排除 `htmlcov/temp/.workbuddy` 等），
  实测口径：全仓 **23 处**文本模式子进程调用，**0 处**未声明编码。


## 六、留下的诚实边界（不是「以后再说」，是写清楚为什么现在不修）

`core/`、`services/`、`utils/`、`ui/` 里还有约 **50 个**模块的 `__main__` 自检没就地加固。
它们今天不崩的原因是**它们打印的是中文，GBK 编得下**；一旦哪句自检改成打印 `⇒/✅`，
直跑 `python core/detector.py` 的人就会撞上同一个坑。

为什么不一次扫平：
* 经**入口**或**测试**spawn 的已经被写侧固定点覆盖了（本阶段的两条边界改动）；
* 剩下的只是「人手工直跑库模块自检」这一条 dev 路径，收益低、改动面 50 个文件；
* 而且第 1 条守卫目前只覆盖 `scripts/`（那才是入口会调的地方）。把判据扩到 `core/services/utils/ui`
  需要先把这 50 个文件加固完，**否则守卫一上线就红 50 条** ⇒ 那是「为了守卫而改产品」，方向反了。
⇒ 已登记为开放项：守卫范围随加固范围一起扩，一步到位。

## 七、E 那次全绿暴露的第二件小事：**绿的时候，日志里一个计数都没有**

跑 E 想留「3361 passed」这种证据时才发现留不下来：`run_steps()` 只在 `rc != 0` 时附打末尾输出，
于是 CI 日志里成功那行就是孤零零的 `✅ pytest rc=0  661.8s`——**没人能看出它究竟跑了多少用例**。
这和 #310/#311 是同一族（「说不清的绿」），只是这次说不清的是**成功**。

改法（判定完全不变，只多一行）：`rc == 0` 时也把子进程最后一行非空输出附打，截断 160 字符。
守卫 `test_success_still_prints_a_line_of_evidence`（并断言通过时**不得**用「末尾输出」那种失败格式）。
实跑两个静态步骤确认：

```
✅ undef_scan     rc=0   0.3s   静态未定义名扫描（零依赖）
   └─ 全部通过：未发现「引用了但从未定义」的名字。
✅ docker_static  rc=0   0.1s   容器静态一致性（…）
   └─ 结论：全部通过
```

**本轮我自己也被这条缺陷咬了一次**：临时写的验证脚本没加固、stdout 又是管道(GBK)，
`print("✅ …")` 直接 `UnicodeEncodeError` 退出码 1——**同一天的第二次**，恰好是这条经验最好的活广告。
