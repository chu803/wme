# 阶段 78 · 文件命名与路径安全真值审计设计

> 审计对象：`utils/path_helper.py` 的命名与路径构造链路
> （`sanitize_filename` / `build_output_filename` / `make_unique_path` / `normalize_unicode`）。
> 审计范式：**探针量化 → 定位根因 → 修复 → 回归测试 → 门禁化**（沿用 49 起的真值审计期范式）。

---

## 1. 为什么审计命名链路

命名链路是**每一次上传与每一次导出必然经过**的公共路径：

```
用户上传文件 ── sanitize_filename ── make_unique_path ──► 落盘
导出结果    ── build_output_filename ── make_unique_path ──► 落盘
```

它同时满足三个「高危条件」：

1. **输入完全不可信**——文件名来自用户，任意字符都可能出现；
2. **失败后果直接可见**——名字错了用户一眼就能看到，或干脆写不出文件；
3. **覆盖面极大**——14 个服务模块、4 个界面页、API 与 CLI 都依赖它。

而审计发现：**这三个函数此前零直接测试覆盖**（`grep sanitize_filename tests/` 为空）。
零覆盖不是巧合——它同时解释了缺陷为何能潜伏：**没有测试的地方，错误不会被任何东西抓住**。

## 2. 探针量化（修复前）

探针脚本写到 `%TEMP%`（项目内零残留），逐项取证：

| 编号 | 承诺（文档 / 直觉） | 实际行为（探针实测） | 严重度 |
|---|---|---|---|
| **N1** | 输出名按模板生成，信息完整 | **默认模板 `{stem}_cleaned_{time}` 不含扩展名** → `rsplit(".", 1)[0]` 把主名里的点误当扩展名分隔点：`my.photo` → **`my.png`**（丢 `.photo` 与 `_cleaned_125053`） | **高（默认配置即触发）** |
| **N2** | 清洗「所有 Windows 非法字符」 | 清洗**只作用于主名**，扩展名部分原样透传：`a.//evil` → **`a.//evil`**（路径分隔符残留） | 中高 |
| **N3** | 生成可安全创建的文件名 | Windows 保留设备名未处理：`CON.png` / `aux.jpg` / `COM1.png` 原样返回（创建会失败或写入设备） | 中高 |
| **N4** | 同上 | 控制字符未剔除：`a\x00b.png` 保留 NUL（`open()` 直接抛 `ValueError`）、`line\nbreak.png` 保留换行 | 中 |
| **N5** | 「不允许以空格或点结尾」 | 去尾只对主名生效：`a.png␠`、`trail.␠` 的尾随空白/点从扩展名位置漏过 | 中 |
| **N6** | 模块提供「全角转半角」能力 | `normalize_unicode` 是**死代码**（唯一「调用」是自检断言），`ａｂｃ.png` 全角原样保留 | 中 |
| **N7** | `max_length` 控制文件名长度 | 只约束主名，不约束整体：主名 3 + 扩展名 120 → 总长 123 | 低 |

探针原始输出（节选）：

```
N1  模板='{stem}'  stem='my.photo' ext=png -> 'my.png'        主名信息丢失=True
    模板='{stem}_去水印' stem='a.b'   ext=webp -> 'a.webp'      主名信息丢失=True
N2  in='a.//evil'              -> out='a.//evil'             含路径分隔符=True
N3  'CON.png' -> 'CON.png'    仍为保留名=True
N4  in='a\x00b.png' -> out='a\x00b.png'  残留控制字符=['0x0']
N6  normalize_unicode 非定义调用点：['assert normalize_unicode("ＡＢＣ") == "ABC"']
N7  主名 3 + 扩展名 120 -> 总长 123
```

**N1 的默认触发面**（实测，`config.OUTPUT_NAME_TEMPLATE` 默认值 `{stem}_cleaned_{time}`）：

```
my.photo             → my.png                       ← 丢 .photo 与时间戳
screenshot.2024.08   → screenshot.2024.jpg          ← 丢 _cleaned_125053
v1.2.3               → v1.2.png                     ← 丢 .3 与时间戳
普通图                → 普通图_cleaned_125053.png     ← 正常
```

含点的原图名（`photo.2024.png`、`IMG_2024.08.13.png`、`v1.2.jpg`）**极为常见**，
所以这不是边缘情况，而是**默认配置下的常态错误**。附带后果更隐蔽：
`{time}` 被丢弃后，同一批导出的多张图会**坍缩成同一个名字**，只能靠 `(1)`、`(2)` 区分——
用户无法从文件名辨认是哪一张。

## 3. 根因分析

### 3.1 N1：对「点」的语义假设不成立

```python
# 修复前
if not name.lower().endswith("." + extension.lower()):
    name = name.rsplit(".", 1)[0] + "." + extension.lower()
```

`rsplit(".", 1)` 隐含假设：**「最后一个点」之后就是扩展名**。
这个假设在处理「已有扩展名的文件名」（`shot.jpg`）时成立，
但在处理**任意字符串**（模板渲染结果）时**根本不成立**——模板里可能一个点都没有。

修复选择有两条路：
- (a) 把 `rsplit` 换成更聪明的"猜扩展名"——但**猜不准**（`my.photo` 的 `photo` 像不像扩展名？）；
- (b) **不猜**：只有当末尾段**确定是扩展名**（在已知扩展名白名单内）时才替换，否则**安全追加**。

选 (b)。理由：文件名里"多一个点"是无害的（`my.photo_cleaned_125053.png`），
而"少一段信息"是不可恢复的（`my.png`）。**不确定性应当偏向可恢复的一侧。**

### 3.2 N2：清洗管线的顺序错了

```python
# 修复前：先切分，再只清洗主名
if "." in name:
    stem, suffix = name.rsplit(".", 1)
    suffix = "." + suffix      # ← suffix 从未经过 _ILLEGAL_RE
stem = _ILLEGAL_RE.sub("_", stem)
```

清洗被放在**切分之后**且**只覆盖 stem**，于是扩展名成了「清洗盲区」。
根因不是漏写一行替换，而是**管线顺序错**：清洗一个字符串的正确时机是
**在按结构解析它之前**（先净化、再解析），而不是之后。

这与阶段 70 的教训同构：**「失败位置越靠后越糟」→ 规范化应在入口统一完成**。
此处入口 = `sanitize_filename` 的第一行，而不是"主名分支"。

### 3.3 N3/N4/N5：把「合法字符集」当成了「安全文件名全集」

`_ILLEGAL_CHARS = r'<>:"/\|?*'` 是**Windows 的非法字符表**，
但「不含非法字符」远不等于「可以安全创建」：

- 保留设备名 `CON` 等**全部由合法字符组成**；
- 控制字符 `\x00`/`\n` 不在非法字符表里，但系统层面同样不可接受；
- 尾部空格与点也不是"非法字符"，Windows 会在创建时**静默截断或拒绝**。

这是典型的**判据定义不完整**：把一个必要条件（字符集）当成了充分条件（可创建）。
同类问题在阶段 57/58 出现过（"随尺寸缩放的相对阈值"只覆盖一半情形）。

### 3.4 N6：死代码（与阶段 61 同族）

`normalize_unicode` 有完整实现、有文档、有自检断言——**唯独没有被生产代码调用**。
自检断言 `assert normalize_unicode("ＡＢＣ") == "ABC"` 制造了「功能已验证」的假象，
但验证的是函数本身，不是「文件名会被归一化」这个承诺。

**教训复用（经验 7）**：自检/测试若只验证"函数能跑"，就抓不到"函数没人调用"。

### 3.5 N7：约束对象选错

`max_length` 的语义是「文件名（不含扩展名）的最大长度」，
但文件系统的真实约束是**整个文件名**（以及完整路径）。
约束选错对象 → 上限失效。

## 4. 修复设计

### 4.1 `sanitize_filename`：改为「整串先行清洗，再分离扩展名」的单向管线

```
输入
 │
 ├─① NFKC 归一化        全角 → 半角（接入 normalize_unicode，消除死代码）
 ├─② 控制字符剔除       \x00-\x1f、\x7f → _
 ├─③ 非法字符替换       <>:"/\|?* → _        ← 整串执行，扩展名不再是盲区
 ├─④ 分离主名/扩展名    此时串内已无分隔符与非法字符，切分安全
 ├─⑤ 分别去尾           主名 strip(" .")；扩展名 rstrip(" .")（保留前导点）
 ├─⑥ 保留设备名加前缀    CON → _CON
 ├─⑦ 长度控制           扩展名限长 16 → 剩余额度给主名
 └─ 输出
```

顺序即修复本身：**②③ 前移到切分之前**，N2/N4 一并根治；⑤ 覆盖主名与扩展名两侧，N5 根治。

### 4.2 `build_output_filename`：不猜扩展名

```python
target_ext = "." + extension.lower()
if not name.lower().endswith(target_ext):
    dot = name.rfind(".")
    tail = name[dot + 1:] if dot > 0 else ""
    if tail.lower() in _KNOWN_EXTS:      # 确定是扩展名 → 替换（保留原意图）
        name = name[:dot] + target_ext
    else:                                 # 不确定 → 安全追加（绝不截断）
        name = name + target_ext
```

`_KNOWN_EXTS` 覆盖 png/jpg/jpeg/webp/tif/gif/pdf/zip/html/mp4 等 33 个常见扩展名。
效果：

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 默认模板 + `my.photo` | `my.png` | `my.photo_cleaned_125053.png` |
| 模板 `{stem}.jpg` + `shot` + png | `shot.png` | `shot.png`（意图保持） |
| 模板 `{stem}_去水印` + `a.b` | `a.webp` | `a.b_去水印.webp` |

另修：连续下划线折叠由 `str.replace("__","_")`（只替换一次）改为 `re.sub(r"__+","_",...)`。

### 4.3 `make_unique_path`：纵深防御

```python
desired_name = Path(str(desired_name)).name or "output"    # 剥离目录成分
if desired_name in (".", ".."):                            # 显式兜掉相对路径
    desired_name = "output"
```

这是写出路径的**最后一道防线**：即便某个调用方忘了先 `sanitize_filename`，
带路径分隔符的名字也无法越出 `target_dir`。
（实现期被测试抓住一个坑：`Path("..").name` 返回 `".."` 而**不是空串**，
故必须显式兜掉 `.`/`..`。）

### 4.4 顺带修复：测试隔离缺陷

跑子集时 `test_history_filter.py` 出现 2 例失败，根因**不是本次改动**：

> 多个测试文件调用 `i18n.set_language(...)` 验证双语后**不还原**，
> 语言状态跨用例泄漏。跑全量时被后面某个"设回 zh-CN"的文件碰巧掩盖，
> 而**任意子集运行或顺序变化就会误报**。

实测复现：`test_cache_disk`（设 `en-US` 不还原）→ `test_history_filter`（断言中文文案）→ 失败。

修复：在 `conftest.py` 加 **autouse fixture** `_isolate_i18n_language`，
每个用例前后快照/还原 `i18n._LANG`。这是「测试基础设施」层面的根治，
比逐个给 20+ 处调用加 try/finally 更可靠。

**这类缺陷的价值在于**：它说明「全量跑绿」**不能证明测试彼此独立**。
只有换一种执行方式（子集/乱序）才能暴露顺序耦合——与阶段 63 的
「假性崩塌信号」同源：**换口径才会露出真相。**

| N7 长度控制 | 总长上限、扩展名限长、空输入兜底（3 类） | 5 |

**回归保护组的价值**：这 7 个用例锁定"正常文件名逐字不变"。
命名链路是高耦合公共路径，任何后续改动都可能悄悄改变正常名的行为——
**先固定不变量，再谈演进**。

## 6. 已知边界（诚实记录）

- **`make_unique_path` 存在 TOCTOU 竞态**：`exists()` 检查与实际创建之间没有锁。
  批量并发写同一目录时理论上可能撞名。项目为单进程顺序处理（批量队列串行），
  未触发；若未来引入多进程导出，需改为「以 `O_EXCL` 原子创建」。
- **`_KNOWN_EXTS` 是白名单**：极端自定义扩展名（如 `.myraw`）在模板写死时不会被替换，
  而会被追加成 `.myraw.png`。这是**刻意选择**——白名单外一律走"安全追加"这一无损分支。
- **保留名判定只覆盖 Windows 规则**（CON/PRN/AUX/NUL/COM1-9/LPT1-9）。
  POSIX 系统无此概念，加前缀是无害的多余动作。
- **未做完整路径长度（Windows 260）检查**：只约束文件名本身。
  若用户把输出目录设得极深，仍可能触顶。属环境配置问题，未纳入本阶段。
- **`sanitize_filename` 对全非法字符输入返回下划线串**（`???` → `___`）而非兜底名——
  与修复前行为一致，属刻意保留的向后兼容语义（文档已注明）。

## 7. 结论

七项缺陷可归为三类根因：

1. **语义假设不成立**（N1「最后一个点之后是扩展名」）→ 修法：**不猜，选可恢复的一侧**；
2. **管线顺序错 / 判据不完整**（N2/N4 先切分后清洗；N3/N5/N7 把必要条件当充分条件）→
   修法：**先净化再解析**；**约束对象选完整文件名**；
3. **死代码与零覆盖**（N6，以及"三个函数零测试"本身）→ 修法：接入真实调用链 + **从零建测试**。

最有价值的一条经验来自 N1 的修复取向：

> 当无法确定一个边界的语义时，**选择「错误可被察觉且可恢复」的那一侧**。
> 多一个点只是难看，少一段名字则是静默的信息丢失。

而顺带发现的 i18n 隔离缺陷进一步印证：

> **「全量跑绿」不等于「测试彼此独立」。** 阶段 78 若只在全量口径下验证，
> 这次顺序耦合会被继续掩盖——**换一种执行口径（子集/乱序），耦合才会现形**。
