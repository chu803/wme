# 阶段 320e · 设备选择惰性化：OpenCV 引擎不再为不用的 GPU 付钱

> 日期 2026-10-23 · 产物 `core/inpainter.py`（一行条件）、
> `tests/test_lazy_device_selection320e.py`（3 例）

## 一、定位（不是"感觉慢"，是量出来的）

阶段 319 拆冷启动时发现：`core/inpainter.py` 里写着

```python
if device is None:
    device = select_device()
```

而实测 `select_device()` = **1.66s**，并会顺带 `import torch`。但：

- 内置 **OpenCV 引擎**的 `inpaint(..., device=None)` **根本不看这个参数**（`core/plugins.py`）；
- **LaMa / 插件引擎**在入口自行 `device or select_device()`，传 `None` 是安全的；
- `select_device()` 的结果**有缓存**（`_cached_device`）。

⇒ 这行对 OpenCV 通路是纯粹的浪费；对模型引擎则是「本来就会做、且已缓存」的事。

## 二、改动

```python
if device is None and engine != "opencv":
    device = select_device()
```

任何配置下**输出逐字节不变**（OpenCV 分支本就忽略 device）；模型引擎行为不变。

## 三、实测（真跑 CLI，同会话对照）

| 配置 | 首图墙钟 | 日志有「自动选择设备」 | 有 EasyOCR 初始化 |
|---|---|---|---|
| OCR 开（默认） | 7.64s | 是 | 是 |
| **OCR 关**（`WME_DETECT_USE_OCR=false`） | **3.27s** | **否** | 否 |

**收益条件必须说清**：默认 OCR 开启时，**检测阶段**（OCR 阅读器）已经选过设备 ⇒ inpainter 的那次
只是缓存命中，本改动省不到时间。真正省下的是 OCR 关闭的配置（或未来不含文字/边缘策略的预设）：
**7.64s → 3.27s，−4.4s（−57%）**。

> 这条比原计划诚实：319 里我一度以为「默认 OpenCV 通路必然白付 1.66s」，
> 实测发现只要检测跑了 OCR，设备就已经被选过。**先量再断言**，又救回一条错误结论。

## 四、守卫（3 例，纯接线、不加载模型）

- `test_opencv_engine_skips_device_selection`：OpenCV ⇒ `select_device` 调用数 0，且引擎收到 `device=None`；
- `test_model_engine_still_selects_device`：LaMa ⇒ 调用数 1（否则模型会缺设备句柄）；
- `test_explicit_device_is_respected`：调用方给了 device ⇒ 不再选一次。

## 五、诚实边界

- 默认配置（OCR 开）下**几乎没有收益**——因为设备在检测阶段已被选中（缓存）。
- 只对 `engine == "opencv"` 生效；插件引擎一律照旧选设备（不能替第三方插件假设）。
- 未做「OCR 本身也按需初始化」：实测所有内置预设都含 `enable_corner/enable_edge`，
  都会跑 OCR ⇒ 那部分不是浪费。真要省，得先改预设语义（属产品决策）。
