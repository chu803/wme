# 阶段 341 · 一页渲染失败就把整份 PDF 中止：`except RuntimeError: raise` 抓错了对象

> 日期 2026-10-26 · 性质：**产品缺陷修复**（第二轮审计 F7，已核实并修）

## 一、缺陷（读码确认 + 反例实证）

逐页循环里：

```python
if not config.PDF_KEEP_FAILED_PAGE:
    raise RuntimeError(f"第 {pr.index} 页处理失败：{pr.error}")
except RuntimeError:
    raise          # 注释写着「由 PDF_KEEP_FAILED_PAGE=False 主动抛出的中断」
```

那层 `try` 包住的是**整段逐页处理**，而这段里抛 `RuntimeError` 的不止「主动中止」这一处：

* `_encode_page_image` 自己就抛 `RuntimeError("页面图像编码彻底失败（cv2.imencode 返回 False）。")`（`:316`）；
* PyMuPDF 的渲染 / `insert_pdf` 失败同样可能是 `RuntimeError`。

⇒ **一页坏就中止整份文档**，而默认值是 `PDF_KEEP_FAILED_PAGE=True`（`config.py:2055`），
同一函数里还写着「单页异常不该毁掉整份文档」（`:560`）⇒ 代码与它自己的注释、配置承诺三者互斥。
一份 20 页里第 3 页编码失败的 PDF，用户拿到的是「整份失败」而不是「19 页正常 + 1 页保留原样」。

**反例（HEAD 实测）**：三页文档、第 2 页抛 `RuntimeError`、`keep=True` ⇒
HEAD 上 `res.status == "failed"`（整份中止），修复后 `"success"`、`failed_pages=1`、
`skipped_pages=2`，且输出 `page_count == 3`（坏页按原样保留，页数不塌）。

## 二、修法：「我要中止」与「出事了」不能共用一个异常类型

新增专用异常（**子类仍是 `RuntimeError`**，上游按 `RuntimeError` 兜底的代码不受影响）：

```python
class PdfAbortOnFailedPage(RuntimeError):
    """只在 PDF_KEEP_FAILED_PAGE=False 且某页真的失败时才抛。"""
```

捕获点从 `except RuntimeError: raise` 改成 `except PdfAbortOnFailedPage: raise`
⇒ 其它 `RuntimeError` 落回「单页韧性」那条路（标 failed + 保留原页 + 继续）。

## 三、顺手统一了一个语义分叉（这一点不是审计报的，是修的过程中发现的）

`PDF_KEEP_FAILED_PAGE=False` 原本只在「管线返回 failed」时中止；
「本页抛异常」那条路径根本不检查这个开关 ⇒ **同一个开关对两种失败方式给两种解释**。
现在两条路径都走同一判断：

```python
except Exception as exc:
    ... 标 failed / 保留原页 ...
    if not config.PDF_KEEP_FAILED_PAGE:
        raise PdfAbortOnFailedPage(f"第 {pr.index} 页处理失败：{pr.error}") from exc
```

判据：配置项的含义必须与**失败方式无关**，只与「这一页没做成」有关；否则用户按字面理解设了
`keep=False`，却有一半的失败悄悄被保留（或反过来）。

## 四、守卫与桩的教训

`tests/test_pdf_page_abort341.py`（4 例）：默认 keep=True 坏页不中止且页数不塌 /
keep=False 必须中止且错误里能看到专用类型与页号 / 无故障文档行为不变 / 专用异常仍是 `RuntimeError` 子类。
既有 `test_pdf_service_audit131`、`test_pdf_history` 修后仍绿。

写桩时又踩一次 339/340 那条：**第一版给 `status` 填了个不存在的 `"no_watermark"`**，
于是两页正常页被计入 `failed_pages=3`，我差点把「测试自己错」报成产品缺陷。
真实取值域在 `auto_pipeline:192`（`success / skipped / failed`）⇒ 桩必须按契约取值域造。
