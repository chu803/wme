# 阶段 336 · 批跑结束后按「取消」会谎称「已发送取消信号」

> 日期 2026-10-26 · 性质：**产品缺陷修复**（334 审计候选③，本轮自己读码核实）

## 一、缺陷

`ui/tab_batch.py` 的 `_CURRENT_QUEUE` 在批跑开始时赋值，**从不置回 `None`**；
而取消按钮（以及快捷键 `Shift+C`，`ui/app.py:320`）的处理器只判 `is not None`：

```python
def cancel_batch():
    if _CURRENT_QUEUE is not None:
        _CURRENT_QUEUE.cancel()
        return t("batch.msg.cancel_done")   # 「⏹ 已发送取消信号，未开始的任务将不再处理…」
    return t("batch.msg.cancel_none")       # 「ℹ️ 当前没有正在运行的批量任务。」
```

⇒ 批跑**已经结束**之后再按取消，界面仍回「已发送取消信号」——对着一个早就空了的队列
声称自己做了事。这属于 330–335 一直在追的同一族：**说不清的输出**，只是这次说的是「我做了什么」。
危害不致命（没有数据损坏），但它是**用户可见的假陈述**，且会让「取消没生效？」这类排查白花时间。

## 二、修法（两处一起收，缺一处就还会退化）

1. 生成器把队列跑完的那段包进 `try/finally`，`finally` 里 `_CURRENT_QUEUE = None`
   ——正常结束、异常、前端提前关闭生成器三种情况都清掉。
2. `cancel_batch()` 不再只看句柄，改看**队列真实状态**：`pending + running == 0` 就用
   既有的 `batch.msg.cancel_none`（它的措辞「当前没有正在运行的批量任务」正好对）说真话；
   真有活才干 `cancel()` 并回 `cancel_done`。**不新增 i18n 键**（少一处中英同步的维护面）。

为什么两处都要：只改 ①，句柄清掉了但「跑完瞬间还残留 pending」的边界仍可能误报；
只改 ②，句柄会一直泄漏到下一次批跑（下一次按取消时判的是**上上次**的队列）。

## 三、守卫与反例

`tests/test_batch_cancel336.py`（5 例）：跑前取消 ⇒ `cancel_none`；**排空后的队列**取消 ⇒ 必须
`cancel_none` 且**不得调用 `cancel()`**（spy 断言）；有 pending ⇒ `cancel_done` 且 `is_cancelled()` 为真，
跑完后再按一次必须**改口**；生成器源码必须含 `finally: _CURRENT_QUEUE = None`（防退化）。

`git worktree` 在修复前代码上跑同一套：**3 红 / 2 绿**（绿的两条是「跑前取消」与「文案走 t()」，本来就该绿）。

写测试时自己踩的两个坑（都是对 `queue_worker` 语义的假设错，不是产品错）：
`run()` 是**生成器**，不消费就等于没跑（第一次断言 pending==0 直接失败）；
`cancel()` 只置**队列级标志**，任务状态要等 `run()` 消费时才改成 `CANCELLED`
⇒ 断言应看 `is_cancelled()` 而不是 `summary()["cancelled"]`。**断言要按被测对象的真实语义写，不能按想象写。**
