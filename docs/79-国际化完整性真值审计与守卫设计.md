# 阶段 79 · 国际化完整性真值审计与守卫设计

> 审计对象：`utils/i18n.py`（548 个键 × 2 语言）及其在生产代码中的使用面。
> 审计范式：**探针量化 → 定位根因 → 修复 → 回归 + 守卫 → 门禁化**。

---

## 1. 为什么审计 i18n

双语（zh-CN / en-US）是 README 明示的产品能力，i18n 覆盖 4 个界面页、
14 个服务模块与全部操作反馈文案。它此前有 22 例测试，但**全部是「机制测试」**：

- `t()` 的缺失键回退；
- 占位符格式化；
- 语言切换与持久化；
- 注册/应用语言更新的辅助函数。

**唯独没有「内容完整性测试」**——即「生产代码里引用的键，键表里到底有没有」。
这个空窗与阶段 61/77/78 的形态完全一致：**测试验证了机制，却没有验证机制在实际数据上的结果**。

更关键的是：阶段 75 已经踩过同一个坑的一处实例（i18n 键名含点导致 `t()` 分层遍历查空），
当时的处理是**只修那一处、改个名**，**没有做全局扫描**。于是同族问题在其余 14 处继续存活。

---

## 2. 探针量化（修复前）

探针从三个维度取证：中英键对称性、源码引用面、结构性一致性。

| 编号 | 缺陷 | 实测 |
|---|---|---|
| **I1** | **键名层级错位**（8 处） | `ui/tab_settings.py` 调用 `settings.msg.*`，键表定义的是 `settings.snap.msg.*`（少一层 `.snap`） |
| **I2** | **键名缺失**（5 处） | `history.count` / `history.tip_select` / `history.not_found` / `history.reprocess_done` / `history.reprocess_no_result` 被调用但从未定义 |
| **I3** | **键名不匹配**（2 处） | `compare.slider` / `compare.heatmap` 不存在，键表实为 `compare.mode_slider` / `compare.mode_heatmap` |
| **I4** | **段落遗漏**（1 处） | `auto.sensitivity_info` 未定义（同段 `auto.sensitivity_label` 存在） |

**探针原始输出**：

```
P2  源码中 t() 引用但键表缺失（静默返回键名）
静态 t() 键 512 个 | 动态 f-string 键 35 处
引用但完全未定义的键 = 20
   'auto.sensitivity_info'      ← ui\tab_auto.py
   'compare.heatmap'            ← ui\tab_media.py
   'compare.slider'             ← ui\tab_media.py
   'history.count'              ← ui\tab_history.py
   'history.not_found'          ← ui\tab_history.py
   'history.reprocess_done'     ← ui\tab_history.py
   'history.reprocess_no_result'← ui\tab_history.py
   'history.tip_select'         ← ui\tab_history.py
   'settings.msg.clear_ok'      ← ui\tab_settings.py
   'settings.msg.err'           ← ui\tab_settings.py
   …（共 9 个 settings.msg.*）
```

（20 个里有 6 个是探针误报：`detect.kind.` 为动态拼接前缀、`not.exist.key` 为自检、
`x`/`y` 为文档字符串示例——真实缺陷 **14 处**。）

**同时确认健康面**（这些不修，但要记录）：

```
P1  中英键覆盖对称性：仅中文有 = 0 | 仅英文有 = 0        ← 完全对称
P4  占位符不一致 = 0                                     ← 完全一致
P5  非字符串叶子 = 0
```

**用户可见后果**：`t()` 对缺失键返回**键名本身**（`return key`），因此

- 设置页点「清空缓存 / 导出 ZIP / 清理孤儿」后，反馈消息显示 `settings.msg.clear_ok`；
- 历史页的计数与空状态提示显示 `history.count`、`history.not_found`；
- 对比查看器的模式选择按钮显示 `compare.slider`、`compare.heatmap`；
- 所有这些在**中英文环境下都一样**（回退链两端都没有，最终落回键名）。

这不是边缘情况——**用户在设置页的每一次操作都会看到**。

## 3. 根因分析

### 3.1 直接原因：两层结构的「半途重命名」

最有力的证据是**同一文件内自相矛盾**：

```python
# ui/tab_settings.py
t("settings.snap.msg.err", exc=exc),      # ← 第 212 行：正确
t("settings.msg.err", exc=exc),           # ← 第 121/124 行：错误（少 .snap）
```

以及同一 `choices` 列表内：

```python
# ui/tab_media.py
(t("compare.mode_concat"), "concat"),     # ← 正确
(t("compare.slider"), "slider"),          # ← 错误
(t("compare.heatmap"), "heatmap"),        # ← 错误
```

**一处对、多处错**排除了「设计如此」的可能，确凿是**改名不彻底**：
某次重构把消息键从 `settings.msg.*` 迁到 `settings.snap.msg.*`（快照区块），
或把 `compare.*` 模式键规范化成 `mode_*`，但只改了定义与部分调用点。

### 3.2 为什么没被测出来：测试只覆盖「机制」不覆盖「数据」

`tests/test_i18n.py` 里有一例 `test_t_missing_key_falls_back_to_zh_then_key`——
它**验证了「缺失键会回退为键名」这一机制本身**。讽刺之处在于：

> 这个测试恰恰**为缺陷提供了通行证**——它证明了系统"能优雅地处理缺失键"，
> 却没有检查"到底有没有缺失键"。**被验证的鲁棒性，掩盖了数据的错误。**

这是阶段 61「死代码会伪装成已验证功能」的同构变体：
**被测试的容错能力，会成为错误的藏身处。**

### 3.3 更深一层：修一处 bug 时没做同族扫描

阶段 75 的工程插曲已经写下结论：

> 「i18n 键名 `msg.applied` 含点 → `t()` 按点分层遍历查不到 → 静默回退键名……**点号是 i18n 键的路径分隔符，键名里不得再含点**。」

结论是对的、也已记录，但**动作只落在一处**。当时若立即执行一次
「扫描生产代码全部 `t()` 调用 vs 键表」的检查，这 14 处会当场全部暴露。

**通用教训**：修复一个「数据与代码不一致」类缺陷后，**必须立刻用同一判据全局扫描一遍**——
否则等于承认"这一类缺陷只存在于我恰好看到的那一处"。

## 4. 修复设计

### 4.1 逐项处置（按「改代码」还是「补数据」分工）

| 缺陷 | 处置 | 理由 |
|---|---|---|
| I1 `settings.msg.*`（8 处）| **改调用点** → `settings.snap.msg.*` | 键表已有完整、正确的文案；改数据会留下孪生键 |
| I3 `compare.slider/heatmap`（2 处）| **改调用点** → `compare.mode_*` | 同上，且 `mode_concat` 已经是正确写法 |
| I2 `history.*`（5 处）| **补键** | 键表确无对应文案，需新写（含 `{n}`/`{name}`/`{status}` 占位符） |
| I4 `auto.sensitivity_info`（1 处）| **补键** | 同段 `sensitivity_label` 已在，属段落遗漏 |

**分工原则**：键表里**已有正确文案** → 改调用点（不留孪生）；
键表里**确实没有** → 补键（不改界面语义）。

新增 5 + 1 = 6 个键 × 2 语言 = 12 条文案：

```
history.count            = "共 {n} 条记录。" / "{n} record(s)."
history.tip_select       = "点击缩略图查看详情。" / " Click a thumbnail for details."
history.not_found        = "未找到该历史记录（可能已被清理）。" / "History record not found (it may have been cleaned up)."
history.reprocess_done   = "✅ 已重新处理 {name}（{status}）。" / "✅ Reprocessed {name} ({status})."
history.reprocess_no_result = "⚠️ 重新处理未产生结果。" / "⚠️ Reprocessing produced no result."
auto.sensitivity_info    = "调高可揪出更淡的半透明水印，但误判率上升" / "Higher = catches fainter translucent watermarks, but more false positives"
```

（`tip_select` 的英文带**前导空格**：调用点是 `t("history.count", …) + t("history.tip_select")`
直接拼接，英文需要词间空格；中文排版不需要。已在源码注释说明。）

### 4.2 守卫：把「内容完整性」变成一条自动化断言（本阶段核心）

新增 `tests/test_i18n_coverage.py`（**20 例**），核心用例是：

```python
def test_all_referenced_keys_are_defined():
    """生产代码里每个静态 t("...") 键都必须存在于键表。"""
    referenced = _scan_static_keys()          # 正则扫描 core/services/utils/ui + 5 个顶层模块
    assert len(referenced) > 400              # 防止扫描自身失效而"空跑通过"
    missing = [k for k in referenced if k not in ALL_KEYS and not 白名单/动态前缀]
    assert not missing, "以下键被引用但未定义，界面会直接显示原始键名：..."
```

三个设计要点：

1. **断言扫描规模**（`> 400`）——防止正则或路径失效导致"扫不到任何键 → 全部通过"的假绿。
   这是阶段 77「字段存在断言抓不住值为空」教训的直接应用。
2. **动态前缀白名单**（`detect.kind.` / `detect.preset.` / `compare.viewer.` 等）——
   这些是 `t("detect.kind." + kind)` 形式的拼接，无法静态枚举；
   另用 `test_dynamic_prefix_keys_exist` 断言**每个前缀下确实有键存在**，
   避免白名单变成"永久豁免区"。
3. **显式豁免列表**只有 3 项（自检键 `not.exist.key` 与文档示例 `x`/`y`），每项都有注释说明。

配套内容守卫：

| 用例 | 断言 |
|---|---|
| `test_zh_en_key_parity` | 中英键集合完全一致（防半翻译） |
| `test_placeholder_parity` | 同一键在中英版本的 `{占位符}` 集合相同 |
| `test_all_leaves_are_non_empty_strings` | 无空文案 / 非字符串叶子 |
| `test_key_segments_contain_no_dots` | **键名每一层不得含点**（阶段 75 教训的守卫化） |
| `test_no_orphan_keys_within_used_prefixes` | 键表不得再出现错误的 `settings.msg.*` 层级 |
| `test_settings_tab_uses_snapshot_message_path` | 源码级：`tab_settings.py` 不得再有裸 `settings.msg.` |
| `test_compare_mode_labels_exist` | 源码级：`tab_media.py` 不得再有 `compare.slider/heatmap` |
| `test_fixed_keys_render_in_both_languages`（10 参数化） | 修复后的键在中英下渲染为**真实文案而非键名** |

### 4.3 守卫的「反例验证」

守卫测试若从未失败过，就无法证明它有效（阶段 77 的教训）。
因此做了一次**注入式反例验证**：

```
1. 在 ui/components.py 末尾注入：def _probe_missing_key_guard(): return t("probe.injected.missing.key")
2. 运行守卫 → 失败，并精确列出：
   AssertionError: 以下键被引用但未定义，界面会直接显示原始键名：
       probe.injected.missing.key  (引用自 ui\components.py)
3. 还原文件 → 守卫通过
```

守卫「能抓住」已获证实，不是摆设。

## 6. 已知边界（诚实记录）

- **静态扫描的固有盲区**：`t(some_var)` 这类完全动态的键无法被守卫覆盖。
  现状是只允许「固定前缀 + 变量后缀」的拼接形式（白名单管理），
  这既是约束也是保护——它使新增的动态键必须显式登记。
- **守卫不检查「键是否被真正使用」**（死键检测）：探针显示 548 键中约 56 个未被静态引用，
  扣除动态前缀后仍有 8 个疑似死键（`common.restart_to_apply`、`settings.snap.msg.superres_applied`
  等，后者实际由注册机制间接使用）。**未做死键清理**——
  删错键的代价（界面显示键名）远高于留着多余键（仅占几行代码），
  且死键不影响正确性。作为已知项记录。
- **不检查文案语义质量**：守卫只能保证「有、对称、占位符一致」，
  无法保证译文贴切。人工评审仍不可替代。
- **`_DYNAMIC_PREFIXES` 需随新代码维护**：若未来出现新的拼接前缀而未登记，
  守卫会把它的键误报为"缺失"。这是**有意的摩擦**（宁可误报也不漏报）。

## 7. 结论

本阶段的缺陷本身并不复杂（键名写错、层级少一层），但它揭示了两条更重要的规律：

**规律一：被测试的容错能力，会成为错误的藏身处。**

`t()` 的缺失键回退是一条优秀的鲁棒性设计，
`test_t_missing_key_falls_back_to_zh_then_key` 也忠实地验证了它——
但正因为系统"优雅地"处理了缺失，缺陷才能静默存活 4 个阶段。
**容错机制必须配一条「容错未被触发」的断言，否则它就是在替错误兜底。**

**规律二：修一处 bug 之后必须做同族全局扫描，否则等于承认「这一类只有这一处」。**

阶段 75 已经用「键名含点」的实例写下了正确的结论，但动作只落在一处；
14 个同族实例因此继续存活。本阶段把这个判据**固化成自动化守卫**，
才真正关闭了这一类问题——这与阶段 57 起用 `quality_gate.py` 守护质量红线是同一个思路：

> **一次性的修复解决当下，固化的守卫解决将来。**
