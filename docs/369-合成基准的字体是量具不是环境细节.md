## 二、它为什么是缺陷而不是"细节"

`make_demo_assets` 不是画图工具，它是**基准的数据源**：四类合成水印
（`corner_logo` / `edge_text` / `grid` / `faint_tiled`）被 15 个用例文件当输入，
那些文件里全是 `recall >= 0.8`、`coverage_pct`、`iou >= 0.35`、`mask_px == 0` 这类**数字断言**。
字体决定字形，字形决定像素，像素决定这些数字。同一 seed=7、同几何，实测：

| 指标 | arialbd（Windows 现状） | 系统 DejaVu（Linux） |
|---|---|---|
| `edge_text` ΔPSNR | 12.43 | **17.12** |
| `edge_text` coverage_pct | 1.16 | **1.49** |
| `faint_tiled` ΔPSNR | 7.13 | **12.67** |
| `corner_logo` coverage_pct | 3.15 | **3.58** |
| 256 png `corner_logo` 默认路径掩码 | **0 px** | **2813 px** |

在 CI 等价环境里把字体强制成 Linux 那块 DejaVu（`PYTEST_PLUGINS`，不改产品代码）跑整套入口：
**恰好翻红 1 条**（`test_lowres_rescue::test_default_path_keeps_blackout[256-png-textured-corner_logo]`），
其余 `3398 passed / 37 skipped` 全绿 ⇒ 这一类是真的，但它只解释 6 条 CI 红里的 1 条，
剩下 2 条仍未点名（诚实边界，见 §六）。

## 三、三条路都用数据筛过

1. **改用 Pillow 内嵌字体**（`ImageFont.load_default(size)`，零新增文件、字体字节就在 Pillow 源码里）：
   跨 OS 同字节，听着最干净。实测同一批用例 **11 条翻红**——`test_jpeg_robustness` 的
   `photo/edge_text 召回 82.8% < 90%`、预设推荐 4 条、`test_mask_dilate_calibration` 等。
   根因不是"数字变了"，而是 **Aileron 是 Regular、arialbd 是 Bold**：换过去等于把被测水印**改细了**，
   那些阈值标的就不再是原来那个东西。⇒ 否决。
2. **字体不匹配就 rc=2 跳过**（沿用 360 的「环境事实 ≠ 产品质量」口径）：
   会把 15 个用例文件的数字断言在 CI 上**集体失去覆盖**。红线是"CI 要能真的量到东西"，
   用跳过换绿是自欺。⇒ 否决。
3. **把字体当量具随源码分发**（采纳）：`scripts/assets/DejaVuSans-Bold.ttf`（687 KB，
   取自 matplotlib 随包分发的**未修改**件，许可原文逐字收在 `LICENSE-DejaVu.txt`——
   Bitstream Vera 许可要求"副本须带许可原文"，且未修改才不触发改名条款）。
   选 DejaVu Bold 而不是别的，是因为实测里它与 arialbd **最接近**：口径是「4 类用例的基准指标
   × 3 个字体源（arialbd / 系统 DejaVu / Pillow 内嵌）」+「4 条黑屏组合 × 同一 3 个字体源」——
   DejaVu 只让 1 条跨过阈值（256 png 角标），而 Pillow 内嵌让 11 条断言翻红。换过去的重锚面最小。
   分发口径不用改：`MANIFEST.in` 已把 `scripts/` 与 `docs/` prune 掉 ⇒ 它**不进 wheel 也不进 sdist**，
   是开发期量具而非交付物；CI 用 git checkout，拿得到。仓库里已有 292 个 >200 KB 的追踪文件（547 MB），
   687 KB 是噪声级。

`_font()` 的新契约：只认仓库内那份，**缺失就报错并说清成因与下一步，绝不回退本机字体**
（回退=换量具还自称同一把尺）。

## 四、更要紧的第二条修复：黑屏表从"常量"改成"现场测量"

换字体只让数字**稳定**，没让那条断言**变对**。逐格实测 42 个组合（3 编码 × 7 尺寸 × 2 用例）后：

```
224 png corner_logo → 0 px      256 png corner_logo → 2813 px
288 png corner_logo → 3304 px   320 png corner_logo → 0 px
192 grid 全编码 0 px；256 grid 只有 png 检出 117 px，jpeg75/webp75 仍 0 px
```

**非单调**（224 漏检、256 检出、288 检出、320 又漏检）。也就是说 `_BLACKOUTS` 那四条
钉的是"检出门槛下方的混沌区"，`== 0` 这种断言不只会因为换字体翻红，
也会因为 numpy/opencv 的 resize 与 JPEG/WebP 编码器换版本而翻红——**钉住它本来就是错的**。

改判据（[tests/test_lowres_rescue.py:100](file:///D:/qoder/watermark-workbench/tests/test_lowres_rescue.py#L100)
`test_silent_miss_phenomenon_measured_not_pinned`）：不钉"哪条黑屏"，钉这个开关存在的理由——

- 网格里**仍存在**默认路径完全漏检的组合（现象没消失；若消失，就该重估这个开关）；
- 每一个这样的组合，放行兜底后召回**必须 > 0**（放行闸确实救得回来）。

顺带两处收尾：`_BLACKOUTS` 降级为 ②③ 的**输入样本**（并写明 256 png 那条已不再是黑屏、
为什么仍留着）；`test_rescue_side_zero_disables` 原来按 `_BLACKOUTS[1]` 下标取样本，
改成按值取 `_SIDE_ZERO_SAMPLE`（下标一改就静默换样本，是同一类"看不见的漂移"）。

## 五、守卫 `tests/test_font_standard369.py`（9 例）

- **L1** 字体在位 + SHA-256 等于钉住的值（换字体=换量具，必须连基准一起重锚）；许可文件同目录。
- **L2** `_font(20)` 解析到的路径**就是**仓库内那份，且在仓库内；
  以及"字体缺失 ⇒ 报错要点名文件并给出下一步"（不许静默回退）。
- **L3** AST 扫全仓 `.py`（含 `tests/`——测试也不许把量具交给本机，360 的教训是盲区比假绿贵），
  任何**字符串常量**指向 OS 字体目录就红。
- **L4** 反例双向：注入 Windows / POSIX 字体路径必须被抓；写成注释不许被抓
  （判据只吃字符串常量，第一版文本判据在 359/362 各误报过一次）。
- 已知取舍，写在文件里而不是藏起来：
  ① docstring 也是字符串常量 ⇒ 会被照红，所以本文件与产品注释里都不写 OS 字体目录原文；
  ② 判据表自己用片段拼接，否则守卫被自己照红（首跑就撞上）；
  ③ 用拼接绕过 L3 是可能的 ⇒ 补位的是 L1/L2（`_font()` 必须解析到仓库内那份、指纹必须对）。
- 首版把 basetemp 目录也扫了，**62.9 秒**；改成跳过点开头的目录后 **1.04 秒**。

## 六、边界（还没覆盖的，别当已覆盖）

- **只解释 1/3**：剩下 2 条 CI 红仍未点名，等推送后的 entry.log（362 的全量回显）。
- **FreeType 版本维**未验证：同一份 TTF 在 manylinux 轮与 Windows 轮里理论上仍可能因
  FreeType 版本不同差出像素；本机无法复现 Linux，这条只能等 runner 数据。
  因此 L1 钉的是**字体字节**，不是渲染结果——渲染一致是推论，不是实测。
- `docs/assets/` 里已提交的演示 PNG 仍是 arialbd 生成的，与新标准不再逐像素一致；
  **没有任何守卫比较它们**（`test_demo_assets` 一律重定向到 tmp 再断言），所以不会红，
  但"重生成会改动文档图片"这件事留给用户决定，没有顺手替。
- 字体随源码分发但**不进 sdist/wheel**：从 sdist 复现基准的人拿不到量具 ⇒ `_font()` 的报错
  就是为他写的（点名文件 + 说清成因 + 给出"用 git 检出"的下一步）。
