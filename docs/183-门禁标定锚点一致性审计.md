## 2. 附带修正：`mask_iou` 崩溃护栏 0.10 → 0.15

`real_gate.py` 自带不变式（阶段 106 注释）：「**红线不得松于实测的一半**」。
177 用真实真值重算后 `mask_iou` 实测 0.1705 → **0.2975**（实测/2 = 0.14875），
而护栏仍停在被旧实测校准的 0.10 ⇒ 0.10/0.2975 = **0.34×**，已违反该不变式。
按同一规则抬到 **0.15**（= 实测 × 0.504）。方向安全：`min` 型护栏**抬高 = 放宽**，
不会制造新红灯；真实回退仍由 15% 漂移层拦截（分层设计不变）。

### 4.1 环境边界（如实登记，非代码缺陷）

受限沙箱的 **safe-delete 批量护栏**（单次删除目标下文件数 > 50 ⇒ `SAFE_DELETE_BULK_REJECTED`
+ `SystemExit(1)`）在本会话被**闩锁**，导致全库复跑出现 17 例**假失败**：

- **触发点**：pytest 在 `%TEMP%\pytest-of-HP\` 下的**遗留 garbage 目录**（278/63/17 文件）
  被会话启动的 tmp GC 一次性删除 ⇒ 92 > 阈值 ⇒ 拒绝；
- **闩锁证据**：把该目录**改名搬走之后**，后续每一次 `os.remove` 仍收到**同一条**消息
  （`targets` 指向那个已经不存在的 `garbage-5d25…`）⇒ 判定是**会话/轮次级缓存**，非重新计算；
- **第二轮证据（更直接）**：新 turn 复跑时，护栏改为在**累计删除数**达阈值时报
  `SAFE_DELETE_BULK_CONFIRM_REQUIRED (count=50 == threshold)`，且 `targets` 指向
  **本项目 basetemp 内由测试自己创建的文件**（如 `.pytest_183v3/…/app.log.4`）⇒
  失败的只是「当轮第 50 次之后的删除」，与代码无关；
- **传染面**：本会话内所有含删除的用例（`cache_service` 清理缩略图 / `orphan_cleanup` /
  日志轮转 / `history_batch_delete` / `model_manager` 删备份 / `collect_real_assets` /
  `selfcheck[api.py]`）在删除点同一异常；
- **反向验证**：这些用例在**会话首跑**（护栏未闩锁）**全部通过**，且模块横跨**完全无关**的
  cache / logger / model_manager / orphan 四族；报错来源是
  `sitecustomize.py::_check_bulk_delete_guard`（沙箱自身）。→ **环境态，非代码态。**
- **处置**：不再重试（沙箱明确拒绝）；登记为环境边界，留待**下个会话或 CI** 复验。
  长期建议见 `docs/184`：把验证入口固化为 `scripts/run_all_checks.py`，
  并在其中的 pytest 步骤**强制使用项目内 `--basetemp`**。

> 本阶段把这套判据（**看异常来源 + 看失败分布 + 看历史绿红**）显式登记，
> 避免下次把「环境闩锁」误读成「代码回归」而浪费排查时间（LESSONS 196）。

## 5. 附带发现 · 留出探针（30 张**未标注**真实 AI 图）

`.probe183_holdout.py` 在 `benchmark_real` 的 30 张 `watermarks: []` 图上量测守卫先验触发率：

```
基线（杠杆 OFF）检出 corner_logo  = 28/30 张
守卫先验新增整牌（ON − OFF）      = 14/30 张
新增触发者的锚定重叠 max_fp_ov    = 0.62 ~ 1.00（几乎全部 ≥ 0.5 ⇒ 守卫**不拦截**）
```

**诚实的读法**：
1. 这 30 张是**采集来的真实 AI 图**（`watermark_style_hint: mixed`，真值在 149 被判伪造后清空）
   ⇒ **触发 ≠ 误报**（可能确有水印），**不能**当作 FP 率。
2. 但它**限定**了 182 的结论：182 实测的 `prior_fp_rate = 0.00` **只对 5 张合成对抗样本成立**，
   在真实照片上锚定判据**几乎不设限**（证据本就落在足迹内）。⇒ 「干净图误报率」在真实照片上
   **仍未测量**，杠杆保持默认 OFF 的决定**因此更加稳固**（不是更松，是更紧）。
3. 另一方向：基线在 28/30 张未标注真实图上检出 `corner_logo`，而 `general` 在 10 张已标注图上的
   precision 仅 0.0690 —— 同向暗示**基线 corner_logo 通路在真实照片上过检**。登记为候选审计目标
   （需真值才能判定，正是遗留 ②「inbox 收编」要解决的）。
