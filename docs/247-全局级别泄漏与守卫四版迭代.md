## 2. 泄漏本体

```python
def _capture_logs():
    h = _Capture()
    lg = logging.getLogger("ui.tab_settings")
    lg.addHandler(h)
    lg.setLevel(logging.DEBUG)      # ← 改全局级别
    return h, lg# ← 只返回 handler 与 logger，不返回旧级别 ⇒ 调用方无从还原
```

调用点（2 处）都正确配对了 `lg.removeHandler(h)`，但**没有任何一处还原级别**。
`ui.tab_settings` 是**产品真实使用**的 logger 名。

### 为什么这类泄漏比 handler 泄漏更隐蔽

handler 泄漏会**立刻抛错**（写入已关闭的流），所以 245 能抓到它。
而级别泄漏**不抛错**，它只是**放大日志量**并**可能淹没 WARN**——
若某个用例断言「不应出现某告警」（如本文件的 `test_d2_save_success_no_warning`
断言无「未生效」告警），DEBUG 噪声会让断言在**别的**用例里莫名失真，
且**难以归因**（「明明这个用例自己没打日志」）。

### 实测取证

```python
#探针（pytest 内观测，被测文件跑完后）
lg = logging.getLogger("ui.tab_settings")
assert lg.level != logging.DEBUG
# → AssertionError: assert 10 != 10（DEBUG）
```

## 3. 修复

```python
def _capture_logs():
    ...
    prev_level = lg.level          # ← 先存旧级别
    lg.addHandler(h)
    lg.setLevel(logging.DEBUG)
    return h, lg, prev_level# ← 连同旧级别一起返回

# 调用点
h, lg, prev_level = _capture_logs()
try:
    ...
finally:
    lg.removeHandler(h)
    lg.setLevel(prev_level)        # ← handler 与 level 都还原
```

与 245/246 同一铁律：**还原必须成对**。当时是「先摘除、后关闭」；
此处是「handler 与 level 都还原」。**只还原其一是残留。**

## 4. 守卫设计的四版迭代（本阶段最有价值的部分）

246 立了判据「守卫不得依赖顺序、不得测复刻品、须做注入反向验证」。
本阶段**亲身实践**这条判据，结果**前三版全部被打回**：

| 版 | 设计 | 为什么**不行** |
|---|---|---|
| v1 | 外部文件 `test_zz_level_probe247.py`，靠**文件名字母序**排在被测文件后观测 | 顺序依赖（246 已批）。实测字母序成立（`test_tab_*` < `test_zz_*`），但仍是脆弱设计 |
| v2 | 文件内「布场（故意不还原）→ 后置断言」 | **布场者自己就是泄漏源** ⇒ 断言必然失败（实测红）。设计根本错误 |
| v3 | 文件内「自证配对写法」：自己调 `_capture_logs` + 自己还原 + 断言前后一致 | **哑巴**：注入删除**真实调用方**的还原后，守卫仍**全绿**（实测 rc=0）。它只验证了「写法能工作」，没验证「真实调用方配对了」 |
| **v4（采用）** | 直接读本文件源码，**逐个点名**断言每个调用点含 `setLevel(prev_level)` | — |

### v4 为什么能成立

运行期观测（含后置断言）**覆盖不到「漏还原的调用点」**——
漏还原的那次调用若发生在其它用例**之前**，后置断言早已跑过。
v4 靠**逐个点名**（`_REAL_CAPTURE_CALLERS`）覆盖到每一个真实调用点，
且**不依赖执行顺序、不自造污染**。

代价：读源码断言看似"硬编码"，但它**精确对应**「这些调用点必须配对还原」这一定义，
且注入验证证明它真的会红。

### 注入式反向验证（v4 有效）

```
还原点总数 before=2 after=0
注入后 rc = 1
E   AssertionError: 以下真实调用点用了 _capture_logs() 却没有在 finally 里
    setLevel(prev_level) 还原全局级别：
    ['test_d2_save_failure_is_observable', 'test_d2_save_success_no_warning']
```

**精准点名**两个漏还原的调用方 —— 正是 v3 漏掉的那两个。

## 5. 诚实登记

1. **本阶段又踩了一次 bash 反引号坑**（第 3 次）：在 `python -c "..."` 里含反引号的
   代码被命令替换吃掉，导致守卫段语法错误。修复方式是**改用脚本文件**执行。
   这个坑本项目已犯多次，**应固化为铁律**（见 LESSONS #264）。
2. `test_tab_settings_audit129` 的守卫用的是**读源码**方式，它不验证「还原在运行时
   真的有效」——那部分由`_capture_logs` 返回旧级别的前提守卫间接保证。
   两者合起来构成完整判据。
3. 全库仍有其它测试可能触碰 `logger.setLevel`（246 扫描的 G1 组只匹配
   `propagate=` 与 handler 操作，**未含 `setLevel`**）。若要彻底，可把 `setLevel`
   加入扫描模式重跑一遍。
