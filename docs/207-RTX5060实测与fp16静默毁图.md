# 阶段 207 · RTX 5060 实测（A5 目标 + D1 并发默认值）

> 用户指定任务：「RTX 5060 实测（A5 目标 + D1 并发默认值）」。
> 这是项目第一次在**真实 NVIDIA 显卡**上跑起来——此前所有质量/性能验证都在 CPU 上，
> GPU 路径从未被真实执行过。

## 一、环境澄清：本机就是 RTX 5060

```
nvidia-smi: NVIDIA GeForce RTX 5060 Laptop GPU, 驱动 610.88, 8151 MiB
torch(原始): 2.9.1+cpu  →  cuda.is_available() = False
```

⚠ 一个此前被误解的事实：我一直把当前环境当作「沙箱 CPU 机」，实际**它就是用户的
RTX 5060 真机**，只是装了 CPU 版 torch。

## 二、发现①：项目 GPU 配方**不适配 50 系卡**（依赖层）

`requirements-gpu.txt` / `Dockerfile.gpu` 原配方：`torch==2.3.1` + `cu121`
+ 基础镜像 `nvidia/cuda:12.1.1`。三处都不适配：

| 问题 | 后果 |
|---|---|
| `cu121` 的 torch 只含到 **sm_90**（Hopper）的 kernel | RTX 50 系（Blackwell **sm_120**）**没有对应 kernel** |
| `torch==2.3.1` 发布早于 Python 3.13 | **无 cp313 wheel** ⇒ py3.13 上 `pip install` 找不到版本 |
| `Dockerfile.gpu` 硬编码同一套版本 | 与清单**两处真值来源**，升级易漏改 |

⇒ 换句话说：**按项目文档给 RTX 5060 装 GPU 加速，装不上、或装上也用不了。**

### 修复与验证

改用 **`cu128` + `torch==2.9.1`**（与现有 CPU 版同版本，把变量降到最小）：

```
torch = 2.9.1+cu128   cuda build = 12.8   cuda.is_available() = True
device = NVIDIA GeForce RTX 5060 Laptop GPU   capability = (12, 0)
arch list = [sm_70, 75, 80, 86, 90, 100, sm_120]   GPU matmul 正常
```

并同步收敛真值来源：
- `requirements-gpu.txt` → `torch==2.9.1` + `cu128`，新增「按显卡架构选 CUDA 版本」对照表；
- `Dockerfile.gpu` → 基础镜像 **12.8.1**，且**改为从 `requirements-gpu.txt` 安装**
  （不再硬编码 torch 版本）⇒ 版本只在一处维护；
- 契约测试由「断言硬编码版本」改为**对账式判据**（必须 `-r requirements-gpu.txt`，
  且**不得**再出现 `torch==x.y.z` 硬编码；基础镜像 CUDA 必须 ≥ 12.8）。

> 另注：`torchvision` 从未被代码 import（只在帮助文本/Dockerfile 里出现），
> 新版配方不再安装它（省约 100MB 与一次版本配对风险）。

## 三、发现②：**P0 静默毁图** —— GPU 默认 fp16 下 LaMa 输出全 NaN

这是本次实测最重要的发现。在 GPU 上按**项目默认设置**（`DEVICE_USE_FP16=True`）跑修复：

### 证据链

| 观测 | 数值 |
|---|---|
| 模型输出张量 NaN 数 | **12,582,912 / 12,582,912（100%）**，值域 `[nan, nan]` |
| 运行时报错 | `UserWarning: ComplexHalf support is experimental and many operators don't support it yet` |
| 随之的告警 | `RuntimeWarning: invalid value encountered in cast`（`core/image_utils.py:720`） |
| **掩码区均值** | 原图 172.2 → **fp16: 5.65** / fp32: 161.96 |
| **掩码区近黑占比** | fp16: **73.9%** / fp32: 0.0% |
| API 返回 | `status="success"`（**静默**） |

**人眼复核**（` .scratch/fp16_crops/compare_small.png`，上排 fp32 / 下排 fp16）：
fp32 输出把「豆包AI」水印干净去除；fp16 输出则**满屏黑色斑点 + 水印处一块纯黑矩形**。

### 根因链（三段，缺一不可）

1. **LaMa 的 FFC（Fast Fourier Convolution）用复数运算**，而 PyTorch 的 `ComplexHalf`
   至今实验性 ⇒ fp16 前向**输出全 NaN**；
2. `image_utils.tensor_to_rgb` 原来只做 `clamp(0, 1)`，而 **`clamp` 拦不住 NaN**
   （`clamp(nan,0,1)` 仍是 `nan`）⇒ `(arr*255).round().astype(np.uint8)`
   触发非法 cast 并把 NaN 变成 **0**（黑）；
3. `inpainter` 的输入 dtype 由 `use_fp16()` 单独决定，与加载侧是否 `.half()`
   是**两处真值来源**。

### 为何长期未被发现

**全部质量验证（172/177 real_gate、mask_recall 等）都跑在 CPU/fp32 上**，
而 GPU 路径直到本阶段才第一次被真正执行——这正是「有守卫≠有覆盖」的又一实例
（LESSONS 183）：指标很美，但从未覆盖 GPU 那条路。

### 修复（三层，各司其职）

| 层 | 改动 | 作用 |
|---|---|---|
| **根因** | `model_manager._FP16_UNSAFE_MODELS = {"lama"}` + `_is_fp16_unsafe()`；加载时对 LaMa **保持 float32** | 不让问题产生 |
| **结构** | `inpainter._run_lama_tile` 的 dtype **跟随模型**（不再独立读 `use_fp16()`）；显式传入矛盾值则**响亮失败** | 消除两处真值来源 |
| **安全网** | `image_utils.tensor_to_rgb` 先 `torch.nan_to_num(nan=0, ±inf→0/1)` 再 clamp | 任何路径都不能把 NaN 变垃圾像素 |

**修复后验证**（配置仍为 `DEVICE_USE_FP16=True`）：

| 配置 | 掩码区均值 | 近黑占比 |
|---|---|---|
| fp16 开（修复后） | **161.96** | **0.0%** ✅ |
| fp16 关 | 161.96 | 0.0% |

⇒ 与 fp32 完全一致。另新增 `tests/test_gpu_numerics_guard.py`（9 例）锁死三层不变式。

## 四、A5 目标实测：P95 远超 1.5s，且**瓶颈不在 GPU**

### 实测数据（10 张真实基准图 × 3 次取 min，全链路 = 检测 + LaMa 修复）

**修复 fp16 缺陷之后**（正确性优先，故用 float32）：

| 口径 | min | P50 | **P95** | 对照目标 1.5s |
|---|---|---|---|---|
| 默认配置（超分关） | 5.76s | 12.26s | **19.07s** | **12.7×** |
| 当前覆盖（真超分 2× 开） | 7.31s | 14.32s | **30.27s** | **20.2×** |

> 修复 fp16 前的对照（当时输出是坏的，仅供说明 fp16/fp32 的耗时差）：
> 默认配置 P95 **17.13s**、覆盖配置 P95 **20.84s**。
> 即**改用 float32 会再慢约 11%**（17.13 → 19.07），但**换回了正确输出** —— 这个代价是必须付的。

> 注：`REAL_SUPERRES_ENABLED` 在 `config.user_overrides.json` 里被**用户覆盖为 true**（scale=2），
> 项目默认是 `False`（config 注释写明「默认关闭」）。两种口径都测了，以便区分
> 「算法本身」与「用户开启的增强」各占多少。

### 归因：耗时去哪了

单张 2048² 真实图的逐段计时：

| 阶段 | 耗时 |
|---|---|
| 检测（OpenCV，CPU） | 0.79s |
| LaMa 修复（GPU） | 4.8–5.2s |
| **端到端 API（默认配置含 2× 放大时）** | **22.6s** |

**GPU 利用率采样仅 0–6%**（显存 1491 MiB 已载模型）⇒ **GPU 大部分时间在等**。
瓶颈是 **CPU 侧**，主要是：
- 后处理的 **2× 双三次放大**（2048² → 4096²）与由此放大的编码开销；
- 检测阶段（CPU 绑定的 OpenCV 通路，与 186 的既有结论一致）。

**结论**：路线图的「P95 < 1.5s」在**当前实现下不可达**，且**加 GPU 并不能解决**——
除非把 CPU 侧的后处理/编码一并优化。这条结论是**实测**，不是推断。

### 附带发现：基线可比性键缺了「会显著改变工作量的增强开关」

`perf_probe.baseline_comparable` 只比对 `source/stage/repeat/device/gpu_name`，
但**打开/关闭真超分会让 P95 差 20%**（17.1s vs 20.8s）而**仍被判为「可比」**。
⇒ 与阶段 188/198 的「可比性必须覆盖影响数值的配置」同源，建议把这类专业增强开关
纳入可比性键（本阶段已如实记录，未擅自改动判定逻辑）。

## 五、D1 并发默认值标定

`config.API_MAX_CONCURRENCY` 默认 2 是阶段 199 的**判断值**（当时只有 CPU torch，
无从实测）。现在在真实 GPU 上标定：对 8 张真实基准图**同时**打 `/api/remove`
（全链路：检测 + LaMa 修复；8 个请求 > 最大上限，保证「上限 N」与「不限」可区分）。

### GPU（RTX 5060，默认配置=超分关）

| 并发上限 N | 吞吐（请求/秒） | P50 | P95 | 总墙钟 | 峰值 |
|---|---|---|---|---|---|
| 1（串行） | 0.179 | 22.83s | 44.56s | 44.62s | 1 |
| **2（当前默认）** | 0.305 | 22.49s | 26.23s | 26.24s | 2 |
| **4（推荐）** | **0.409** | 15.72s | **19.57s** | **19.57s** | 4 |
| 8 | 0.395 | 14.11s | 20.23s | 20.23s | 8 |

**结论：推荐默认 4。** 依据：
- 吞吐相对当前默认 2 **提升 34%**（0.305 → 0.409），相对串行提升 **2.28×**；
- **P95 同时最低**（19.57s）—— 不存在「换吞吐牺牲时延」的取舍；
- N=8 已**饱和**（吞吐略降、P95 略升）⇒ 拐点在 4，不是越多越好；
- 8 张并发全部成功（`ok=8/8`），说明 8 GiB 显存下 4 并发无显存压力。

⚠ 反直觉但重要：**N=1（串行）是最差的**（吞吐 0.179、P95 44.56s）。
因为全链路里 CPU 阶段（检测/后处理）与 GPU 阶段（LaMa）本可**跨请求重叠**，
串行把两者强行排成一条线 ⇒ 两边都闲着。

### CPU 口径（同一负载，`WME_DEVICE_MODE=cpu`，用于确认默认值对无卡用户也合理）

| 并发上限 N | 吞吐（请求/秒） | P50 | P95 | 总墙钟 |
|---|---|---|---|---|
| 1（串行） | 0.099 | 61.16s | 80.73s | 80.77s |
| 2 | 0.141 | 41.29s | 56.78s | 56.79s |
| **4（推荐）** | **0.159** | 43.39s | **50.45s** | **50.46s** |
| 8 | 0.130 | 40.08s | 61.57s | 61.57s |

⇒ **CPU 也推荐 4**（吞吐最高、P95 最低，相对串行 1.61×）。
**两种设备模式独立标定，结论一致** ⇒ 默认值取 4 有据可依。

### 已落地的改动

`config.API_MAX_CONCURRENCY` 默认值 **2 → 4**（`config.py` 注释改为记录实测依据），
`server.py` 的 docstring 与用法页同步为「默认 4」。

> 阶段 199 选的默认 2 并非错误——当时**没有 GPU 可测**，取保守值是合理的
> （「判断值」而非「实测值」，已在 `config.py` 注释里如实标注）。
> 本阶段把该备注替换为**实测依据**。

## 六、诚实边界

- **D1 标定样本规模有限**：每档只发 8 个请求（保证 8 > 最大上限 N，从而能区分
  「上限 N」与「不限」）。趋势清晰（4 是拐点），但**未做长稳态压测**；
  若上生产建议用更大负载复测。
- **未测多图并发的显存峰值**：本机 8151 MiB，实测模型占用约 1491 MiB，
  8 并发亦全部成功；但**峰值显存未逐档测量**（若要上生产建议补）。
- **GPU 利用率是 2 秒间隔采样**，只能说明「大部分时间空闲」，不能给出精确利用率。
- **`REAL_SUPERRES_BACKEND=esrgan` 无训练权重**，实际退化为双三次放大（日志明示）
  ⇒ 那 30.27s 里不含任何学习式超分收益。
- **路线图 1.5s 目标未修好**：本阶段给出的是**实测与归因**（含「瓶颈不在 GPU」这一
  关键结论），**未做性能优化**。后续若要认真逼近目标，应针对
  「后处理 2× 放大 + 编码」与「检测阶段」下手，而不是继续加 GPU。
- **修改了本机 Python 环境的 torch**（`2.9.1+cpu` → `2.9.1+cu128`，约 2.7 GB）——
  这是完成本任务的必要变更，已如实记录。
- **未做 Docker 实构建**：`Dockerfile.gpu` 的改动（CUDA 12.8 + 从清单安装）由
  契约测试守护，但**未真跑 `docker build`**（本机未验证 Docker 可用性）。
