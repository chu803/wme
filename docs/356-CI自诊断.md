# 阶段 356 · 让 CI **自诊断**：失败步骤的日志尾巴直接进 Summary 与 issue

> 日期 2026-10-27 · 性质：**CI 可观测性**（不再靠截图问原因）

## 一、为什么做这个

CI 从 10-18 起连续红（#15~#35），每次都「红得飞快」（1m10s~1m49s ⇒ 失败在 setup 段），
但**原因只在 runner 的日志里**；会话内读不到 GitHub（API 被安全策略拦）⇒ 只能一次次让人截图。
阶段 351 修了「系统依赖写死包名」这一条，CI **仍红** ⇒ 还有别的原因，而**继续猜的成本已经高于让 CI 自己说**。

## 二、改法

1. **每个 run 步骤的输出 `tee` 到 `logs/<step-id>.log`**
   （`set -eo pipefail` 保留 ⇒ tee 不吞退出码；329 的坑不能再踩）。
2. **诊断步骤把各步骤日志的最后 40 行写进 Summary 与自动建的 issue**，
   连同原有的「哪一步红了」状态表与 FAILED 清单。
   ⇒ 下一次红，**那张 issue 自己就写着原因**（比如 pip 的 `No matching distribution found`）。

## 三、守卫（`tests/test_workflow_selfdiag356.py`，4 例 × 两个 workflow）

* 带管道的步骤必须 `tee` 到 `logs/`；
* 带管道的步骤必须有 `set -o pipefail`（否则 tee 把退出码吞回 0）；
* 诊断步骤必须真的读 `logs/` 并把 `stepLogs` 同时放进 Summary 与 issue（出现次数 ≥ 4）；
* 写 `logs/` 前必须先 `mkdir -p logs`。

## 四、诚实的边界

* 这一步**不修任何 bug**，只让 bug 自己现形 ⇒ 下一个红的原因要等下一次 CI 才拿到；
* 若失败发生在 `checkout`/`setup-python`（连 logs 都还没建），诊断会写 `(no logs/)`
  ——那时才需要看 runner 日志；
* `logs/` 是工作目录下的临时产物，**不入库**（.gitignore 已覆盖？⇒ 本阶段顺手确认）。
