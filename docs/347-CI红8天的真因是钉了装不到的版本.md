# 阶段 347 · CI 红了 8 天的真因：清单钉了「只有本机装得到」的版本

> 日期 2026-10-26 · 性质：**发布阻断级缺陷修复**（CI #15–#20 全红的根因，附一条「不许再犯」的守卫）

## 一、这次是**从截图**倒推出来的

用户发来 Actions 列表截图，一眼就看出关键信息：

| CI | 提交 | 时长 | 结论 |
|---|---|---|---|
| #14 | ef64fd7（10-18） | **5m 23s** | 绿 ⇒ 跑完了整个入口 |
| #15 | 0cb20e3（10-18） | **31s** | 红 |
| #16 | 38cc3ea（10-18） | 26s | 红 |
| #17 | 479c5d4（10-25） | 45s | 红 |

**红得飞快**（26 秒～1 分半）⇒ 根本进不到「运行验证入口」那一步（那一步本机要 10～20 分钟）⇒
失败在**装依赖**。而 `git log ef64fd7..HEAD -- requirements-*.txt` 只有**一个**提交碰过清单：
`0cb20e3`「对齐依赖清单到已验证 venv 版本」——**正是 CI #15，也就是第一次红的那次**。

## 二、真因精确到「轮子的 Python 标签」

`0cb20e3` 把 6 个核心包从「CI 装成功过的版本」换成了**本机 venv 的精确版本**：

```
opencv-python-headless==5.0.0.93   numpy==2.5.1   Pillow==12.3.0
scikit-image==0.26.0                scipy==1.18.1  pydantic==2.13.4
```

**这些版本在 PyPI 上都是有的**（实测镜像索引页：opencv 5.0.0.93 / numpy 2.5.1 / scipy 1.18.1 全部可查）。
真正的杀手是**轮子的 Python 标签**：

| 包 | 版本 | 该版本的 cp 标签 | CI 的 Python **3.11** 能装吗 |
|---|---|---|---|
| opencv-python-headless | 5.0.0.93 | cp37-**abi3**（向前兼容） | ✅ 能 |
| **numpy** | 2.5.1 | cp312 / cp313 / cp314 | ❌ **没有 cp311** |
| Pillow | 12.3.0 | cp310–cp315 | ✅ 能 |
| scikit-image | 0.26.0 | cp311–cp314 | ✅ 能 |
| **scipy** | 1.18.1 | cp312–cp315 | ❌ **没有 cp311** |
| pydantic | 2.13.4 | py3-none-any | ✅ 能 |

⇒ CI（Python 3.11）装 `numpy==2.5.1` / `scipy==1.18.1` **必然** `No matching distribution found`
⇒ 每次都红在 26~92 秒（跑不完入口步）。
（对照本机：Python **3.13** 上这两个版本都有 cp313 轮子 ⇒ 本机一路绿灯，**只有 CI 红**——
这就是它能潜伏 8 天的原因：**本地验证通过 ≠ CI 能装上**。）

**这一步有个决定性的推理**：清单里**其余**的精确 pin（requests 2.32.3 / tqdm 4.66.5 / urllib3 2.2.3 /
certifi 2024.8.30 / psutil 6.0.0 / py-cpuinfo 9.0.0 / colorama 0.4.6 / python-dotenv 1.0.1）
在 `0cb20e3` 里**一个字没动**，而 CI #14 用它们**装成功过** ⇒ 它们可解析；
嫌疑精确地落在被改动的那几个身上，且不需要联网就能锁定范围。

**更要紧的是**：`requirements-min.txt` 同时是 **README 让用户照着装的清单**
⇒ 这 8 天里，**用 Python 3.11 照着 README 装包的用户也装不上**。这不只影响 CI，还影响交付。

> **一处自我订正**：本阶段最初写的是「这些版本不在 PyPI 上，是本机从 CI 源码树构建的」。
> 那是**推断**（依据是本机 opencv 的构建信息里写着 `D:\a\opencv-python\...`），
> 后来实测索引页才发现：**版本都在 PyPI 上**，真正的差别是 **cp311 轮子缺失**。
> 结论方向不变（钉死本机版本 = 发布阻断），但**理由必须换成实测的那一条**。

## 三、修法：把「装得到」和「验证过」拆成两份清单

* `requirements-min.txt`（**安装**用）：那 6 个改成**区间**——
  **下界 = 上一版 CI 装成功过的版本**（保证 CI 仍能装到已知可用的组合），
  **上界 = 本机验证过的版本**（保证「我们测过的那套」仍在允许范围内）。
  例：`numpy>=1.26,<3`、`opencv-python-headless>=4.10,<6`、`scipy>=1.14,<2`。
* `requirements-verified.txt`（**记录**用，新增）：留下阶段 297 那套本机验证组合的精确版本，
  注明「不用于安装」，并写清为什么会有这份文件。
  ⇒ 阶段 297 的成果（对齐到已验证版本）**信息没丢**，只是不再用「钉死一个装不到的版本」的方式表达。

## 四、守卫：把「再钉一个本机专属版本」这条路堵死

`tests/test_requirements_ci_installable.py`（4 例）：

1. 精确 pin **只允许**出现在「CI 装成功过」的集合里（集合来源写进注释：CI #14 / ef64fd7）；
2. 区间下界不得高于那个装成功过的版本；
3. `requirements-verified.txt` 必须存在，且它记的版本要被安装清单的上界覆盖
   （否则清单会悄悄把「我们测过的那套」排除掉）；
4. `requirements-dev.txt` 同规则。

**反例（把这条守卫放到 0cb20e3 的清单上跑）**：它**逐个点名**了那 6 个装不到的 pin：

```
requirements-min.txt: opencv-python-headless==5.0.0.93（不在 CI 装成功过的集合里）
requirements-min.txt: numpy==2.5.1（CI 装成功过的是 1.26.4）
requirements-min.txt: Pillow==12.3.0（不在 …）  scikit-image==0.26.0（…是 0.24.0）
requirements-min.txt: scipy==1.18.1（…是 1.14.1）  pydantic==2.13.4（…是 2.9.2）
```

⇒ 这条守卫本可以在 10-18 就把 CI #15 拦下来。**判据从「我以为对齐了」变成「CI 装成功过」**。

## 五、连带影响：1.0.3 那次发版**没有真正上架**

`v1.0.3` 的 tag 在依赖修复**之前**推的 ⇒ publish.yml 会在同一个 `pip install` 步骤失败
⇒ 门禁与发布都到不了 ⇒ **PyPI 上没有 1.0.3**（发布链自守生效了，但也意味着「推了 tag ≠ 发版成功」）。
修完依赖后需要**重推一次 tag**（把 tag 指到修复后的提交）才能真正发出去。

## 六、教训

1. **「本机能装」≠「PyPI 上有」**：把本机 venv 的版本钉进安装清单，等于把「我这边有」写成了「大家都有」。
   本机是从 CI 源码构建出来的 opencv，这种来源差异最容易被忽略。
2. **对齐版本 ≠ 对齐可安装性**：阶段 297 的目标（CI 装的和本机跑的一样）本身是对的，
   但实现方式选了「钉死」而不是「区间 + 记录」，于是把一个测试便利变成了发布阻断。
3. **红得飞快 = 失败在很前面**：26 秒 vs 5 分 23 秒，这个对比一眼就排除了「测试失败」，
   把范围缩到 setup 段。**看 CI 列表的时长比读日志更快。**
4. **一张截图抵得过我半小时推理**：用户发来的 Actions 列表里，#14 绿（5m23s）与 #15 起全红
   （26s～1m32s）的对比就是全部证据链的起点。
