## 2. 审计发现（真实缺口，非风格问题）

HTTP 层原本只暴露：`GET /api/health`、`POST /api/remove|detect|inpaint|batch`。

而 `api.py` 另有这些**已实现但调用方够不到**的能力：

| 能力族 | 函数 | UI 有入口？ | HTTP 暴露？ | 判定 |
|---|---|---|---|---|
| 模型管理 | `list_models` / `get_active_model` / `verify_model` / `set_active_model` / `download_model` | ✅ `ui/tab_models.py` | ❌ | **缺口**：容器化部署无法查询「预置了哪些模型、当前用哪个、权重齐不齐」 |
| 能力自发现 | `get_capabilities` | — | ⚠仅混在 `/api/health` | **语义混杂**：健康 ≠ 能力 |
| PDF / 视频 | `remove_watermark_pdf` / `remove_watermark_video` | ✅ `ui/tab_media.py` / `tab_batch.py` | ❌ | **缺口**：项目宣传「图片/PDF/视频全源」，但 API 侧只能处理图片 |

## 3. 本轮改动

### 3.1 四个只读端点（`server.py::do_GET`）

```python
elif self.path.startswith("/api/capabilities"):     # 能力自发现
elif self.path.startswith("/api/models/active"):    # ⚠ 必须排在 /api/models 之前
elif self.path.startswith("/api/models/verify"):   # 支持 ?name=<槽>
elif self.path.startswith("/api/models"):           # 列表（放最后）
```

⚠ **路由优先级**：`startswith` 路由里更「长」的路径必须排前面，否则
`/api/models/active` 会被 `/api/models` 吃掉。守卫专门钉这条。

### 3.2 并发闸门豁免（`_is_exempt_from_gate`）

新增豁免 `/api/capabilities` 与 `/api/models*`。理由：

- 它们是**纯只读、毫秒级**的查询。若也排队，则服务繁忙时调用方
  **恰恰最需要**自省「用哪个模型、权重齐不齐」却拿不到——
  **可观测性被闸门本身挡住**。
- 只读端点无副作用，豁免不构成旁路；**推理类端点仍全部排队**（199 的 fail-closed）。

### 3.3 文档与文案同步

- `/` 用法页新增两节（⑥ 能力自发现、⑦ 模型查询），并明确写出**尚不提供**什么及原因；
- 并发闸门一节同步写明豁免清单；
- 404 文案改为列出全部端点；
- `/api/health` **保持含 capabilities**（拆端点是**新增**，不能让既有调用方静默失效）。

## 4. 守卫（15 例）

`tests/test_api_readonly_endpoints251.py`，三条契约：

1. **端点可用**：真起 `_BoundedThreadingHTTPServer`，真发 HTTP（不用 mock）；
   并断言 `/api/capabilities` 的字段集**等于** `api.get_capabilities()`（禁止 HTTP 层私自裁剪）。
2. **向后兼容**：`/api/health` 仍含能力字段与 `concurrency`。
3. **豁免契约**（最关键）：
   - 5 个只读路径 `must`豁免；
   - 4 个推理路径 `must NOT` 豁免（否则等于给未鉴权的重活开免检通道）；
   - 用法页 `must` 登记新端点（文档漂移是本项目既有失分模式）。

注入验证 3/3（能力清单置空 / 豁免全关 / 错误路由顺序）均被对应守卫捕获。

## 5. 本轮**未做**的（及原因，需决策）

| 缺口 | 为什么不做 |
|---|---|
| `POST /api/models/active`（切模型） | **写操作**，需配套确认机制（参照 233 的「全自动擦除确认门」思路）+ 鉴权考量 |
| `POST /api/models/download` | **长任务**（数百 MB 下载）且需联网；同步 HTTP 会占满并发槽并超时 |
| `POST /api/pdf` / `api/video` | 同上，且更重（视频可能几分钟）。**正解是引入异步作业模型**（提交 job → 轮询 → 取结果），属架构决策，不宜顺手塞进同步端点 |

> 这三项都**不是**「做不到」，而是需要先定契约（写操作确认？作业状态机长什么样？进度怎么报？），
> 否则会做出一个「能调但不该用」的接口。

## 附：元教训 · 注入式反例必须真的命中执行路径（250→251 的第二次教训）

R3（路由优先级）的**第一版注入无效**：我把 `api.list_models` 换成抛异常，指望
「active 请求被短前缀吃掉时会命中它 ⇒ 守卫红」。但因为实现顺序本来就是对的，
**`list_models` 根本不会被调用** ⇒ 无异常 ⇒ 守卫仍绿。

**此时我以为「注入通过」，实际上只证明了「实现正确」，证不了「守卫有效」**——
若当时守卫本身是哑巴，我同样会看到「通过」。

改法：注入一个**确定会被执行且改变行为**的错误实现（把 `do_GET` 换成短前缀在前的版本），
守卫立刻红。⇒ **反例必须命中执行路径**，否则「注入通过」是假阳性。
