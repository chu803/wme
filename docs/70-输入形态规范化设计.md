# 阶段 70 · 输入形态规范化设计（EXIF 方向 / 位深 / 动图）

> 目标：审计并修复「**输入形态**」这一层——阶段 49~69 的全部真值审计都在合成 uint8 PNG 上进行，
> 而真实用户的文件形态（手机照片的 EXIF 方向、16 位扫描/TIFF、带 alpha 的 PNG、动图）
> 从未被审视。
> 交付：加载端两级规范化（位深 → 方向）+ 动图明确拒绝、校验层同步、
> `tests/test_input_normalization.py`（39 例）、2 个配置开关。

---

## 1. 审计矩阵与结论

以工程真实入口（`validate_image_file` → `load_image(_with_alpha)`）逐一验证，参考基准取
Pillow（`ImageOps.exif_transpose`）：

| 输入形态 | 修复前实测 | 判定 |
|---|---|---|
| **EXIF Orientation=6/8**（手机竖拍） | 加载 (80,120)，参考 (120,80) —— **未旋转** | ❌ **缺陷** |
| **EXIF Orientation=3** | 尺寸相同但**内容上下颠倒**（maxdiff=197） | ❌ **缺陷** |
| EXIF Orientation=1 | 一致 | ✅ |
| **16 位 PNG / TIFF** | 校验通过 → `load_image` 返回 **uint16**(max 64250) → 检测侥幸出掩码 → **修复抛 `icvInpaint ... Unsupported format`** | ❌ **硬失败** |
| **动图 WebP**（扩展名在白名单内） | `cv2.imdecode` **静默截取首帧**（40×60），用户以为整段被处理 | ❌ **缺陷** |
| 灰度 JPEG / 调色板 PNG / 1 位二值 PNG | 与参考一致 | ✅ |
| CMYK JPEG | 正常转 BGR | ✅ |
| 带 alpha 的 PNG | `load_image_with_alpha` 返回 alpha；修复不改 alpha；保存保留 4 通道 | ✅ |
| 极端宽高比（4000×8 / 8×4000 / 1×1 / 2000²） | 均正常加载 | ✅ |

## 2. 根因

### 2.1 EXIF 方向被忽略（导出图"看起来被旋转"）
- `_decode_image_raw` 走「读字节 → `cv2.imdecode`」，而 **`imdecode` 不应用 EXIF 方向**
  （只有 `imread` 默认应用，工程又刻意避开 `imread` 以兼容中文路径）；
- 保存端不写 EXIF → **输入在查看器中是竖构图、导出图变成横构图**，用户直观感受是"处理完图被转了"；
- 连带的隐性危害：「底部小字」（`search_bottom`）与「角落 LOGO」这类**锚定位置**的判据，
  会在**错误的边**上搜索，召回随拍摄方向随机波动；
- **旁证**：`requirements.txt` 早已声明 Pillow 负责「EXIF 方向校正」，但实现里从未调用——
  与阶段 61 的"死代码伪装成已验证功能"同族：**声明过的能力不等于实现了的能力**。

### 2.2 16 位图穿透到修复层（硬失败）
- 输入白名单含 `.tif/.tiff`，16 位 PNG/TIFF 解码为 `uint16`；
- 全链路常量（`DETECT_MIN_DELTA`、面积门限、`clip(0,255)`）都按 8 位设计；
- OpenCV `inpaint` 只支持「8 位 / 16 位 / 32 位浮点 **单通道**」与「8 位 **3 通道**」——
  16 位 3 通道直接抛异常：**用户在"检测看起来正常"之后才遇到失败**（最差的一种失败位置）。

### 2.3 动图静默截首帧
- GIF 因扩展名不在白名单而被明确拒绝；但**动图 WebP / APNG** 的扩展名在白名单内，
  于是被静默当成静态图取首帧 —— 同一类问题两种处置，属**行为不一致**。

## 3. 修复

`core/image_utils.py` 在加载端做**两级规范化**（顺序：先位深、再方向，避免对大位深数组做旋转开销），
rgb 与 alpha **同步变换**：

```
cv2.imdecode(IMREAD_UNCHANGED)
  → 通道规范化（灰度→RGB / BGRA→RGB+alpha）
  → ① 位深规范化（16 位 → uint8）
  → ② 方向规范化（按 EXIF Orientation 烘焙进像素）
  → 动图检测（帧数 > 1 → 明确拒绝）
```

- **位深映射**：`uint16 → round(v/257)`（对"16 位存储的 8 位数据"完全无损）；其他整型按位深线性
  映射；浮点按"最大值 ≤1 视为 0~1 归一化，否则视为 0~255"处理；已是 uint8 → 原样返回。
- **方向映射**：8 个取值与 `ImageOps.exif_transpose` 一一对应，由测试对每个取值逐位锁定
  （1 不变 / 2 左右镜像 / 3 旋转 180° / 4 上下镜像 / 5 主对角线转置 / 6 顺时针 90° /
  7 副对角线转置 / 8 逆时针 90°）。
- **元数据读取必须软失败**：`read_image_flags(p)` 只读元数据（不解码像素），任何异常
  （Pillow 不可用、无 EXIF、文件损坏、动图头解析失败）都回退 `(1, 1)`——**绝不因为校正而让加载失败**。
- **校验层同步**：`validate_image_file` 也拒绝动图，并报告**校正后**的宽高
  （Orientation ∈ {5,6,7,8} 时交换），保证界面标签与实际处理尺寸一致。
- 两个开关（默认 True，可环境变量关闭）：
  `IMAGE_APPLY_EXIF_ORIENTATION`、`IMAGE_NORMALIZE_BIT_DEPTH`。

## 4. 验证

| 检查 | 结果 |
|---|---|
| 方向正确性 | 8 个取值 × PNG/JPEG 均与 `ImageOps.exif_transpose` 参考一致（PNG 逐位、JPEG ±2 容差） |
| 16 位规范化 | `v = k×257` 精确还原为 `k`；PNG/TIFF 双格式 |
| 16 位端到端 | 检测 + 修复不再抛异常，输出 uint8（修复前为 `icvInpaint` 硬失败） |
| 动图 | 校验层与加载层**双重拒绝**，附可操作建议 |
| alpha 一致性 | 方向变换后透明区仍与同一图像区域重合 |
| 校验层宽高 | EXIF=6 的 90×60 → 报告 60×90，与加载结果一致 |
| 兼容性 | WebP + EXIF 也一并被校正（Pillow 元数据路径与格式无关） |
| **零回归** | 普通 8 位无 EXIF PNG **逐位等于 cv2 解码结果**；门禁/benchmark 走内存数组不经加载器 |

护栏 `tests/test_input_normalization.py` **39 例**；全量回归见文末。

## 5. 边界（诚实声明）

- **刻意不写回 EXIF**：方向已烘焙进像素，再写方向标签会导致"双重旋转"；
  ICC 色彩配置未处理（不做色彩管理，与既有行为一致）；
- 动图被拒绝而非"只处理首帧"——这是**刻意的产品选择**：静默降级会让用户以为整段动画已处理；
- 多页 TIFF 视为动图同类（帧数 > 1）一并拒绝；
- 未测：超大位深（32 位 float TIFF 仅做了合理映射，未做真值验证）、JPEG XL / HEIF（不在白名单）。

## 6. 经验沉淀（已并入 MEMORY 第 15 条）

15. **「输入形态」必须与「像素内容」分开审计（阶段 70）**：同一张图在不同**容器形态**下
    （EXIF 方向 / 位深 / 帧数 / 通道）会走完全不同的代码路径，而合成测试数据几乎总是
    "uint8 RGB + 无 EXIF + 单帧"，于是这一层长期无人审计。三条可复用判据：
    ① **声明过的能力 ≠ 实现了的能力**（`requirements.txt` 写着 Pillow 负责 EXIF 校正，
       实现里从未调用——与阶段 61 死代码同族，收尾时应把"依赖声明里的承诺"当审计入口）；
    ② **失败位置越靠后越糟**：16 位图在"检测看起来正常"之后才在修复层硬失败，比一开始就拒绝
       更难排查，故规范化必须在**入口**统一完成；
    ③ **同类问题要同类处置**：GIF 被明确拒绝而动图 WebP 被静默截首帧，是行为不一致，
       发现一处后应立刻检查同族入口。
