## 二、真缺陷：`services/pdf_service.py` 的自检缺 PyMuPDF 时 `SystemExit(1)`

子进程只打印一句「未安装 PyMuPDF，请执行：pip install PyMuPDF」然后**退出码 1**。
而 CI 只装 min/dev（**刻意不含 PyMuPDF**）⇒ 守卫 `assert rc == 0` ⇒ **CI 红**。

两处口径同时错位：

1. **模块侧**：本项目对退出码有明确家族约定（`0` 通过 / `1` 质量失败 / `2` 依赖缺失或环境不满足 / `3` 环境错误）。
   「这台机器没装这个可选库」是**环境事实**，写成 `1` = 把它申报成产品质量问题。
2. **守卫侧**：`test_legacy_selfcheck` 用 `assert rc == 0` **禁止了契约里合法的 2**——
   它自己就是「断言比契约更严」的那种守卫，于是把契约的另一半挤到了看不见的地方。

### 修法

- `services/pdf_service.py`：缺依赖时改为「说明缺什么、怎么装」+ `SystemExit(2)`。
- `tests/test_legacy_selfcheck.py`：接受 `0` 与 `2`；**但 2 必须带原因**——
  ```
  if r.returncode == 2:
      assert ("未安装" in out) or ("缺失" in out) or ("pip install" in out)
  ```
  否则「跳过」会变成真失败的新藏身处（这正是 330–335 一整族「假绿」的形态）。

### 牙齿（反例真跑）

把自检改成「返回 2 但不说原因」⇒ 守卫 **CF_RC=1**，报错原文：
`services/pdf_service.py 自检返回 2（跳过）却没说明缺什么 ⇒ 「跳过」正在替真失败打掩护`；
复原后 **rc=0**。消费者核查：`README.md` / `scripts/media_gate.py` 只引用路径字符串，
无人依赖旧退出码 ⇒ 改 1→2 不破坏任何调用方。

## 三、这段最值钱的结论：探针为什么没抓到它

`ci_env_probe.py` 靠 **`sys.meta_path` finder** 在**导入层**屏蔽模块 —— 这是**进程内**机制。
而 `test_module_selfcheck` 是 `subprocess.run([sys.executable, mod])`：
**子进程用的是本机真实完整环境**（PyMuPDF 装着）⇒ 探针一路绿灯，CI 一路红。
⇒ 这不是"探针参数没调对"，是**探针的模拟层跨不过进程边界**。

判据（教训 #336）：**凡是「派生子进程」的守卫，环境模拟必须沿进程边界传递**，否则它验的是本机、不是 CI。
可行做法只有两条：① 把屏蔽层传下去（给子进程注入 sitecustomize / 环境变量白名单）；
② **建一个真的等价 venv**（本阶段）。②还顺带覆盖了解释器版本与安装版图，成本是一次性装环境 + 每次 7 分钟。

⇒ 因此 359 那条「CI 常驻收集检查」和 360 这条「等价 venv 跑同一入口」是**互补**的，不能互相替代。

## 四、诚实边界

- 本机是 **Windows + Python 3.11.4**，CI 是 **Ubuntu + Python 3.11.x**：OS 维度（路径分隔符、
  大小写敏感、系统库）仍未覆盖；`libgl1`/glib 那类由 351 的探测式安装兜住。
- 本次只把 **`pdf_service`** 这一处 1→2。同类形态（其它自检在可选依赖缺失时 `SystemExit(1)`）
  在等价 venv 里**已被这条入口跑过并全绿** ⇒ 当前没有第二处；但新增可选依赖时要用同样方式复跑。
- `test_docs_index` 那条失败是**竞态产物**（INDEX 在入口跑完后才登记），复跑已通过；
  它提醒：登记类守卫与并行的文档改动天然冲突，复跑确认比"猜它是竞态"可靠。
