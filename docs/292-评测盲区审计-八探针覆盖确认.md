## 三、为何残余缺口是「披露+blocked」而非「隐藏盲区」

| 方向 | 现状 | 为何不设硬红线（探针 6） | blocked_on |
|---|---|---|---|
| full 管线耗时 | P95 8.585s vs 目标 1.5s（结构地板 ≈4.4s） | 现在设硬线必**恒红**（GPU 未落地）⇒ 训练人忽略红灯，连带上贬值所有红线；正确处置=披露于记分卡 performance C- | infra（GPU） |
| 真实类型覆盖/精度 | 对外仅承诺 ai_logo；precision 0.079 | 补图/补标注只有用户能做；硬失败=恒红。已收敛承诺 + 逐行标「未验证」 | user / data |

判据：这两类「变坏」当前**不可执行**（缺数据/缺机器），故只能披露+告警；待 infra/user 到位再据实测分布设线（skill：阈值等实测够了再定，防恒红/恒绿）。

## 四、什么情况算完备（可判定验收线，非感觉）

满足以下全部，方可称「无隐藏盲区」；任一不满足即回到对应探针：

1. 每条契约红线都能回答「它防的是哪一类变坏」，且变坏类型并集 ⊇ 全部已知方向（探针 1）。
2. 新增契约指标会被机器强制纳入 calibration/crash_guard 与 margin floor（元守卫，探针 1b/8）。
3. README/UI 承诺类型 ⊆ 登记表，且无正向证据者逐行标「未验证」（探针 3）。
4. 真值 manifest 声明与 truth 类别分布有脚本级一致性守卫（探针 2）。
5. 修复类质量报告同时给「真值掩码」与「检测掩码」两列（探针 5）。
6. 写盘/刷新路径写后仍走完整 evaluate，且向下刷新有护栏 + 显式逃生门只跳护栏不跳红线（探针 8）。
7. 每条红线既非恒红也非恒绿（有余量且被监控或漂移保护）（探针 6）。

## 五、自反证伪

- 本审计结论「已覆盖」的证据是**活守卫实跑 50 例全绿 + 文件行号**，非阅读自述；若某守卫被改成死代码，注入式反例应能捕获（既有反例体系）。
- 「无隐藏盲区」不等于「产品可上线」：full 管线耗时与真实覆盖是**已知且 blocked** 的真实短板，由记分卡（docs/291）与路线图跟踪，本审计不越权宣称就绪。
- 若后续新增一类「变坏方向」（如新增 watermark 类型、新增引擎）却无对应红线/覆盖守卫，则第 1/1b/3 条验收线会失败——那才是本审计要防的回归。
