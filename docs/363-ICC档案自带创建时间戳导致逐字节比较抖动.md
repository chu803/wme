# 阶段 363 · ICC 档案自带创建时间戳 ⇒ 「写入端与断言端各取一次」是秒位炸弹

> 日期 2026-11-01 · 性质：**测试抖动（flaky）根因修复**——CI 会随机红的那一类

## 一、现象：同一条命令，一次全绿、一次一条红

在 CI 等价环境（Python 3.11 + 只装 min/dev）跑与 CI 同一条入口命令：

| 轮次 | 结果 |
|---|---|
| 上一轮（阶段 362 复验） | `3377 passed / 36 skipped` ⇒ rc=0 |
| 本轮（加 `--durations` 复测耗时） | **`1 failed, 3376 passed`** ⇒ rc=1 |

红的是 `tests/test_icc_profile.py::test_load_image_full_with_alpha_and_icc`，
而**单跑该文件 3/3 全绿** ⇒ 典型抖动：只在整套跑时现形，本地单独复现不了，
最后容易被归成"环境不稳"糊过去（而 CI 上它就是随机红的来源）。

## 二、根因：ICC 头第 24–35 字节是创建时间

失败信息只有一句有用：

```
assert b'\x00...x0f\' == b'\x00...x0f\'
    At index 35 diff: b'"' != b'#'      # 0x22 vs 0x23
```

测试的结构是：**用 `_icc_srgb()` 写入 PNG，读回来之后，再调用一次 `_icc_srgb()` 做逐字节比对**。
而 `_icc_srgb()` 的实现是每次都重新生成：

```python
ImageCms.ImageCmsProfile(ImageCms.createProfile("sRGB")).tobytes()
```

LittleCMS 生成 sRGB 档案时会把**当下时间**写进 ICC 头的 Date/Time 字段（偏移 24–35，
秒位在 34–35）。⇒ 两次调用只要跨过一秒，比较的就是时间戳而不是内容。

坐实它的最小实验（不靠推测）：

```
生成 A → sleep 1.2s → 生成 B
len_equal: True  len: 588
diff_offsets: [35]                     # 正好就是失败信息里的那个 index
all_in_date_field(24..35): True
```

单跑永远绿的原因也一并解释了：毫秒级间隔跨不过一秒；整套跑时前后夹着大量 I/O，跨秒是常态。

## 三、修法 + 两条防复发的钉子

`tests/test_icc_profile.py`：

1. **会话内取一次**：`_ICC_SRGB = ...(tobytes())` 放模块级，`_icc_srgb()` 只返回它 ⇒ 写入端与断言端同源。
2. 钉子一 `test_freshly_generated_profile_differs_only_in_the_header_date()`：
   重新生成的档案与常量相比，差异**只允许落在 24–35**。
   哪天差异跑到别处 ⇒ ICC 生成路径本身变了 ⇒ 本文件所有逐字节比较的假设都要重审（这条是把"成因"变成守卫）。
3. 钉子二 `test_no_other_call_site_regenerates_the_profile()`：本文件**真正调用** `createProfile(...)`
   的行只能有 2 处（常量 + 钉子一）。第三处就是又埋一颗炸弹。
   ⚠ 判据必须走 **AST**：第一版我写成 `src.count("createProfile(")`，被**说明文里的字面量**算成 6 次而误报，
   守卫当场把我自己判红了——LESSONS #316 / #337 的同一课，第三次还是要重新学。
4. 同类普查：全仓 `createProfile` / `ModDate` / `CreationDate` / `date_time` / `xxx.tobytes() ==`
   ⇒ 只命中这个文件，没有第二处「重新生成再逐字节比」的埋点。

复验：3.11 等价环境 与 canonical 3.13 环境各跑一遍，
`test_icc_profile / test_os_portability362 / test_run_all_checks / test_output_fidelity` **88 例双向绿**。

## 四、顺带：两条关于「耗时翻倍」的假设，都被数据打掉

本机整套从 **6 分 47 秒** 变成 **13 分 22 秒**。我按顺序试了两个解释：

| 假设 | 实验 | 结果 |
|---|---|---|
| ① 仓库根堆了 61 个 basetemp（45,255 个文件），拖慢整树扫描类守卫 | 全部**移到** `.scratch/stale_basetemp_20261101/`（可逆，未删）后清空重跑 | 仍 **13 分 09 秒** ⇒ 否证 |
| ② 整机持续负载降频（项目已知的 perf 环境性现象） | 固定负载对照 `ci_env_probe.py --collect-only`（此前实测 20.0 秒） | 现在 **10.6 / 10.7 秒**（更快） ⇒ 与"整机变慢"矛盾，否证 |

⇒ **原因未查明**，本阶段不编解释。可对照的事实：runner 上同一条入口是 **257 秒**且稳定，
比本机任何一次都快 ⇒ 本机数字适合看趋势，不宜当基线；要追这件事，先在空闲时段做
"整套 + 固定负载对照"，两个数一起看才能区分"我的代码变慢"和"机器在忙"。

## 五、可迁移的判据（教训 #339）

- **凡是"重新生成"的产物都不能逐字节比较**：ICC / ZIP 条目时间 / PDF `CreationDate`+`ModDate` /
  PNG `tEXt` 时间戳……判据：比较的**两侧必须来自同一个值**，或显式剔除时间字段再比。
- **单跑绿 + 整套红 ⇒ 先怀疑时间或顺序相关**（跨秒、共享状态、固定 basetemp 名），
  再用固定负载对照区分"代码问题"与"机器在忙"。
- **先测再下结论**：本阶段两个听起来都合理的解释，是被两次测量否证的；文档里写"未查明"比编一个故事有用。
