# 阶段 48 · 孤儿文件扫描与清理（磁盘治理闭环）设计文档

> 项目：AI 智能水印擦除工作台
> 依赖阶段：1–47（含阶段 43 批量删除与二次确认、阶段 46 保留策略可配置化、阶段 47 磁盘占用统计与按体积保留）
> 运行要求：零 torch 可测；Gradio 6.22

---

## 1. 动机与现状

### 1.1 磁盘治理的「两条腿」缺一条

阶段 46 / 47 已经把**历史记录**的治理做完整了：

| 维度 | 配置项 | 作用对象 |
|------|--------|----------|
| 时间 | `CACHE_KEEP_DAYS` | 历史**记录** |
| 条数 | `CACHE_MAX_RECORDS` | 历史**记录** |
| 体积 | `CACHE_MAX_BYTES`（阶段 47） | 历史**记录** |

但三者治理的都是**记录条目**，而**文件**层面从未被回收。二者的差集就是孤儿文件。

### 1.2 孤儿文件是怎么产生的

缓存目录下有两类文件，均由 `services/file_service.py` 定义：

- `cache/thumbs/` —— 缩略图（画廊展示用，256px）
- `cache/uploads/` —— 原图落盘副本（`save_upload()`，供「重新处理」免重复上传）

而项目既有的删除语义**刻意保留文件**：

- 阶段 43 `delete_by_filter()`：只清理缩略图，结果成品图保留（防误删用户资产）。
- 阶段 47 `prune_by_size()`：只清理缩略图与索引条目，成品图保留。
- **原图副本（`uploads/`）从未被任何清理路径回收。**

于是形成稳定累积：索引越干净，孤儿越多。

### 1.3 实测数据（本阶段开发时取自真实工作区）

```
thumbs    :   4886 个,    1.26 MB
uploads   :   6042 个,    0.96 MB
合计      :  10928 个孤儿文件, 2.22 MB
引用路径数:      0 条（历史索引为空）
```

**10,928 个文件、0 条引用**。文件数量本身就是负担：目录枚举、备份同步、杀毒扫描的成本都与**文件数**而非体积成正比。而用户在 UI 上对此**完全不可见**——既看不到，也没有任何入口清理。

> 说明：本阶段工作区体积占比不大（2.22 MB），因为累积的多是测试残留的小图。但在真实使用（尤其视频/批量场景）下，`uploads/` 会按原图尺寸累积，体积增长是线性且可观的。

## 2. 设计目标

- 提供**孤儿文件可见性**：只读扫描 `cache/thumbs` 与 `cache/uploads`，按来源统计「文件数 + 可释放空间」。
- 提供**安全的回收路径**：先扫描预览清单 → 用户勾选来源并二次确认 → 才执行删除。
- **绝不误删**：被引用的文件、用户成品目录（`outputs/` / `exports/`）一律排除。
- 与既有范式对齐：复用阶段 43 的二次确认守卫、阶段 47 的确认复位约定（返回 `gr.update(value=False)`）。
- 抽取共享工具：把阶段 47 埋在 `ui/tab_history.py` 的私有 `_fmt_bytes` 下沉到 `utils.format_utils`，消除重复实现。
- 全程零 torch，分层无反向依赖（`ui→services→core→utils→config`）。

## 3. 关键改动

### 3.1 utils/format_utils.py（新增，共享纯函数）

阶段 47 的 `_fmt_bytes` 是 `ui/tab_history.py` 的私有函数。阶段 48 的设置页同样需要字节格式化，若各自实现一份会导致：

1. 两处格式可能漂移（例如小数位不一致）；
2. 违反「`utils` 承载可复用纯函数」的分层约定。

因此下沉为 `utils.format_utils.format_bytes(n)`：

- 1024 进制，单位 `B / KB / MB / GB / TB`；
- 小于 1024 B 输出整数（更贴合直觉），其余档位保留两位小数；
- **输入容错**：`None` / 负数 / 非数字一律按 0 处理，**绝不抛异常打断 UI 渲染**；
- 零第三方依赖（不导入 gradio / numpy / cv2）；
- 带 `python -m utils.format_utils` 自检（11 组断言）。

`ui/tab_history.py` 的 `_fmt_bytes` 保留同名包装并委托给它，**既有调用方与测试无需改动**。

### 3.2 services/cache_service.py（三个新方法）

放置在 `prune_by_size()` 之后。该模块已在文件头从 `file_service` 导入 `THUMB_DIR` / `UPLOAD_DIR`，**无需新增 import，也不产生循环依赖**（`file_service` 不反向依赖 `cache_service`）。

#### 3.2.1 `referenced_paths() -> set`

遍历 `_records`，收集四类路径字段：

```
original_path（原图副本） / thumb_path（缩略图） /
result_path（结果成品图） / video_path（视频）
```

**并发处理**：先持锁快照 `_records`，再在**锁外**做路径规范化。孤儿扫描涉及上万文件，把字符串处理拖进临界区会阻塞其它标签页的读写。

路径比较前统一 `os.path.normcase(os.path.abspath(p))`，消除 Windows 下盘符大小写与分隔符差异导致的误判。

#### 3.2.2 `scan_orphans() -> dict`

```python
{
  "thumbs"   : {"count": int, "bytes": int, "files": [绝对路径, ...]},
  "uploads"  : {"count": int, "bytes": int, "files": [...]},
  "__total__": {"count": int, "bytes": int},
}
```

- 扫描范围**仅限** `THUMB_DIR` / `UPLOAD_DIR`，用 `os.listdir`（非递归）+ `isfile()` 过滤，天然跳过子目录。
- `outputs/` / `exports/` 是用户可见的成品目录，**不纳入扫描**。
- 纯只读，不删任何文件；单文件 `OSError`（占用/权限）仅跳过，不计入、不删除。

#### 3.2.3 `purge_orphans(origins: Optional[list]) -> tuple[int, int]`

返回 `(删除文件数, 释放字节数)`。

```python
want = set(origins) if origins is not None else {"thumbs", "uploads"}
if not want:
    return (0, 0)
```

**空列表 `[]` 的语义是「未选择 → 不删」**，绝不退化成全删。这是本方法最关键的一条防御：UI 若未勾选任何来源，绝不能因为 `set([])` 为假值而误触发全量删除。

### 3.3 ui/tab_settings.py（磁盘清理面板）

新增函数：

- `scan_orphans_md() -> str`：只读扫描并渲染 Markdown 清单（按来源列出「文件数 · 可释放空间」+ 合计）；干净时返回 `disk_clean.none`；异常时返回 `disk_clean.fail`（**不抛出**，避免打断 Gradio 事件链）。
- `purge_orphans(src_thumbs, src_uploads, confirm)`：返回三元组 `(清单md, 信息文案, gr.update(value=False))`。

UI 结构（紧邻「🗂 历史保留策略」Accordion，默认折叠）：

```
🧹 磁盘清理（孤儿文件回收）           [Accordion, open=False]
  ├─ 说明 Markdown（hint）
  ├─ 清单 Markdown（初始为 need_scan 提示）
  ├─ ☑ 清理缩略图（cache/thumbs）
  ├─ ☑ 清理原图副本（cache/uploads）
  ├─ ☐ ⚠️ 我确认已查看清单，执行清理
  └─ [🔍 扫描孤儿文件]  [🧹 清理所选孤儿文件 (stop)]
```

信息文案分支：

| 条件 | 文案键 |
|------|--------|
| 未勾选确认框 | `confirm_needed` |
| 已确认但两个来源都未勾选 | `need_select` |
| 全部清理成功 | `ok` |
| 部分文件被占用/权限失败 | `partial`（含跳过数量） |
| 异常 | `fail` |

### 3.4 utils/i18n.py（双语键）

新增 `settings.disk_clean.*` 共 16 个键（zh-CN / en-US），并在模块自检区补充双语解析断言与标题前缀断言。

## 4. 安全性设计（核心）

孤儿文件清理是**不可逆的破坏性操作**，本阶段设置了四道防线：

| # | 防线 | 实现 |
|---|------|------|
| 1 | **差集保证** | 只有不在 `referenced_paths()` 中的文件才是孤儿；被引用的文件永远不会被删 |
| 2 | **目录隔离** | 只扫 `cache/thumbs` 与 `cache/uploads`；`outputs/` / `exports/` 用户成品目录完全不纳入 |
| 3 | **二次确认** | UI 必须勾选「我确认已查看清单」；执行后复选框自动复位（`gr.update(value=False)`），防止连点误触 |
| 4 | **执行前重扫** | `purge_orphans()` 内部**重新调用 `scan_orphans()`**，而非复用预览结果——若预览之后新增了历史记录，其引用文件会被重新排除，避免误删刚产生的资产 |

此外：

- **空来源不删**：`origins=[]` 明确表示「未选择」，返回 `(0, 0)`。
- **失败不中断**：单文件删除失败（被占用/无权限）仅跳过并继续，最终以 `partial` 文案告知跳过数量。
- **禁用缓存即空操作**：`enabled=False` 时 `purge_orphans()` 直接返回 `(0, 0)`。

## 5. 与相邻阶段的边界

| 能力 | 阶段 | 治理对象 | 是否删文件 |
|------|------|----------|-----------|
| 保留策略（时间/条数） | 46 | 历史**记录** | 仅删缩略图 |
| 按体积保留 | 47 | 历史**记录** | 仅删缩略图 |
| **孤儿文件清理** | **48** | 缓存**文件** | **删孤儿文件** |

三者互补而非重叠：

- 45/46/47 回答「留哪些历史条目」；
- 48 回答「那些没有任何条目引用的文件怎么办」。

典型联动：用户先按体积清理（47）删掉大量旧记录 → 这些记录的缩略图与原图副本随即变成孤儿 → 再用孤儿清理（48）回收磁盘。

## 6. 测试

新增 `tests/test_orphan_cleanup.py`（21 例，零 torch），覆盖：

**服务层（12 例）**

- `referenced_paths`：四类字段均被收集；同路径去重；`None` 字段忽略。
- `scan_orphans`：被引用文件被排除；按来源分组统计；`__total__` 聚合；跳过子目录；空目录返回 0。
- `purge_orphans`：`None` 清全部；单来源只清所选；**空列表不删任何文件**；被引用文件留存；**执行前重扫（预览后新增引用不被误删）**；禁用缓存返回 `(0,0)`。

**utils（2 例）**

- `format_bytes`：各档位单位 + `None`/负数/非法值容错。
- `tab_history._fmt_bytes` 与 `utils.format_utils.format_bytes` 输出一致（验证委托生效）。

**UI（5 例）**

- `scan_orphans_md`：渲染清单；干净时返回 `none` 文案。
- `purge_orphans`：未确认不删；未选来源不删；确认后正确删除并反馈条数与释放空间；部分成功返回 `partial`。

**i18n（1 例）**：16 个新键中英双语可解析 + 标题前缀断言。

**隔离范式**：`orphan_env` fixture 把 `THUMB_DIR` / `UPLOAD_DIR` / `INDEX_PATH` 全部 `monkeypatch` 到 `tmp_path`，服务层与 UI 层均不触碰项目真实缓存目录。

## 7. 已知边界与后续建议

1. **只治理缓存目录**：`outputs/` 与 `exports/` 是用户成品目录，即使存在无人引用的文件也不纳入清理——这是有意为之的保守策略，避免误删用户资产。若未来要做，必须单独设计「成品图孤儿」入口并配更强的确认。
2. **扁平扫描**：实现用 `os.listdir` 而非递归 `os.walk`，子目录不参与扫描。缓存目录在设计上应保持扁平；若未来引入分层存储，需改为递归并重新评估风险。
3. **扫描成本与文件数成正比**：当前 1 万文件量级耗时可忽略。若缓存增长到十万级，可考虑缓存扫描结果（以目录 mtime 为失效依据）。
4. **未做定时自动清理**：孤儿清理保持纯手动（与阶段 47 的 5 秒定时刷新不同——后者只是刷新只读统计）。自动删除文件风险过高，不引入。
