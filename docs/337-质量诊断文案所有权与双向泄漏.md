# 阶段 337 · 质量诊断文案的所有权：服务层产键，UI 产句子（泄漏是**双向**的）

> 日期 2026-10-26 · 性质：**产品缺陷修复**（334 审计候选②，本轮自己 grep 出第三处消费点）

## 一、修复前那行长什么样（本机实跑，不是推测）

```
language = en-US
line     =     🔎 Quality: pic.png score 75 (warn) — 改动区域过大且结构变化明显，可能修复过头（误伤原图）。
CJK in en-US line = True
zh line  =     🔎 质量评估：pic.png 分75（warn）— 改动区域过大且结构变化明显，可能修复过头（误伤原图）。
zh 里出现英文原值 level = True
```

**同一行里两种泄漏同时存在**：英文界面拿到中文诊断，中文界面拿到英文级别词 `warn`。
审计只报了前一半；后一半（**反向泄漏**）是我读消费点时自己看出来的——
`level` 从来没被翻译过，而 `report_service` 早就有正确写法 `t(f"report.quality_{level}")`
⇒ **同一件事在仓里有三种做法**：报告层翻译、批量页不翻译、CLI 也不翻译。

## 三、修法：文案所有权归 UI，服务层只回「键 + 数字」

1. `services/quality_service.QualityReport`：删掉 `detail: str`（一句硬编码中文），
   换成 `detail_key` / `detail_base_key` / `review_floor`。
   `detail_base_key` 是为了保住**阶段 87 那条语义**：分数跌破复核线时，要同时说
   「低于复核线」和「原诊断是什么」——只改级别不改措辞会产出方向相反的报告
   （level=review 配「修过头」），这个坑当年实测过，改造 i18n 时不能把它弄丢。
2. 渲染收敛成**两个唯一实现**：`level_text(level)`（复用既有 `report.quality_*` 键）与
   `detail_text(report)`（负责 `{score}/{floor}/{base}` 组合）。批量页与 CLI 共用，
   `report_service` 保持自己等价的写法不动（它渲染进 HTML/PDF，键相同、语义相同）。
3. `ui/tab_auto.py` 用新键 `auto.msg.postprocess_gain`（`{before}/{after}/{delta}`），
   数据取自 `evaluate_improvement` **已经返回**的结构化字段——服务层那句 `detail` 不再被任何界面消费。
4. `utils/i18n.py` 新增 `quality.detail_*` 5 键与 `auto.msg.postprocess_gain`，中英对称
   （`validate_i18n_parity()` 是既有构建期守卫，占位符名两侧必须一致）。

**CLI 的边界如实说明**：`cli.py` **完全没有 i18n 层**（不 import `t`、没有 `--lang`），
它自己的中文标签（「质量分」「需关注的结果」）本轮**没动**——那是「CLI 要不要国际化」的产品决策，
不是这次泄漏修复的范围。本次只让它**不再把英文原值和中文句子混着打**（`level_text` 后中文 CLI 显示「告警」）。

## 四、判据：语言切换 + CJK 扫描（LESSONS #72 终于落到这一层）

`tests/test_quality_i18n337.py`（8 例）：

* `test_report_carries_no_sentence`：四种改动比例下，报告对象里**不许再有中文字符串**，
  且 `detail` 字段必须已经不存在（`assert not hasattr(rep, "detail")`）——防「句子又流回界面」。
* `test_level_text_is_translated_both_ways`：en 侧零 CJK 且不回退成键名；zh 侧必须有中文、
  且**不许出现英文原值**（反向泄漏就是靠这条钉住的）。
* `test_batch_log_line_has_no_cjk_under_en` / `test_auto_postprocess_gain_is_translated`：
  断言的是**用户实际看到的那一行**，不是中间字段。
* `test_forced_review_keeps_the_original_diagnosis`：复核叠加时中英两侧都要带原诊断（守 87 的语义）。
* `test_i18n_parity_still_clean`：新键中英对称。

## 五、留下的开放项

* `cli.py` 整体没有 i18n 层（中文标签硬编码）。要不要给 CLI 加语言开关，是产品决策，登记未做。
* 本轮**没有**加「AST 扫 CJK 字面量」那种整族守卫：`services/` 与 `ui/` 里有大量**日志**中文
  （`log.warning("质量评估失败…")`），静态判据要么误报一片、要么就得把 `log.*` 排除掉——
  排除规则本身又是一种「手抄清单」。改用**行为级**判据（语言切换 + CJK 扫描）更准，也更难被绕过。
  若将来要做整族守卫，正确的切入口是「哪些字符串会流到界面」的数据流，而不是「哪个文件里有中文」。
