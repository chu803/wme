### D1 危害：把调用方 bug 伪装成合法配色

模块 docstring 的设计原则写得很清楚：

> **不静默返回黑色：静默兜底会把配色错误伪装成"看起来正常"**

而 `str(hex_color)` 正是同一类伪装——只是方向相反（不是兜底成黑色，而是兜底成"另一个颜色"）：

| 输入 | 修复前结果 | 真实意图 | 后果 |
|---|---|---|---|
| `123456`（int） | `(18, 52, 86)` | 写错的 `#123456` 或十进制度量 | 静默错色 |
| `True`（bool） | 见下 | — | 静默错色 |
| `Fake()`（`__str__` 返回 hex） | `(37, 99, 235)` | — | 任意对象可混入 |

且**报错信息误导**：`hex_to_rgb((37, 99, 235))` 报「长度应为 3 或 6」，
而真实原因是**类型错**——把变量传错函数的调用方会被这条信息带偏。

### D3 危害：内部空白制造「长度对、字符也对」的假象

首尾空白已被 `strip()` 处理，内部空白则让 `int(" 4", 16)` 成功（前导空白被容忍）：

```
"#12 456"  → len(s)=6 → int("12",16)=18, int(" 4",16)=4, int("56",16)=86 → (18,4,86)
```

口径不自洽：`"#2563e\t"`（尾部制表符，strip 后长度 6）**通过**，但 `"#12 456"` 也**通过**——
一个是有意缩进、一个是笔误，实现无法区分，索性都该拒绝。

### 危害窗口与「无守卫」判据

`tests/test_ui_audit91.py::test_brand_hex_to_rgb_rejects_garbage` 只测了
`("#12345", "#gggggg", "", "not-a-color")` —— **类型错与内部空白两类零覆盖**。
即阶段 83 判据成立：改坏它没有任何自动化会失败。

## 二、最小修复（utils/brand.py）

1. **入口类型检查**：非 `str` 抛 `TypeError`，错误信息**指出真实类型**（便于定位调用方 bug）。
2. **内部空白检查**：`strip()` 之后若 `any(ch.isspace())` 抛 `ValueError`（首尾空白仍容忍）。
3. **docstring**：补「阶段 141 修复」段说明两处静默伪装；`HEX_TOKENS` 注释补「构建期快照」语义。
4. **自检**：补两组断言（4 种非字符串 → `TypeError`；3 种内部空白 → `ValueError`；首尾空白仍通过）。
