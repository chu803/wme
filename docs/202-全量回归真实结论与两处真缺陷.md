# 阶段 202 · 全量回归拿到真实结论（19 失败 = 3 真缺陷 + 16 环境连坐）

> 阶段 201 留的缺口：「沙箱内跑不了全量回归」。本阶段用**充足超时**（3000s）跑完了
> 完整的 2500 个 CI 子集用例，拿到了缺失的那个结论，并因此发现 **2 处真实缺陷**
> （其中 1 处是 198 阶段遗留的锚点腐化）。

## 一、阶段 201 结论的修正：全量其实跑得完

阶段 201 我断言「沙箱内跑不了全量回归」，理由是「pytest 收尾清理数千临时文件必撞护栏」。
**这个判断不准确**——真实情况是：

- 全量跑**能跑完**（约 10 分钟），退出码 1，**19 个失败**（不是 2400+ ERROR）；
- 撞护栏的是**个别测试的删除操作**，不是 pytest 的收尾清理。

⇒ LESSONS 201 里「第二次运行 2400+ E」那个现象另有其因（固定名 basetemp 复用），
但**全量跑本身可行**。诚实边界应该写成「全量需 10 分钟且有 16 个用例因删除闩锁
不可判」，而不是「跑不了」。

## 二、19 个失败的归因

| 类别 | 数量 | 详情 |
|---|---|---|
| **★真实缺陷** | **3** | `test_main_entry` × 2（`_Args` 桩腐化）、`test_docs_index` × 1（新文档未登记 INDEX） |
| 环境连坐（删除闩锁） | 16 | `orphan_cleanup` / `utils_audit90` / `cache_service_audit132` / `cache_disk` / `history_batch_delete` / `model_manager_download` / `legacy_selfcheck::api.py` |

### 「删除闩锁连坐」的机制（LESSONS 202 的延伸）

本沙箱的删除护栏是**两段式闩锁**：一旦某次删除被拒，**此后所有删除操作直接
`SystemExit(1)`**——连单个文件也不例外。实测证据：

```
[SAFE_DELETE_BULK_REJECTED] {"count":50,"threshold":50,"scope":"turn",
  "targets":[..."\\.pytest_170216_s\\test_download_success_removes_0\\ok.pt.bak"],"targetCount":1}
sitecustomize.py:826: SystemExit: 1
```

注意 `count:50 / targetCount:1`：**目标只有 1 个文件，但此前会话里累计计数已达 50**，
所以仍被拒。而报错消息**始终指向最初那个已被搬走的路径**（`os.rename` 归档后路径已不存在）
——这是缓存裁决，**极具误导性**。

⇒ 连带后果：`test_legacy_selfcheck::test_module_selfcheck[api.py]` 也失败，
但它的报错里出现的是**另一个早已归档的目录**（`.pytest_170216_s/...`），
与本次执行毫无关系。**这是「报错文本指向错误对象」的第二个实例**（同 LESSONS 215）。

## 三、真实缺陷 1：`_Args` 桩腐化（198 阶段遗留）

### 现象

```
AttributeError: '_Args' object has no attribute 'api'
  main.py:436: in main
```

### 归因

阶段 198（D1-Stage 2）给 `main.py` 加了 `--api` 分支，`main()` 开始读
`args.api` / `args.api_host` / `args.api_port`；而 `tests/test_main_entry.py` 的
`_Args` 桩**只列了 3 个属性**（selftest / no_download / skip_check）。

`main.py` 读 6 个、桩有 3 个 ⇒ 缺 3 个。

**为什么 198 没发现**：198 只跑了自己新增的 3 个文件，没跑 `test_main_entry.py`。
这正是 LESSONS 208「新增脚本必须跑全量回归」要防的事——**全量回归不是形式要求，
它真的抓到了跨阶段的锚点腐化**（同 LESSONS 183）。

### 修法（含一次自我纠错）

**第一版（错的）**：让桩从 `m.parse_args([])` 取基线 ⇒ **引入 5 个新失败**：
`TypeError: <lambda>() takes 0 positional arguments but 1 was given`
——因为本文件多处用 monkeypatch 把 `parse_args` 替换成 **0 参 lambda**，
桩构造时反向调用它就炸了。**自引用比原缺陷更糟。**

**第二版（对的）**：桩显式列出 6 个属性 + **新增对账守卫**：

```python
def test_args_stub_covers_every_cli_flag():
    """桩的属性集必须与 main.py 定义的全部 CLI 参数**对账一致**。"""
    flags = set(re.findall(r'add_argument\(\s*[\'"](--[A-Za-z0-9_-]+)', _src))
    derived = {f[2:].replace("-", "_") for f in flags}
    assert not (derived - stub)      # 不许缺
    assert not (stub - derived)      # 也不许多（桩自己腐化）
```

守卫**与真值来源对账**（解析 `main.py` 源码），而非「再手抄一份」——
手抄清单会随下次加参数再次腐化（LESSONS 196）。

**反例有效性已验证**：删掉桩里的 `self.api` 后，守卫精准报错——

```
AssertionError: _Args 桩缺少 main() 会读取的属性：['api']
（CLI 参数 ['--api', '--api-host', '--api-port', '--no-download', '--selftest', '--skip-check']）
```

### 结果

`tests/test_main_entry.py` **13/13 全绿**（原 10 用例 + 新增 1 守卫）。

## 六、诚实边界

**16 个删除类用例的判定仍未完成**。沙箱的删除闩锁是**会话级**的，一旦触发就
`SystemExit(1)`，本会话内无法再跑任何涉及删除的测试；我按规则未重试或变通。

⇒ 这 16 个用例的真实状态**未知**（很可能全绿，因为 `orphan_cleanup` 单独跑过 21/21
但那次已在闩锁触发前）。需要在**沙箱外 / CI** 跑一次确认。

## 七、教训 → LESSONS 216

**① 「环境跑不了」是结论，不是借口——先把超时给足再下结论**。阶段 201 我用
590s 超时跑全量，**超时后**就宣称「跑不了」；本阶段给 3000s 后**跑完了**（10 分钟），
拿到 19 个失败的确切清单。判据：**「超时/被拒」只说明「这一次没跑成」，
不等于「跑不了」**；两者之间隔着一条「有没有给足资源」的差距
（同 LESSONS 188「量测≠决策」）。

**② 两段式删除闩锁会让「报错文本指向错误对象」**——闩锁触发后，**任何**删除都
`SystemExit(1)`，且消息里的路径是**最初被拒那个**（可能已被 rename 归档、不复存在）。
本例中 `test_legacy_selfcheck::api.py` 的失败信息指向另一个目录，
与本次执行毫无关系。判据：看到 `SAFE_DELETE_BULK_REJECTED` 出现在**与当前测试
无关的路径**上 ⇒ 是闩锁连坐，不是该测试的问题（同 215：不看名字看形态）。

**③ 防腐烂守卫要等到全量跑才生效**——`test_docs_index` 完美抓到了我连续三个阶段
的文档漏登记。这说明：**只跑局部时，跨文件的守卫处于「未被触发」状态**，
不能因为「我跑过的都绿」就认为整体健康（LESSONS 208 的真正理由）。
