# 阶段 85 · 无参考质量分的梯度特征爆炸与语义修复

> 一个**全量套件里的 `MemoryError`** 牵出的缺陷：`core/quality._features` 的
> 「区域内梯度」特征从阶段 56 起就**从未按设计工作**——既算错（语义），又爆内存（资源）。
> 本阶段只做一件事：把它修对，并补上「规模」这一维度的守卫。

阶段 84 完成后按铁律跑全量测试，出现 1 例失败：


三点值得注意：

2. 该用例是 `dual_run=True` 的端到端，唯一会真正走到 `no_reference_inpaint_score` 的 API 测试；
3. 640² 的输入，竟要**3.9 GiB** 的数组——规模完全不合理。

## 2. 根因：掩码的 dtype 决定了索引的语义

`_features` 里取「区域内部梯度」的原始写法：

```python
in_gx = (bin_mask[:, :-1] & bin_mask[:, 1:])          # 左右都在区域内
g = np.concatenate([gx[in_gx].ravel(), gy[in_gy].ravel()])
```

而 `bin_mask` 在**真实调用链上是 uint8**：

- `core/image_utils.threshold_mask` 返回 `cv2.threshold(..., 255, THRESH_BINARY)` → **uint8 0/255**；
- 检测器掩码同为 uint8；`core/inpainter.py:435` 的 `bin_mask` 即来自它。

于是 `bin_mask[:, :-1] & bin_mask[:, 1:]` 得到的是 **uint8 数组**（值 0/255），
numpy 把它当**整数花式索引**——`gx[in_gx]` 的意思是「逐个位置取第 0 行 / 第 255 行」，
而不是「取布尔为真的位置」。

### 2.1 形状演算（与报错逐位吻合）

| 量 | 形状 | 元素数 |
|---|---|---|
| `gx` | (640, 639) | 408,960 |
| `in_gx`（uint8） | (640, 639) | — |
| `gx[in_gx]` | **(640, 639, 639)** | 261,325,440 |
| `gy[in_gy]` | **(639, 640, 640)** | 261,734,400 |
| 拼接结果 | (523059840,) | **523,059,840** ✓ |

探针逐位复现（同一构造下，布尔索引只有 **19,800** 个样本）：

```
in_gx dtype: uint8   shape: (640, 639)
gx[in_gx] shape: (640, 639, 639)   elements: 261325440
gy[in_gy] elements: 261734400
TOTAL: 523059840  | 布尔版本: 19800
```

### 2.2 后果一：语义全错（更隐蔽）

整数索引取的是 `gx` 的**第 0 / 第 255 行**、`gy` 的第 0 / 第 255 列——
**与掩码在图上落在哪里完全无关**。也就是说：

> 「梯度只统计区域内部、以消除边界偏置」这一设计**从阶段 56 起就没有生效过**。

值得一提的是：`_features(source, ring)` 里的 `ring` 是**布尔**（`(ring > 0) & (mask_bin == 0)`），
所以**背景环一侧的特征是对的、修复区一侧是错的**——同一函数两种语义混用，更难察觉。

### 2.3 后果二：资源爆炸（反而是"救星"）

| 图像 | 拼接结果元素数 | 单次分配 |
|---|---|---|
| 640² | 5.23 亿 | **3.90 GiB**（+ 两个 2.09 GB 中间量，峰值 ~8.4 GB） |
| 1024²（真实 AI 图） | 13.4 亿 | **~17 GiB → 必然 OOM** |

所以 `INPAINT_DUAL_RUN` / 双跑择优在**真实尺寸上根本跑不起来**——
阶段 74 交付的「择优」在真实图上是一个会 OOM 的能力。
**某种意义上这是运气：没有这个 OOM，语义错误会一直潜伏下去。**

### 2.4 为什么全部单测都漏了

`tests/test_quality.py` 全部用 **64×64**：

```
64² → (64,63,63) + (63,64,64) = 254,016 + 258,048 = 512,064 个元素 ≈ 4 MB
```

不报错、不慢、结果还是「确定性」的——**规模本身是判据的一部分**，
而旧测试恰好把规模这一维消掉了。

## 3. 修复：单一实现 + 先规整为布尔

`core/quality.py` 抽出 `_interior_gradients(ch, bin_mask)`，把「区域内部」的判定
收成唯一实现，并在入口统一 `inside = bin_mask > 0`：

```python
def _interior_gradients(ch, bin_mask):
    inside = bin_mask > 0                       # ← 关键：无论 uint8/bool/float，一律布尔
    gx = np.abs(np.diff(ch, axis=1))            # (H, W-1)
    gy = np.abs(np.diff(ch, axis=0))            # (H-1, W)
    in_gx = inside[:, :-1] & inside[:, 1:]      # 左右都在区域内
    in_gy = inside[:-1, :] & inside[1:, :]      # 上下都在区域内
    return np.concatenate([gx[in_gx].ravel(), gy[in_gy].ravel()]).astype(np.float64)
```

`_features` 亦改用 `inside = bin_mask > 0` 取 `region`（原先 `ch[bin_mask > 0]` 本就正确，
现统一到同一变量，消除「同一函数两种 dtype 语义」的隐患）。

**修复是纯增量的语义收口**：不改阈值、不改公式、不改调用方签名。

## 6. 行为影响审计：分数变了，择优结果变了吗？

`no_reference_inpaint_score` 有四个真实调用点，改分数必然可能改变决策：

| 调用点 | 用途 | 影响 |
|---|---|---|
| `core/inpainter.py`（dual_run） | 双跑择优 | **决策可能变化** |
| `services/postprocess_service.py` | 自动回退网（阶段 61） | 回退判定可能变化 |
| `scripts/validate_selector.py` | 一致性校验 | 见下 |
| `scripts/quality_gate.py` | 仅展示列（不进红线） | 无判定影响 |

**逐用例 before/after（seed=1，8 用例）**——用 monkeypatch 注入旧实现，同协议对照：

| 用例 | OCV ΔPSNR | LaMa ΔPSNR | 修复前判选 | 修复后判选 |
|---|---|---|---|---|
| gradient 极淡平铺 | 12.95 | 10.28 | **opencv ★** | **lama ✗** |
| textured 极淡平铺 | −3.25 | −0.45 | **opencv ✗** | **lama ★** |
| 其余 6 例 | — | — | — | 不变 |

- **2/8 用例的择优结果发生翻转**，净值仍为 **5/8 = 62.5%**；
- 即：这是一次**真实的行为变化**（不是纯重构），但**决策力总量未变**。

### 6.1 顺带否证一个旧结论：「8/8」不可复现

README §6 与 `docs/56-*` 记载「阶段 56 修复后 1 种子 8 用例一致率 **8/8（100%）**」。
本次**两种实现（修复前 / 修复后）在当前代码上都只得到 5/8**：

- 说明该结论**在阶段 57~84 的检测/修复演进中早已失效**，只是从未有人重跑；
- 与本次修复**无关**（注入旧实现同样是 5/8）；
- 当前诚实口径：**seed 1 = 5/8（62.5%）；4 种子 32 用例 = 16/32 = 50.0%**。

**这对阶段 74 的结论是负面的**：无参考质量分在合成数据上的**辨析力仅相当于随机**，
远低于「恒定选 OpenCV」（合成数据上 OpenCV 8/8 占优，恒定策略可达 100%）。
因此 **`INPAINT_DUAL_RUN` 维持默认关闭（opt-in）** 的原有决定**得到更强支持**，
而 README 中「一致率 8/8」的表述需就地修正（见 §7）。

## 8. 通用经验（并入 MEMORY）

**44. 索引数组的 dtype 决定语义。** `arr[idx]` 中 `idx` 是 bool 才是掩码，是 uint8/int 就是
**取行号**。凡把「掩码」传给 numpy 索引，入口必须**先规整为布尔**；
`mask > 0` 是唯一安全写法，且应在**单一实现**里做一次（经验 24 的同族）。
判据：`np.bool_` 还是 `np.uint8`？——**一字之差，静默取错行**。

**45. 测试的「规模」也是判据的一部分。** 64² 下 5.23 亿的爆炸只剩 51 万元素，
缺陷必然漏网。资源类/复杂度类缺陷必须用**真实尺寸**（这里是 640²）构造用例；
判据可以不是时间，而是**可解析的结构量**（样本数）与 `tracemalloc` 峰值。

**46. 同一行代码可以同时错语义、错资源，而资源错误是发现语义错误的入口。**
若没有 OOM，取错行的语义问题会永久潜伏（结果"确定性且有区分度"，看起来完全正常）。
因此**性能/内存异常要当作正确性线索追**，而不是当成环境问题忽略。

**47. 改分数就要审计决策层。** 任何被打分函数都必须在改动后做**逐用例 before/after**，
因为「总数不变」不等于「结果不变」——本阶段 2/8 翻转、净值 5/8 不变。
**只跑单测通过 ≠ 交付语义未变。**

**48. 陈旧结论会在无关改动中被"顺带复活"。** 为本次修复做对照时顺手重跑了
`validate_selector.py`，才发现文档的「8/8」在当前代码上**两种实现都不可复现**。
**给结论做守卫的最好时机，是下一次因为别的原因重新运行它的那一刻**——
重跑旧脚本时，务必把「结果与文档是否一致」也当成一个断言。

## 9. 剩余边界

- `no_reference_inpaint_score` 的**真实图选优效力仍未验证**（无真实图 ground truth），
  本阶段只证明它「计算正确、代价可接受」，**不证明它选得对**；
- 合成数据上辨析力 ≈ 随机（16/32），已如实记录；是否改用「正交指标交叉验证」（经验 27）
  属后续课题；
- 本次只修 `_interior_gradients` 一处；`_features` 的 mean/std 分量本就正确。
- `quality_score` 仍仅作门禁展示列，**未纳入任何红线**（它依赖启发式分数，不宜作红线）。
