# 阶段 306 · D1 真实 GPU 并发吞吐实测（RTX 5060 / cu128）

> 收口「API 并发实测」：在真机 RTX 5060 上跑通 `scripts/d1_concurrency_probe.py`（阶段 299 脚手架），
> 对**同步 API 路径**（`api.remove_watermark_bytes` 全链路 detect+inpaint）做并发扫描，
> 给出吞吐 / 尾延迟 / 峰值显存曲线，验证默认 `API_MAX_CONCURRENCY=4`（HTTP 并发闸门）
> 与 `API_ASYNC_MAX_WORKERS=2`（异步作业池）在真实负载下的合理性。

---

## 一、测什么 / 怎么测

- **被测路径**：同步 API 入口 `api.remove_watermark_bytes`（HTTP 处理器实际调用的函数），
  经 `ThreadPoolExecutor` 并发提交，直接复刻「N 个并发请求打到同步处理器」的形态。
  由于 Python GIL + Torch 默认 CUDA 流，**GPU 计算实质串行化**——这正是真实 HTTP 并发下的
  计算并发上限；HTTP 层本身仅增加 ~ms 级解析/序列化开销（相对 ~10s 的 GPU 工作量可忽略）。
- **设备**：RTX 5060 Laptop（Blackwell sm_120，8123 MiB），`device=cuda`，torch 2.9.1+cu128。
- **负载**：`benchmark_real/images` 12 张（10×2048² + 2×1024²，全为真实 AI 水印图），
  `auto_preset=True` + `allow_auto_erase=True`，即生产默认行为。
- **扫描**：worker ∈ {1, 2, 4, 8}，每档 12 请求（轮转铺满），`--no-warmup`（首请求也计入，
  更贴近冷用户真实体验）。原始数据：`docs/quality/api_concurrency_rtx5060.json`。

## 二、实测结果（RTX 5060，full 全链路）

| worker | 吞吐(img/s) | P50(s) | P95(s) | max(s) | 墙钟(s) | 相对串行吞吐 |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 0.132 | 7.989 | 12.594 | 14.752 | 90.90 | 1.00× |
| 2 | 0.257 | 7.444 | **10.163** | 18.924 | 46.75 | 1.95× |
| 4 | **0.331** | 11.085 | 14.871 | 21.403 | 36.29 | **2.51×** |
| 8 | 0.287 | 22.227 | 40.100 | 41.781 | 41.79 | 2.18× |

**峰值显存（全档累计 max）：6543.2 MB ≈ 8123 MiB 的 80.5%**（峰值出现在 worker=8 档）。

### 读图
- **吞吐甜点 = worker=4**：2.51× 优于串行；worker≥4 后收益递减，worker=8 **反而回落**（0.287 < 0.331），出现饱和悬崖。
- **尾延迟（P95）甜点 = worker=2**：10.16s 为全局最低；worker=4 升至 14.87s（+47%），worker=8 崩到 **40.1s（≈4×）**。
- **worker=8 是脚枪**：吞吐回归 + P95 翻 4 倍 + 峰值显存冲到 80.5%——三指标同时恶化，明确过饱和。

## 三、与 D1 两杠杆的映射与结论

D1 是两个独立杠杆（见 `docs/199-REST并发闸门.md` / `docs/257-D1异步作业worker池并发标定.md`）：

1. **HTTP 并发闸门** `API_MAX_CONCURRENCY`（默认 **4**，范围 [0,64]）：限制同时进入同步处理器的请求数。
   本实测显示 GPU 计算并发甜点恰在 4（吞吐最高、未到悬崖）→ **默认值 4 站对了位置**，既吃饱 GPU 又不越界。
2. **异步作业池** `API_ASYNC_MAX_WORKERS`（默认 **2**，范围 [1,8]）：只管 PDF/视频/模型下载等长任务。
   本实测（同步 API 路径，本地单用户最相关的是「我的图多久好」= 尾延迟）显示 **worker=2 的 P95 最优（10.16s）**
   → **默认值 2 对单用户延迟优先场景仍然成立**。吞吐优先可上探到 4（2.51×），代价 +47% P95。

**结论：两个默认值在真实 GPU 负载下均合理，无需改动。**
- 保持 `API_MAX_CONCURRENCY=4`（吞吐甜点、避悬崖）；
- 保持 `API_ASYNC_MAX_WORKERS=2`（单用户延迟甜点）；吞吐优先场景用户可上调至 4（仍需在 [1,8] 内）。

## 四、自反证伪与诚实边界

- ⚠️ **并发甜点与显存上限是工作负载相关的，不可把一个负载的结论外推**：
  阶段 257 标定 `API_ASYNC_MAX_WORKERS=2` 时，负载是 **2 页 PDF @1200×900**，k=4 峰值仅 **1272 MB（16% 卡容）**，
  据此称「k=4 仍仅 16% 卡容、安全余量充足」。本实测负载是 **2048² 整图水印**（裁剪修复对整帧水印无效，
  仍走 2048² 推理，见日志 `裁剪到水印包围盒 2048x2048（占图 100.0%）`），worker=8 峰值 **6543 MB（80.5%）**——
  同样并发数下显存差 **5×**。故「16% 卡容」仅适用于小图/局部水印负载；**大图整帧水印在 worker=8 已逼近危险区**。
- **worker=8 在重负载下是脚枪**：吞吐回归 + P95 40s + 显存 80.5%。这暴露 `API_ASYNC_MAX_WORKERS` 上限
  [1,8] 的高位对重负载过于宽容；但当前默认 2 安全，仅当用户主动调到 8 且喂大图时才触雷，
  故**不收缩区间**（保留可调性），仅在本文档与记忆中标注警告。
- 探针只覆盖「同步 API 全链路 detect+inpaint」一种负载，**未覆盖**异步作业（PDF/视频，阶段 257 已单独标定）
  与模型下载（网络瓶颈、几乎不占 GPU）。两条路径结论不冲突：同步路径甜点=4/2，异步路径甜点=2（257）。
- 探针并发由 `ThreadPoolExecutor` 模拟，非真 HTTP 套接字；HTTP 层额外开销相对 ~10s GPU 工作量可忽略，
  故本数据是「计算并发上限」而非「HTTP 栈开销」测量——后者在本工具场景无决策意义。
- 真实 GPU 负载的正确性由阶段 256 守卫背书；本阶段只测**并发吞吐曲线**，不重跑重负载质量门禁。
