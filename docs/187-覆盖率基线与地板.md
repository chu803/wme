### 1.2 三个可直接行动的发现

1. **`main.py` 覆盖率 0.00%**：Gradio 入口的**装配段从未被任何测试 import**
   ——「UI 能启动」这件事目前只靠人工点开验证（`ui/*` 内部倒是有覆盖）。
   建议：加一条「冒烟 import + 构建 Blocks 对象（不 launch）」的用例。
2. **`ui/tab_batch.py` / `ui/tab_media.py` 是全仓最低的两块产品代码**（≈55%），
   而它们正是「批量」「视频/PDF」两条最重链路 ⇒ 与 `docs/185` 的「产品化 D」相互印证。
3. **门禁脚本的 `main()` 编排段普遍未覆盖**（`quality_gate` 62%、`prompted_area_gate` 39%）：
   真正跑门禁的是子进程，pytest 里测的多是纯函数 ⇒ 这类缺口属**方法论固有**
   （不是「忘了写测试」），登记时不要与真缺口混为一谈。

## 2. 统计口径（`.coveragerc`）

- 只统计产品代码：排除 `tests/`、`conftest.py`、`scripts/_verify_clean_probe.py`
  （本地验证器）、`__pycache__`、`.workbuddy/`、`.pytest_*`、`cache/exports/outputs/temp/build/dist`。
- **语句覆盖**（暂不开分支覆盖）：先拿基线，分支覆盖待基线稳定后评估（先测量、后收紧）。
- `exclude_lines`：`pragma: no cover` / `if __name__ == "__main__":` / `raise NotImplementedError`。

### ⚠ 口径坑（本阶段实测，已写进配置注释）

pytest-cov 默认使用**并行数据**（`.coverage.<host>.<pid>…`），并在收尾 `combine()` 时
**删除**这些文件。在受限沙箱里删除会撞「单轮批量删除」护栏（> 50 即拒）⇒ coverage 收尾抛
`SystemExit` ⇒ **pytest INTERNALERROR、报告整体丢失**（实测：用例跑到 97% 才崩）。
⇒ `.coveragerc` 显式 **`parallel = False`**，此后只写单个 `.coverage`，**无删除动作**。

## 3. 地板与用法

- **地板 `COVERAGE_FLOOR = 67`**（`scripts/run_all_checks.py`）：
  标定依据 = 实测 75.29% × ≈0.90 向下取整。理由：既拦住「覆盖率明显下滑」，
  又不因**环境差异**误红（换机器会改变 skip 集合 ⇒ 分母与结果都会变）。
- 用法：
  ```
  python scripts/run_all_checks.py --cov --full      # 全量 + 覆盖率地板判定
  ```
  地板由 pytest 原生 `--cov-fail-under` 执行——**不另写一份判定逻辑**（单一真值来源）。
- 报告落点：`htmlcov/`（已在 `.gitignore` 内）。

## 4. 边界（如实登记）

- **CI 子集覆盖率尚未测量**：CI 跑 `-m "not torch_required and not network"`，
  其分母与结果都不同于本阶段的 `--full` 口径。**故 CI 暂不启用 `--cov`**
  （用一个没量过的数字去判定 ⇒ 假红）。待下一轮先测出该口径的数字再启用。
- **端到端 `--cov` 冒烟本轮未跑通**：本会话的沙箱「批量删除」护栏已被闩锁
  （报错指向一个**已被改名搬走**的路径 ⇒ 缓存裁决），coverage 的任何收尾动作都会被拒。
  `--cov` 的参数装配已由 `tests/test_run_all_checks.py` 的单测覆盖；**真实跑一次**
  留待护栏复位的下一轮（与 `docs/183` §4.1 同一环境边界）。
- 未覆盖的合理部分（`download_model.py` 需网络、`superres/device_manager` 需 GPU 权重）
  **不应**通过写「假装测试」去刷分——若纳入统计范围，应显式 `pragma: no cover` 并写明理由。
