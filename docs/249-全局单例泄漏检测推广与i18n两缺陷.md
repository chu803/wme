## 2. 真缺陷 ①：派生路径被全局缓存（产品缺陷）

`utils/i18n.py::_state_path()`（修复前）：

```python
global _STATE_FILE
if _STATE_FILE is None:
    d = config.CACHE_DIR ...
    _STATE_FILE = os.path.join(str(d), "i18n_state.json")   # ← 派生路径烤死在全局
return _STATE_FILE
```

`CACHE_DIR` 被 conftest 每用例重定向 ⇒ **第一个触发语言持久化的用例**把它的
tmp 路径烤进全局；此后**同进程内所有** i18n 状态读写都指向那个**随后被清理**
的目录。真实运行时 CACHE_DIR 不变所以无感——但任何「运行中改缓存目录」的
场景都会**静默写错位置且永不自愈**。

**修法**：`_STATE_FILE` 改为**显式覆盖钩子**——默认 `None`（每次跟随
CACHE_DIR 现算，成本=一次字符串拼接），显式赋值才生效（测试/自检重定向用，
monkeypatch 自动还原）。语义更正确：**可变的派生值不该被缓存**。

**为什么这值得修**：248 的检测器抓到的表象是「批末 `_STATE_FILE` 残留 tmp 路径」，
顺着查下去发现的却是**产品代码缺陷**——这正是「测试卫生审计」的价值路径：
测试环境的异常暴露了产品在配置可变场景下的隐藏假设。

## 3. 真缺陷 ②：收集期污染（测试缺陷）

5 个文件（compare_viewer / history_filter / pdf_history / recommend_view /
validators_media）在**模块级**调 `set_language('zh-CN')`：

- 模块级代码在 **pytest 收集期**执行，**先于一切夹具** ⇒ conftest 的
  `_isolate_i18n_language` 只能「保存已污染的值再还原」，**结构上挡不住**；
- 实测表象：检测器报 `_LANG: None → 'zh-CN'`（import 默认是 None）。

**修法**：移入文件内 autouse 夹具（`_lang_zh`）。顺序由 pytest 契约保证：
conftest 夹具（上层）先实例化、逆序终结 ⇒ 快照在「设置 zh-CN」**之前**、
还原在其**之后** ⇒ 每个用例拿到 zh-CN 且收集期零副作用。5 文件 62 例全绿。

## 4. 检测器两版迭代（假阳性教训）

| 版 | 设计 | 问题 |
|---|---|---|
| v1 | deepcopy 快照 + 值比较 | **两类系统性假阳性**：① 对象含锁/流 ⇒ deepcopy 失败被丢弃 ⇒ 误报 `<gone>`（`_cache_singleton`）；② 无 `__eq__` 的对象，deepcopy 副本 vs 原对象**必然不等** ⇒「没变也报变」（plugins/model_manager/device_manager 全军覆没） |
| **v2（采用）** | `id + repr[:300]` 指纹，**不 deepcopy** | 同 id ⇒ 看 repr 变没变（抓**原地修改**）；不同 id ⇒ repr 相同=等值替换不算变。已知限制：>300 字符对象尾部变化不可见 |

**泛化教训**：给「任意对象」做状态对比时，**deepcopy+== 不是通用解**——
它对「含锁对象」崩、对「无 `__eq__` 对象」假阳。`id+repr` 指纹是更稳的通用口径
（repr 是 Python 对象事实上的自描述）。

## 5. 复用 basetemp 的隐藏杀手（第三次踩「快得反常」）

检测器 v1/v2 的全库跑都出现 **1m51s「完成」17 批**（单批真实 33s × 17 = 应 ~9min）。
真因：每批用**固定名** basetemp（`.pytest_mm00`…），上一次运行残留数百文件 ⇒
pytest 启动清空 basetemp ⇒ **safe-delete 批量删除护栏（>50 文件）⇒ SystemExit** ⇒
子进程秒退、rc=1、整批用例没跑——但差异统计「看起来还在出」（只是 import 期差异），
**极易误读成有效结果**。

**修法**：每次运行用**时间戳唯一前缀**（`.pytest_mm{ts}_{批次:02d}`），从机制上
杜绝复用。修复后全库跑 13m18s（与健康基线一致），数据才可信。

**这已是本项目第三次被「快得反常」骗**（244 首次、248 第二次、249 第三次），
且这次的危害最大：**两轮「全库零泄漏」的结论建立在坏数据上**（248 的 `_cfg4` 亦然）。
