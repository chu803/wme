# 阶段 357 · 诊断脚本本身必须**能跑通**（否则"自诊断"只是纸面功能）

> 日期 2026-10-27 · 性质：**守卫**（把阶段 356 的新能力钉住）

## 一、为什么还要这一条

阶段 356 给 CI 加了「各步骤日志尾巴进 Summary 与 issue」，但那段 JS **从没被执行过**
（会话内读不到 GitHub）⇒ 万一它自己抛异常，issue 根本不会生成，我们又会退回"让人截图"。
**没跑过的诊断 = 没有诊断。**

## 二、守卫（`tests/test_workflow_diag_script357.py`）

把 `ci.yml` 里那段脚本**原样抽出来**，在临时目录里放一份假的 `logs/*.log`（含一行
`ERROR: No matching distribution found for numpy==2.5.1`），用 **node 真跑一遍**，断言：

1. 退出码 0、输出里没有 `THREW:`（脚本自己不抛）；
2. **那行错误出现在输出里**（失败原因真的被带出去了）；
3. Summary 写出来了（`SUMMARY_DONE`）、issue 正文构造出来了（`ISSUE:`）。

GitHub 的 `${{ toJSON(steps) }}` 在本地是字面量（node 会报语法错）⇒ 探针里替换成等价 JSON
（真实运行时由 GitHub 替换）。node 不在环境里就 skip（不因缺工具而红）。

## 三、顺带记两个本轮踩到的坑（都属于"跨进程/跨语言"的同一族）

* 用 `subprocess.run(..., text=True)` 读 **node 的 UTF-8 输出** ⇒ 又一次 `UnicodeDecodeError: 'gbk'`
  ⇒ 探针也必须显式 `encoding="utf-8", errors="replace"`（阶段 331 的教训第 N 次应验）；
* YAML 里那段 JS 含 GitHub 表达式 `${{ toJSON(steps) }}` ⇒ **它不是合法 JS** ⇒
  任何"把 YAML 里的脚本抠出来本地跑"的验证都必须先替换它，否则会把**探针的错**当成**产品缺陷**。
