# 阶段 325 · 七道门禁其实不在任何自动链路上（CI/发布覆盖缺口）

> 日期 2026-10-25 · 性质：**核实 → 已实施**（改的是统一入口的默认步骤；CI/发布文件一行没动）

## 一、发现

`.github/workflows/ci.yml` 与 `publish.yml` 都只调用同一条命令：

```
python scripts/run_all_checks.py        # ← 没有 --gates
```

⇒ CI 上跑的是「CI 等价子集 + 两个静态扫描」；`--gates` 里那 **7 道效果/真值门禁**
（`clean_bench_probe`、`quality_gate`、`real_gate`、`perf_probe`、`media_gate`、
`removal_truth_gate`、`corner_signal_gate`）**在任何自动链路上都不跑**，只在本地手动执行。
（本节描述的是**改动前**的状态；§四 已把其中一道提进默认步骤，其余六道留在 `--gates` 是有意为之。）
`publish.yml` 注释里写的「tag → **门禁** → build → PyPI」，实际门禁口径 = CI 等价子集。
这不是新缺陷（315/322a 之前就是这样），但本轮新加两道门禁后，**「门禁」这个词与自动链路的
差距又变大了**，值得显式记一笔，否则下一个人会以为绿过的 CI 包含真值门禁。

## 二、实测：哪一道今天就能进 CI

用 `importlib.util.find_spec` 打桩，把环境伪装成「装了 `requirements-min.txt`、没有 easyocr/torch」，
再跑本轮新增的两道：

| 跑什么 | 无 OCR 环境结果 | 说明 |
|---|---|---|
| `tests/test_removal_truth_gate.py` + `tests/test_corner_signal_gate.py` | **42 例全绿** | 新守卫本身不依赖 torch/OCR |
| `corner_signal_gate.main([])` | **退出码 0**（≈10s，38/49、误命中 0、未匹配恰好 5 条） | 纯 numpy/cv2 信号，**能进 CI** |
| `removal_truth_probe.main(["--gate"])` | **退出码 2** + 一句人话「EasyOCR 不可用…请确认用的是项目虚拟环境的解释器」 | 正确跳过，**不会假绿**（322a 那条守卫的实战验证） |

数据集是随仓库分发的：`git ls-files benchmark_real` = **321 个文件**（含 `images/` 与 `clean/`）
⇒ CI checkout 里就有图，不需要额外拉取。

## 三、其余六道为什么不能顺手加

`quality_gate` / `real_gate` / `clean_bench_probe` / `media_gate` / `perf_probe` 的红线基线
**是在「OCR 在位」的口径下标定的**（319/320e 实测：OCR 会跑遍所有内置预设）。
把它们放到无 torch/无 easyocr 的 CI runner 上，检测通路会降级 ⇒ 数字变了但**不是产品回归**，
结果是「CI 常红」或「逼人重锚基线」。`removal_truth_gate` 同理，且它要 6 分钟 GPU 时间。
⇒ 这些就该留在 `--gates`（本地/带模型的环境），不是漏配。

## 四、已实施（最终形态比上面的建议更对）

原建议是「往 `ci.yml`/`publish.yml` 各加一步 `python scripts/corner_signal_gate.py`」。
实现时**否掉了自己这条**：在入口文件里另写一条验证命令，正是阶段 192 打掉的「入口副本」——
守卫 `test_entry_surfaces_call_the_same_unified_entry` 防的就是这个。正确形态是**提进统一入口的默认步骤**：

- `run_all_checks.build_steps()` 默认段新增第 4 步 `corner_signal_gate`（原先挂在 `--gates` 段，已移走，
  不重复出现——`--gates` 连默认一起跑，写两遍就是跑两遍，有测试钉住）；
- `ci.yml` / `publish.yml` / `test.bat` / `test.sh` **一行都不用改**，自动获得这道守卫；
- 代价：默认口径 +≈10 秒。

风险面逐条核过：

| 担心 | 实际 |
|---|---|
| 缺数据集的机器会不会把 CI 拖红 | `aggregate()` 只把 `rc==1` 判失败 ⇒ 该脚本返回 2 时横幅是 ⏭、总退出码不受影响（**不是假绿 ✅，是看得见的跳过**） |
| CI 到底有没有图 | `git ls-files benchmark_real/images` = **109 个受控文件**（108 张 + `.gitkeep`），`clean/` 27 个；无 LFS，`.gitattributes` 里 `*.jpg binary` ⇒ push 后 CI checkout 就有图，守卫不空转 |
| Linux/无 torch 环境能不能跑 | 实测把 `torch`/`torchvision`/`easyocr` 全部屏蔽后 **rc=0、10.2s**（中文文件名走 `np.fromfile + imdecode`，Linux 原生 UTF-8 更宽松） |
| 会不会又造一份真值来源 | 步骤清单仍只有 `run_all_checks.py` 一处；测试侧同步改的是**断言**（默认清单、不重复、重门禁仍不进默认） |
