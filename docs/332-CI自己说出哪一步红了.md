# 阶段 332 · 让 CI 自己说出「哪一步红了」（不再依赖人截图）

> 日期 2026-10-26 · 性质：**为了拿到证据而做的能力建设**（改 workflow 的诊断步骤；判定链路一行没动）

## 一、卡在哪

328/329/330/331 连着修了四层「说不清的绿」，结果第一次真红（CI #17，45 秒）我**读不到现场**：

- 本机没有 `act`，跑不了 GH runner；
- pip 连不上 PyPI（`from versions: none`）⇒ 复刻不了 CI 那套 `requirements-min.txt` 环境；
- 会话内查 GitHub API 被安全策略拦（`WebFetch` 到 `api.github.com` 直接 blocked，两次）。

⇒ 唯一的外部窗口是用户手动打开 Actions 看步骤列表。**「只有人能看懂」的诊断等于没有诊断**，
而且它把每次排查都变成一次往返等待。

## 二、旧诊断步骤的真实覆盖面（这才是要修的东西）

`ci.yml` / `publish.yml` 里那个 `if: failure()` 的诊断步骤，只读 `gate_output.txt`：

```js
let out = '(no gate_output.txt)';
try { out = fs.readFileSync('gate_output.txt', 'utf8'); } catch (e) {}
```

而 `gate_output.txt` **只有 `entry` 那一步真跑过才存在**。所以：

| 失败位置 | 旧诊断会写什么 |
|---|---|
| `entry`（验证入口） | FAILED 清单，有用 ✅ |
| `checkout` / `python` / `system`(apt) / `deps`(pip) | **`(no gate_output.txt)`** ——一句等于没说 ❌ |

#17 用了 **45 秒**。`entry` 步单跑 `undef_scan+docker_static+corner_signal_gate` 就要 ≈8 秒，
pytest 子集在 CI 上远超 1 分钟 ⇒ **45 秒几乎不可能走到 `entry` 之后**。
⇒ 假设：红在 `entry` **之前**的某一步（`deps` 装包 / `system` apt 最像）。
这只是推断，不是结论；**结论要由下一次红自己说出来**——这正是本阶段要保证的事。
（旧诊断在这种情况下只会写 `(no gate_output.txt)`，所以 331 之前那次红也没人看得懂。）

## 三、改法：把「哪一步红了」做成诊断的第一句话

```js
let stepStatus = {};
try { stepStatus = ${{ toJSON(steps) }} || {}; } catch (e) { stepStatus = {}; }
const rows = Object.entries(stepStatus)
  .filter(([id, v]) => v && (v.conclusion || v.outcome))
  .map(([id, v]) => `${id}: ${v.outcome || v.conclusion}`);
const table = rows.length ? rows.join('\n') : '(步骤状态不可用：请确认每个 step 都有 id)';
```

Summary 与自动建的 Issue 都以这张表**开头**，FAILED 清单跟在后面。两个文件同形改（不留第二套口径）。

配套：给每个 step 补 `id`（`checkout/python/system/deps/entry/diagnose[/buildtools/build/artifact/publish]`）。
**这一步才是关键**——`steps` 上下文只包含**有 id 的步骤**，漏 id 的那一步在状态表里静默消失，
那比没有表更糟（表会骗人）。

## 四、守卫与反例（本机跑不了 CI，就更要把能验的都验掉）

`tests/test_run_all_checks.py` 新增：

1. `test_every_workflow_step_has_an_id`（参数化 = **机械枚举** `.github/workflows/*.yml`，不手抄清单——
   331 刚踩过「手抄的枚举自己也是分布式的」）：每个步骤必须有 `id`；文件里必须仍出现
   `toJSON(steps)` 与「哪一步红了」；切出的步骤数 `>= 5` 才是非空转。
   解析**刻意不用 PyYAML**：CI 只装 `requirements-min.txt`，守卫不能建在可选依赖上。
2. `test_workflow_step_ids_are_unique_per_file`：id 重复会让后一个盖掉前一个 ⇒ 状态表少一行且无声。

反例证明可构造（内存里删，不动工作树）：把 `id: checkout` 那行删掉后跑判据 ⇒
抓到 `- name: 拉取代码` ⇒ **守卫有牙齿**。

YAML 与 JS 都真验过（本机 `yaml.safe_load` + `node` v24）：

```
ci.yml:      YAML 解析 OK，steps=6，  ids=['checkout','python','system','deps','entry','diagnose']
publish.yml: YAML 解析 OK，steps=10， ids=[..., 'buildtools','build','artifact','publish']

# 把诊断 JS 抽出来、用桩替换 core/github 后实跑三种 payload：
{"checkout":{"outcome":"success"},"entry":{"outcome":"failure"}}
   → HEADING: CI 门禁失败 · 哪一步红了 / RAW: "checkout: success\nentry: failure"
{"deps":{"conclusion":"failure"}}                       ← pip 失败那一类
   → RAW: "deps: failure"  +  "(no gate_output.txt)"（清单仍可缺，但表已经指出是谁）
{}                                                       ← 表为空时
   → "(步骤状态不可用：请确认每个 step 都有 id)"        ← 空表也说实话，不假装正常
```

（桩里那句 `issue 创建失败: Cannot read properties of undefined 'owner'` 是**桩缺 `context.repo`**，
真实 runner 有；顺带证实了降级路径：issue 建失败时 Summary 照样写完，只 `core.warning`。）

## 五、这次没做的两件事（写清楚，别让人以为已经完备）

- **`toJSON(steps)` 只包含已经跑过的步骤**：诊断步之后的步骤（如 publish 的 build/publish）
  在表里不出现——它们本来也没跑，方向安全。
- **#17 的根因仍未证实**。本阶段只是让下一次红**自带答案**；如果 #17 之后不再重跑，
  那这一条推断（红在 `deps`/`system`）就一直只是推断。
