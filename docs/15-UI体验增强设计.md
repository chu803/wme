# 阶段 15 · UI 体验增强设计文档

> 本阶段聚焦「用户操作体验」层面的增强，不改动任何修复核心算法（`detector` / `image_utils` / `inpainter` 内部数学零改动），纯属 UI/交互/展示层改造。
>
> 四大增强：① 全局拖拽上传；② 键盘快捷键；③ 批量进度可视化；④ 结果画廊对比（Before | After）。
>
> 配套底层改动（阶段 14 已落地、本阶段复用）：`config` 三项开关、`services/queue_worker.py` 的 `summary()["current"]` 当前项、`services/export_service.py` 的 `make_compare_array` 内存拼接。

## 1. 定位与目标

| 维度 | 说明 |
| --- | --- |
| 问题 | 原版界面功能完整，但操作偏「点击式」：上传须精确点到输入框、多次重复操作缺少键盘流、批量处理时不知当前在处理哪张、画廊只显示结果图无法直接对比原图。 |
| 目标 | 在不引入新依赖、不改动算法契约的前提下，补齐四类高频体验能力，并全部可经 `config` 开关降级（出问题可一键关掉）。 |
| 原则 | 分层铁律 `ui → services → core → utils → config` 仍严格成立；所有自定义 JS 统一在 `launch(js=...)` 注入，**不污染 Python 后端**；任何 JS 异常都被 `try/catch` 包裹，绝不影响 Gradio 主体。 |
| 风险隔离 | 算法层零改动；新增组件均带 `visible=config.UI_COMPARE_VIEW` 或受开关保护；测试全绿（见 §7）。 |

## 3. 增强一：全局拖拽上传

### 3.1 痛点
用户希望把图片从资源管理器直接拖进页面，而不必先找到某个具体的 `gr.File` / `gr.Image` 输入框。

### 3.2 方案（JS 注入，零 Python 改动）
- 在 `ui/app.py` 新增 `_build_custom_js()`，构造注入字符串；`launch_app()` 的 `app.launch(js=_build_custom_js())` 注入。
- 脚本在 `window` 上挂 `dragenter/dragover/dragleave/drop` 监听：
  - 拖入文件时显示全屏半透明蓝色虚线浮层（`#global-drag-overlay`，纯装饰，`pointer-events:none` 不抢事件）；
  - `drop` 时调用 `firstVisible(TARGETS)` 取**当前可见页签**对应的输入组件根节点，再 `querySelector('input[type=file]')` 找到原生 file input；
  - 用 `DataTransfer` 把拖入文件写入该 input 并派发 `change`/`input` 事件，触发 Gradio 原生上传流程。

### 3.3 关键设计决策
- **`TARGETS` 候选列表（按优先级）**：`single_editor` → `auto_upload` → `batch_files` → `batch_folder` → `media_pdf` → `media_video`。批量页优先填「多文件」框，媒体页按当前可见子页自动命中。
- **不抢原生区域**：若拖放落在 Gradio 已原生支持拖拽的区（`input[type=file]`/`.file-droparea`/`.gradio-image`/`.gradio-file`/`.image-editor`），脚本直接 `return`，交给 Gradio 自己处理，避免双重触发。
- **可见性判定 `isVisible()`**：沿父链检查 `hidden`/`display:none`/`visibility:hidden`，保证跨页签不会误填隐藏页。

### 3.4 各输入组件 elem_id（在对应 tab 文件中设置）
| 组件 | 文件 / 行 | elem_id |
| --- | --- | --- |
| 单图编辑器 | `ui/tab_single.py:222` | `single_editor` |
| 自动模式上传 | `ui/tab_auto.py:323` | `auto_upload` |
| 批量多文件 | `ui/tab_batch.py:457` | `batch_files` |
| 批量文件夹 | `ui/tab_batch.py:450` | `batch_folder` |
| 媒体 PDF | `ui/tab_media.py:381` | `media_pdf` |
| 媒体视频 | `ui/tab_media.py:449` | `media_video` |

## 4. 增强二：键盘快捷键

### 4.1 方案
同样在 `_build_custom_js()` 中，监听 `window` 的 `keydown`：
- **仅在非输入框聚焦时生效**（`e.target` 为 `INPUT`/`TEXTAREA`/`contentEditable` 时直接 return），避免与打字冲突；
- 依赖按钮组件的 `elem_id`，用 `clickIfVisible(id)` → `clickEl()` 触发（elem_id 打在外层 wrapper，向内 `querySelector('button')` 再 `.click()`）。
- **Gradio 6.x 无 `gr.Button(shortcut=...)` 参数**（实测确认），故按钮交互完全靠 JS 监听，而非框架原生 shortcut。

### 4.2 快捷键映射
| 快捷键 | 触发按钮（elem_id） | 备注 |
| --- | --- | --- |
| `Shift+R` | `single_run` 或 `auto_repair` | 单图页/自动页各自命中当前可见者 |
| `Shift+D` | `auto_detect` | 自动检测 |
| `Shift+B` | `batch_run` | 开始批量 |
| `Shift+C` | `batch_cancel` | 取消批量 |
| `Shift+F` | `history_refresh` | 刷新历史 |

## 5. 增强三：批量进度可视化

### 5.1 痛点
原批量页只有进度条 + 日志，看不到「当前正在处理哪一张」。

### 5.2 方案
- `ui/tab_batch.py` 新增内部函数 `_status_md(s: dict) -> str`，依据 `queue_worker.BatchQueue.summary()` 的 `current` / `done` / `failed` / `cancelled` / `total` 渲染一行 Markdown：
  ```
  🔄 正在处理：**{current}**
  完成 {done} / 失败 {failed} / 取消 {cancelled} / 共 {total}
  ```
- 右列新增 `batch_status = gr.Markdown(...)` 组件（行 506）。
- `run_batch` 的生成器在「早期 return」与三处主循环 `yield` 处，由原来 3 元输出扩展为 4 元 `(frac, log, gallery, _status_md(s))`，`outputs` 同步扩展为 `[batch_bar, batch_log, batch_gallery, batch_status]`。

### 5.3 复用点
`queue_worker.summary()["current"]` 在阶段 14 已就绪（队列在「开始处理」时把当前任务名写入 summary），本阶段直接消费，零算法改动。

## 6. 增强四：结果画廊对比（Before | After）

### 6.1 方案
复用 `services/export_service.make_compare_array(orig, result)`（阶段 6 实现，内存拼接「原图 \| 处理后」横向数组，不落盘）。

#### 6.1.1 单图页（`ui/tab_single.py`）
- `editor_kwargs` 加 `elem_id="single_editor"`；运行按钮加 `elem_id="single_run"`。
- 右列新增 `compare_view = gr.Image(label="原图 | 处理后 对比拼接", type="numpy", interactive=False, height=300, visible=config.UI_COMPARE_VIEW)`。
- `process_single` 返回元组由 4 元改 5 元（第三位置插入 `compare` 或 `None`）；成功路径尾部：
  ```python
  compare = make_compare_array(image, result) if (config.UI_COMPARE_VIEW and result is not None) else None
  return image, result, compare, status, out_path
  ```
- `run_btn.click` 的 `outputs` 扩展为 `[orig_view, result_view, compare_view, status_box, out_file]`。

#### 6.1.2 自动页（`ui/tab_auto.py`）
- `upload` / `detect_btn` / `repair_btn` 分别加 `elem_id="auto_upload"` / `auto_detect` / `auto_repair`。
- 右列新增 `compare_view`（同单图，`visible=config.UI_COMPARE_VIEW`）；`process_auto_repair` 返回由 4 改 5，尾部同单图加 `make_compare_array`。
- `repair_btn.click` 的 `outputs` 扩展为 5 元。

#### 6.1.3 批量页（`ui/tab_batch.py`）
- `run_batch` 签名新增 `compare: bool = True`（位于 `evaluate` 之后、`progress` 之前）。
- `_on_update` 的 `DONE` 分支：当 `compare` 且原图（`task.path`）+ 结果（`rp`）均存在时，载入两图经 `make_compare_array` 拼接后作为画廊缩略图 `gallery.append((arr, caption))`；否则退回 `(rp, caption)`。
- 新增 `compare_toggle = gr.Checkbox(value=config.UI_COMPARE_VIEW, label="结果对比视图")`；`run_btn.click` 的 `inputs` 增加 `compare_toggle`。
- `_process_one` 调用改为 `_, result, status, _, out_path = process_auto_repair(...)`（5 元解包，丢弃 compare 避免重复计算）。

#### 6.1.4 历史页（`ui/tab_history.py`）
- `load_gallery(compare: bool = False)`：当 `compare` 且 `r.original_path` 存在时，载入原图+结果经 `make_compare_array` 拼接作为画廊项。
- `delete_selected` / `clear_all` / `reprocess` 均新增 `compare` 参数并透传 `load_gallery(compare=...)`。
- 新增 `compare_toggle` 复选框；四个事件绑定（refresh/clear/delete/reprocess）经 lambda 透传 `compare_toggle`。

## 8. 边界与已知限制

1. **Gradio 6.x API 约束（实测结论）**
   - `gr.Blocks(js=...)` 已移除 → 全部 JS 改在 `launch(js=...)` 注入（launch 参数列表确实含 `js`）。
   - `gr.Button` 无 `shortcut` 参数 → 快捷键靠 JS `keydown` + `elem_id` 模拟。
   - `gr.Image` / `gr.TabItem` / `gr.File` 等支持 `elem_id` → 用它做 JS 锚点。
2. **拖拽范围**：仅「拖文件到页面非原生上传区」时浮层接管；落在 Gradio 原生拖拽区时由 Gradio 自行处理。
3. **快捷键安全**：仅在非输入聚焦时生效，且每个快捷键都先 `clickIfVisible` 校验组件可见，隐藏页不会被误触发。
4. **对比视图性能**：批量对比对每张成功图都做一次内存拼接，`visible=False` 或 `compare_toggle` 关闭时不计算；大批量建议关闭以省内存。
5. **无算法改动**：本阶段不触碰 `core/*` 与 `services/auto_pipeline` 的主干逻辑（`_process_one` 仅调整解包方式）。
