> 方向：在用户选定「性能与内存再优化」后，先做**离线基线探针**量化热点，再只落地**实测确有收益**的两项优化；对实测无收益的项明确放弃，避免过早优化。

## 1. 基线探针结论（先量后改）

用无 torch 的离线脚本（`_probe_perf.py`，已删）度量非模型路径耗时：

| 场景 | 优化前 | 说明 |
| --- | --- | --- |
| decode 2000×2000 ×4（同文件重复） | **121.8 ms** | 批量 `_on_update` 里 `evaluate` 解码 2 次 + 对比又解码 2 次同一对文件 |
| evaluate_quality 2000×2000 | **673.7 ms** | SSIM 的 `filter2D` 主导，随面积线性增长 |
| make_compare_array 2000×2000 | 61.9 ms | 拼接 + 标注 |
| export_compare 2000×2000（落盘） | 284.5 ms | 2 次解码 + 拼接 + PNG 编码 |
| find_by_hash over 2000 条 | **0.2 ms** | 线性扫描代价可忽略（默认上限才 200 条） |

**结论**：
- 真正的大头是「重复解码磁盘图片」与「大图质量评估」。
- `find_by_hash` 线性扫描实测仅 0.2ms，**不值得**为它加哈希索引（过早优化，已放弃）。

## 2. 优化一：图片解码内存缓存（LRU）

### 2.1 方案
在 `core/image_utils.py` 增加进程级解码缓存：
- **键** = `(绝对路径, mtime_ns, 文件大小)`。文件被覆盖重写后 `mtime`/`size` 变化 → 自动失效，不会读到陈旧内容。
- **值** = 解码后的 `(rgb, alpha)`；取用时返回**数组副本**（避免调用方修改污染缓存，保持只读语义）。
- **并发安全**：`_IMAGE_CACHE_LOCK`（`threading.RLock`）保护，兼容批量 worker 线程与 UI 线程同时解码。
- **边界保护**：单图像素数超过 `IMAGE_DECODE_CACHE_MAX_PIXELS_SINGLE`（默认 2500 万）不参与缓存，防超大图撑爆内存；LRU 超出 `IMAGE_DECODE_CACHE_MAX_ENTRIES`（默认 128）淘汰最久未用项。
- `load_image` 与 `load_image_with_alpha` **共用同一缓存**（都改走 `_load_image_cached`），因此任一调用命中都能惠及另一调用。
- 新增 `clear_image_cache()` 供测试或内存紧张时手动清空；`IMAGE_DECODE_CACHE_ENABLED=False` 时完全旁路缓存。

### 2.2 配置项（config.py 第 8.z 节，支持 .env）
| 配置项 | 默认 | 作用 |
| --- | --- | --- |
| `IMAGE_DECODE_CACHE_ENABLED` | `True` | 总开关 |
| `IMAGE_DECODE_CACHE_MAX_ENTRIES` | `128` | LRU 最大条目 |
| `IMAGE_DECODE_CACHE_MAX_PIXELS_SINGLE` | `25_000_000` | 超过该像素的图片不缓存 |
| `QUALITY_MAX_EVAL_SIDE` | `1024` | 见优化二 |

### 2.3 改写清单
- `core/image_utils.py`：新增缓存机械（`_img_cache_*` / `_decode_image_raw` / `_load_image_cached` / `clear_image_cache`），`load_image` 与 `load_image_with_alpha` 改走缓存加载。

### 2.4 实测收益
- decode 2000×2000 ×4：**121.8 → 53.7 ms**（约 **−56%**，首解后三次为缓存副本命中）。
- make_compare_array 2000×2000：**61.9 → 23.0 ms**（同运行内前序加载已暖缓存）。
- export_compare 2000×2000：**284.5 → 239.8 ms**（两次解码命中缓存，省下解码、编码不受影响）。

## 3. 优化二：质量评估大图降采样

### 3.1 方案
`services/quality_service.py` 新增 `_downscale_for_eval(o, r)`：当原图或结果任一边长超过 `QUALITY_MAX_EVAL_SIDE` 时，**两者同步等比缩放到该上限以内**再做 SSIM / 变化比例评估。
- 同步缩放保证像素一一对应，启发式分级结论基本不变。
- **只缩小、不放大**（小图原样返回），避免无谓上采样。
- 使用 `cv2.resize(INTER_AREA)`，返回新数组，**绝不修改**可能被解码缓存持有的原数组。
- `QUALITY_MAX_EVAL_SIDE=0` 表示始终用原图评估（关闭降采样）。

### 3.2 改写清单
- `services/quality_service.py`：`evaluate_quality` 在加载后、比较前调用 `_downscale_for_eval`；新增该辅助函数。

### 3.3 实测收益
- evaluate_quality 2000×2000：**673.7 → 344.5 ms**（约 **−49%**，SSIM 面积约降 4×）。
- 分级正确性由单测保证：800×800 的「修得好→good」「没修掉→review」在激进降采样（64px）下结论不变。

## 4. 放弃项（据测量结论）

- **`cache_service.find_by_hash` 哈希索引**：线性扫描 2000 条仅 0.2ms，默认上限 200 条，O(N) 代价可忽略。加内存索引反而引入写入/删除/清空时的索引维护复杂度与一致性风险 → **不实现**，符合「先量后改、不做过早优化」。

## 6. 边界与已知限制

1. 解码缓存是**尽力而为的性能优化**，非正确性依赖：键含 `mtime_ns`+`size`，理论上「同路径同毫秒同大小但内容不同」极低概率误命中——仅发生在连续纳秒级覆写同尺寸文件，正常业务不会出现。
2. 取缓存返回**副本**，因此单图大图缓存命中仍有一次数组拷贝开销（远小于解码，可接受）。
3. 降采样仅影响质量评估的**计算输入**，不改变导出/展示用的原图与结果图；分级阈值含义不变。
4. 所有优化均可在 `.env` 关闭（`IMAGE_DECODE_CACHE_ENABLED=False` / `QUALITY_MAX_EVAL_SIDE=0`）。
