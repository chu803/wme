# 阶段 11 设计文档：自定义模型接入 + 插件体系

> 本文档配套 `core/plugins.py`、`config.py`（第 8.6 节）、`plugins/` 目录与 `cli.py`/`api.py`/`ui/*` 接线代码。
> 目标：在既有的「单图 / 批量 / 自动 / 历史 / 设置 / 文档视频」六入口之外，提供一个**插件框架**，让用户可接入自己的修复引擎（diffusion 模型、其它 TorchScript 模型、远程 API 等），且 **GUI / CLI / 程序库 / REST** 四入口共用同一套动态引擎列表。

---

## 1. 背景与动机

原生工作台只内置两种修复引擎：

| 引擎 | 名称 | 特点 |
|------|------|------|
| LaMa 深度学习 | `lama` | 效果最好，能凭空补全纹理；需要模型文件 |
| OpenCV 传统算法 | `opencv` | 速度极快、无需模型；适合细小水印 |

但它们的分派逻辑原本硬编码在 `core/inpainter.py`（`if engine == "lama" / "opencv"`），**新增一种引擎必须改核心代码**，违反「开闭原则」，也不利于第三方扩展。

阶段 11 的改造思路：**把「修复引擎」抽象成插件**，让注册表成为唯一真值来源，从而：

1. 用户无需改核心代码，写一个类放进 `plugins/` 即可扩展；
2. 四入口（GUI / CLI / 库 / REST）自动共享同一份引擎清单；
3. 核心算法（`core.inpainter` / `detector` / `image_utils`）零改动，风险可控。

---

## 2. 分层与依赖约束（铁律不变）

```
ui/         →  services/  →  core/  →  utils/  →  config
(界面层)       (业务编排)      (算法/框架)  (基础工具)  (全局配置)
```

- `core/plugins.py` 属于 **core 层**，严禁 import gradio 或任何 ui 组件；
- 插件文件在 `plugins/` 下，import 链为 `plugins/*` → `core.plugins`（→ `config`/`utils`）；
- 杜绝循环依赖：`core.plugins` 在分派时**延迟导入** `core.inpainter` 的具体函数（见 §4）。

---

## 3. 整体架构

```
                        用户插件文件 (plugins/my_engine.py)
                                    │ register_engine(...)
                                    ▼
        ┌───────────────────────────────────────────────────────┐
        │           core/plugins.py  引擎注册表 (_REGISTRY)        │
        │  内建: _BuiltinLama / _BuiltinOpenCV  （同在此注册）       │
        │  API:  register_engine / get_engine / list_engines       │
        │        get_engine_choices / get_engine_detail /         │
        │        load_plugins / has_engine                        │
        └───────────────────────────────────────────────────────┘
                                    │ 统一分派
                                    ▼
        ┌───────────────────────────────────────────────────────┐
        │        core/inpainter.py   repair_image(...)             │
        │  engine=="auto" → 有模型选 lama 否则 opencv              │
        │  其余 → plugin_manager.get_engine(engine)               │
        │         eng.requires_model → eng.setup()               │
        │         eng.inpaint(image, mask, device, progress)      │
        │  框架统一完成：掩码后处理 / 降噪 / 力度融合                │
        └───────────────────────────────────────────────────────┘
              ▲              ▲              ▲              ▲
              │              │              │              │
        ┌─────┴────┐   ┌─────┴────┐   ┌─────┴────┐   ┌─────┴────┐
        │ ui/tab_* │   │  cli.py  │   │  api.py  │   │ server.py│
        │ 引擎下拉 │   │ --engine  │   │ get_cap- │   │ /api/*   │
        │ 动态填充 │   │ --list-   │   │ abilities│   │          │
        │          │   │ engines   │   │ engines  │   │          │
        └──────────┘   └──────────┘   └──────────┘   └──────────┘
             四入口共用同一份 get_engine_choices() / list_engines()
```

要点：**所有入口都不自己维护引擎列表**，全部问 `core.plugins` 要，保证「注册一个插件，四处同时生效」。

## 4. 插件接口契约

### 4.1 基类 `InpaintEnginePlugin`（抽象类）

```python
class InpaintEnginePlugin(ABC):
    name: str = ""            # 引擎唯一键（小写），命令行/API 用它选择
    display_name: str = ""    # 界面显示名
    description: str = ""      # 一句话简介
    requires_model: bool = False  # 是否需要外部模型文件（决定是否先调 setup()）

    def setup(self) -> None:  # 可选：懒加载权重/建立连接，默认空实现
        return None

    @abstractmethod
    def inpaint(self, image, mask, *, device=None, progress=None) -> np.ndarray:
        ...
```

### 4.2 `inpaint` 入参 / 出参约定（务必遵守）

| 参数 | 类型与含义 |
|------|-----------|
| `image` | `H×W×3` `uint8` **RGB** 原图（整图，含掩码外像素） |
| `mask`  | `H×W` `uint8`，值域 **0/255** 的二值掩码（已膨胀/阈值/羽化后二值化） |
| `device`| 设备句柄（可为 `None`，插件自行决定是否使用） |
| `progress` | 进度回调 `callback(frac: float(0~1), msg: str)`，可阶段性上报 |
| **返回** | `H×W×3` `uint8` **RGB**，掩码区域已被填充，其余区域应与原图一致 |

> 关键简化：**插件只负责「填充掩码区域」**。掩码后处理、降噪、力度融合由框架（`core/inpainter.repair_image`）统一完成，插件作者无需关心这些细节，接口因此极简。

### 4.3 内建引擎也注册为插件

为消除「硬编码」与「注册表」两套真相，LaMa / OpenCV 同样实现为插件类并在模块加载时注册，使 `_REGISTRY` 成为唯一真值来源：

```python
class _BuiltinLama(InpaintEnginePlugin):
    name = "lama"; display_name = "LaMa 深度学习"; requires_model = True
    def inpaint(self, image, mask, *, device=None, progress=None):
        from core.device_manager import select_device
        from core.inpainter import _inpaint_lama_full, empty_cache, is_model_available
        if not is_model_available():
            raise FileNotFoundError("指定的 LaMa 引擎缺少模型文件，请先运行 download_model.py 下载。")
        dev = device or select_device()
        out = _inpaint_lama_full(image, mask, dev); empty_cache(); return out

class _BuiltinOpenCV(InpaintEnginePlugin):
    name = "opencv"; display_name = "OpenCV 传统算法"
    def inpaint(self, image, mask, *, device=None, progress=None):
        from core.inpainter import _inpaint_opencv
        return _inpaint_opencv(image, mask)

register_engine(_BuiltinLama)
register_engine(_BuiltinOpenCV)
```

注意：真正的修复函数通过**函数内部延迟导入** `core.inpainter` 取得，因此 `core.plugins` 模块被导入时**不会**触发 `core.inpainter` 的导入，彻底规避 `plugins ↔ inpainter` 的循环依赖。

## 5. 注册、发现与加载机制

### 5.1 注册表（进程内单例）

- `_REGISTRY: dict[str, InpaintEnginePlugin]`：引擎名（小写）→ 插件实例。
- `register_engine(plugin)`：接受**类**或**实例**；实例键取 `name.lower()`，重复注册直接覆盖。
- `get_engine(name)` / `has_engine(name)`：`has_engine("auto")` 恒为 `True`（`auto` 是自动选择器，分派时再解析真实引擎）。

### 5.2 惰性发现

- 插件扫描**不是**在 import 时强制进行，而是 `_ensure_loaded()` 在**首次查询引擎列表或分派引擎**时触发 `load_plugins()`。
- `_LOADED` 守卫防止重复扫描。
- 因此无论走 GUI / CLI / 库 / REST 哪条入口，只要碰过一次引擎列表，插件就会被正确加载。

### 5.3 扫描规则（`load_plugins`）

1. 解析目录：读 `config.PLUGIN_DIRS`（见 §8），相对路径按 `PROJECT_ROOT` 拼接；配置缺失回退 `<项目根>/plugins`。
2. 遍历目录下 `.py` 文件，**跳过以 `_` 开头的文件**（如 `__init__.py`）。
3. 若 `PLUGIN_ENABLED` 非空，只加载清单内（文件名去 `.py`、小写）的插件，其余跳过——便于灰度/调试。
4. 每个文件 `importlib.util.spec_from_file_location` 动态导入，导入即执行模块末尾的 `register_engine(...)`。
5. **加载失败仅告警**（记录 warning + traceback），不抛出，保证一个烂插件不会拖垮整个程序。

加载流程伪代码：

```
load_plugins():
    if _LOADED: return len(_REGISTRY)
    _LOADED = True
    对每个插件目录:
        对每个 *.py 且非 _ 开头 的文件:
            若启用清单非空且不在清单内 → 跳过
            try: 动态导入模块 (执行其 register_engine)
            except: 记 warning，继续
```

### 5.4 引擎清单导出

- `list_engines() -> list[EngineInfo]`：第一项恒为 `auto`（自动选择），随后内建 `lama`/`opencv`，再追加已注册插件。
- `EngineInfo` 字段：`name` / `display_name` / `description` / `builtin` / `requires_model`（`to_dict()` 供 JSON 序列化）。
- `get_engine_choices() -> list[str]`：供 UI Radio / CLI `--engine choices` 使用的字符串列表。
- `get_engine_detail() -> list[dict]`：供 `api.get_capabilities()` 的 `engines` 字段。

## 6. 在 `core/inpainter.repair_image` 中的分派接线

`engine == "auto"` 先解析为真实引擎名（有模型 → `lama`，否则 `opencv`），其余一律走注册表：

```python
# engine == "auto" → 有模型选 lama，否则 opencv
...
eng = plugin_manager.get_engine(engine)
if eng is None:
    avail = ", ".join(plugin_manager.get_engine_choices())
    raise ValueError(f"不支持的修复引擎：{engine}（可用：{avail}）")
# 需要外部模型文件的引擎（含内建 lama）先做一次性初始化（如加载权重）。
if eng.requires_model:
    try:
        eng.setup()
    except Exception as exc:
        raise FileNotFoundError(f"引擎 {engine} 初始化失败（可能缺少模型文件）：{exc}") from exc
result = eng.inpaint(image, bin_mask, device=device, progress=progress)
# 之后：框架统一降噪 + 力度融合
```

这段改造**只扩展分派**，没有改动任何像素级修复算法；`detector` / `image_utils` 零改动。

## 7. 四入口暴露方式

### 7.1 GUI（界面）

- `ui/components.py` 新增 `get_engine_choices()`（异常时回退内建三选一 `auto/lama/opencv`）。
- `build_repair_params` 的引擎 Radio 由硬编码 `choices=["auto","lama","opencv"]` 改为动态 `get_engine_choices()`。
- 受影响的页签：`tab_single`（单图）、`tab_auto`（自动）、`tab_history`（历史复用）均改为动态填充；`tab_batch`、`tab_media` 复用同一组件，自然联动。
- 用户装好插件、重启程序后，引擎下拉自动出现新选项。

### 7.2 CLI（`cli.py`）

```bash
# 查看全部可用引擎（含插件引擎）
python cli.py --list-engines

# 用指定引擎修复
python cli.py -i 图.png -o 结果.png --engine demo_model
```

- 模块顶部 `ENGINE_CHOICES = core.plugins.get_engine_choices()`（`import` 失败时回退 `["auto","lama","opencv"]`）。
- `--engine` 的 `choices=ENGINE_CHOICES`，确保只能选到已注册引擎。
- `--list-engines` 打印 `get_engine_detail()` 的 `name → display_name` 清单。

### 7.3 程序库（`api.py`）

- `get_capabilities()` 新增 `"engines": _list_engines_safe()`（带 try/except 兜底，绝不因插件问题让能力接口崩）。
- `remove_watermark` / `remove_watermark_array` / `batch_remove` 等底层都走 `repair_image(engine=...)`，因此 `--engine` 的值可直接透传给库函数。

### 7.4 REST（`server.py`）

- `GET /api/capabilities`（由 `api.get_capabilities` 提供）返回的 `engines` 字段即动态引擎清单；客户端据此决定可传的 `engine` 值。
- 修复端点（`/api/remove` `/api/batch`）接收的 `engine` 字段同样经 `repair_image` 走注册表分派。

## 8. 配置项（config.py 第 8.6 节）

| 配置常量 | 默认值 | 环境变量 | 含义 |
|----------|--------|----------|------|
| `PLUGIN_DIRS` | `["plugins"]` | `WME_PLUGIN_DIRS` | 插件目录列表（相对 `PROJECT_ROOT` 或绝对），逗号分隔，按序扫描 |
| `PLUGIN_ENABLED` | `[]`（空=全部） | `WME_PLUGIN_ENABLED` | 启用的插件文件名（去 `.py`、逗号分隔）；非空时仅加载清单内插件 |

解析辅助：`_env_list(key, default)` 读取逗号分隔列表，支持 `.env` 覆盖（如 `WME_PLUGIN_DIRS=/opt/myplugins,./local_plugins`）。

`validate_config()` 放宽：非内建引擎不再被强制改成 `auto`，而是**软告警**提示（真正缺失的模型文件在运行期 `setup()` 时才硬校验并报 `FileNotFoundError`），避免配置期误杀合法插件引擎。

`get_config_snapshot()` 追加展示「插件目录」「已启用插件」，便于排查加载情况。

## 9. 自定义模型示例（plugins/sample_model_plugin.py）

该示例开箱即跑：

- 未配置自定义模型时，用 **OpenCV TELEA** 兜底，保证插件立即可用；
- 设置环境变量 `WME_CUSTOM_MODEL_PATH` 指向 TorchScript 模型后，自动加载并在 `inpaint()` 中调用 `_run_custom_model()`。

核心结构（节选）：

```python
class DemoModelEngine(InpaintEnginePlugin):
    name = "demo_model"
    display_name = "示例·自定义模型"
    description = "自定义模型接入模板：默认 OpenCV TELEA 兜底，可替换为任意 inpaint 模型"
    requires_model = False

    def setup(self):
        path = os.environ.get("WME_CUSTOM_MODEL_PATH", "").strip()
        if not path or not os.path.exists(path):
            self._model = None; return
        import torch
        self._model = torch.jit.load(path, map_location="cpu"); self._model.eval()

    def inpaint(self, image, mask, *, device=None, progress=None):
        if progress: progress(0.4, "示例插件：正在修复...")
        return self._run_custom_model(image, mask) if self._model else self._opencv_fallback(image, mask)

    def _run_custom_model(self, image, mask):
        import torch
        from core.image_utils import mask_to_tensor, rgb_to_tensor, tensor_to_rgb
        img_t = rgb_to_tensor(image, device_str="cpu") * 2 - 1   # [-1,1]
        mask_t = mask_to_tensor(mask, device_str="cpu")
        with torch.no_grad():
            out = self._model(img_t, mask_t)                     # 输出 [-1,1]
        return tensor_to_rgb((out * 0.5 + 0.5).clamp(0, 1))      # 反归一化

    def _opencv_fallback(self, image, mask):
        import cv2
        bgr = cv2.cvtColor(image, cv2.COLOR_RGB2BGR)
        return cv2.cvtColor(cv2.inpaint(bgr, mask, 5, cv2.INPAINT_TELEA), cv2.COLOR_BGR2RGB)

register_engine(DemoModelEngine)
```

接入你自己模型的步骤（详见 `plugins/README.md`）：

1. 复制 `sample_model_plugin.py`，改名（如 `my_diffusion_plugin.py`）；
2. 改 `name` / `display_name` / `description`；
3. 在 `_run_custom_model()` 里按你模型真实签名改写（示例给出与 LaMa 一致的 `(img, mask) → [-1,1]` 调用框架）；
4. 把文件放进 `plugins/`；
5. 重启程序，即可在「修复引擎」里选到它。

> 远程 API 模型：直接在 `inpaint()` 里发起 HTTP 请求并返回 `np.ndarray` 即可，接口不受限制。

## 10. 边界与约束

| 维度 | 约定 / 限制 |
|------|------------|
| 插件作用域 | 只替换「核心填充」一步；掩码后处理/降噪/融合由框架统一做 |
| 输入色彩空间 | `image` 必须是 **RGB** uint8；`mask` 必须是 **0/255** 二值 |
| 输出 | 掩码外区域应与原图一致，否则会出现接缝 |
| 设备 | `device` 参数可忽略；需要 CUDA 的插件自行在 `setup()` 内选择设备 |
| 循环依赖 | `core.plugins` 不得顶层 import `core.inpainter`，修复函数须延迟导入 |
| 加载失败 | 单插件异常仅告警，不阻断程序与其他插件 |
| 命名唯一 | 引擎 `name` 小写唯一，重名后注册覆盖前者 |
| 启用清单 | `PLUGIN_ENABLED` 为空=全加载；非空=仅加载清单内 |
| auto 引擎 | 永远是 `auto` 选择项；`has_engine("auto")` 恒真，但 `auto` 不进入 `_REGISTRY` |
| 配置校验 | 非内建引擎不再被强制改 `auto`，缺失模型运行期才硬报错 |
| 沙箱移动 | `api._move_file` 对 `shutil.move` 失败（如回收站不可用）兜底 `copy2`+尽力删源，删除失败忽略 |

## 11. 验证结论

阶段 11 完成后执行的验证（全部通过）：

1. **`core/plugins.py` 自检**：注册临时引擎 → `has_engine` / `get_engine_choices` / `get_engine` 均正常；内建 `lama`/`opencv`/`auto` 恒在注册表；清理测试引擎不污染真实注册表。
2. **`config.py` 自检**：`PLUGIN_DIRS` / `PLUGIN_ENABLED` 解析正确；`validate_config` 对非内建引擎软告警。
3. **`core/inpainter.py` 分派**：经 `plugin_manager.get_engine(engine)` 统一分派，内建与插件引擎走同一路径。
4. **`build_app` 装配**：209 blocks，六主页签 + 文档视频子页正常装配，引擎 Radio 动态填充。
5. **`api.py` 自检**：8 用例（含 PDF / 视频）全过；`get_capabilities()["engines"]` 含插件引擎。
6. **CLI 端到端**：`python cli.py --list-engines` 正确显示 `auto / lama / opencv / demo_model`；`--engine demo_model` + manual 模式显式掩码产出修复结果（日志出现「示例插件：正在修复...」）。
7. **插件健壮性**：`sample_model_plugin.py` 未配模型时 OpenCV TELEA 兜底跑通；配置 `WME_CUSTOM_MODEL_PATH` 时进入 `_run_custom_model` 模板路径。

修复核心算法未被改动：`core.inpainter` 仅扩展分派逻辑，`core.detector` / `core.image_utils` 零改动。本阶段新增插件层 + 接线 + 文档，风险隔离在「扩展点」之内。
