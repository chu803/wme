## 二、310–312 补登（来源只有两处：Dockerfile 注释 + 2026-10-20 日志）

### 阶段 310 · 移除 `# syntax=docker/dockerfile:1`

`Dockerfile.gpu` 首行的 syntax 指令会先去 Docker Hub 拉前端镜像，国内直连超时 ⇒ build 在**解析阶段**就死。
已移除。**遗留**：当时只清了 GPU 配方，CPU 版 `Dockerfile` 漏了（311 补做同步）。

### 阶段 311 · 真 build 前的三处确定性失败修复

1. `python3.11 -m pip` 必然 `No module named pip`——Ubuntu 22.04 **没有 `python3.11-pip` 包**，
   `python3-pip` 装的是 3.10 的 pip。
2. CPU/GPU 两个配方的 `# syntax` 同步移除。
3. `--no-deps` 会跳过 `nvidia-cudnn-cu12` 等依赖 ⇒ `import torch` 找不到 `libcudnn.so.9` 直接崩。
   修法：去掉 `--no-deps`，nvidia 系包走清华 `--extra-index-url`。

**同轮真 build 结果**：registry mirror 生效（`#1–#4` 全 DONE、基础镜像 2.06GB 下完），
但 `builder 1/5` 死于 `ensurepip is disabled in Debian/Ubuntu for the system python`
⇒ **311 的"修正 1"本身是第二次误判**（Debian 给系统 python 打补丁禁了 ensurepip）。
真解：`python3.11 -m venv`（后由 312 升级为整体换 3.12）。

### 阶段 312 · 基础镜像升 Ubuntu 24.04 + python3.12

`requirements.txt` 钉 `numpy==2.5.1` 要求 **Python ≥ 3.12**，3.11 装不上。
方向性决策：**抬部署目标去满足依赖契约**（换基础镜像），而不是把钉子降到镜像能装的版本
（那会制造「契约 / 开发机 / 镜像」三套依赖漂移）。
配套：apt 源改用 deb822 的 `/etc/apt/sources.list.d/ubuntu.sources`（只 sed 老路径会**静默无效**）。

**⚠ 312 的收口状态未知**：日志记录到「第 4 次修正后等待用户侧重跑」，之后无落盘记录。
⇒ **C5 真 build 至今没有确认成功**，仍是 MEMORY 登记的开放项。
