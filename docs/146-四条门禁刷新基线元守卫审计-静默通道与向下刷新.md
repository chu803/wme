## 二、缺陷

### F1（P1）两个主门禁的 `--update` 是**静默通道**

```python
if args.update:
    ... json.dump(summary, f) ...
    print(f"\n基线已刷新 → {display_path(args.baseline, _ROOT)}")
    return 0                      # ← 绕过 evaluate() / evaluate_real()
```

**危害**：一次 `--update` 会
1. **不判绝对红线** —— 即使 `precision` 已掉到红线以下，也返回 0；
2. **不判数据完整性** —— 图被静默跳过、清单与真值矛盾都不报；
3. **不判漂移** —— 把当前（可能已劣化的）值写成新基准；
4. 用户看到「基线已刷新」+ 退出码 0 ⇒ **以为一切正常**。

### F2（P1）刷新无「向下刷新」护栏（**三处皆无**）

没有任何机制阻止把某个指标**合法化到一个更坏的值**。而**只靠漂移层保护、没有绝对红线**的指标会被**渐进刷新**到任意低值。

**实测数据（合成门禁的 `recall`）**：

```
基线 actual:  precision = 0.542442   ← RED_LINES: ("min", 0.35)  ✅ 有绝对红线
              iou       = 0.521467   ← RED_LINES: ("min", 0.35)  ✅ 有绝对红线
              recall    = 0.818831   ← RED_LINES: 查无此项        ❌ 只有 TOLERANCES 0.20
```

⇒ 连续 `--update`：`0.819 ─刷→ 0.655 ─刷→ 0.524 ─刷→ 0.419 ─…`
**每一步都在 20% 容差内 ⇒ 门禁全程绿，而漏检率可以趋近 100%。**

> **不对称是确凿的**：三个检测侧指标里，`precision` 与 `iou` 都有绝对红线，
> **唯独「漏检」方向（`recall`）没有**。而漏检恰是产品最不能容忍的方向之一。

### F3（P1 附带）`e2e` 的 L1 被 `--gate` 开关限定

```python
if a.update_baseline:
    _save_baseline(agg, engine, limit)
    if not a.gate:
        return 0              # ← 不加 --gate 时，刷新仍然是静默通道
```

⇒ 它对「刷新绕过红线」的处理是**正确**的，但**范围被 `--gate` 限定了**。

### 新增 `scripts/baseline_guard.py`（三条门禁共用）

```python
def check_downward_pairs(pairs, rules) -> list:
    """零结构假设的主接口：pairs = (键, 旧值, 新值) 序列，rules = 键 → (方向, 相对容差, 绝对容差)。"""
def check_downward_refresh(old, new, rules) -> list:
    """扁平 dict 场景的便捷封装（quality_gate 用）。"""
def render_refusal(problems, *, baseline_label, force_flag) -> list:
    """统一的拒绝文案（含逃生门提示）。"""
```

**三条硬约束**：

1. **零结构假设** —— 三条门禁的基线结构各不相同（扁平 dict / `per_preset`+`area_only` 两层嵌套 / 按 case 的 list），
   因此「指标从哪取」由**调用方**用它既有的遍历逻辑完成；护栏只做判定。
   （避免在护栏里再造一份结构知识 ⇒ 经验 151「契约须配机器校验」的反面。）
2. **不新增任何阈值** —— 容差与方向**全部复用**各门禁既有的漂移表
   （`TOLERANCES` / `REAL_TOLERANCES`+`AREA_DRIFT_TOLERANCE` / `E2E_DRIFT_TOL`+`E2E_DRIFT_ABS`），
   保证「漂移层允许的抖动」与「刷新层允许的下滑」**同口径**，
   不会出现「漂移层判它违规、刷新层却放它写入」的自相矛盾。
3. **不写盘** —— 纯函数；调用方决定拒绝还是 `--force-update` 写入。

### 三处门禁的改动

| 门禁 | 改动 |
|---|---|
| `quality_gate.py` | ① 读旧基线**提前**到 `--update` 之前；② 刷新前跑护栏（`_refresh_rules()` 从 `TOLERANCES` 派生）；③ 拒绝则 `return 1`；④ **刷新后继续走 `evaluate()`**（`baseline = summary`，与 e2e 同口径）；⑤ 新增 `--force-update`。 |
| `real_gate.py` | 同上，但用 `_refresh_pairs()` 处理 `per_preset` / `area_only` 两层嵌套，`_refresh_rules_for()` 从 `REAL_TOLERANCES` + `AREA_DRIFT_TOLERANCE` 派生。 |
| `e2e_real_probe.py` | ① 补护栏（写盘**之前**判定，避免污染）；② **去掉对 `--gate` 的依赖** —— 刷新时无条件继续判定（未加 `--gate` 则自动启用并提示）；③ 新增 `--force-update`。 |
| **`prompted_area_gate.py`** | 与 `quality_gate` 同款改造（`per_preset.<预设>.<指标>` 三层键；容差复用它的 `AREA_DRIFT_TOLERANCE` + `ABS_TOLERANCE`）。<br>⚠ **一处有意的口径放宽（已登记）**：该门禁漂移层是「近零 ⇒ 绝对、否则 ⇒ 相对」的 **if/else 二选一**，而护栏取 `max(绝对, 相对)` 的**较宽者** ⇒ 两者仅在 `0.001 < old < 0.0333` 窄区间有差异，方向是**护栏更宽（少拦、绝不误拦）**。刻意如此：若护栏比漂移层更严，正常波动会让 `--update` 失败，用户就会转去用 `--force-update` ⇒ 护栏形同虚设。 |

**统一原则（四条门禁一致）**：
> **刷新基线是「受护栏约束的动作」，不是「绕过判定的通道」。**
> `--force-update` 只跳过**向下刷新护栏**，**永不跳过红线**。

### 附带资产化：`scripts/undef_scan.py`（静态未定义名扫描）

本阶段在实现过程中**又踩中两次**「引用了但从未定义的名字」：

这类缺陷**编译期不报**，只在分支被跑到时 `NameError`（跨阶段已累计 4 次）。
⇒ 把技能家族 15 的 ast 方法**资产化为脚本**（零依赖，`--all` 可全仓扫）。

工具自身首版有两个误报源（**都已修并写进 docstring**）：
- `f"{x:.1f}"` 的**格式说明符**子树里会出现 `Name('f')`；
- `with open(...) as fh:` 的绑定在 `node.items[i].optional_vars`，**不是** `node.optional_vars`。
