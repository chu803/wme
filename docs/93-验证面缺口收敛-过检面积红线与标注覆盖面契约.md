## 1. S2 · 给「过检面积」上红线（本阶段最要紧的一条）

### 1.1 先修度量管道：`mask_coverage` 此前**只算不聚合**

`run_real_benchmark.evaluate_one()` 早就算出了 `mask_coverage` / `mask_iou`，
但 `_aggregate()` **没有把它们放进聚合结果**，于是「过检面积」这一维度在门禁层根本不可见
（红线无从挂载）。阶段 93 补齐聚合字段：

```
mask_coverage_mean / truth_coverage_mean / coverage_ratio_mean / coverage_ratio_n
```

### 1.2 新增一个**与数据类型无关**的面积判据

绝对覆盖率对「角标只看几千像素、平铺看整幅」这两类水印**不可比**。
故同时引入：

```
coverage_ratio = 预测掩码面积 ÷ 真值水印面积        （理想值 1.0）
```

真值面积为 0 时无定义 → 记为 `None`，聚合时**剔除**（而不是当 0 拉低均值）。
这样以后补 4 类新样式时，红线不会被「合法的大面积水印」顶掉（经验 1：绝对量优先、相对量兜底；此处两者并存且各有分工）。

### 1.3 实测（阶段 86 基线，30 张真实图 · `general` 预设）

| 指标 | 均值 | 中位 | 最差 | 最好 |
|---|---|---|---|---|
| precision | 0.0385 | — | — | — |
| recall | 1.0000 | — | — | — |
| mean_iou（区域级） | 0.7573 | — | — | — |
| mask_iou（掩码级） | **0.0635** | — | — | — |
| **mask_coverage** | **0.1618** | 0.1545 | 0.2900 | — |
| **coverage_ratio** | **16.62×** | — | — | — |

微平均：`tp=60 · fp=2582 · fn=0` → **P = 0.0227**（2642 个预测区域里 2582 个是误报）。

> **标定踩到的坑（值得记住）**：我最初按 `0.1618 ÷ 0.00346 ≈ 47×` 估倍率，
> 结果门禁实测是 **16.62×**。原因：正确口径是「**逐图先算比值、再取平均**」，
> 而每张图的真值框大小不同 ⇒ **均值之比 ≠ 逐图比值的均值**。红线值以门禁输出为准，
> 该注意点已写进 `REAL_PRESET_CONTRACT` 的注释里。

### 1.4 三条新红线（登记为**崩溃护栏**，不是结论编码）

```python
"mask_coverage":  ("max", 0.25),    # 实测 0.1618 → 约 1.5× 余量
"coverage_ratio": ("max", 25.0),    # 实测 16.62  → 约 1.5× 余量
"mask_iou":       ("min", 0.042),   # 实测 0.0635  → 约 1.5× 余量
```

**为什么是「约 1.5× 余量」而不是贴着实测值？** 因为分层设计刻意做成
**漂移容差（15%/20%）守「变化」、红线守「崩溃」**：

| 指标 | 漂移容差 | 漂移触发点 | 红线 |
|---|---|---|---|
| mask_coverage | 15% | 0.1618 → 0.186 | 0.25 |
| coverage_ratio | 15% | 16.62 → 19.1 | 25.0 |
| mask_iou | 20% | 0.0635 → 0.0508 | 0.042 |

日常回归由漂移先拦住，红线只在真正崩坏时才亮。

### 1.5 顺带发现：检测器内部**已有**覆盖率上限，但它形同虚设

跑门禁时日志里出现两条告警：

```
[WARNING] [core.detector:2664] 检测掩码覆盖率 30.9% 超过上限 30.0%，
          已按区域面积从小到大裁剪，保留更可能是水印的小区域。
```

即：`core/detector` 里**本来就有**「最大覆盖率」概念和一个 30% 单图上限。
但 30 张里只有 2 张触发 ⇒ **那个上限只防「爆炸」，守不住「典型值已经是 16%」这个事实**。

> **推广**：项目里但凡「已有一个守卫」，都要问一句「它在**当前分布**下会不会触发」。
> 一个永不触发的守护阈值，与没有守卫在功能上等价，但会给人「已经有保护了」的错觉
> （与阶段 91 的「配置项名存实亡」同族：**存在 ≠ 生效**）。

### 1.6 漂移方向必须从红线方向**派生**（本次的代码级修正）

旧实现里漂移只查「下滑」：

```python
if float(now) < float(base) * (1.0 - rel_tol):   # 旧：只认「变低 = 变坏」
```

而 `mask_coverage` 是**越高越坏** ⇒ 掩码膨胀到 30% 都不会被报。
同一指标在红线处说「越高越坏」、在漂移处说「越低越坏」，是典型的**同一语义两套实现**（经验 24/77）。

修正：方向不在 `REAL_TOLERANCES` 重复声明，而是从契约派生：

```python
def _metric_direction(key, preset) -> str:
    entry = (REAL_PRESET_CONTRACT.get(preset) or {}).get(key)
    return entry[0] if entry else "min"        # 未登记 → 默认「越高越好」
```

契约未登记该指标时默认 `"min"`，**保证新增监控项不会因为忘记写方向而静默失效**。

## 2. S1 · 把「没标注」与「没有」区分开

### 2.1 缺口回顾

30 张图的清单**全部**声明 `watermark_style_hint="mixed"`（多种风格并存），
而真值 60 个标注**全部**是 `corner_logo`。**未被标注的水印不会计入漏检**
⇒ `recall` 被结构性抬到 1.0000。**「没标」被静默读成了「没有」。**

### 2.2 新增 `annotation_scope(manifest, truth)`（纯函数，可单测）

返回 `labeled / n_labeled_styles / declared_images / unspecified_images /
contradictory / unknown_styles / complete`，判定规则：

| 情形 | 判定 | 严重度 |
|---|---|---|
| 清单 hint 是具体风格，真值里 0 标注 | `contradictory` | **始终硬失败**（标注错误） |
| 真值出现枚举外 style | `unknown_styles` | **始终硬失败**（数据错误） |
| 清单 hint 是 catch-all（`mixed`/`unknown`/空） | `unspecified_images` | 默认**告警**，`--strict-scope` 升级为失败 |

### 2.3 为什么 catch-all 默认不失败

覆盖面不足是**数据集现状**、不是代码缺陷。若默认失败，门禁会永久变红，
从而**失去「拦住回退」的作用**（这是更坏的后果）。所以设计成：

- **默认**：打印显著横幅 + 写入结果 JSON + 随 `to_markdown` 一起输出（限定跟着数字走）；
- **`--strict-scope`**：把覆盖面不足升级为失败，供 CI 表达「我要全类验证」的意图。

### 2.4 实测行为

```
默认：      ✅ 真实图质量门禁通过        EXIT=0（同时打印覆盖面横幅）
--strict:   ❌ 未通过                    EXIT=1
            · [范围] 严格模式下标注覆盖面不足：仅 1 类（corner_logo）有真值，
              30 张图只有 catch-all 声明
```

### 2.5 让脚本发现「此前靠肉眼发现」的不一致

`build_real_ground_truth.py validate` 现在会复用**同一份** `annotation_scope`
（避免「同一规则两套实现」）：

```
校验完成：ok=60, errors=0

⚠ 标注覆盖面 1 类：corner_logo
  · 清单中 30 张图只声明了 catch-all 风格（mixed/unknown），真值未覆盖任何具体风格
  · 因此本次 recall/precision **仅代表上述已标注类型**；其余宣称支持的类型的真实指标是**未知**，不是 100%
标注覆盖面：1 类（corner_logo）；具体声明 0 张 / catch-all 声明 30 张 → 不完整（召回只代表已标注类型）
```

### 2.6 S1 尚未闭环的部分（需要你）

`annotation_scope` 只能**指出**缺口，不能**填补**它。真值里补上 4 类样式仍然需要真实图片。
**这一步我无法代劳**——见文末「需要你做什么」。

## 3. S3 · 端到端（预测掩码 → 修复）质量量化

### 3.1 方法

在**同一份代码**上跑两轮引擎对决（`mask_source=truth` 与 `mask_source=detect`），
`seam_delta`（掩码区 vs 邻域环带色差，越低越好）为准。

> 注意：09-13 曾跑过一次 `detect` 模式（`decision_20260913_144817.json`），
> 但那**早于阶段 82/84/86 的掩码质量修复**，数字已不可比，故本阶段重跑。

### 3.2 结果

| 掩码来源 | 掩码像素均值 | 占画面 | opencv_seam | lama_seam | 引擎领先幅度 | 胜出 |
|---|---|---|---|---|---|---|
| `truth`（真值掩码） | 10,213 | **0.97%** | 13.88 | 21.77 | **9.18** | opencv 18 / lama 2 / 平 10 |
| `detect`（预测掩码） | 169,703 | **16.18%** | 9.50 | 11.96 | **5.97** | opencv 15 / lama 5 / 平 10 |

**交叉验证通过**：`169703 ÷ 10213 = 16.62` —— 与门禁独立算出的 `coverage_ratio_mean = 16.62×`
**完全吻合**。两套独立实现得到同一个数字，说明度量管道可信。

### 3.3 两个结论

**结论 A（反直觉）：`detect` 模式下 `seam_delta` 数值更小（9.50 < 13.88），但这不代表「修得更好」。**

原因：掩码覆盖 16% 时，「掩码区」里包含了大量**非水印的平滑区域**，
而 `seam_delta` 恰恰是「掩码区与邻域环带的色差」——在那些本就没被破坏的平滑区域，
这个色差天然就小。**指标被稀释了，不是质量提升了。**

> ⇒ **跨掩码来源的 `seam_delta` 不可直接比较。** 这是「度量会奖励劣化」的第二个实例
> （第一个在方向 A：`masked_psnr` 高 ≠ 好）。凡是「区域级指标」，其**区域的构成**变了，
> 指标就换了含义。**任何"变好/变坏"的结论都必须锁定口径。**

**结论 B（真结论）：检测误差会**稀释**引擎差异。**

引擎领先幅度从 9.18 → 5.97（**降到 65%**），胜率从 opencv 18:2 → 15:5。
即「OpenCV 明显优于 LaMa」这个结论**主要成立于「掩码精确」的前提**；
端到端情况下两者差距显著缩小。

> 对产品的含义：`INPAINT_DUAL_RUN` 维持 opt-in 是**偏保守但站得住**的选择；
> 而在把掩码面积从 16% 收敛到接近真值之前，「换更强修复引擎」的收益是被上游误差
> 淹没的——这也正是阶段 92 里「不建议现在上 GPU / 换大模型」的量化依据。

## 4. S4 · 能力声明的单一真值来源

### 4.1 矛盾回顾

`README.md` §1 把 `ai_gradient` 列为 5 大支持类型之一；
`scripts/real_gate.py` 自述它「**设计上恒为零输出**」；且它**不在** `quality_gate` 的合成用例集里。

### 4.2 修复：`config.WATERMARK_TYPE_SCOPE`（附录 A）

关键设计原则：**只登记真正新增的信息，不复制已有的名字来源**。

| 信息 | 唯一来源 |
|---|---|
| 合成用例名 / 用例中文名 | `scripts/make_demo_assets.CASES`（`quality_gate` 直接 from-import，不另建） |
| 检测模式显示名 | `core.detection_presets` 的 `display` |
| **真值 style 名** | **只有本表登记** ← 唯一"两边都缺"的映射 |

第三行是真问题所在：`faint_tiled` 是**合成用例名**，真值侧对应的是 `translucent`；
两者若混用，标注计数会**静默恒为 0**（看起来像「没标」，实为「名字写错」）。

```python
WATERMARK_TYPE_KNOWN_SYNTHETIC_GAP = frozenset({"ai_gradient"})   # 显式写下「已确认没有」
WATERMARK_TYPE_SCOPE = {
    "ai_faint_tiled": {"truth_styles": ("translucent", "overlay")},
    "ai_logo":        {"truth_styles": ("corner_logo", "logo_watermark")},
    "ai_text_heavy":  {"truth_styles": ("edge_text",)},
    "ai_grid":        {"truth_styles": ("grid_watermark",)},
    "ai_gradient":    {"truth_styles": ("gradient_watermark",)},
}
```

> 设计取舍：初版我把「合成用例名 + 中文名」也一起登记了，写成测试后立刻炸出
> 「半透明平铺文字 vs 极淡平铺文字」的分歧。**但这不是缺陷**——「极淡平铺文字」是
> 合成水印的**内容描述**，「AI 极淡平铺」是**检测模式名**，两者本就属于不同层面，
> 而那张 case→preset 映射本来就有唯一来源。**真正的问题是我制造了第三份名字。**
> 故改为只登记真值映射。（若当时强行"统一命名"，就是拿一个新引入的重复源去覆盖
> 一个已有的正确分工。）

### 4.3 README 增加「验证状态」列 + 结构守卫

```markdown
| 类型 | 预设名 | 说明 | 验证状态 |
| 角落 LOGO | `ai_logo` | ... | 合成用例 + **真实图 30 张已验证** |
```

2. `quality_gate.CASES is make_demo_assets.CASES`（**不能复制用例表**）；
3. 声明表键 ⊆ `core.detection_presets` 注册表；

第 1 条与第 7 条是**双向钉子**：一旦给 `ai_gradient` 补了合成用例、或给别的类型补了真实标注，

## 6. 新增经验（续 `LESSONS.md` 43–47）

43. **「已有守卫」必须问「它在当前分布下会不会触发」（93）**：`core/detector` 早有 30% 覆盖率上限，30 张真实图里只有 2 张触发 ⇒ 与没有守卫在功能上等价，却提供了「已经有保护」的错觉。凡发现「已存在阈值」，先量化它的**触发率**。
44. **漂移方向必须从红线方向派生，不能各写一份（93）**：`mask_coverage` 越高越坏，而旧的漂移实现只查「下滑」⇒ 掩码膨胀到 30% 也不报。**同一指标的「变坏方向」只能有一个真值来源。**
45. **均值之比 ≠ 逐图比值的均值（93）**：`total_pred / total_truth = 47×` 与门禁实测 `16.62×` 相差近 3 倍，因为各图真值面积不同。**凡"倍率/比率"类指标，必须先明确是"宏平均还是微平均"，并以实现输出为准标定阈值。**
46. **跨口径的指标不可直接比较（93）**：`detect` 模式下 `seam_delta` 更小（9.50 < 13.88）**不是修得更好**，而是掩码区从 0.97% 膨胀到 16.18% 后**区域构成变了**、指标被稀释。**任何"变好/变坏"的结论都必须锁定口径**；区域级指标的"区域构成"是口径的一部分。
47. **「没标」必须与「没有」可区分（93）**：真值稀疏会被结构性读成零漏检。修法有两层——① 允许把「确无该类」**显式登记为 0**；② 把「覆盖面不足」变成**可打印、可落盘、可被 CI 要求**的信号（默认告警 + `--strict-scope` 升级），而不是默认失败（永久红灯会让门禁失去拦回退的作用）。
