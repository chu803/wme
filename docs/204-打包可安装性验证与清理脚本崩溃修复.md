# 阶段 204 · 打包可安装性验证 + `clean_artifacts` 崩溃修复

> 起点：代码侧判据已全部对称、全库无真缺陷。转向**从未实测过**的一环——
> `pyproject.toml` 明确写着「足以支撑**本地可安装**（`pip install .`）」，
> 但这个承诺**从未被验证过**（188 只加了元数据 + 版本一致性测试）。
> 「文件存在」≠「能用」，这正是我一路在找的「承诺面 vs 实测」缺口。

## 一、发现 1：`pip install .` 在残留 `build/` 下失败（不幂等）

第一次验证：

```
python -m pip install --no-deps --no-build-isolation --target .scratch/install_probe .
...
error: [WinError 183] 当文件已存在时，无法创建该文件。:
  'build\bdist.win-amd64\wheel\wme_watermark_eraser-1.0.0.dist-info'
ERROR: Failed building wheel for wme-watermark-eraser
```

根因：仓库工作区残留着上一次构建的 `build/bdist.win-amd64/wheel/...dist-info`，
`bdist_wheel` 再次构建时**撞名**。

**这是真实的可复现性缺陷**（虽属「工作区残留」类）：
`pip install .` **不幂等**——在同一工作树上跑第二次会失败。
新克隆的仓库没这个问题（`build/` 在 `.gitignore` 里），但**开发者日常的工作树**会中招。

## 二、发现 2（更重要）：`clean_artifacts.py --archive` **崩溃**

既然要清 `build/`，就**dogfood 项目自己的 E2 工具**（`--archive` 是主路径、
用 rename 可逆，符合 LESSONS 202）。结果它**当场崩溃**：

```
Traceback (most recent call last):
  File "scripts/clean_artifacts.py", line 285, in archive
    rel = _os.path.relpath(src, root)
ValueError: path is on mount '\\\\.\\NUL', start on mount 'D:'
```

### 根因：分类器造出了处理器不认识的类别

`classify_file` **早就**产出了 `stray_nul` 类别（源码 124/131 行有文档与实现），
报告里也确实单独列出 `stray_nul 1 1 0 B`。但 `archive()` **没有处理这个类别**：

```python
rel = _os.path.relpath(src, root)      # ← 在 try 之外
dest = ...
try:
    shutil.move(src, dest)
except OSError as e:
    failed.append(...)
```

Windows 的保留设备名（`NUL` / `CON` / `AUX`）会被 `ntpath` 识别为**设备路径**
（`\\.\NUL`），与项目所在盘符不是同一个 mount ⇒ `relpath` 抛 `ValueError`。
而它在 `try` **之外** ⇒ **整个归档轮次当场中断**——
**一个坏条目毁掉全部**（实测：崩溃前已归档的条目成功，崩溃后的全都没处理）。

> 实测确认：`NUL` / `CON` / `AUX` 均触发；`COM1` **不**触发（ntpath 只对这几个特殊名处理）。

### 顺带发现的第二个小缺陷

原实现在 `shutil.move` **之前**就 `print("归档 → ...")`——
move 失败时输出与真实状态**矛盾**（说了"归档 →"却没归档）。
同源经验（`regression-gate-authoring` skill 已记录）：
**成功路径的展示性输出不可先行**。

## 三、修复

### `scripts/clean_artifacts.py`

1. **新增 `_NON_ARCHIVABLE` 登记表**（带理由）：
   分类器产出的**每个**类别，处理器都必须有明确处置——
   `stray_nul` 应「被报告但不被归档/删除」。
2. **逐条目错误隔离**：`relpath` / `makedirs` / `move` 全部纳入 per-item `try`，
   单条失败只记入 `failed`，**绝不中断整轮**。
3. **`print` 移到 `move` 之后**（消除状态矛盾）。
4. 结束时汇报 `成功 N / 失败 M / 跳过 K`，并把跳过的条目**连理由一起列出**
   （用户需知道它仍存在）。

### `tests/test_clean_artifacts.py`

新增 3 条守卫：

| 用例 | 作用 |
|---|---|
| `test_archive_skips_registered_non_archivable_without_crashing` | 不可归档类别必须**跳过**而非崩溃 |
| `test_archive_isolates_per_item_failure` | **单条坏路径不得中断整轮**（本缺陷核心修法） |
| `test_non_archivable_keys_are_real_categories` | `_NON_ARCHIVABLE` 的键必须是分类器**真会产出**的类别（防幽灵登记，同 217） |

## 六、教训 → LESSONS 218

**① 「承诺面」必须实测。** `pyproject.toml` 写着「足以支撑 `pip install .`」，
但从未有人真的跑过——**未经实测的承诺等于没有承诺**（同 185 A5：「没量过」≠「不行」，
但更糟的是「写了却说不出依据」）。

**② 分类器产出的每个类别，处理器都必须有明确处置。**
一个**未处置的类别**（本例 `stray_nul`）就足以中断**整轮**处理——
这是「分类器与处理器不一致」，比「分类错误」更隐蔽（分类明明是对的）。

**③ 逐条隔离 > 全或无。** 批量操作里单条失败不应毁掉整批：
`relpath`/`makedirs`/`move` 这类**每条目都可能独立失败**的调用，
必须包进 per-item `try`。本轮实测的后果很具体：**一个 `NUL` 让其余 78 条都没处理**。

**④ 成功路径的展示性输出不可先行。** `print("归档 → X")` 放在 `move` 之前，
失败时输出与真实状态矛盾（同 skill 中 `relpath` 跨盘符的既有提醒，**这次真的撞上了**）。
