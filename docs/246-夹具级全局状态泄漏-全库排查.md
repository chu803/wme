## 3. 真根因：夹具只close 不摘除

`tests/test_utils_audit90.py::fresh_logger` 的 teardown（修复前）：

```python
for h in list(L._shared_handlers.values()):
    h.close()          # ← 只关句柄，从不 lg.removeHandler(h)
```

于是**每个**用 `fresh_logger.get_logger(...)` 建过 logger 的用例，都把一批
**已关闭**的 handler 留在**全局** `logging` 注册表里跨用例存活。

**为什么 245 只修 1 个反例不够**：245 定位到「注入式反例污染全局」，于是把那个反例
补了还原——但夹具造成的泄漏是**普遍性的**：该文件 12 个 `fresh_logger` 用例，
每个都留下 3~5 个关闭的 handler。245 的探针只看 `t90.old1`/`t90.old2` 两个名字，
**低估了污染范围**。

### 修复（一处覆盖全文件）

```python
for lg in list(L._logger_cache.values()):
    try:
        for h in list(lg.handlers):
            lg.removeHandler(h)      # ① 先摘除
    except Exception:
        pass
for h in list(L._shared_handlers.values()):
    try:
        h.close()                   # ② 后关闭
    except Exception:
        pass
```

**顺序不可颠倒**：只close 不摘 = 残留；只摘不 close = 漏句柄。

## 4. 守卫设计：两次踩坑后才对

本阶段守卫**改了三版**，每一版都踩了自己上一版立的坑，这本身就是教训：

| 版 | 设计 | 为什么**不行** |
|---|---|---|
| v1 | 独立文件 `test_zz_probe246.py`，靠**文件名字母序**排到被测文件之后观测 | `test_logging_*` < `test_utils_*` ⇒ 实际排在**前面**（idx 84 vs 180）⇒ **观测不到任何东西，守卫恒绿 = 哑巴** |
| v2 | 自带被测逻辑（内联复刻夹具生命周期） | 测的是**复刻品**不是被测实现 ⇒ 注入退化时仍绿（实测确认：删掉 `removeHandler`，守卫仍 PASS） |
| **v3（采用）** | 放进 `test_utils_audit90.py` **文件内**，用 `fresh_logger` **真实夹具**，靠「上一个用例布场、下一个用例后置断言」实现 | — |

**v3 的机制**：`test_zz_fixture_teardown_leaves_no_closed_handler` 用真实夹具建一个
`logger 并**故意不清理**（布场）；夹具 teardown 在该用例**之后**执行；
于是下一个用例 `test_zzz_fixture_teardown_actually_detached` 断言「此刻该logger
上不应有本项目的已关闭 handler」。两次都走真实夹具 ⇒ 顺带验证 teardown
**可重复且幂等**。

### 守卫有效性验证（注入式反例）

删除夹具里的 `removeHandler` 段后：

```
FAILED tests/test_utils_audit90.py::test_zzz_fixture_teardown_actually_detached
E   AssertionError: 夹具 teardown 未把 't90.teardownprobe' 上本项目的 handler 摘干净，
    残留已关闭的：['logging.StreamHandler', 'logging.handlers.RotatingFileHandler',
                  'logging.handlers.RotatingFileHandler']
```

还原后即恢复 ⇒ **不是哑巴守卫**。

`tests/test_logging_fixture_leak246.py` 另含两条**判据自检**：
① 证明「只 close 不摘除」确实会留残留（否则主守卫是哑巴）；② 证明
「removeHandler 后即不判泄漏」（否则守卫逻辑本身有误）。
