## 性能门禁（perf_probe）红：归因为 CPU 持续负载降频，非代码回退（2026-10-22 晚）

**现象**：`perf_probe`（detect 阶段，`use_ocr=False`）报 P95 1.70~1.81s vs 护栏 0.882s（基线 0.679s）；
第二次起触发探针自己的「锚点轮内劣化」判定（尾/首 1.545 / 1.599），退出码 2。

**排除代码的三条证据**：
1. **对照实验**：`WME_DETECT_OCR_BOX_TRUST=0`（完全关掉本阶段改动的救援通路）→ P95 1.807s、同样轮内劣化
   ⇒ 与阶段 313 的改动无关（改动只删循环，不增加工作量）。
2. **GPU 不是瓶颈**：纯 MatMul 持续压测 60s，SM 时钟稳定 2437~2460MHz、功耗 114W、温度 70→77°C、显存 1.8G/8G
   ⇒ 无 GPU 硬降频、无显存溢出。
3. **决定性判据**：用「纯 numpy FFT」当基准尺——检测负载前 0.092s，一轮检测后 **0.197s**（2.1×），
   两轮后 0.191s、三轮后 0.201s，维持在该水平 ⇒ **同一进程内，与检测无关的纯 CPU 计算也一起变慢**。

**结论**：机器在「平衡」电源计划下，持续负载时 CPU 降频约 2×（WMI 的 `CurrentClockSpeed` 恒报基频 2200MHz，
读不到睿频，不能作判据；只能用外部基准尺测）。基线 0.679s 是 2026-10-06 在可维持睿频的状态下测得。

**处置**：**未重锚性能基线**（重锚会把 2× 降速固化成"正常"，属掩盖退化）。
待用户切「最佳性能」电源计划后复测；若仍不达标，再查是否为散热/功耗墙。

## 阶段 314 · 产品入口输出编码加固 + 非 ASCII 路径告警（功能实测审计产出）

**发现路径**：按「不读文档、逐条真跑」审计 13 项能力（API 各入口 / 批量 / PDF / 视频 / 模型管理 /
REST 自检 / CLI / UI）。11 项一次通过；2 个「失败」复核后是我调用姿势问题（`evaluate` 默认 False
返回 None；批量漏传 `allow_auto_erase`）——**产品行为正确，不改**。

**真缺陷一：三入口在 GBK 管道下崩**
- 最小复现：`python -c "print('✅ 完成')" > out.txt 2>&1` → EXIT=1。
- `main.py`(4) / `cli.py`(11) / `server.py`(10) 都有 GBK 不可编码字符；重定向时在**任务完成后**
  崩，退出码 1 ⇒「成功」被读成「失败」，日志汇总丢失。
- 为什么漏了：阶段 170 的元守卫只扫 `scripts/*.py`，**产品入口天然在射程外**——门禁越全越容易
  给人「整族已修」的错觉。
- 修法：实现从 `scripts/console_encoding.py` 迁到 `utils/console_encoding.py`（`packages.find`
  不含 scripts/，入口从 scripts 导入会在 pip 安装后 ImportError）；scripts 侧留一行转出，
  30 个脚本导入路径不变；三入口在 `from __future__` 之后、**业务模块导入之前**调
  `force_utf8_stdio()`。
  ⚠ 第一版只放在 `main()` 里，重定向文件仍混着 GBK 与 UTF-8——插件注册日志发生在
  **模块导入期**（早于 main）。加固必须早于业务模块导入；已加守卫
  `test_entry_hardens_before_business_imports` 锁住顺序。

**真缺陷二：非 ASCII 安装路径 ⇒ 模型加载报「文件不存在」**
- 本机实证：项目在含中文路径时 `torch.jit.load(big-lama.pt)` 报 WinError 127，文件明明在；
  一次拖垮 46 个用例，症状与「权重缺失」无法区分。
- 为什么漏了：`path_helper` 文件头早写了「中文路径」痛点，但那条只覆盖 OpenCV 读图（字节读入
  绕过），**torch 自己的文件打开从未纳管**。
- 修法：`non_ascii_path_warning()` 纯函数 + 启动自检 2.2b（WARN 不阻断）+ ModelLoadError 追加提示。
  取「第一段连续非 ASCII」而非去重排序（`工具` 而不是 `具工`）。

**刻意不改**：`batch_remove` 逐条返回 failed 是阶段 233 的设计（有守卫锁着「如实报 failed +
原因指向确认门」）；perf 红是环境（见上一节）。

**验证**：新增守卫 13 例全绿；编码相关三文件 53 passed；全量首轮 3187 passed / 2 failed——
① `test_real_gate` 守卫钉了旧文件路径（真回归，已改为按函数对象 `inspect.getsource` 断言）；
② `test_cpu_load_probe` 隔离跑通过，全量时受 CPU 降频抖动（环境）。

**教训**：**元守卫的扫描范围就是它的盲区边界**。170 把「凡 print 非 GBK 字符的脚本」机械化了，
但范围写死 `scripts/`，于是产品入口永远是绿的——**守卫的绿只证明它扫过的地方**，不证明没扫的地方。
同族：313 的 Docker 反例硬编码常量、107 的 `guard=` 实参遮蔽 config。

## 阶段 314b · UI 端到端实测：ImageEditor 丢 alpha ⇒ 一键修复重绘整图（严重）

**方法**：真开内置浏览器，走「上传 → 自动检测 → 一键修复 → 取结果」，而不是只调 API。

**主缺陷**：检测完成后直接点「一键修复」，状态栏显示「编辑框 4,194,304 像素 / 你补画 4,134,147 像素」
（用户一笔没画），输出图 **82.11% 像素被改动**，远离水印的左上角也变了。

**根因（插桩实证）**：浏览器回传的图层是 `shape=[2048,2048,3]`、`alpha_uniq=None`、
`rgb_mean=[255,59,48]` ⇒ **Gradio 6.x 把图层压成 RGB、丢弃 alpha**。而 `_mask_to_rgba_layer`
当时是「RGB 全图刷红 + 靠 alpha 表达掩码」⇒ alpha 一丢，整层灰度恒 ≈116 > 阈值 10 ⇒ 整图掩码
⇒ `merge_masks` 得整图 ⇒ 整图修复 + 整图后处理。**服务端单测全绿**，因为测试直接传 RGBA、
从未模拟 Gradio 的往返形态。

**修复**：只在水印处上色、其余纯黑（alpha 仍写）。修复后：编辑框 4,194,304 → **63,106**，
「你补画」4,134,147 → **2,949**，图层 RGB 均值 → (3.75,0.93,0.77)。
新增 `tests/test_mask_editor_alpha_loss.py`（5 例）模拟「丢 alpha 的往返形态」。
剩余 ~79% 像素变化经 A/B 归因为**默认后处理**（全局降噪/锐化）：`postprocess=False,denoise=0`
改动 5.05%，开默认 35.05% ⇒ 既有设计，未改（若要做「只动水印区」需收窄后处理作用域，独立阶段）。

**异常输入审计**：0 字节图片透出 `OpenCV(5.0.0) ... loadsave.cpp` 原始异常
（`cv2.imdecode` 对空数组是抛错而非返回 None）；损坏 PDF 透出英文 `FileDataError`。
已改为 `CorruptedImageError("图片文件为空（0 字节）…")` 与「无法打开 PDF…原因：…」，
新增 `tests/test_bad_input_readability.py`（4 例）。其余坏输入实测已合格。

**测试稳健性**：`test_process_and_system_estimates_are_same_order` 全量偶发红（隔离必绿）
⇒ 两个 1.5s 采样串行、落在不同负载窗口 + 低负载比值无意义。改为**并发采样** + 负载 <5% 显式 skip。连跑 3 次全绿。

**教训**：**服务端单测全绿 ≠ 浏览器往返可用**。组件库会在序列化/反序列化时**改变数据形态**
（这里丢了 alpha），而单测通常只喂「理想形态」。凡「UI 预填数据靠非主通道（alpha）承载语义」，
必须有「模拟组件往返形态」的守卫。

**手涂页自动化的边界**：合成 pointer/mouse 事件画线后，服务端回报「未检测到任何涂抹/框选区域」
⇒ 笔迹根本没进编辑器，**手涂路径没做成点击级 E2E**。改用数据层等价验证补位
（`test_user_brush_layer_survives_alpha_loss`：浏览器笔迹 = 透明底 + 不透明笔迹，
丢 alpha 后底为黑 ⇒ 掩码恰等于笔迹面积），钉住「预填才踩坑、手涂天然安全」的区别。
