## 阶段 318 ·「只动水印区」后处理作用域开关 + A/B 判决

> 实现写于 10-22 晚，A/B 数据落在 10-23（昨夜的第一次 A/B 在关闭工作区时被连进程终止，
> 停在 51/60、JSON 未落盘 ⇒ 今晨重跑整轮）。

**动机链（三条实测）**：314b 关后处理 5.05% vs 开默认 35.05% → 316 原分辨率真图水印**外**改动
46.9%–88.4% → 317 误伤 33.8%–72.7% 且**四种水印几乎一样** ⇒ 与预设无关，来自后处理。
**根因不是 bug**：阶段 60 明确裁决「掩码内不锐化（unsharp 会放大填充区残留）、掩码外照常锐化」，
"顺手锐化整张图"是**有意设计**。本阶段不改裁决，另给一种契约。

**实现**：`POSTPROCESS_PRESERVE_UNTOUCHED`（默认 False）+ `POSTPROCESS_PRESERVE_BAND_PX`（8）。
后处理第 ⑧ 步把「掩码 + 8px 带之外」**逐字节还原**成原图像素。缺原图/掩码/形状不符 ⇒ 静默跳过 + info
（与真·超分同惯例）。**纯 config 驱动**，不新增任何门面参数 ⇒ UI/CLI/api/REST 四条链同时生效，
刻意规避 315 撞出的「服务层支持、门面漏接」（LESSONS #298）。

**A/B（60 用例，只翻开关，逐用例配对 60/60）**：
| 类型 | gain off→on | 误伤% off→on | ΔPSNR off→on |
|---|---|---|---|
| edge_text | 0.939 → 0.939 | 50.58 → **1.09** | −5.97 → **−2.31** |
| corner_logo | 0.532 → 0.532 | 50.59 → **0.80** | −5.42 → **−3.17** |
| faint_tiled | **−0.117 → 0.010** | 49.58 → **2.09** | −7.88 → **−5.82** |
| grid | **−0.172 → 0.002** | 49.02 → **1.39** | −7.65 → **−6.09** |

硬判据：**0/60 gain 变差**、**60/60 误伤下降**（中位 50% → ~1%，20–60×）、**60/60 ΔPSNR 改善**
（+2.2~3.7 dB）。残余误伤 57/60 仍有 0–16.5%，但全部落在**工具自己判定的水印区**（检测误报），
归检测侧 —— 不是后处理乱动。

**计时别抄错**：跨会话 304s→680s（2.2×）是**机器状态**（今晨整机 off 基线也从 4.0s/张变 11.5s/张）。
同进程、同图、A/B/B/A 交替对照：`off=11.48s on=11.39s 比值=0.99x` ⇒ **开关不增加耗时**
（一次 dilate + 一次 np.where）。教训：**跨会话的绝对耗时不可比**，性能结论必须同进程交替。

**两个实现坑（守卫反推出来）**：
- `cv2.dilate` 默认边界值 `morphologyDefaultBorderValue`(DBL_MAX) 对膨胀等于「图外全是前景」
  ⇒ 沿四边凭空生出 8px 实心带，把最该还原的边缘错误保留成后处理结果（与 317 探针同族）。
- OpenCV 5 的 `dilate` **不接受 bool**（`Unsupported data type (=9)`）⇒ 先 `astype(np.uint8)`。

**守卫**：`tests/test_preserve_untouched318.py` 11 例（纯 numpy 毫秒级），三段式
「关时不变 / **开时确有差异** / 差异只在作用域」。关键设计：`test_outside_band_is_bit_exact_when_on`
**先断言关闭态带外真有 >50% 像素被改**（否则"开起来一样"是空断言），
`test_band_zero_restores_the_ring_that_band_eight_keeps` 同时钉「带宽真的起作用」与「keep 方向没写反」
（反写会把修复成果一起抹掉，而纯 no-op 比较发现不了）。经验 #304。

**默认值未翻**（用户 10-22 定「先看判决再定」）：建议 318b 做 `--preserve-untouched` + 设置页 + REST 暴露，
按 315 的对称性守卫推进，跑一段真实反馈再谈默认 —— 翻默认等于换一代产品的观感。

## 假设否证：给 `grid_on` 加 regularity 门槛（不实施，留档防重试）

**动机**：317 显示 1/15 真实照片被误推成 `ai_grid`（clean_01，grid 分 0.351），而 `grid_on`
**不要求** `regular`（`tiled_periodic` 要求）。看起来加一条 `regular` 就能挡住误触发。

**实测（推荐器打分，纯 CPU）**：
- 15 张真实照片的 `regularity` 全在 **0.000–0.001**（`corner` 二值 0/1，5/15 命中；`text` 恒 1.0）；
- **合成点阵用例的 `regularity` 也只有 0.001–0.003**
  （`make_textured_base` + `wm_grid` = 0.003；`bench_grid_seed1.png` = 0.002；`bench_tex_grid_seed1.png` = 0.001），
  但它们正是靠 `grid=0.39–0.79` 才被正确推荐成 `ai_grid` 的。

⇒ **加 `regular` 会连带打死合成点阵通路**（quality_gate 的网格用例立即失效），而它对真实照片的
区分力为零。**假设否证，不实施。**
（与 LESSONS #248 的 0.094/0.381 不矛盾：#248 量的是**填充式平铺**（整块 tile），
稀疏点阵的频域能量是弥散的，regularity 天然低。）

**真正的缺口**：不是「少一条门槛」，是**风格覆盖面**——
① 角标：NCC 模板库来自 9 张豆包图 + 白底板先验（V≥140/S≤80），而本次合成的是**深色圆角板 + 白字**，
两条信号都不命中 ⇒ 落到 `text` 分支「误打误着」；
② 点阵/极淡平铺：检测器在真实纹理上检回 0.001–0.204（317），属检测能力，不是推荐门槛。
两条都要动检测侧并走「先出判决再定重锚」，不在今天改。

## 319-C 消融：哪些预设真的需要 OCR（冷启动砍半的前置判决）

**问题**：冷启动 7.23s 里 CUDA ≈2s + EasyOCR ≈2s，但默认引擎是 OpenCV（`INPAINT_AUTO_PREFER=opencv`）、
且部分预设根本不做 OCR —— 那这两笔初始化是不是白付？

**消融（3 张真照片 × 3 类水印，engine=opencv，auto_preset）**：
| 用例 | 被推荐 | used_ocr |
|---|---|---|
| corner_logo（×3 图） | ai_grid 1 / ai_text_heavy 2 | **True ×3** |
| edge_text（×3 图） | ai_text_heavy ×3 | **True ×3** |
| grid（×3 图） | ai_grid ×3 | **False ×3** |

⇒ 文字/角标通路需要 OCR；**点阵通路完全不需要**。而当前实现里 EasyOCR 与设备选择
都在首次处理时**无条件初始化**。
⇒ 可省：① 点阵类预设跳过 OCR（≈2s）；② `engine=opencv` 时跳过 CUDA/torch（≈3s，默认就是 opencv）。
合计理论可省 ≈4s（7.2s → ~3s），但需改 `core/detector` 与 `core/inpainter` 的**初始化时机**，
风险高于前几个阶段，按「先出判决再定」流程：**本日不改，列为 320 候选**。

## 阶段 320e · 设备选择惰性化（OpenCV 引擎不再为不用的 GPU 付钱）

**定位**：`core/inpainter.py` 无条件 `select_device()`（实测 **1.66s** + `import torch`），
而内置 OpenCV 引擎的 `inpaint(device=None)` 根本不看它；LaMa/插件引擎自行
`device or select_device()`；且 `select_device()` **有缓存**。
改为 `if device is None and engine != "opencv": device = select_device()`。输出逐字节不变。

**实测（真跑 CLI，同会话）**：OCR 开（默认）7.64s，日志**仍有**「自动选择设备」——因为检测阶段的
OCR 阅读器先选了（缓存命中，本改动省不到）；`WME_DETECT_USE_OCR=false` 时
**7.64s → 3.27s（−4.4s，−57%）**，日志不再出现设备选择。

**又救回一条错误结论**：319 时我一度以为「默认 OpenCV 通路必然白付 1.66s」，实测发现只要检测
跑了 OCR，设备早就被选过。收益条件只有「OCR 关闭 / 无文字策略预设」。

**守卫**：`tests/test_lazy_device_selection320e.py` 3 例（OpenCV 不选 / LaMa 仍选 / 显式 device 不再选），
纯接线不加载模型。

**产物**：`docs/320e-设备选择惰性化.md`（已登记 INDEX）、`core/inpainter.py`、测试。

### 收尾：两次「INDEX 只写小节、漏文件链接行」
320c 与 320e 各犯一次（文档索引守卫 test_every_doc_is_referenced_in_index 两次都抓住）。
**规矩**：给 INDEX 加阶段时必须成对写「### 编号 · 标题 小节 + - 文件.md 链接行」，
小节写完立刻检查最后一行是不是文件链接——否则守卫会红一次、多跑一整轮门禁。

### 320c 补丁：CLI 的 -f 默认值把「没意见」伪装成「显式指定」
单测全绿后真跑复验组合行为，输出仍是 .png（尽管 WME_OUTPUT_FMT_FOLLOW_INPUT=true）。
根因：cli.py 的 -f 默认 = config.DEFAULT_OUTPUT_FORMAT("PNG")，而 _resolve_out_fmt 的
第一优先级是「显式 out_fmt 永远最高」⇒ CLI 每次把配置默认值当成了用户选择，跟随输入永远走不到。
修法：-f 默认改 None；头部显示「格式=跟随输入（默认 PNG）」。
单测没抓到的原因：端到端用例直接调 process_file(out_fmt=None)，绕过了 CLI 层——
层与层之间的默认值没被证明是"没意见"还是"做了决定"（#298/#304 的老坑）。
新增守卫：args.fmt is None + 真跑 CLI 断言 .jpg 且无体积提示。实测：开→.jpg/无提示，关→.png/有提示。
