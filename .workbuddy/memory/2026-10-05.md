## 单图 OCR 超时护栏收口（关闭上文待办「加单图 OCR 超时护栏」）
- 动机：general 全量曾撞某真实图触发 EasyOCR CPU 极慢路径，单 patch 卡数分钟（general 全量 918.8s）。需护栏使单图 OCR 卡死时降级而非拖累整批。
- 实现：`core/detector.py:_ocr_readtext` 改为 daemon 线程 + `th.join(timeout)`；超时返回 `[]`（降级走板块/图标通路）。`config.py` 新增 `DETECT_OCR_TIMEOUT: Final[float] = _env_float("DETECT_OCR_TIMEOUT", 30.0, 0.0, 3600.0)`（默认 30s，env 可覆盖，<=0 关护栏走原生 readtext）。
- 设计反转（重要）：初版用 `multiprocessing.Pool` 子进程 + `apply_async.get(timeout)`（OS 级可靠超时），但**回退**：① 子进程内 OCR 跑在 worker，测试用 monkeypatch `_get_ocr_reader` 注入的伪 reader 无法跨进程到达 → 破坏既有 `test_ocr_corner_fallback.py` 3 例守卫；② 每次调用额外付出 IPC + 图像 pickle + worker 内 EasyOCR 重建开销。而真实慢 OCR（torch/cv2）**释放 GIL**，故线程 `join(timeout)` 即可靠返回——子进程仅对「GIL 持有的长阻塞」才必需（极端边角，仍会跑完只是慢）。线程方案零 IPC、保留测试注入模型、对真实场景足够。
- 验证：
  - 单测 `tests/test_ocr_timeout_guard.py`（2 例：快路径 timeout<=0 直返结果 / 慢 reader+小超时按时降级 []）+ `test_ocr_corner_fallback.py`（3 例）全过（5/5）。
  - 端到端冒烟 `benchmark_real/images/q1.png`：`detect_watermark_mask(use_ocr=True)` → `used_ocr=True`、6 区域（含右下角豆包文字水印 2444,1428 / 2539,1432）、9.8s、无挂死。证明超时护栏对快 OCR 透明、不破坏 ai_logo 召回（0.3460 维持，护栏仅在 >30s 挂死时触发，正常图永不触发）。
- ⚠️ 诚实边界：护栏对「GIL 持有的无限阻塞」不保证打断（仅降级为「跑完为止」，仍会结束而非永久挂死）；真实场景罕见，且即便触发也只是单 patch 多等最多 30s。如需绝对上限，将来可改 `signal.alarm`（Unix only）或保留子进程方案并改测试注入方式（如 worker 内读 env 选伪 reader）。

## Stage 211 · 性能 P2：P95 1.53s → 0.68s（首次达标）+ 修复门禁永久失效
> 起因：Docker 真构建阻塞在用户侧（无 docker CLI），自主转P2 性能。**发现两个独立缺陷**：① 检测阶段一个 O(keep×H×W) 复杂度错误 ② 性能门禁自2026-10-01 起一直判「跳过」（护栏零约束）。

### 缺陷 A：`_suppress_natural_light` 的 O(keep × H×W) 写回（性能真凶）
- 归因**做到语句级**（不止cProfile）：真实图 `ai_logo_04_neon_street_night.jpg`(2048²) 有 **14098个连通域**（area≥16 者 1589个）。把守卫循环体逐语句计时，真凶不是 Sobel 也不是 percentile，而是**写回结果那两行**：
  | 语句 | 耗时 | 占比 |
  |---|---|---|
  | `labels == i`（**全图**比较） | 684.9ms | **45.2%** |
  | `out[labels == i] = 255` | 276.4ms | **18.2%** |
  | `np.percentile(P90)` | 269.8ms | 17.8% |
  | Sobel/dilate/mean/其余 | ~229ms | ~19% |
  ⇒ 「循环内逐域做一次全图比较+写回」= 1589 × 2048² ≈ **66 亿次**。角标通路仅 0.018s、edge_text 0.018s ⇒ 记忆里「瓶颈在CPU 检测」没错，但**具体是半透明水印的自然光影/纹理守卫**。
- 修复（最小、逐位等价）：三处（`_suppress_natural_light` / `_suppress_texture_like` / `_components_mask`——后者是所有掩码生成的必经路径）统一改为「**循环内只收集 keep_ids，循环外 `lut[labels]` 一次查表**」，O(keep×H×W) → O(H×W)。
- **验收（同一进程内对照，排除跨运行噪声）**：10 张真实图 mask **10/10 逐位相同**（`np.array_equal`），P95 **1.534s → 0.672s（−56.2%）**、总耗时 8.499s → 5.563s（1.53×）、最慢图 1.53s → 0.67s（2.28×）。**零质量代价**，故无需刷新任何真值基线/重跑召回门禁。
- 守卫 `tests/test_perf_guard_rewrite.py`（新，12 例）：① 用「朴素循环」作参照实现做**逐位等价**断言（5 seed × 4 种保留比例 + `_components_mask` dilate∈{0,1,3}）② **源码级防复发**——功能测试对「输出相同但慢 60倍」完全无感，必须靠源码断言禁掉 `labels == i` 回归。

### 缺陷 B：性能门禁永久跳过（护栏零约束，已失效约 4 天）
- 现象：`perf_probe` 恒返回**退出码 2（跳过）**，提示「device 不一致（基线 None vs 本次 cuda）」。
- 根因：D1-Stage 6（10-04）把 `device`/`gpu_name` 加入可比性维度时**忘了递增 `BASELINE_VERSION`** ⇒ 2026-10-01 建的v1 基线仍过版本检查，落到键值比较才判不可比。
- **为什么特别危险**：退出码 2 =「未标定/不可比」在门禁契约里看似**良性**（有输出、有解释、不报错），而回归护栏「不许变慢」**一次都没生效过**；更糟的是提示会被**误读**成「本机是GPU、基线是CPU，硬件不同不便比」，于是纯代码缺陷被伪装成合理环境差异。
- 修复（四层）：① `COMPARABILITY_KEYS` 提取为显式常量；② `baseline_comparable` **区分诊断**——「缺字段（结构过旧，可修→提示 --update）」vs「值不同（跨硬件，设计意图，不该建议重标定）」；③ `BASELINE_VERSION` 1→2；④ 重新标定基线（带 `device=cuda` + gpu_name）。
- 顺带修一个**自相矛盾的死胡同**：`--update` 原会因「基线结构过旧」被判不可比而拒绝（要 `--force-update`），可版本递增的**目的就是逼人重标定**——递增版本却不许重标定。改为「结构过旧 ⇒ 允许直接替换；口径真的不同（source/stage/repeat/device）⇒ 仍硬挡」。
- 守卫 `tests/test_perf_gate_staleness.py`（新，6 例）：钉死版本铁律、**落盘基线必含每个可比性字段**（该缺陷的直接检测面）、缺字段与值不同必须给不同诊断、不可比仍必须判跳过（不许因 P95 好看放行）。写完先跑→**确实报红并精确指出缺 `['device','gpu_name']`**（注入式反例生效，非自我安慰）。
- **结果**：`perf_probe --update` 退出码 0，P95 **0.681s**，**首次低于路线图目标 1.5s**（此前 1.505s 恰好卡在线外），护栏恢复真实约束。
- ⚠️ **缺陷 C（同阶段暴露，诚实登记暂未修）**：`--update` 后紧接着跑纯判定，门禁**判红**（P95 1.564s vs 基线 0.681s×1.3）。归因=**机器负载噪声，非代码回退**，证据：同进程 A/B 对照在**同一高负载下**仍显示朴素 3.281s vs LUT 1.581s（−51.8%）、10/10 逐位等价——绝对值整体抬高 ~1.5× 而**相对收益稳定**。即 `min-of-k` 只滤**run 内**噪声，**跨 run 的机器负载漂移（本次约 2.3×）滤不掉**。**待修方向**（未定）：① 判定前探测系统负载（CPU占用/进程数）并如实标注「本次测量在负载下，护栏判定不可靠」；② 基线记录测量时的负载指纹，比对时纳入可比性；③ 或把护栏从绝对 P95 改为「与同机同负载的对照比」。**未擅自改动**——涉及门禁语义，需用户定调。
- 教训固化：见 LESSONS #229（复杂度错误要归因到语句级）、#230（维度变更必须递增版本号，否则护栏静默失效；「跳过」不等于「通过」）、#231（min-of-k 只滤run 内噪声，跨 run 负载漂移需另行处理）。
