## 阶段 330 · 一张码表不能喂给语义不同的子进程

**缺陷**：`run_all_checks.aggregate()` 用全局四档（0/1/2/3）直接解释每个步骤的原始退出码。
七道门禁的契约是我们自己定的 ⇒ 同源、没问题。但第 1 步是 **pytest**，它的 **2 = Interrupted
（收集期报错 / `-k` 选空）**，入口却按「⏭ 跳过」解释 ⇒ `[2,0,0,0]` 没有 1、没有 3、也不是全 2
⇒ **聚合返回 0、印「✅ 全部通过」**。翻译成人话：**一条用例都没跑，CI 也可以是绿的**。
CI 恰好是拿 `requirements-min.txt` 装最小依赖的机器，缺包最常见的形态就是导入期炸 ⇒ 2。

**实测（不背码表）**，本机 venv：

| 场景 | rc |
|---|---|
| 收集期 ImportError（`import definitely_not_a_module_xyz`） | **2** |
| `-k zzz_nothing` 选到 0 条 | **2** |
| 路径不存在 | **4** |
| 未知参数 `--badopt-zz` | **4** |

第一次量的时候 `$?` 拿到的是 `tail` 的 0 —— **LESSONS #310 同一个坑，同一天踩第二次**；
改成 `> file 2>&1` 再读码才对。3/5 本次没能自然造出，按 pytest 官方 `ExitCode` 枚举处理，没编实测值。

**修法**：不动全局表（那会把 328 的正确语义倒回去），改成**约定挂到步骤自己身上**——
`Step.skip_codes=(2,)` / `env_codes=(3,)` 为默认 ⇒ 七道门禁一行没改；pytest 显式 `(), ()`；
新增纯函数 `normalize_rc()`，`run_steps()` 逐步归一后才喂 `aggregate()`。
原始码仍留在日志（`rc=2→判1`）和报告 `rc` 字段，另加 `verdict`。

**守卫**（`tests/test_run_all_checks.py`，先红 `pytest 返回 2 时入口应判失败，实得 2`）：
① `test_pytest_nonzero_codes_are_failures_not_skips`（2/3/4/5 ⇒ 1，且那行含 ❌ 与原始码）；
② `test_gate_step_skip_and_env_codes_are_preserved`（反向：门禁的 2/3 仍是跳过/环境错误，防修复过头）；
③ `test_run_steps_all_skipped_returns_two` 把 pytest 排除在外并**把理由写进注释**
（它想测「全跳过」，而 pytest 回 2 不构成跳过；不写理由下一个人会以为是有人为了让它绿而放宽）。
该文件 **43 例全绿**。

**CI #17 仍是红的，还没诊断**：YAML 解析通过、门禁步骤确有 `shell: bash` + `set -eo pipefail`、
`corner_signal_gate` 在把 torch/easyocr/gradio/PIL 等全部打桩屏蔽后仍 rc=0（325 已量）。
本机 pip 连不上 PyPI（`from versions: none`）⇒ 无法复刻 min 环境。
缺的证据只有一个：**Actions 日志里哪一步带 ❌**（只有用户点得开）。
注意方向：**#17 变红有可能正是 329 修好的链路在正常工作**——以前这类错误被洗成绿，现在才第一次报出来。
这是假设，要靠日志证实或否证，不作为结论写进文档。

## 阶段 331 · 跨进程编码没有唯一固定点（330 那次验证的副产品）

## 阶段 332 · 让 CI 自己说出「哪一步红了」

四层「说不清的绿」修完之后，第一次真红（#17，45 秒）本机**读不到现场**：无 `act`、
pip 连不上 PyPI 复刻不了 min 环境、查 GitHub API 被安全策略拦 ⇒ 只剩「请人截图」。
**只有人能看懂的诊断 = 没有诊断。**

旧诊断只读 `gate_output.txt`，而那文件**只有 `entry` 步跑过才存在** ⇒
失败在 `checkout/python/system/deps` 时它只会写 `(no gate_output.txt)`：**诊断存在，覆盖面是 1/N**。
#17 只用 45 秒，走不到 `entry` 之后 ⇒ 假设红在 `entry` **之前**（pip/apt 最像）。标注为推断。

改法：诊断以「哪一步红了」状态表**开头**（`${{ toJSON(steps) }}` ⇒ `id: outcome` 逐行），
FAILED 清单在后；两文件同形改。配套给每个 step 补 `id` —— `steps` 上下文只含有 id 的步骤，
漏 id 的那一步在表里静默消失 ⇒ **表会骗人，比没有表更糟**。
守卫 `test_every_workflow_step_has_an_id`（机械枚举 `workflows/*.yml`、断言有 id / 仍有 `toJSON(steps)` /
仍有「哪一步红了」/ 切出步骤数 `>=5` 非空转；**不引 PyYAML**，CI 只装 min 依赖）
＋ `test_workflow_step_ids_are_unique_per_file`。反例：内存里删 `id: checkout` ⇒ 抓到 `- name: 拉取代码`。

本机把跑不了的部分拆成能跑的：抽出诊断 JS，`${{ toJSON(steps) }}` 换成三种 payload，
用桩替 `core/github` 交 `node` 跑 ⇒ `checkout: success / entry: failure`、`deps: failure`（早于 entry 的红也能指认）、
空表时老实写「(步骤状态不可用…)」。`tests/test_run_all_checks.py` 48 例全绿、两文件 `yaml.safe_load` 通过
（ci 6 步 / publish 10 步全带 id）。**#17 根因仍未证实** ⇒ 这一阶段只保证下一次红自带答案。
