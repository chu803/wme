## Stage 233 · 实施「全自动擦除确认门」（232 定性的产品层落地）
> 232 定性为**产品预期不符**（非检测缺陷）⇒ 修法落在产品层：让「系统替用户选预设 +
> 直接擦除」这条**静默**路径不再静默。

### 实现（异常式，**无法被静默忽略**）
1. **`config.API_REQUIRE_AUTO_ERASE_CONFIRM: bool = True`**（`_env_bool`，可 `WME_...=0` 关闭）——
   可逆杠杆，置 False 恢复旧全自动行为。
2. **`api.AutoEraseNotConfirmed(RuntimeError)`**：含 `.entry` / 可读消息，**消息里直接给出三条出路**
   （显式 preset / `allow_auto_erase=True` / 先 `detect_watermark_bytes()` 预览）+ 配置关法。
   **为何用异常而非返回值/状态位**：返回值与状态位都可被旧调用方**静默忽略**——
   那正是本门要消灭的形态（若返回原图，调用方会把「没擦」当成「擦干净了」）。
3. **`api._guard_auto_erase()`**（纯函数，便于单测）：放行条件四条——配置关 / 显式 preset /
   显式 `allow_auto_erase` / `auto_preset=False`。拒绝即「没指定预设 + 让系统自动选 + 没显式允许」。
   **判定不需要任何检测**（不需「不可靠检测」判据——那正是 232 三条路都没走通的地方）⇒ 零成本。
4. **`api.detect_auto_erase_required()`**：只查询不抛，供 CLI/REST **提前提示**。
5. 两个入口 `remove_watermark` / `remove_watermark_bytes` 增参 `allow_auto_erase: bool = False`；
   `batch_remove` **转发**该参数。
6. **`server.py`**：参数白名单加 `allow_auto_erase`（含字符串布尔归一）+ 把该异常映射为
   **独立状态 `needs_confirmation` + `hint`**（不混进通用 `failed`）。

### 机制：`_suppress_texture_like` **无法区分「文字字形」与「水印字形」**
其判据是「笔画内部平坦、只在轮廓陡变 ⇒ density 低」。**文字笔画形态完全相同**
（白字黑边：内部平、轮廓陡）⇒ **它不是坏了，是在回答另一个问题**。

用**合成正样本**（在真实图上叠微弱半透明水印，alpha 0.08~0.35）补上正样本分布

| lap_mean | 14.9 ~ 44.8 | 34.9 ~ 62.4 | ❌ 重叠 |
⇒ 单阈值不可行（skill：「区间 < 阈值分辨率 ⇒ 须换正交维度」，而我没找到干净的正交维度）。

### ❌ 否决 2：「区域数上限护栏」**方案被数据推翻**（**订正我在 222 登记的待办**）
标定基准图区域数分布：**min 3 / 中位 26 / p90 875 / max 1568**，
而**用户封面只有 21 个** ⇒ **正常基准图（800~1568 区域、覆盖率贴 15% 上限）比问题图更多**。
⇒ **「区域数过多」不是信号**，该护栏**完全无效**。**222 我登记的方案是错的**。

### ❌ 否决 3：收紧检测器会**撞红线**
项目红线 **precision ≥ 0.050**（`real_gate`）⇒ **故意容忍 ≥95% 误检**，
为的是保召回。本例 15 FP / 4 TP ⇒ precision ≈0.21，**远在红线之上**，
**按项目自身标准「可接受」**。⇒ 收紧会伤召回红线。

### ✅ 最终定性：**这是「产品预期不符」，不是「检测缺陷」**
- 检测器设计目标是**召回优先、容忍过检**（红线为证）；而产品用户期望「**别毁我的图**」。
- 工作台**本就有**正确路径：`detect_watermark_bytes` 出掩码 → **人工确认** → 再擦
  （记忆里「自动出候选 → 人工确认 → 擦除」的交互设计初衷）。
- **缺陷只存在于「静默全自动」通路**：`remove_watermark_bytes(auto_preset=True)` 无人确认即擦。

### 建议（**待用户定调，未擅自改**）
① **API 层显式化**：`remove_watermark_bytes` 增加「**预览/确认**」语义或让「静默全擦」

② **文档明示**：全自动路径对「文字密集插画/封面」有毁图风险，建议走预览确认流程；

## Stage 227 · LaMa 修复段彻底拆解：**真凶是「降噪」，比 LaMa 推理还慢**（且是实现缺陷）

### ⭐ 拆解结果（生产口径，2048²，min-of-3）
| 环节 | 耗时 | 占 inpaint |
|---|---|---|
| 掩码预处理（astype/二值化/prepare/threshold/feather） | 0.039s | 1.1% |
| LaMa 推理（含张量搬运） | 1.459s | 42.8% |
| **`_denoise(strength=3)`** | **1.489s** | **43.7%** ← **真凶** |
| float32 力度融合（全图） | 0.227s | 6.7% |
| `empty_cache()` | 0.000s | 0% |
| — | — | — |
| **真实 GPU 算力**（`model(img_t, mask_t)`） | **0.379s** | **11.1%** |

⇒ **GPU 只占 11%**；`DENOISE_STRENGTH_DEFAULT=3` 的降噪**比 LaMa 推理本身还慢 4%**。

###根因：`only_masked` 只管输出合并，**降噪本身仍在全图跑**
`core/inpainter.py:316-324`：
```python
denoised = cv2.fastNlMeansDenoisingColored(bgr, None, strength, strength, 7, 21)  # ← 全图 2048²×3
if only_masked:
    m = (mask > 0).astype(np.float32)[:, :, None]
    return result*(1-m) + denoised*m# ← 只影响「用哪部分」，降噪已全做完
```
`DENOISE_ONLY_MASKED=True` 的**语义**是「只在掩码区降噪（保护细节）」，
**实现**却是「全图降噪 + 只用掩码区结果」⇒ **掩码区外的像素被白算了一遍**。
本图掩码覆盖 15% ⇒ **约 85% 的降噪计算是纯浪费**。
且 `fastNlMeansDenoisingColored` 是**非局部均值**算法（h=3, templateWindow=7, searchWindow=21），
常数极大，全图跑尤其昂贵。

- **双跑择优**：`INPAINT_DUAL_RUN=False`，不是双跑。
- **分块**：225 已复核收益噪声级（1.01×）且有画质代价。

### ⚠️⚠️ 但真正的收获是：**我先差点「制造」了一个不存在的负载干扰**
为确认机器空闲，我读Windows `GetSystemTimes` 算 CPU 占用，得到**51.8%**，
据此判定「有外部负载、基线不可信」——**这是错的，且错得很危险**：
若据此认定「机器忙、基线不可信」，就会把优化方向指向**不存在的瓶颈**（LESSONS 233）。

**根因**：**Windows `GetSystemTimes` 的 kernel 时间包含 idle**（微软文档明确）。
故`busy = kernel + user` 恒等于 100%×(1) 且把 idle 当忙。
**正确公式（已实测验证）**：
```
非 idle 占用 = (kernel - idle) + user
总量         = kernel + user          ← kernel 已含 idle，无须再加
占用率       = (kernel - idle + user) / (kernel + user)
```
**重复计数坐实**：三者和 = 131.47 核·满载秒，而物理上限只有 24 核 ⇒ kernel 含 idle。

**我自己也踩了第二个坑**：修公式后，我把「三者和 vs 1×N」当自检阈值——
而正确上界是**2×N**（idle 最多被重复计一次），结果**任何正常采样都被判「计时域异常」**
（实测 131.47 vs 阈值 24）。放宽到 2.2×N 后恢复正常。

## Stage 218 · OCR 成本结构定性：**像素主导**（给出 217 三方向的决策依据，仍不改生产代码）
> 217 定位到「OCR 被调 10 次、13.993s」但没答「该优化什么」。本阶段测**成本结构**——
>因为「像素驱动」与「固定开销主导」指向**完全不同的方案**，不测就是猜。

### ⭐ 成本结构：像素主导，固定开销可忽略
实测 9 档尺寸（先烧热排除惰性初始化），拟合 **`t ≈ 0.073s + 1.523s/百万像素`**：

| 尺寸 | 像素(万) | min-of-2(s) | 每百万像素(s) |
|---|---|---|---|
| 64² (小) | 0.4 | 0.030 | 7.362 |
| 320×320 | 10.2 | 0.229 | 2.234 |
| **640×640 生产主 patch** | 41.0 | 0.708 | 1.727 |
| **640×1280 放大后长条** | 81.9 | 1.348 | 1.645 |
| 2048² 整图 | 419.4 | 6.440 | 1.535 |

· **固定开销仅 0.073s**：在最小样本占 92%，但在**生产尺寸上只占 1~2%**。
· **每百万像素成本随尺寸下降并收敛到 ~1.5s/百万像素** ⇒ 纯线性像素驱动。
⇒ **「减少调用次数」收益有限**（10 次 × 0.073s ≈ 0.7s），**真正的杠杆是「别送大 patch 进 OCR」**。
（这直接否掉了我在 217 列的方向②，改为支持方向①/③。）

### 关键矛盾：放大是为召回小字，但代价是像素 ×4
`DETECT_OCR_UPSCALE` 对长边<640 的 patch 做 2× 放大 ⇒ 像素 4×。
生产 10 个 patch 的构成（217 实测尺寸 + 本阶段系数估算）：
- 640×640 未放大 ×5 ≈ 3.48s
- 153×1280→**306×2560** ×3 ≈ 3.80s（放大后最贵）
- 320×1280→**640×2560** ×2 ≈ 5.14s（放大后最贵）
⇒ **「被放大的那些」反而是最贵的**，而放大存在的唯一理由是「小 patch 识别不出」。

### 权衡实测（4 张真实图，同参对照，只翻转该开关）
| 配置 | 总耗时 | 区域数 | mask 像素 |
|---|---|---|---|
| upscale=True（当前） | 25.364s | 39 | 204181 |
| upscale=False | **16.479s** | **38** | 202402 |
⇒ **省 8.885s（35.0%）**，代价 = **丢 1 个区域** + mask 少 1779px。
丢的那个是**小尺寸文字**（217 已定位为 `ocr_text @ 1586,379, 32×8` 附近区域）——**只有放大后才识别得出**。

### 结论：**不擅自改，交用户定调**（质量 vs 速度是产品决策，不是技术判断）
可选：
  ① **保持放大**（现状）：召回优先，full 口径约 13.9s（OCR 段）。
  ② **关闭放大**：省 35% OCR 时间，但丢小字召回——**不建议默认开**（实测有真阳性损失）。
  ③ **按patch 尺寸自适应**：只对**确实小**的 patch 放大（如< 256），640 边界那个不放大——
     预期收益中等、召回损失可能为零，**但需逐图验证召回**（本阶段未做，因需真值标注对照）。
  ④ **改用 GPU 跑 OCR**：实测 `EasyOCR device = cpu`（**OCR 完全不吃 GPU**，而LaMa 在 GPU 上）——
     这是**尚未探索的独立方向**，理论上收益最大，但 EasyOCR 的 GPU 支持需核实。

- 74/74 性能家族全绿（本阶段**只读 + 探针，未改生产代码**）。
- 全部结论来自**同图同参对照**（只翻转 DETECT_OCR_UPSCALE），排除跨运行噪声。

`core/inpainter.py:273` 判据 `max_side > config.INFER_MAX_SIDE`，而 `INFER_MAX_SIDE=2048`：
```
长边 2047 → 不分块    长边 2048 → 不分块    长边 2049 → 分块
```
⇒ 2048²（最常见的大图尺寸）**整张塞进推理**：实测 `_run_lama_tile` **只跑 1 块**（本应 25 块），
单块 2048² = 2.503s。且 `_tile_if_needed` 只占总耗时 44%，**另 4.97s 在引擎之外（后处理/融合）**。

**但我没有改它** —— 查config 注释发现这是**有意的显存换速度设计**：
「512 适合 4GB / 768 适合 6GB / 1024 适合 8GB+」，且实测手动分块的收益**高度不稳定**：
| 图 | 整图 | 分块 | 加速 | PSNR |
|---|---|---|---|---|
| snow_mountain | 7.419s | 9.596s | **0.77×（更慢）** | 33.85dB |
| white_coffee | 3.669s | 0.440s | **8.34×** | 42.51dB |
| neon_street | 3.556s | 1.866s | 1.91× | 33.41dB |
| 均值 | 4.881s | 3.967s | 1.23× | — |
⇒ 逐块 Python 调用开销会抵消收益（慢的那张要跑 11 块），且 **PSNR 33~42dB 偏低**（分块是近似算法、接缝有损）。

## Stage 212 · 性能门禁「瞬态污染」闸门（收口 Stage 211 缺陷 C）
> 起点：Stage 211 我自己登记的缺陷 C（性能护栏因机器负载漂移假红）并给了倾向方案。
> **本阶段的最大价值不在于实现，而在于两度推翻自己的方案**——最终方案比原方案小得多。

### 缺陷 C 的重新定性（先证伪，再修）
Stage 211 观察到：`--update` 得 P95 0.681s，紧接着纯判定报 1.564s（**2.3×**）判红。
当时归因为「机器负载漂移」，Stage 212 先去修「负载度量」，结果**被自己的实验推翻**：

| 候选负载度量 | 实测结果 | 判定 |
|---|---|---|
| `time.process_time()/perf_counter` | 比值 **1.31~2.30（>1）** —— OpenCV 多线程下累加**所有线程** CPU 时间，衡量「并行度」非「被抢占」 | ❌ 方向反了 |
| `os.getloadavg()` | Windows 不存在（AttributeError） | ❌ 不可用 |
| `psutil` | 未装 | ❌ 不为一个探针引入新依赖 |
| `ctypes`+`kernel32.GetSystemTimes` | 24 进程真并行压满 24 核仅报 **1.6%** | ❌ 本环境不可信 |
| （附带）**Windows 语义坑** | `GetSystemTimes` 的 kernel 时间**已含 idle**，照抄 Linux `/proc/stat` 公式会算成 `real_busy+idle`（恒偏大）| — |
| （附带）探针自身错误 | 24 个 **Python 线程**压不满 CPU（**GIL 串行化**），必须用**多进程** | — |

### 决定性数据（探针 D，24 核机器，真实图，min-of-3）
| 状态 | P95 | 相对噪声 spread/P95 |
|---|---|---|
| 干净 | 0.655 / 0.666s（均值 0.661） | ~0.02~0.06 |
| **稳态高负载**（24 进程压满） | 0.805 / 0.702s（均值 0.754） | **0.062** |
| **瞬态受扰**（刚跑完负载探针、系统未回落） | 1.443s | **0.346** |

⇒ **两个关键结论**：
1. **稳态高负载只抬升 1.141×（+14.1%），远小于 30% 护栏容差 ⇒ 护栏本来就不会因它误判红**。缺陷 C 的实际危害比 Stage 211 判断的**小得多**。
2. `min-of-k` 对**同向**负载天然免疫：负载让每次都变慢 ⇒ 三值彼此接近 ⇒ **极差反而小**。故离散度**只抓瞬态，抓不到稳态**。
3. Stage 211 那次 2.3× 假红属**瞬态**（冷启动/进程池残留），噪声比 0.346 恰好能抓。

### 最终实现（比原方案小得多）
在「可比性」与「回归护栏」之间插入**第 2 层：测量可信度**，判据 = `spread_mean / P95`（**完全内生**、零新增采集成本，`measure()` 早已返回 `spread_mean`），阈值 `NOISE_MAX=0.20`（落在实测两组之间：>0.083 稳态、<0.346 瞬态）。
- 噪声超阈值 ⇒ **判跳过(2)，绝不判通过**，理由明确写「测量被环境污染，请重测」而非「变慢」——避免把红归因引向代码回滚。
- `--update` 同样受闸门约束且**无逃生门**（连 `--force-update` 也不放过）：否则一次受扰的慢测量会固化基线、**永久摧毁**性能参照。
- 噪声比写入基线字段 `noise_ratio`（仅供审计，不参与可比性比较）。

### 自我推翻 #1：撤掉 `repeat<2` 硬拦
初版把「`repeat≤1` ⇒ 极差恒 0 ⇒ 噪声无法自证」也做成硬拦。**实测后判定为过度设计并撤销**：
- 它是**配置问题**不是**污染问题**，两者混为一谈会掩盖真实回归——若代码真慢了 20%，用 `--repeat 1` 跑本该报红，却因「噪声算不出」被判跳过 ⇒ **红色消失**。
- 改为：只在输出里如实提示「⚠️ repeat=N噪声判据无法工作（**不等于**环境干净）」。
- 保留 `spread_mean` **缺失**时的硬拦（那是**无证据**，与`repeat=1` 的「有证据但无区分力」性质不同）。

### 自我推翻 #2：反向验证暴露闸门覆盖不全（**未掩盖，登记为能力边界**）
起 24 进程真并行压满 CPU 实跑 `perf_probe`：噪声比仅 **0.062** ⇒闸门**放行**。
⇒ 它**不是**负载检测器，只抓瞬态。**但因稳态负载仅抬 14% < 30% 容差，漏抓无害**。
已把该边界写进 `NOISE_MAX` 注释 + 守卫 `test_steady_high_load_is_not_caught_but_is_harmless`（钉死「NOISE_MAX 必须 > 0.062，否则会误伤正常高负载测量」）。

### 守卫（`tests/test_perf_noise_gate.py`，新）
覆盖：噪声比计算/None 语义、**噪声+数字漂亮仍不得放行**（防「噪声大+P95 小」绕过）、噪声层**先于**护栏层（否则红会被归因成代码变慢）、`main()` 绝不传 `skip_noise_gate`（仅供单测）、`--update` 闸门在写盘前且无逃生门、阈值必须落在实测间隙、能力边界钉死。
- ⚠ 一并修正既有 `test_perf_probe.py` 4 例：加 `skip_noise_gate=True` 显式声明「本例只测护栏层」（生产路径绝不这样调用）。
- ⚠ **源码级提取守卫的坑**（实测踩到两次）：① 不能用「固定长度字符窗口」找代码块（会跨界扫到后面的 `force_update`）② 收尾条件须用「缩进**严格变浅**」，用 `<=` 会把同级的 `return 1` 一起截掉。

### 验证
- 48/48 性能家族用例全绿（`test_perf_probe` + `test_perf_noise_gate` + `test_perf_gate_staleness`）。
- 真实 e2e（干净）：输出「相对噪声 = 0.024（阈值 0.20）→ ✅ 可信」，P95 0.711s，**EXIT=0**。
- 反向 e2e（高负载）：EXIT=0（未拦）——**如实记录为能力边界**，理由见上（稳态负载仅 +14.1%）。

### 教训固化：LESSONS #232
- **`min-of-k` 对同向负载免疫**——别把「离散度」当负载检测器。
- **Windows `GetSystemTimes` 的 kernel 含 idle**，照抄 Linux 公式必错；且其在部分环境读数不可信。
- **「数字漂亮 ⇒看起来良性」是同一族陷阱的第三形态**：0.0 噪声比看起来像「完美干净」，实为「没机会测」；`--repeat 1` 硬拦会让真实回归的红消失。

- **过度设计的闸门比没有闸门更危险**：它会拦截合法测量从而掩盖真问题。
