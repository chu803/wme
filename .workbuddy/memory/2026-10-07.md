### 教训 262 · 「隔离复跑全绿」≠「不是缺陷」：flaky 定性必须给出**机制**（245）
- 本例中隔离复跑该文件**确实全绿**（泄漏只在**同进程内后续用例**使用同名 logger 时才
  发作；单跑该文件时残留的 `t90.old1`/`t90.old2` 无人使用）⇒ 被误判为「环境 flaky」，
  且**连续多个阶段（234/239）沿用该结论**。真根因是**全局状态泄漏**（真实缺陷）。
- **判据**：
  1. flaky 的定性**必须给出机制**，否则「偶发绿」会被当成免责证据。
  2. 定位 flaky 根因时，除了「能否稳定复现」，必须问「**它在什么条件下会咬人**」。
     本例答案是「同进程内有其它用例使用同名 logger」⇒ 于是**同批次共现**成为关键线索。
  3. **「隔离复跑全绿」只能证明「该用例自身无自依赖」，不能证明「无跨用例污染」**——
     污染的证据必须在**同进程多用例**里找。
  4. 注入式反例的**铁律**：反例只负责复现失败，**必须自带还原**（handler/全局状态/
     环境变量）。留下残留状态是把「测试的缺陷」传导成「其它测试的假红」。
- 遗留：本阶段只修了这一个已证实泄漏；**全库尚未排查**「往全局注册表挂东西却不还原」的
  其它测试文件（可作为后续审计方向）。
## 阶段 245 · utils/logger 测试全局注册表泄漏（订正 234 段「环境 flaky」的误判）

### 教训 262 · 「隔离复跑全绿」≠「不是缺陷」：flaky 定性必须给出**机制**（245）
- 本例中隔离复跑该文件**确实全绿**（泄漏只在**同进程内后续用例**使用同名 logger 时才
  发作；单跑该文件时残留的 `t90.old1`/`t90.old2` 无人使用）⇒ 被误判为「环境 flaky」，
  且**连续多个阶段（234/239）沿用该结论**。真根因是**全局状态泄漏**（真实缺陷）。
- **判据**：
  1. flaky 的定性**必须给出机制**，否则「偶发绿」会被当成免责证据。
  2. 定位 flaky 根因时，除了「能否稳定复现」，必须问「**它在什么条件下会咬人**」。
     本例答案是「同进程内有其它用例使用同名 logger」⇒ 于是**同批次共现**成为关键线索。
  3. **「隔离复跑全绿」只能证明「该用例自身无自依赖」，不能证明「无跨用例污染」**——
     污染的证据必须在**同进程多用例**里找。
  4. 注入式反例的**铁律**：反例只负责复现失败，**必须自带还原**（handler/全局状态/
     环境变量）。留下残留状态是把「测试的缺陷」传导成「其它测试的假红」。

### 教训 263 · 泄漏根因常在**夹具/共享代码**而非触发点；修症状不等于修根因（246）
- 245 定位「注入式反例污染全局注册表」并修了那个反例 ⇒ 但夹具的普遍性泄漏未被发现，

  （t90.old1/old2），没枚举全部受影响 logger** ⇒ 低估污染规模。
- **判据**：
  1. 定位泄漏要**枚举**所有受影响对象（`loggerDict` 全量普查），而非只查最初那一个；

  2. 若某处**每个**用例都会经过（夹具/基类/共享 setup），那它就是**根因候选**——
     在那里修**一处**，而不是在每个触发点各修一遍（重复劳动 + 漏网）。
  3. **还原必须成对**：「先摘除（removeHandler）、后关闭（close）」。只 close = 残留；

  ① **守卫不得依赖执行顺序**。靠文件名/位置排序观测的守卫可能排到被测对象**之前**
     ⇒恒绿 = 哑巴（v1：`test_logging_*` < `test_utils_*` 实测排在前面）。
  ② **守卫必须测真实现**，不能测自己的复刻品。自带一份复刻逻辑的守卫会在实现退化时
     仍绿（v2 实测：删掉被测代码的 removeHandler，守卫仍 PASS）。
     正确做法：**把守卫放进被测文件内部**，用真实夹具/真实对象，
     靠「上一个用例布场、下一个用例后置断言」跨用例验证 teardown。
  3. **任何守卫都要做注入式反向验证**：手动注入缺陷，确认它变红。未验证的守卫
     可能一直是哑巴（本阶段 v1/v2 都是「验证后才暴露问题」的哑巴）。

### 教训 264 · 守卫必须能钉死「真实调用方」，且 bash 传参的反引号坑须固化为铁律
- **守卫有效性只能靠注入式反向验证证明**。本阶段 v1/v2/v3 三版**全部是哑巴或设计错误**，
  每版都是「跑通后注入验证才暴露」。**没有注入验证的守卫等于没写。**
- **v3 的失败模式最值得记**：守卫自己复刻了一份正确写法并断言它正确 ⇒ 它验证的是
  「写法能工作」，**不是**「真实调用方配对了」。⇒ 守卫必须**指向真实调用点**
  （本阶段用「读源码逐个点名」），否则真实调用方漏还原它仍绿。
- **运行期观测的盲区**：后置断言只能覆盖「污染发生在它之前」的调用点；
  污染若发生在更早的其它用例，后置断言**看不见**。⇒ 覆盖「每个调用点」需静态点名，
  不能只靠运行期观测。
- **铁律（bash 传参）**：在 `bash` 里用 `python -c "..."` 内联写含**反引号**或
  `$(...)` 的代码，会被 shell 做命令替换**吃掉内容**（本项目已犯 3 次：245/246/247）。
  ⇒ **凡需写入含特殊字符的代码，一律先用 Write 工具落成 `.py` 文件再执行**，
  或用 Edit 工具直接改文件，**不要**内联进 `bash -c`。

### 教训 264 · 守卫必须能钉死「真实调用方」，且 bash 传参的反引号坑须固化为铁律
- **守卫有效性只能靠注入式反向验证证明**。本阶段 v1/v2/v3 三版**全部是哑巴或设计错误**，
  每版都是「跑通后注入验证才暴露」。**没有注入验证的守卫等于没写。**
- **v3 的失败模式最值得记**：守卫自己复刻了一份正确写法并断言它正确 ⇒ 它验证的是
  「写法能工作」，**不是**「真实调用方配对了」。⇒ 守卫必须**指向真实调用点**
  （本阶段用「读源码逐个点名」），否则真实调用方漏还原它仍绿。
- **运行期观测的盲区**：后置断言只能覆盖「污染发生在它之前」的调用点；
  污染若发生在更早的其它用例，后置断言**看不见**。⇒ 覆盖「每个调用点」需静态点名，
  不能只靠运行期观测。
- **铁律（bash 传参）**：在 `bash` 里用 `python -c "..."` 内联写含**反引号**或
  `$(...)` 的代码，会被 shell 做命令替换**吃掉内容**（本项目已犯 3 次：245/246/247）。
  ⇒ **凡需写入含特殊字符的代码，一律先用 Write 工具落成 `.py` 文件再执行**，
  或用 Edit 工具直接改文件，**不要**内联进 `bash -c`。

### 教训 265 · 静态扫描判不了「是否所有路径都还原」⇒ 用运行期检测；修复必须重跑检测直到归零

  路径还原」——尤其「还原写在函数末尾而非 `finally`」时，抛异常即漏还原，而扫描只看到
  「有还原语句」就放行。⇒ 凡「泄漏/污染」类问题，**优先用运行期检测**（快照→跑→再快照），
  它是唯一能给出确定性「有/无」结论的方法。
- **同一根因往往不止一处**：本阶段预期修 1 处，实际 **3 处**（同一文件里 3 个用例调了
  同一个「会写 config 的函数」）。**修完必须重跑检测器**，不能凭「我改完了」下结论；
  若仍报，用**逐文件二分**收敛（本项目 `.scratch/bisect248.py` 模式）。
- **隐式副作用最难查**：`apply_superres_config()` 写 config，调用方看不见——
  「被调函数偷偷改全局状态」是跨用例污染最隐蔽的一类。⇒ 设计上应让**副作用显式化**
  （返回改了什么 / 或由调用方负责还原并写进 finally）。
- **治标 vs 治本双层**：逐点修复治标（3 处），**autouse 夹具治本**（结构性拦截任意忘记还原）。
  两者都要做——逐点修证明「问题真实且可修」，夹具防「未来新增的同类忘记」。
- **检测器/夹具都要做双向验证**：夹具开启（0 泄漏）× 夹具关闭（3 泄漏）互为对照，
  才能排除「两者同时失灵」的可能。永久守卫同理（关掉夹具 ⇒ 守卫变红）。

### 教训 266 · 「数据可信」先于「结论正确」：坏数据上的零泄漏等于没测
- **249 最大的教训不是又修了两个 bug，而是发现此前两轮「全库零泄漏」结论建立在坏数据上**
  （检测器子进程被 safe-delete 杀掉、整批用例没跑，但探针照常输出「差异统计」⇒ 像有效结果）。
- **判据**：
  1. **先核对「过程量」再信「结果量」**：批量跑的每批都必须回答「用例真的跑了吗」
     （收集数/用时/rc 三者互证）。**用时反常地短**是最廉价且最可靠的探针（本项目
     244/248/249 三次中招，全是它先报警）。
  2. **「没有失败」≠「跑了」**：子进程秒退时 pytest 无输出、探针照常打印统计 ⇒
     必须把「pytest rc + 摘要」显式透传并逐批核对（249 加了 PYTEST_SUMMARY 行）。
  3. **临时文件的清理方式要选对**：测试 basetemp 动辄数百文件，**删除会撞 safe-delete
     批量护栏**（>50 文件 ⇒ SystemExit）⇒ 用「rename 归档」替代删除（项目既有惯例），
     且每次运行用**时间戳唯一前缀**从机制上杜绝「清空旧目录」这个动作本身。
  4. **对任意对象做状态对比，`deepcopy+==` 不是通用解**：含锁对象拷不动（假 gone）、
     无 `__eq__` 对象必假阳。通用口径是 `id+repr` 指纹（repr 是 Python 对象的事实自描述）。
  5. **良性豁免必须逐条带理由并保持可见**（单列而非静默），否则豁免表会变成藏泄漏的后门
     （与 203「幽灵条目」同判据）。

### 教训 266 · 「数据可信」先于「结论正确」：坏数据上的零泄漏等于没测

- **判据**：
  1. **先核对「过程量」再信「结果量」**：批量跑的每批都必须回答「用例真的跑了吗」
     （收集数/用时/rc 三者互证）。**用时反常地短**是最廉价且最可靠的探针（本项目
     244/248/249 三次中招，全是它先报警）。
  2. **「没有失败」≠「跑了」**：子进程秒退时 pytest 无输出、探针照常打印统计 ⇒

     且每次运行用**时间戳唯一前缀**从机制上杜绝「清空旧目录」这个动作本身。
  4. **对任意对象做状态对比，`deepcopy+==` 不是通用解**：含锁对象拷不动（假 gone）、
     无 `__eq__` 对象必假阳。通用口径是 `id+repr` 指纹（repr 是 Python 对象的事实自描述）。
  5. **良性豁免必须逐条带理由并保持可见**（单列而非静默），否则豁免表会变成藏泄漏的后门

### 教训 269 · 大规模测试与「删除配额型」护栏存在结构性冲突；定性失败必须先有 traceback
- **定性顺序铁律**：**先拿到 traceback，再谈「是不是 flaky」**。252 之前那2 条
  rotation 失败「隔离绿 / 单批绿 / 3 批连跑绿」，我差点按惯例登记成「环境敏感型 flaky」；
  真因（护栏拒绝删除）**根本不可能从「是否可复现」推断出来**——它压根不是 flaky，
  而是每次都失败、只是被误以为「偶发」。
  ⇒ **「隔离复跑全绿」只排除「该用例自身不自洽」，不排除「环境机制作用于所有路径」。**
- **护栏型环境的规模上限**：任何「阈值型护栏」（删除配额、并发闸门、文件句柄上限）都会与
  「大批量测试」冲突——因为**批量测试的副作用量随规模线性增长，而阈值是常数**。
  ⇒ 应显式承认这个上限，并把「怎么分轮跑」写成规范，而不是每次都产出几十条
  「无法定性」的失败让下一轮接着猜。
- **「快得反常」第三次当报警器**：缺陷 1（basetemp 复用）让 17 批全部 3~9 秒退、报告
  「失败总数=0」——若不是拿「13 分钟 vs 1 分 51 秒」对比，这轮会被读成全绿。
  ⇒ 任何批量跑，**必须先跑一个已知规模的批次做健康检查**（本次：批 01 应 ~90s），
  再启动全量。
- **输出文件被覆盖 = 权威结论被静默污染**：固定文件名写统计/报告时，一次坏跑就能把
  上一次的好结果抹掉，而读者无从察觉。凡权威输出，一律**按 run 隔离文件名**。
## 阶段 252 · 全量回归复验 · 14 条失败的根因定性 = **沙箱删除护栏**（非代码缺陷）
- 补跑全量（195 文件 / 17 批 / 28m36s）⇒ **14 条失败**（批 02/07/08/09/10/16）。
  **根因由 traceback 决定性确认：全部是 `SystemExit: 1`，来自 safe-delete 批量删除护栏**
  （批 08 的 stderr 明确打出 `{"count":426,"threshold":50,"scope":"turn"}`）。
  ⇒ **零条是代码缺陷**；250 登记的 `test_module_selfcheck[api.py]` 未决项**同源、已定性**；
  **244/248 的「16 条失败」也回溯确认同源**（此前归为「批次争用」属归因不足）。
- **结构性冲突（本阶段真正的发现）**：护栏阈值 **50 次删除/turn**，而一轮全量要删
  **数千**文件（实测累计 `count:426` 时已被拒）⇒ **一轮跑完全量必然触发护栏**，
  触发后剩余所有批次里凡碰删除的用例都会失败。
  可行规避（**未验证，本轮配额已耗尽**）：分多轮跑（每轮 ~4 批，让单轮删除数 < 50）。
- **脚本三处基建缺陷（244 脚本，本阶段修复）**：
  ① **复用固定名 basetemp** ⇒ 第二次全量跑时 pytest 清空旧目录撞护栏 ⇒ 每批 3~9 秒
     「RC=1 但无 FAILED 行」、**用例根本没跑**；若只看「失败总数=0」会**误判为全绿**
     （「快得反常」第三次当报警器；也是 249 同坑第二次——244 脚本一直带着它）。

  ② **`--tb=no` ⇒ flaky 无法定性** ⇒ 改为失败批自动 `--tb=long` 重跑并落盘
     `.scratch/stage252_traceback_batchNN.txt`。**本项目迄今投入产出比最高的基建改进**：
     正是它让我们 10 秒内从「14 条不明失败」定位到同一根因。
  ③ **输出文件覆盖历史** ⇒ 坏数据把 13m32s 那次健康结果整个抹掉，**读者不会察觉**

### 教训 269 · 大规模测试与「删除配额型」护栏存在结构性冲突；定性失败必须先有 traceback
- **定性顺序铁律**：**先拿到 traceback，再谈「是不是 flaky」**。252 之前那2 条
  rotation 失败「隔离绿 / 单批绿 / 3 批连跑绿」，我差点按惯例登记成「环境敏感型 flaky」；
  真因（护栏拒绝删除）**根本不可能从「是否可复现」推断出来**——它压根不是 flaky，
  而是每次都失败、只是被误以为「偶发」。
  ⇒ **「隔离复跑全绿」只排除「该用例自身不自洽」，不排除「环境机制作用于所有路径」。**
- **护栏型环境的规模上限**：任何「阈值型护栏」（删除配额、并发闸门、文件句柄上限）都会与
  「大批量测试」冲突——因为**批量测试的副作用量随规模线性增长，而阈值是常数**。
  ⇒ 应显式承认这个上限，并把「怎么分轮跑」写成规范，而不是每次都产出几十条
  「无法定性」的失败让下一轮接着猜。
- **「快得反常」第三次当报警器**：缺陷 1（basetemp 复用）让 17 批全部 3~9 秒退、报告
  「失败总数=0」——若不是拿「13 分钟 vs 1 分 51 秒」对比，这轮会被读成全绿。
  ⇒ 任何批量跑，**必须先跑一个已知规模的批次做健康检查**（本次：批 01 应 ~90s），
  再启动全量。
- **输出文件被覆盖 = 权威结论被静默污染**：固定文件名写统计/报告时，一次坏跑就能把
  上一次的好结果抹掉，而读者无从察觉。凡权威输出，一律**按 run 隔离文件名**。

### 教训 270 · 阈值型护栏下要「按副作用密度编排 + 撞阈值即停」，而非等分批次硬跑
- **护栏与批量测试的冲突需重新设计跑法**（承接 252 的 #269）：#269 说「分多轮」，
  但 253 的实验进一步修正为——**决定能跑多少的不是批数，而是「批里有多少
  删除/写入密集型测试」**。等分批次 + 固定轮次是错的编排。
- **「撞阈值即停」比「跑完再看」重要**：护栏一旦触发，后续所有碰副作用的用例会集体假红。
  脚本必须**探测护栏命中（`SystemExit`/`SAFE_DELETE`）并立即停 + 落盘进度**，
  否则「跑完全量」这个动作本身就会产出大量误导性失败。
- **同一个失败现象可能有「编排原因」而非「代码/环境原因」**：rotation 用例失败三次都被
  归为 flaky，实际是**它恰好与删除密集测试同批**。⇒ 遇到周期性失败，除了查代码与隔离复跑，
  还要问「**它同批的邻居是谁**」。
- **否定一个假设也要留痕**：253 的 A/B 实验**否定了**我自己的假设（护栏只管项目内），
  但正是「否定的证据」揭示了真因（密度不均）。⇒ 实验设计要能区分「假设不成立」
  与「实验没测到」，前者同样是有价值产出。
