## C5 真 build 环境攻坚（续）—— Docker registry 镜像源配置：根因与「直写文件」解法

**背景**：C5 需在用户 Windows 宿主真跑 `docker build -f Dockerfile.gpu`。阶段 310 已移除 `# syntax=docker/dockerfile:1`（该指令会先去 Docker Hub 拉前端镜像，国内直连超时，build 在解析阶段即死）。剩余依赖是 `nvidia/cuda:12.8.1-runtime-ubuntu22.04` 基础镜像，仍走 Docker Hub ⇒ 必须配 registry mirror。

**症状**：用户在 Docker Desktop → Settings → Docker Engine 编辑框粘贴含 `registry-mirrors` 的 JSON 后，红字报
`Expected property name or '}' in JSON at position 1 (line 1 column 2)`，Apply 按钮灰化无法提交。

**归因（先验证再动手）**：
1. 直接读磁盘 `C:\Users\HP\.docker\daemon.json`：首字节 `7b`（`{`）、无 BOM、`json.load` 通过 ⇒ **文件本身合法**，问题不在磁盘。
2. 报错位置 `position 1 / line 1 column 2` 精确指向「`{` 之后的第一个字符非法」⇒ 坏字符只存在于 GUI 编辑框，是**粘贴时混入的零宽字符/全角标点**。肉眼不可见，因此反复重贴不可靠。

**处置**：绕开编辑器，直接写磁盘。
1. 备份原件 → `C:\Users\HP\.docker\daemon.json.bak.20261020`（124 B，保留可回滚）。
2. 写入合并配置：原 `builder.gc` + `experimental` 原样保留，追加三个 mirror
   （`https://docker.xuanyuan.me` / `https://docker.m.daocloud.io` / `https://docker.nju.edu.cn`）——
   多源按序 fallback，抗单点失效，因为不同 mirror 对 `nvidia/` 非 `library/` 命名空间的代理覆盖度不一。
3. 写后校验：首字节 `7b`、`json.load` → `PARSE_OK`。
4. 用户侧动作：GUI 点 **Cancel**（丢弃坏文本；Apply 本就灰化，无覆盖风险）→ 重开 Docker Engine 页读回新内容 → **Apply & Restart**。

**当前状态**：配置已落盘并通过字节级 + JSON 级双校验；等待用户 Apply & Restart 后执行
`docker info --format "{{json .RegistryConfig.Mirrors}}"` 确认生效，再跑 build。
未生效则回滚：`copy daemon.json.bak.20261020 daemon.json`。

**若 mirror 仍拉不到 `nvidia/cuda`**：改用 `ubuntu:22.04` 作基础镜像的 Dockerfile.gpu 变体——torch cu128 wheel 自带 CUDA 运行时库（libcudart/libcublas 等），配 `--gpus all` 挂宿主驱动即可，绕开 nvidia 官方镜像拉取（属备选方案，未实施）。

## C5 真 build 前置修复（311）—— pip 引导缺失 + CPU/GPU 两配方 `# syntax` 同步

用户 `docker info` 确认三 mirror 全生效。build 前逐行复审 `Dockerfile.gpu`，发现两处**确定会失败**的问题，先修再让用户跑：

**① `python3.11 -m pip` 必然 `No module named pip`（P0·确定性失败）**
- 原写法：`apt install python3.11 python3-pip python3.11-venv` 后直接 `python3.11 -m pip`。
- 根因：Ubuntu 22.04 **不存在 `python3.11-pip` 这个包**；`python3-pip` 只装 3.10 的 pip。`python3.11 -m pip` 在 3.11 的 sys.path 里找不到 pip 模块。
- 修法：删 `python3-pip`，改用 `python3.11 -m ensurepip --upgrade`（`python3.11-venv` 自带 ensurepip）先引导，再升级 pip。
- **为何静态门禁抓不到**：`docker_consistency_check.py` 的 E1 只校验「ENTRYPOINT 解释器 == 装依赖的解释器」（3.11 == 3.11 通过），**不校验 pip 归属哪个解释器**。这是门禁盲区，只能靠真 build 或人工复审发现。

**② `Dockerfile`（CPU 版）首行仍留 `# syntax=docker/dockerfile:1`**
- 阶段 310 只清了 GPU 版，CPU 版漏了 ⇒ 两配方开始漂移。已同步移除并加同款说明注释。

**验证**：`docker_consistency_check.py` → 7 项全 OK / RC=0；`pytest tests/test_dockerfile_contract.py -q` → 11 passed。

**③ `--no-deps` 会跳过 cuDNN，致 `import torch` 必崩（P0·确定性失败，复审第 2 步时发现）**
- 原写法：`pip install --no-deps -r requirements-gpu.txt`。注释理由是「避免把 CPU 版 torch 的依赖再拉一遍」。
- 根因：`nvidia/cuda:12.8.1-runtime-ubuntu22.04` 只含 CUDA 运行时资源（libcudart/libcublas/...），**不含 cuDNN**；而 torch cu128 wheel 的 `nvidia-cudnn-cu12 / nvidia-cublas-cu12 / ...` 依赖**不在 `requirements-gpu.txt` 里显式列出**（靠 pip 自动解析），`--no-deps` 把它们全跳了 → `import torch` 因找不到 `libcudnn.so.9` 直接崩。
- 修法：去掉 `--no-deps`，并加 `--extra-index-url https://pypi.tuna.tsinghua.edu.cn/simple`（nvidia-* 包走清华快源，torch 本体仍走 pytorch CDN）。torch 靠自身 RPATH 从 site-packages/nvidia/*/lib 取这些库。代价：镜像 +~3GB（nvidia 依赖包），可接受。
- 这是第 3 处「静态门禁+人工都容易漏、只有真 build 才暴露」的盲点，叠加在①解释器/pip 归属、②`# syntax` 之上。

**待续**：真 build（用户宿主执行，`--progress=plain` + Tee 到 `.workbuddy\build-gpu.log`，AI 侧可直接读该日志判读，免截图往返）。这是本配方**首次真 build**，诚实预期可能还差一轮（cu128 wheel 下载慢、镜像大）。

## C5 真 build 第 1 轮失败与第 4 次修正（311 续）

**日志事实**（`.workbuddy\build-gpu.log`，UTF-16LE，需 iconv 解码）：
- `#1`–`#4` 全 DONE（元数据 10.2s ⇒ **registry mirror 确认生效**；上下文 5.35MB）。
- `#5` 基础镜像大层下载速度实测 **≈1.14 MB/s**（镜像源偏慢），2.06GB 整层下完。
- `#6 [runtime 2/8]` 从 `archive.ubuntu.com` 下载，**861s 未下完**（≈100KB/s），后因 builder 失败被 CANCELED。
- `#7 [builder 1/5]` 失败：`ensurepip is disabled in Debian/Ubuntu for the system python.`

**根因**：Debian/Ubuntu 给**系统 Python** 打补丁禁用了 `ensurepip`，而发行版又没有 `python3.11-pip` 包。⇒ 我在阶段 311 的「修正①」本身是**第二次误判**（先误以为 `python3-pip` 能覆盖 3.11，再误以为 ensurepip 可用）。诚实记录：这条错误链连静态门禁 + 人工逐行复审都没拦住，只有真 build 拦住了。

**处置（第 4 次修正）**：
1. builder 阶段改走 **venv**：`python3.11 -m venv /opt/venv`，后续两条 pip 全改 `/opt/venv/bin/python -m pip`（`python3.11-venv` 包正是为「venv 内允许 ensurepip」而存在）。
2. builder + runtime 两阶段的 `apt-get` 前加 `sed` 把 `archive.ubuntu.com` / `security.ubuntu.com` 切成 `mirrors.tuna.tsinghua.edu.cn`，并带 `|| true`（sed 失败则退回原源，不阻断构建）——因实测 archive 仅 ~100KB/s。
3. 复跑门禁：`docker_consistency_check.py` 7 项全 OK / RC=0；`tests/test_dockerfile_contract.py` 11 passed。

**待续**：用户重跑同一 build 命令（基础镜像层已有缓存，从 builder 阶段继续）。诚实预期：apt 提速后剩余主要耗时是 torch cu128 wheel ~1GB（pytorch CDN，慢）+ nvidia 依赖 ~3GB（清华，快）。

## C5 真 build 第 2 轮失败与第 5 次修正（312）—— numpy 钉子的 Python 版本契约

**日志事实**：`#6 [builder 2/5]` DONE 325.1s、`#7 [runtime 2/8]` DONE **120.7s**（apt 切清华后 861s→120s，提速 ~7×，改动生效）。`#11 [builder 4/5]` 失败：
```
ERROR: Could not find a version that satisfies the requirement numpy==2.5.1
ERROR: Ignored versions that require a different python version: 2.5.1 Requires-Python >=3.12
```

**根因实证**（curl 清华 simple 索引页）：`numpy-2.5.1` 只有 `cp312/cp313` wheel，全部 `data-requires-python=">=3.12"`，**cp311 计数 = 0**。即 numpy 2.5.x 是 Python 3.12+ 专属。而镜像（Ubuntu 22.04 + apt python3.11）是 3.11 ⇒ 无匹配版本。
⚠ **我写的探测脚本一度误报 OK**：`releases["2.5.1"]` 在镜像 JSON 上取不到时 fallback 到项目级 `info.requires_python`（反映的是旧版本），得出错误的 `>=3.9`。已定位并删除该脚本（不能留一个会撒谎的探针在 scripts/）。

**决策（关键）**：不是降 numpy 钉子，而是**把镜像 Python 3.11 → 3.12**。
- 理由：`requirements.txt` 是依赖契约的真值源；开发机是 Py 3.13 + numpy 2.5.1。若为迁就镜像而把钉子降到 2.4.x，就会出现「契约声明 2.4.x / 开发机实际 2.5.1」的**第三套依赖漂移**（同 184/187/250 的三套 torch 教训）。正确方向是让部署目标满足契约。
- 连带：CPU 版 `Dockerfile` 的 `PYTHON_VERSION` 也必须 3.11→3.12（否则 CPU 镜像栽同一个坑），保持两配方同步。

**改动**：
1. `Dockerfile.gpu`：基础镜像 `nvidia/cuda:12.8.1-runtime-ubuntu22.04` → `-ubuntu24.04`（builder+runtime 双阶段），`python3.11`→`python3.12`（apt 包名、venv、update-alternatives、HEALTHCHECK、ENTRYPOINT 全链路）。
2. apt 源 sed 升级为 **glob 循环**（`/etc/apt/sources.list` + `sources.list.d/*.list` + `*.sources`）：Ubuntu 24.04 起改用 **deb822** 格式，老的 `/etc/apt/sources.list` 已不存在，只 sed 单文件会静默无效。每项 `|| true` 防阻断。
3. `Dockerfile`（CPU）：`ARG PYTHON_VERSION=3.12`；两处 apt 加清华源 sed（Debian deb822 布局）。
4. 阶段 250 的「解释器错配」注释改写：说明 ubuntu24.04 的 `python3` 本身就是 3.12（错配风险从源头消失），但 symlink + 显式 ENTRYPOINT **保留**（不依赖发行版默认版本恰好是对的）。

**验证**：`docker_consistency_check.py` 7 项全 OK / RC=0（E1 自动适配为「python3.12 + symlink 兜底」；E2 只取 CUDA 主.次版本 ⇒ 12.8 不受 ubuntu 版本影响）；`pytest test_dockerfile_contract.py test_repo_hygiene.py -q` → **15 passed**。
（注：`test_repo_hygiene` 有一条会因 `git` 不在 PATH 而 FileNotFoundError——环境问题非代码问题，补上 PortableGit/cmd 到 PATH 即全绿。）

**待续**：用户重跑 build。剩余风险点：① `nvidia/cuda:12.8.1-runtime-ubuntu24.04` tag 是否存在（若 pull 秒失败即为此，需换 tag）；② torch cu128 cp312 wheel 下载慢；③ ubuntu24.04 上 python3.12-venv 可用性（应无虞）。
