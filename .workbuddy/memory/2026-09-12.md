## 阶段 69 · 角标通路「双阈值并集」（闭合阶段 67 的 WebP/重采样边界）（完成）

**动机**：阶段 67 把 `photo + WebP75 + 角标` 重采样后 16~29% 的部分漏检记为「已记录边界」。
但**同尺寸下 JPEG75 为 100%** ——同为有损编码，差异只能来自编码特性 → 判定为**可修的判据缺陷**。

**根因**：`detect_logo_watermark` 的 Canny 双阈值 (50,150) 比较**梯度幅度绝对值**，WebP 平滑
把梯度整体压低（480² 梯度中位数 18.4 → 14.0），角标轮廓**碎裂成 2 块、0 块通过形状过滤**
（召回 0）；同图 PNG/JPEG 均 1 块通过 → 100%。

**阈值扫描（双向）**：降到 (30,90) 恢复 100%（干净误报 0.40%）；但 (20,60)/(12,36) 让轮廓
连成一片、形状失真，**真轮廓反而不通过过滤**（召回 0%）→ 下限 30 是**能力边界**，写入配置注释。

**方案裁决**：先试「替换为自适应阈值」→ **一半修好、一半打破**（480² 修好；640²
textured/WebP 由 100% → 0%）。按阶段 67 教训改为**并集**：固定阈值主通路 ∪ 噪声锚定自适应
补充通路（`lo = clip(med + 2·MAD, 30, 50)`，`hi = 3·lo ≤ 150`，`med/MAD` 为梯度幅度的稳健统计量）。
- **构造上不可能退化**：并集严格 ⊇ 主通路（不是「大概率不退化」）；
- **零附加开销**：高梯度图像 `lo` 被上限钳到 50 → `_canny_adaptive_pair` 返回 `None` → 跳过
  第二次取轮廓，行为与阶段 68 完全一致（这正是 640 口径逐位不变的原因）；
- 补充通路区域按 bbox IoU > 0.5 去重。

**验证（四重）**：
1. 目标组合 **256/320/448/640/960 × png/jpeg75/webp75 全部 100%**（原 16~29%）；

`test_no_known_boundaries_currently` 锁定该状态。

## 阶段 70 · 输入形态规范化（EXIF 方向 / 位深 / 动图）（完成）

**动机**：阶段 49~69 的全部真值审计都在**合成 uint8 PNG** 上进行，「输入形态」这一层从未被审视；
而真实用户的文件形态（手机照片的 EXIF 方向、16 位扫描/TIFF、带 alpha 的 PNG、动图）与加载路径
（读字节 → `cv2.imdecode`）存在系统性错配。

**发现（三个真实缺陷，其一为硬失败）**：
1. **EXIF 方向被忽略**：Orientation=6/8 加载 (80,120) 而参考 (120,80)；=3 尺寸相同但内容上下颠倒
   （maxdiff=197）。保存端不写 EXIF → **导出图相对输入"看起来被旋转"**；且「底部小字 / 角落 LOGO」
   这类**锚定位置**的判据会在**错误的边**上搜索，召回随拍摄方向随机波动。
2. **16 位 PNG / TIFF 穿透到修复层**：校验通过 → `load_image` 返回 uint16(max 64250) →
   检测侥幸出掩码（13028 px，与正常值接近）→ **修复抛 `icvInpaint ... Unsupported format`**
   （16 位 3 通道不支持）。**失败发生在链路后段**，最难排查。
3. **动图 WebP 静默截首帧**（扩展名在白名单内；而 GIF 已被明确拒绝——同类问题两种处置）。

**旁证（值得记录）**：`requirements.txt` 早已声明 Pillow 负责「EXIF 方向校正」，但实现里从未调用
——与阶段 61 的「死代码伪装成已验证功能」同族：**声明过的能力 ≠ 实现了的能力**。

**修复**：
- `core/image_utils._decode_image_raw` 两级规范化：**先位深、后方向**（rgb 与 alpha 同步变换）。
  位深：`uint16 → round(v/257)`（对"16 位存储的 8 位数据"完全无损），其他整型按位深线性映射，
  浮点按 max≤1 判断归一化。方向：8 个取值与 `ImageOps.exif_transpose` 一一对应。
- `read_image_flags(p)` 只读元数据（不解码像素）且**软失败**——任何异常回退 `(1,1)`，
  **绝不因为校正而让加载失败**。
- 动图在**校验层与加载层双重拒绝**（附可操作建议），而非静默降级。
- `validate_image_file` 报告**校正后**宽高（Orientation ∈ {5,6,7,8} 时交换），与加载结果一致。
- 开关 2 个：`IMAGE_APPLY_EXIF_ORIENTATION` / `IMAGE_NORMALIZE_BIT_DEPTH`（默认 True）。

**验证**：8 方向 × PNG/JPEG 与 Pillow 参考一致（PNG 逐位 / JPEG ±2 容差）；16 位 PNG/TIFF
`k×257 → k` 精确还原 + 端到端可修复；WebP+EXIF 也一并被校正（元数据路径与格式无关）；
灰度/调色板/二值/CMYK/极端宽高比/带 alpha 均实测正常；**零回归**——普通 8 位无 EXIF PNG
**逐位等于 cv2 解码结果**，门禁与 benchmark 走内存数组不经加载器。

**交付**：`core/image_utils.py`、`services/validators.py`、`config.py`（2 常量）、
`tests/test_input_normalization.py`（**39 例**）、`docs/70-输入形态规范化设计.md`、
README §2.18 + §6 + 计数 673/70、TODO P1.24、MEMORY（阶段→70、经验 15，并把 49–62 / 63–66
折叠为两行以控体量）。2 个探针已删除、复核为 0。

**方法论沉淀（MEMORY 经验第 15 条）**：① 声明过的能力 ≠ 实现了的能力（把「依赖声明里的承诺」
当审计入口）；② 失败位置越靠后越糟 → 规范化必须在入口统一完成；③ 同类问题要同类处置
（GIF 被拒绝而动图 WebP 被静默截帧）→ 发现一处立刻检查同族入口。

**剩余边界**：刻意不写回 EXIF（方向已烘焙进像素，再写会导致双重旋转）；不做 ICC 色彩管理；
32 位浮点 TIFF 仅做合理映射未做真值验证；多页 TIFF 与动图同类处理（拒绝）。
P0 真实图验证仍是不变的唯一真实缺口——本阶段恰好把「真实手机照片」这一最可能的 P0 输入形态
打通了。

## 阶段 71 · 导出侧透明通道保真与往返保真审计（完成）

**动机**：阶段 60/68 审的是内存里的像素（修复保真 / 交付链保真），但内存结果与用户最终拿到的
文件之间还有**一次编码**（`save_image`）——这层从未被审计。触发症状：导出 JPG 后原图透明区
出现彩色色块。

**发现（真实缺陷 + 两处「声明 ≠ 实现」）**：
1. **透明通道被静默丢弃并「显形」**：`save_image` 只在「PNG 且 PNG_KEEP_ALPHA」时写 4 通道，
   其余格式直接把原始 RGB 写出。而真实 PNG 的透明区域常驻留不可见 RGB（例如被擦掉的 Logo
   原色）→ 实测导出 JPG/WebP/TIFF 后透明区**变成红块**（隐藏内容显形）。
2. **WebP/TIFF 的 alpha 丢失是不必要的**：实测 cv2 的 `.webp`/`.tiff` 编码器都能写 4 通道并
   原样保留 alpha——却被当作"不支持"。
3. **`PNG_KEEP_ALPHA` 注释声称「False：透明区域统一填充为白色」，实现从未如此**——与阶段 70
   的「requirements.txt 声称 Pillow 负责 EXIF 校正」同族：声明过的能力 ≠ 实现了的能力。
4. AVIF 路径语义相悖：先试 cv2（不带 alpha）再回退 Pillow（带 alpha），有透明通道时若 cv2
   成功则 alpha 丢失。

**修复**：
- alpha 策略统一（`save_image`）：目标格式 ∈ `OUTPUT_ALPHA_FORMATS`（PNG/WEBP/TIFF，以
  「cv2 实测能写 4 通道」为准）且 `PNG_KEEP_ALPHA` → **alpha 逐位保留**；否则按
  `OUTPUT_FLATTEN_BG_COLOR`（默认白）**合成到背景**（`out = rgb×a + bg×(1−a)`），
  绝不直接丢弃 alpha。
- `_flatten_on_background` 新增合成函数；alpha 尺寸不匹配 → 告警并忽略（不误用、不崩溃）。
- `_save_avif` 重构：有透明通道时**优先 Pillow（RGBA）**；`_save_avif_via_pillow` 抽出为独立
  函数供三级回退共用；降级 PNG 时也先合成。
- `PNG_KEEP_ALPHA=False` 的语义落实为注释承诺的「合成到背景」。

**验证**：alpha 逐位保留（PNG/WEBP/TIFF，mode=RGBA 且 alpha 与输入完全一致）；JPG 合成白底
且**全图无一处隐藏 RGB 显形**（缺陷护栏）；`PNG_KEEP_ALPHA=False` → PNG 也合成；PNG/TIFF
往返**逐位无损（100 dB）**；JPG/WebP q95 往返 44.5~51.8 dB（测试下限 40 dB，留 4.5 dB 余量）；
尺寸一致；alpha 尺寸不匹配软忽略。护栏 `tests/test_output_fidelity.py`（**15 例**）。

**交付**：`core/image_utils.py`（save_image 策略 + `_flatten_on_background` + AVIF 重构）、
`config.py`（`OUTPUT_ALPHA_FORMATS` / `OUTPUT_FLATTEN_BG_COLOR`）、
`docs/71-导出侧透明通道保真与往返保真审计设计.md`、README §2.19 + §6 + 计数 688/71、
TODO P1.25、MEMORY（阶段→71、经验 16；折叠 67–69 行控体量）、本日志。

**方法论沉淀（MEMORY 经验第 16 条）**：「保存」也是一条要审计的转换链——像素正确 ≠ 文件正确。
输出编码至少回答三问：① 格式能力（实测，别背书）；② 隐藏信息（透明区 RGB 常驻留不可见内容，
丢 alpha = 把它公之于众，正确做法是合成）；③ 往返损耗（无损格式逐位相等、有损格式设 PSNR 下限）。
再次印证「配置注释/依赖声明里承诺的行为」是最便宜的审计入口。

**剩余边界**：ICC 色彩配置不保留（宽色域输入可能偏色，需色彩管理，留待真实宽色域样本评估）；
WebP 有损编码下透明区隐藏 RGB 有 ±1 量化噪声（被 alpha 遮蔽，视觉无关）。

## 阶段 72 · 多次转码级联鲁棒性审计（完成）

**动机**：鲁棒性维度里最后一条显式记录的「未测」——真实平台会**反复**再压缩（JPEG 上传 →
WebP 存储 → JPEG 缩略图…），阶段 63/67 只覆盖「单轮」。

**口径**：每轮 = `JPEG75 → WebP75 → JPEG75`，轮数 0/1/2/3/5/8（分辨率不变，隔离"次数"）；
真值只由无损配对求，级联只施加于被测输入（阶段 63/67 教训延续）。

**发现**：
1. **召回全程稳固**：corner/edge 98~100%、grid photo 96%、grid textured 89→64%（温和下降）；
2. **精确率单调下降**（grid 34→14%、edge 60→24%）→ 重压缩带水印图上重绘面积增大
   （召回指标看不到的隐藏代价）；
3. **干净误报随轮数爬升**：四预设平均 n≥3 越过 2%（n=8 达 4.76%），逐预设定位上涨集中在
   激进预设（faint_tiled 1.99→6.85%、grid 1.63→5.58%），而 **general（自动模式）全程 ≤1.88%**。

**裁决**：不改全局阈值（召回已在边缘，改阈值 = 用主场景召回去换边缘场景误报），改为
**双线误报契约**：general 全轮次 ≤2%（自动模式硬红线）+ 四预设平均「n≤2 ≤2%（正常区间，
沿用阶段 57）/ n≥3 ≤5%（退化区间的已记录代价，实测最大 4.76%）」。

**交付**：`scripts/cascade_robustness.py`（四条红线，基线 `docs/assets/cascade_baseline.json`）、
`tests/test_cascade_robustness.py`（13 例）、`docs/72-多次转码级联鲁棒性审计设计.md`、
README §2.20 + §6 + 计数 701/72、TODO P1.26、MEMORY（阶段→72、经验 17）。

**方法论沉淀（MEMORY 经验第 17 条）**：「单轮成立」推不出「多轮成立」，但别急着修——召回稳固
而误报爬升时，先做**逐预设分解**；若上涨集中在激进预设而默认预设守住契约，改全局阈值就是用
主场景召回去换边缘场景误报。正确做法是**双线契约**分开守护正常/退化区间，并把**精确率下降**
（重绘面积增大）这一召回指标看不到的隐藏代价一并审计。

**剩余边界**：级联与缩放叠加未测（阶段 67 已单测缩放）；混合质量组合未测；重压缩图上精确率
