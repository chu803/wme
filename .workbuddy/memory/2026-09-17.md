## 明确不建议现在做

- 继续给 `faint_tiled` 调参（信息论极限，收益是噪声）；
- 上 GPU / 换更大修复模型（掩码覆盖率 16% 的前提下没意义）；

## 方法论沉淀（可复用）

**「门禁全绿」不等于「产品可用」，中间隔着一个「红线只罚漏不罚多」的结构性偏向。**
当一套评测只对「漏检」设红线、不对「过检面积/误报绝对量」设红线时，系统会朝「宁可多擦」演化
且永远亮绿。检查方法：把门禁的每条红线反读一次——**每一条红线都必须能回答「它防的是哪一类『变坏』」，
若某类变坏没有任何红线覆盖（此例：掩码面积），那类就是当前的盲区。**

## B. `ui/tab_models` 审计（262 代码行 / 仅 1 文件 4 例 / 比值 65.5 = 第二名的 2.96×）

真缺陷 3 项：
- **D1（根因）** `core/model_manager._ensure_init` 把 `_INITED = True` 写在初始化**之前**

  ⇒ 同一风险面三种处理方式。
- **D3** `on_verify`/`on_rollback`/`on_reload`/`on_detail`/`on_set_active` 五个 handler 无护栏。

**登记边界 3 项（刻意不改）**：
- `gr.Markdown` 的 `label` 在 `container=False`（默认）下**永不渲染**
  （Gradio 6.22 实测告警 `show_label has no effect when container is False`）。
  ⇒ `tab_models` 两处 `label=t(…)` 与 `tab_history` 的 `reg_label` 都是**无害死元数据**。
- `on_download(progress: gr.Progress = gr.Progress())` 导入期求值，实测无害。
- `_slot_choices()` 的 `["lama"]` 硬编码回退**正是其保护目的**。
