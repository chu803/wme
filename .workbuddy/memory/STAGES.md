## 90 utils 日志系统真值审计（共享 handler 与轮转健康）
对象：`utils/logger.py`（审计前 237 行 / **0** 个测试函数 = 全仓唯一真零覆盖，且是**全站横切面**，85 处调用）。
- **L1（P0，Windows 特有）**：每个 logger **各建一套 handler** → 多个 `RotatingFileHandler` 同时持有
  `app.log` 并各自轮转 → `doRollover` 的 `os.rename` 被别的 logger 句柄挡住抛 `PermissionError`
  （`open()` 不带 `FILE_SHARE_DELETE`）。**对照实验只改 logger 数**（maxBytes=4096、每 logger 600 行）：
  1 → **0 次异常 / 备份连续 `.1..5`**；2 → **31 次 / 备份 `.1 .3 .5` 有空洞**；
  4 → **171 次 / 备份只剩 `.1 .5`、主文件 672 B**。后果：轮转失败 → `app.log` 不再受 `LOG_MAX_SIZE_MB`
  约束而**无限增长**，且**日志行丢失**（当时 `logs/app.log` 已 6.1 MB / 阈值 10 MB）。
  修 = **全进程共享一套 handler**（每文件唯一属主；handler 数 `O(logger×3)` → 常数 **3**、句柄 30+ → 2）。
- **L2**：`_resolve_level` docstring 称支持「中文/英文级别名」，实际只有 5 个英文键 → `WARN`/`FATAL`
  被静默降级成 INFO、`None` 直接 `AttributeError`；修 = 补 `WARN`/`FATAL`/`NOTSET` 别名 +
  `str(name).strip().upper()` 安全兜底 + 修正 docstring。
- **L3**：`_ColorFormatter` 注释称「颜色只加在级别名前」「复制不混 ANSI」，实际**整行着色**
  （ANSI 位置 [0, 15]）；修 = 把注释改成真实行为。
- **L4**：`logger.handlers.clear()` 前不 `close()` 旧 handler；修 = 移除前先 `close()`
  （**共享 handler 绝不关**）。
**非缺陷**：`setLevel(min(console,file))` 取更细一级不漏记；`propagate=False`；单例缓存；
colorama 缺失时 `_HAS_COLOR=False` 且 `Fore=Style=None` 双保险降级；文件日志用普通 Formatter（无 ANSI）；
**UI 不暴露日志级别** → 「缓存导致运行时改级别失效」在 UI 路径不可达（边界登记）；
`print_banner` 直接 print 是设计。
注入反例（本轮独立复验 4/4 失败）：回退 L1/L2a/L2b/L4 → 守卫分别失败，逐字节还原 + sha256 校验通过。
**过程坑**：① 注入脚本复用同一个 `--basetemp` → 遗留目录污染 → 基线误报 exit=1；**每轮唯一 basetemp**；
② 源文件 **CRLF**，注入需先 LF 归一化；③ 回退 L1 会让轮转测试病态变慢（触发 `--timeout=300`），
注入必须先落**外部备份**。

**核心判断：功能完整度高，但「验证面」与「功能面」严重不匹配。** 1199 用例 / 95 文档 / 两条门禁全绿，
撑起的是一个「**合成数据上很扎实、真实数据上只验了一个角**」的系统。三条 P0：

- **S1 真实基准只覆盖 5 类中的 1 类**：`ground_truth.json` = 30 条 / 60 个标注，
  `style` 分布 **`{'corner_logo': 60}`**（`labeled_by='manual:measured'`，确实人标的）；
  而 `manifest.json` 30 张**全写** `watermark_style_hint='mixed'`。
  ⇒ **清单与真值互相矛盾**，只能解释为「标注只标了角标」。
  **没被标注的水印不会被算成漏检** ⇒ `real_gate` 的 `recall ≥ 0.98` 实际只在守 `corner_logo`；
  `faint_tiled`/`edge_text`/`grid`/`gradient` 的真实召回是**未知**而非 100%。
- **S2 掩码「面积」没有任何红线**（本次最要紧）：`bench_20260914_155520.json`（30 图 · general）→
  `mask_coverage` 均值 **0.1615**（中位 0.154、最差 0.2889、**27/30 >5%**、8/30 >20%）、
  `mask_iou` **0.0617**、`pred_count` **86.97/图**（最多 207）、微平均
  `tp=57 · fp=2552 · fn=3` → **P 0.0218**。
  **区域级 IoU 0.657 与掩码级 IoU 0.062 的背离就是诊断**：不是「框偏了」，是「**框太多了**」。
  `real_gate` 只有 recall/precision/iou 三条红线，`mask_iou` 仅监控、`mask_coverage` 连监控都没登记
  ⇒ **门禁有「只罚漏（recall）、不罚多（coverage）」的结构性偏向**，
  系统会朝「宁可多擦」演化且**永远亮绿**。
- **S3 端到端真实链路未验证**：`decision_A_fixed.json` 自述 `"mask_source": "truth"` ⇒
  「seam_delta 27.67 → OpenCV 13.88（23/30 胜）」只证明「**给定正确掩码**修得好不好」，
  不是「给实际 16% 覆盖率掩码最终好不好」。无真值那轮 `NIQE` **30/30 null**；
  两份 `decision_*` 口径不同（`masked_psnr` 18/2/10 vs `seam_delta` 23/7/0），权威判据待定。

**另抓两处文档/实现矛盾**：① **`ai_gradient`**——`real_gate.py` L36 自述「设计上恒为零输出」，
`quality_gate.py` `CASES` 只有 4 类（`"gradient"` 属 `BASE_KINDS`＝**底图**种类，不是水印种类），
但 README §1 把它列为 5 大支持类型之一；② 两份 `decision_*` 胜负口径并存。

**次要不足**：无参考质量分辨析力≈随机（85）；引擎对决样本面窄（30 张、全角标、真值掩码，
真实侧 23:7 而合成侧 8:0）；审计覆盖不均（`ui/` 7 审 2、`services/` 13 审 4、
`core/image_utils`+`detector` 从未独审）；工程遗留（LaMa CPU 3~4s、超分权重缺、NIQE 不可用）。

**建议的下一步（＝用户可回复的第 0 项）**：**先补验证面，再继续审计**——
① 真实基准补 4 类样式真值（每类 3–5 张；确无该风格也要登记为 0，避免「没标＝没漏」）
② `real_gate` 给 `mask_coverage` / `mask_iou` 上红线（第一步 coverage ≤0.32、mask_iou ≥0.10）
③ 修复质量报告同时输出 **truth 掩码**与**predicted 掩码**两列
④ 裁决 `ai_gradient`（改 README 措辞 或 补用例+红线）
⑤ 真值校验加「`hint` 与 `truth` 的 style 集合相容」**脚本级**检查
（这次的不一致是靠肉眼发现的，应该由脚本发现）。
**明确不建议**：给 `faint_tiled` 继续调参（信息论极限）、上 GPU/换大模型（掩码覆盖 16% 时无意义）、
继续扩功能面（验证面不补，承诺越虚）。

**方法论沉淀**：**「门禁全绿」≠「产品可用」**，中间隔着一个「红线只罚漏不罚多」的结构性偏向。
检查手法 = **把门禁每条红线反读一次**：每条红线必须能回答「它防的是哪一类『变坏』」；
若某类变坏没有任何红线覆盖（此例 = 掩码面积），那类就是当前盲区。

## 阶段 95 · 能力承诺面收敛（「只处理角标 LOGO 类图片」）与严格范围门禁

**决策来源**：阶段 92 缺口 S1 的两条出路（①补四类真实图 ②把能力声明收敛到已验证范围），

详见 `docs/95-能力承诺面收敛-只做角标LOGO与严格范围门禁.md`。

### 为什么这不是「改文档」

阶段 93 的 `complete` 判据是 `unspecified_images == 0`（清单每张图都要有具体风格声明）。
它在**补图路线**下对；在**收敛路线**下会变成错的判据：

- 30 张图的帧内容客观上可能确实混有多种样式，清单写 `mixed` 是**诚实**的；
- 承诺面收窄到「只做角标」后，`recall` 度量的**正好是被承诺的那一类**——
  未承诺类型的召回「未知」这件事已由「不承诺」承担，不需要再用红灯表达；
- 若继续让 catch-all 压成红灯 ⇒ `--strict-scope` **永远无法为绿** ⇒
  **红灯失去信息量**（"门禁全绿 ≠ 产品可用"的镜像：**门禁恒红 = 门禁无用**，经验 62）。

### 落地

## 阶段 98 · `utils/recommend_view` 审计（i18n 硬编码泄漏通解守卫 + 分值钳制 + SSOT 漂移）

**选点来源**：`audit_selector.py`，审**未审计模块第一名 `utils/recommend_view`**（审计前 152 行 / 8 引用 = **19.0**）。它是「推荐理由 → 人类可读文案」的**唯一边界层**，被 `ui/tab_auto` / `ui/tab_batch` / `ui/tab_media` / `services/report_service` 四路共用；也是 `ui/` 逐个功能页审完之后，自然落到 utils 层的第一站。
详见 `docs/98-utils层续审-审计recommend_view与i18n硬编码泄漏通解守卫.md`。

### 一个真缺陷 + 一个一致性缺陷 + 一个边界

| 编号 | 类型 | 现象 | 修法 |
|---|---|---|---|
| **D1** | **真缺陷（可达）** | 模块 docstring 承诺「翻译统一走 i18n，**绝不暴露裸键**」，实现却有 **4 处硬编码中文**：分隔符 `、`、行标点 `：`、空态 `（无）`、无推荐时 `exc="无推荐结果"`（`t()` 只管模板、**不管入参**）。**中文界面 100% 正常，只有 `en-US` 才暴露**。可达性已证：`RECOMMEND_ENABLED=False` ⇒ `scores={}` ⇒ `shown=False` ⇒ 必走 `（无）` | i18n 中英各补 `msg.no_result` / `list_sep` / `score_line` / `scores_none` **四键**，渲染器全改走 `t()`；用**整行模板** `score_line` 而非只换标点（英文冒号后随空格也该由译文决定）。i18n 自检守卫列表同步登记 4 键 + 英文侧反向断言（「新增键只加一边」立即红） |
| **D2** | 一致性缺陷（低危） | `_char_bar` 钳制 `[0,1]`，`bars_html` **不钳制** ⇒ 上游 >1 分即 `width:150%` 溢出容器（当前不可触发，两条通路已**分叉**） | 只钳**条宽**（`max(0.0,min(1.0,v))`），**保留展示值为原始分**——与 markdown 的 `**{v:.2f}**` 口径一致（否则修一个分叉造出另一个） |
| **D3** | 边界（SSOT 漂移） | `_FEATURE_KEYS` 是 `core.preset_recommender` 的 `scores` 键**硬编码副本**（当前同名同序）。utils 层**不得**依赖 core（牵扯 torch，破坏分层），无法直接 import | 守卫落**测试侧**：`ast` 从**源码**提取 `scores` 字典**字面量**键做同名同序断言。**读源码而非调 `recommend_preset()`**——后者在 `RECOMMEND_ENABLED=False` 时返回 `scores={}` 会**假绿** |

### 本阶段最有价值的产出：i18n 硬编码泄漏的**通解守卫**（I4）
`ast.parse` → 取 `ast.Constant` 中的 `str`（**剔除 docstring 节点**与 `__main__` 子树）→ 断言函数体不含任何 **CJK 码点**。
它对本模块**尚未写下的第 5 处、第 50 处**同样有效——grep 只能守住你已经想到的那几个词。
并配「向临时文件植入 `无推荐结果`，判据必须变红」的**守卫自检**，防止 `skip` 集合写错导致守卫永久绿。

### 新增经验（72~74）
- **72**：i18n 泄漏 **≠ 缺键**，判据是「英文界面」而不是「键表」——`t()` 缺键会返回 key 本身（降级不崩），所以键表检查抓不到「有键不用」。凡文案生成层，回归测试必须含**语言切换 + CJK 码点扫描**。

## 阶段 99 · 真实图过检收敛：覆盖率闸标定 + 过检红线重标

**起点**：用户直问「现在最大的问题是什么」。诊断结论 = **检测器过检**：真实 general 掩码覆盖 **16.18%**、面积比 **16.62×**、`pred_count` 86.97/图，即 **96.15% 的检出像素不是水印**。且**门禁几乎无法证伪它**——结论级红线只罚 `recall`（漏检），过检只有崩溃护栏杆（1.5× 余量）；上游 `core/detector` 的 30% 上限 30 张只触发 2 张（形同虚设）。这是「**改进可以静默回退**」的结构性缺口。

### 探针 A：过检按**类型**归因（`_probe99_attr.py`）
逐图把检出的掩码按最近真值框分类，得覆盖面积占比：

| `translucent` | **2.36%** | 部分命中 |
| 合计 | **16.18%** | 与门禁读数一致 |

## 阶段 105 · 修复侧外溢收敛：羽化不冲淡内部 + 膨胀归零

> 完整版见 `docs/105-修复侧外溢收敛-羽化不冲淡内部与膨胀归零.md`；此处只留推导链与不可淡忘的读数。

### 起点

阶段 102 的修复侧首测把「掩码 5805px → 改动 7549px（+30%）」记账为「**外溢 23.3%**」，
并归因为「`dilate=2` + `feather=5` 扩散」。阶段 104 把它列为下一步。

### 归因（模式 A/C/G/H）——推翻原归因的一半

**机制（解析）**：`inpaint()` 末步
`m3 = proc_mask/255; blended = image*(1-m3*strength) + result*(m3*strength)`
⇒ **`proc_mask==0` 处 `blended ≡ image`（逐字节）** ⇒ **改动区 ⊆ support(`proc_mask`)**。
这把外溢从「模型行为」变成「**掩码几何量**」，并解释 opencv / lama 外溢率几乎相同。

**全网格扫描（模式 A）**：外溢 **∝ `dilate`**（每 +1px ≈ **+11~12 pp**），
**`feather` 贡献 ≤1.1%** ⇒ 「外溢来自 `feather=5` 扩散」是错的。

**下界（解析）**：`proc_mask = feather(threshold(dilate(mask,D),thresh),F)`，
支撑扩张 = D 像素 + ⌈F/2⌉ 像素 ⇒ `外溢 ≥ D·周长/掩码面积`
⇒ **「外溢 ≤5%」与 `D≥1` 数学上不可兼得**。这是**包含关系**，不是调参问题。

### `feather` 的真实危害（模式 H）

`feather=5`（σ≈1.25）作用在 1~2 px 笔画上，`proc_mask` 峰值仅 `0.33×255≈85 < 127`
⇒ 融合权重 <1 ⇒ 修复**按比例施加**（细字 / 网格「修了但只修三成」= **静默半量修复**）。
`proc_mask` 是**融合权重**而非常规二值掩码 —— 这是根因。

### 阶段 65 混杂结论复核（模式 G）

旧 `run()` 只在 `dilate` 维变档、`feather` **仅在 `d==默认值` 时换挡** ⇒ **(0,0) 角从未测**
⇒ 「细字需要膨胀」实为「**羽化冲淡内部**」的账被记到 `dilate` 头上，并以默认 `D=2` 固化两代。

### 修复

1. `core/inpainter.py::_prepare_mask` 末步 `return np.maximum(soft, binary.astype(np.float32))`
   —— 羽化**只在外侧加软坡，内部一律抬回 255**。
2. `config.MASK_DILATE_DEFAULT: 2 → 0`（管线膨胀归零）。

  `edge_text` 1.423→**1.193**；`grid` 2.257→**1.727**；**四项改进、spill 全部 ≤1%**。

## 阶段 106 · 掩码—实体对齐收尾：框内证据几何收敛 + 网格模板门限

> 完整版见 `docs/106-掩码实体对齐收尾-框内证据几何收敛与网格模板门限.md`；此处只留推导链与不可淡忘的读数。

### 起点与归因（模式 A：逐策略消融，10 图 × 4 类）

目标：`overdraw` 双向失准（`edge_text` 5.00 / `grid` 6.21）。消融结果三条**与直觉相反**：

1. **网格通路本身已对齐**（`solo` overdraw **1.79**；`grid` 案例的 6.21 里它只贡献 0.87 个面积点，
   而 `−edge` 少 2.50、`−trans` 少 1.95）——它是 0.64/0.74 真阳性的来源。
2. **框型（edge）通路是最大单一 FP 源**：`faint_tiled` 上多涂 **4.45** 个图面百分点（TP 仅 +0.30）、

3. **唯一承诺类型的真阳性主要来自半透明通路**（`−trans` 后角标 TP 0.51 → **0.07**）——

### 机制

- `_refine_regions_to_mask` 末步 `dilate(ellipse(2·pad+1))` ⇒ **pad=2 时每个证据像素变成 5×5 块**，

### 被本阶段抓出的两个真实缺陷（都属「看起来有护栏、实际不生效」）

1. **`DETECT_TILED_PATH_GUARD` 是死开关**——调用点写死 `guard=(_rescue_depth == 0)`
   （主臂恒 `True`）遮蔽了 `config` ⇒ 开关从未被读取 ⇒ **阶段 104 宣称的注入式反例自诞生起无效**。
   实测：`guard=True`+config=False 与 `guard=None`+config=True **逐位相同**；
   `guard=None`+config=False 是 **3.2×** 面积。修法：主臂改传 `None`（交回 config），
   兜底臂保留 `False`。**既有间谍测试恰好断言 `True in calls`，把这个缺陷钉在了原地。**
2. **输出编码决定退出码**——横幅含 `⚠`（U+26A0），Windows 上 stdout 重定向到管道时按 ANSI 代码页
   （GBK）编码 ⇒ `print(to_markdown(...))` 抛 `UnicodeEncodeError`、**退出码 1**；
   更糟的是 `--update` 的写盘在打印之后 ⇒ **连刷新基线也一起失败**。
   修法：入口 `sys.stdout.reconfigure(encoding="utf-8", errors="replace")`，两条守卫钉住。

基线新增 `aggregate.area_only` ⇒ 手工构造基线字典的单元测试撞上「旧版基线请 `--update`」的
刻意硬失败（3 例）。修法两条：① 夹具补键（同步夹具，不放宽断言）；② 判定写成

缺键才是旧版格式。

### 真实边界

面积监控**不判「认得准不准」**：它守「不得突然变胖」，不是精度。四类未承诺类型的真实
precision/recall 仍是**未知**（需真实水印图，阶段 101 起登记）；30 张真实图上这四类**都不存在
水印**，故「面积越小越好」在方向上明确正确，但**回答不了「有该水印时够不够」**。
